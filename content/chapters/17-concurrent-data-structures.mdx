<SectionHeading n="01" cmd="cat DECISION.md" id="choice">How to make shared state safe</SectionHeading>

Several threads need a shared map, queue or counter. You're choosing how to make
that safe, and the options differ by roughly two orders of magnitude in
throughput.

Before choosing, be clear what any of them buys you. A concurrent structure
promises **linearizability**: every operation appears to take effect
instantaneously at some point between its call and its return, and all threads
agree on the order.

That's a guarantee about *single operations*. It says nothing about sequences.

```cpp
// Each call is individually atomic. The pair is not.
if (!map.contains(key))      // thread B can insert here
    map.insert(key, value);  // and you overwrite it
```

<Callout label="What 'thread-safe' doesn't mean">
`ConcurrentHashMap`, `sync.Map` and `dashmap` all make `get` and `insert`
atomic. None make check-then-act atomic. Composing two safe operations gives an
unsafe one, and that's why every such API grows a `compute_if_absent` /
`LoadOrStore` / `entry()` method — those exist specifically to close this gap.
</Callout>

<SectionHeading n="02" cmd="ls ./options/" id="options">One lock, many locks, or none</SectionHeading>

<Approach
  n="1"
  name="One mutex around an ordinary container"
  breaks="Every operation serialises. Past about two threads of real contention it is your bottleneck."
  bestFor="Genuinely almost everything. Start here and make a profile tell you to move."
>
Boring, almost certainly correct, and trivially debuggable. The cost of being
wrong is low, because replacing it later is a local change behind one interface.
</Approach>

<Approach
  n="2"
  name="Lock striping"
  breaks="A hot key defeats it completely, and size() stops being meaningful."
  bestFor="Many threads, well-distributed keys, short critical sections. Worth 16x in section 3."
>
Replace one lock with an array of them, each guarding a slice of the key space;
the key's hash picks the stripe. Two threads on different stripes never
interact.

```cpp
// Each stripe on its own cache line. Without alignas this reintroduces
// exactly the false sharing chapter 13 measured at 55x.
struct alignas(128) Stripe {
    std::mutex m;
    std::unordered_map<Key, Value> map;
};
std::vector<Stripe> stripes(16);
```
</Approach>

<Approach
  n="3"
  name="Per-thread state, merged on read"
  breaks="Reads become O(threads), and you see a slightly stale aggregate."
  bestFor="Counters, accumulators, statistics — anything commutative. Beats every algorithm here when it applies."
>
Not a concurrent structure at all: the removal of sharing. Each thread writes
its own copy with no synchronisation whatsoever, and a reader sums them.

Probably applies more often than people check, and it's the first thing to try.
</Approach>

<Approach
  n="4"
  name="A lock-free structure"
  breaks="Reclamation becomes a research problem, and throughput collapses under heavy contention — chapter 14 measured 162 ns against a mutex's 16 ns at eight threads."
  bestFor="Signal handlers, interrupt context, hard real-time. Places where blocking is a correctness problem, not a speed one."
>
Chapter 14 covers this in full. The short version for this decision: reach for
it when you cannot tolerate a thread being descheduled while holding something,
and not because it sounds faster.
</Approach>

<SectionHeading n="03" cmd="./bench --stripes 1,8,64" id="crossover">Sixteen times, and why 64 stripes is 8</SectionHeading>

<Callout label="The machine" kind="note">
Apple M4, 10 cores, macOS 26.5.1, clang 21 `-O2 -pthread`. Eight threads,
100,000 critical sections each, median of 3. Every stripe is `alignas(128)`. The
critical-section body is a variable number of multiply-add rounds, so the lock's
share of the cost can be varied.
</Callout>

<Sub n="3.1" title="What striping is worth">

<Compare
  cols={["body", "1 stripe", "8 stripes", "64 stripes", "speedup"]}
  rows={[
    ["0 ops", "23.0 ns", "1.1 ns", "1.0 ns", "22.5×"],
    ["4 ops", "15.8 ns", "1.0 ns", "1.0 ns", "15.6×"],
    ["16 ops", "42.4 ns", "2.5 ns", "2.4 ns", "17.6×"],
    ["64 ops", "152.0 ns", "8.9 ns", "9.0 ns", "17.0×"],
    ["256 ops", "552.4 ns", "34.6 ns", "34.3 ns", "16.1×"],
  ]}
/>

Two findings, and the second is more useful.

**Striping is worth 16–22× at eight threads**, consistently across
critical-section lengths. Close to the eightfold ideal, plus — probably — the coherence traffic you stop
paying.

**Sixty-four stripes is no better than eight.** Those two columns are identical
to within noise at every body size. There are eight threads — once each can hold
its own lock, more locks add only memory and cache pressure. **Stripes beyond
your thread count are decoration.**

</Sub>

<Sub n="3.2" title="The benchmark that lied to me">

My first version of this showed striping getting *slower* as stripes increased:
14.3 ns at one stripe, 25.9 ns at sixteen. That result is wrong, and how it was
wrong is the useful part.

Each thread picked its stripe as `(thread_id * 7919 + i) % stripes` — a different stripe
every iteration. So every thread touched every stripe, no sharding
happened at all, and I measured the cache miss from walking 64 lines instead of
one.

Real sharded workloads have **affinity**: a thread, or a key, maps to a stripe
and stays there. Change the access to `stripes[thread_id % n]` and the 16×
appears. A striping benchmark without affinity measures cache misses, not
striping.

</Sub>

<SectionHeading n="04" cmd="./choose --explain" id="choosing">Five questions</SectionHeading>

1. **Can you avoid sharing entirely?** Per-thread state with a periodic merge
   beats every algorithm in this chapter. Check this first, every time.
2. **Is there a single hardware atomic for it?** A counter wants `fetch_add`,
   not a structure. A flag wants `fetch_or`.
3. **Are your keys well distributed?** If yes, stripe, with stripe count ≈
   thread count. If a hot key takes a large share, striping buys you nothing and
   you're back to step 1.
4. **Is blocking a correctness problem?** Signal handler, interrupt, hard
   deadline — then lock-free, and use an existing implementation.
5. **Otherwise use one mutex** and move on. It's probably right more often than this chapter's existence suggests.

<SectionHeading n="05" cmd="perf lock contention --sort wait_total" id="mistakes">The hot key, and size()</SectionHeading>

<Sub n="5.1" title="The hot key">

Striping assumes keys spread evenly. Real workloads probably have a key taking 40% of traffic, and it lives in exactly one stripe. You've built a 64-way concurrent map
that behaves, for your actual traffic, like a map with one lock.

**Symptom:** throughput doesn't improve with stripe count, and `perf lock
contention` shows one lock dominating. Compare wait time *per stripe*, never in
aggregate — an even total hiding a skewed distribution is the signature.

**Fix:** not a better structure. If it's a counter, give each thread its own and
sum on read. If it's a cache entry, replicate per thread and maybe accept some
staleness. Removing the sharing is the answer, which is step 1 again.

</Sub>

<Sub n="5.2" title="Treating size() as a fact">

`size()` on a striped or lock-free structure either locks everything — making
your cheapest-looking query the most expensive call in the API — or sums
per-stripe counters without a global lock and returns a number that was never
simultaneously true.

Java documents `ConcurrentHashMap.size()` as an estimate. Most people read it as
a fact. Using it for a capacity decision means building on a value that can be
wrong in either direction.

</Sub>

<Sub n="5.3" title="Forgetting the padding">

Every shared counter wants its own cache line. Miss one and chapter 13's 55×
penalty lands on an otherwise well-designed structure, with nothing in the code
looking wrong.

Two usual misses: a size counter sitting next to the buckets, and the head and
tail indices of a ring buffer in one struct.

</Sub>

<Sub n="5.4" title="Benchmarking with uniform keys">

Uniform keys make every striped structure look excellent and hide the one
failure mode that will actually hit you. Test with a **skewed** distribution —
Zipf, or just take your real key frequencies from a log.

</Sub>

<SectionHeading n="06" cmd="./worksheet" id="worksheet">Decide it for your case</SectionHeading>

**Three experiments, and between them they cover every way this goes wrong.**

- Build a `std::unordered_map` behind one mutex, then the same behind N padded
  stripes. Benchmark at 1, 2, 4, 8 threads and N of 1, 8, 64. Confirm the
  plateau: past your thread count, more stripes buy nothing.
- Introduce a hot key — send 40% of operations to one key — and watch the entire
  benefit disappear.
- Remove the `alignas` and measure what you lose.

Then run the first one again with your *real* key distribution instead of a
uniform one. If the answer changes, you've just avoided shipping the wrong
structure.

<SectionHeading n="08" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Your map is thread-safe. Is this correct? if (!m.contains(k)) m.insert(k, v);">
No. Each call is atomic; the pair isn't. Another thread can insert between the
check and the insert, so you overwrite it or double-count.

Every concurrent map API grows a combined method — `compute_if_absent`,
`LoadOrStore`, `entry()` — and those exist specifically to make check-then-act a
single atomic operation.
</QA>

<QA level="intermediate" q="How does lock striping work and what's it worth?">
Replace one lock over the whole structure with N locks, each guarding a slice of
the key space; the key's hash picks the stripe. Two threads on different stripes
never interact.

On an M4 with eight threads I measured 16–22× across a range of
critical-section lengths. Each stripe must be padded to a cache line, or you
reintroduce false sharing and lose most of the gain.
</QA>

<QA level="intermediate" q="You go from 8 stripes to 64 and nothing improves. Why?">
You have eight threads. Once each can hold its own lock, more locks add no
parallelism — only memory and cache pressure. Stripe count should track thread count, not table size.
</QA>

<QA level="deep" q="Why is size() on a concurrent map problematic?">
Two bad options. Lock every stripe and it becomes the most expensive call in the
API while blocking all writers. Or sum per-stripe counters without a global lock
and return a number that was never simultaneously true — stripes are read at
different instants and mutate in between.

Java documents `ConcurrentHashMap.size()` as an estimate for exactly this reason.
Making a capacity decision from it means building on a value that can be wrong
in either direction.
</QA>

<QA level="deep" q="Your striped map shows 16x in the benchmark and nothing in production. What's different?">
Key distribution. The benchmark used uniform keys; production has a hot key
taking a large share, and it hashes to one stripe. A 64-way map behaves like a
1-way map for that traffic.

Confirm by comparing lock wait *per stripe* instead of in aggregate — an even
total with a skewed distribution is the signature. The fix isn't a better
structure: if it's a counter, give each thread its own and sum on read; if it's
a cache entry, replicate and accept staleness. Removing the sharing beats every
algorithm here.
</QA>

<SectionHeading n="09" cmd="cat REFERENCES.md" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="You have 8 threads. How many stripes?">
    Around 8, maybe 16 for headroom. Past your thread count, extra stripes add
    memory and cache pressure and no parallelism.
  </Q>
  <Q q="Why must each stripe be alignas(128) on Apple Silicon?">
    Otherwise several stripes share a cache line and their mutexes invalidate
    each other — chapter 13's false sharing. 128 because that's the M-series
    line size; 64 isn't enough there.
  </Q>
  <Q q="A striping benchmark shows more stripes are slower. What's wrong with it?">
    No affinity. If each thread touches a random stripe every iteration you
    measure cache misses across N lines, not sharding.
  </Q>
  <Q q="What beats every structure in this chapter, when it applies?">
    Not sharing. Per-thread state merged on read, for anything commutative.
  </Q>
</Quiz>
