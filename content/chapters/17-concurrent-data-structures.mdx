A supermarket can run its checkouts three ways. Everyone in the store could queue at a single till, which is simple and always correct. The store could open eight tills, with each shopper sent to one of them. Or each shopper could scan their own basket at a self-service stand and just give the total to the store at the end.

Shared data in a program faces the same three choices. One lock around everything is simple and correct, and it's also a single till. The other two designs trade some simplicity for a lot of speed, and the gap is bigger than most people expect.

<SectionHeading n="01" id="share-or-not">Race a shared counter against eight private ones</SectionHeading>

Save this as `shard.cpp`. Eight threads each add 1 to a counter two million times. In the first version they all share one counter behind a mutex. In the second, every thread has its own counter.

<Sub n="1.1" title="One till against eight self-service stands">

<TryIt what="Increment a shared counter under one mutex, then increment per-thread counters" lang="cpp" toolchain="clang++ 21 -std=c++20 -O2, Apple M4, macOS 26.5.1, 8 threads">
```cpp
#include <chrono>
#include <cstdio>
#include <mutex>
#include <thread>
#include <vector>

struct alignas(128) Padded { long v = 0; };        // one cache line each (128 B on this M4)

static double ms_since(std::chrono::steady_clock::time_point t) {
    return std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t).count();
}

int main() {
    const int T = 8; const long N = 2000000;
    long shared = 0; std::mutex m;
    auto t = std::chrono::steady_clock::now();
    { std::vector<std::thread> ts;
      for (int i = 0; i < T; i++) ts.emplace_back([&] {
          for (long k = 0; k < N; k++) { std::lock_guard<std::mutex> g(m); shared++; } });
      for (auto& th : ts) th.join(); }
    double one_lock = ms_since(t);

    std::vector<Padded> mine(T);
    t = std::chrono::steady_clock::now();
    { std::vector<std::thread> ts;
      for (int i = 0; i < T; i++) ts.emplace_back([&, i] {
          { long local = 0;
            for (long k = 0; k < N; k++) { local++; __asm__ volatile("" : "+r"(local)); }   // stop loop folding
            mine[i].v = local; } });
      for (auto& th : ts) th.join(); }
    double no_share = ms_since(t);
    long total = 0; for (auto& p : mine) total += p.v;

    std::printf("8 threads x %ld increments\n", N);
    std::printf("one shared counter, one mutex : %8.1f ms  (total %ld)\n", one_lock, shared);
    std::printf("one counter per thread        : %8.1f ms  (total %ld)\n", no_share, total);
}
```
<Output>
```
8 threads x 2000000 increments
one shared counter, one mutex :    324.8 ms  (total 16000000)
one counter per thread        :      0.8 ms  (total 16000000)
```
</Output>
</TryIt>

Both versions counted exactly 16,000,000. The shared counter took about 325 ms, and the per-thread counters took under a millisecond. Three runs gave 325, 327 and 343 ms for the mutex, and 0.7 to 0.8 ms for the private counters.

</Sub>

<Sub n="1.2" title="What the gap says">

Eight threads fighting over one lock spend their time waiting for each other, and nothing they do in parallel helps. Eight private counters never touch each other's memory, so nothing waits at all.

The unshared version had a job left over: adding the eight totals at the end. That's the price of not sharing, and for a counter it's tiny. Real structures such as maps and queues are harder to split. The rest of the chapter covers what "thread-safe" promises, how to stripe one lock into many, and where striping stops paying off.

</Sub>

<SectionHeading n="02" id="thread-safe">What thread-safe promises</SectionHeading>

Before choosing how to make shared state safe, be clear what any of the options
buys you.

<Sub n="2.1" title="Linearizability">

A concurrent structure promises **linearizability**: every operation appears to
take effect instantaneously at some point between its call and its return, and
all threads agree on the order.

That's a guarantee about *single operations*. It says nothing about sequences.

</Sub>

<Sub n="2.2" title="Check, then act">

"Check whether the key exists, then insert it" is two calls, and another thread
can insert between them:

```cpp
// Each call is individually atomic. The pair is not.
if (!map.contains(key))      // thread B can insert here
    map.insert(key, value);  // and you overwrite it
```

Step through two threads running that code on the same key:

<Why>So what's the fix, if every call is already atomic?</Why>

Make the pair one call. That's why every concurrent map API grows a combined
method: `compute_if_absent`, `LoadOrStore`, `entry()`. They exist specifically
to make check-then-act a single atomic operation.

<Callout label="Common mistake" kind="warn">
Reading "thread-safe" as "safe to compose". `ConcurrentHashMap`, `sync.Map` and
`dashmap` all make `get` and `insert` atomic. None of them make check-then-act
atomic. Composing two safe operations gives an unsafe one.
</Callout>

</Sub>

<SectionHeading n="03" id="one-lock">One mutex around the whole map</SectionHeading>

Start with the obvious design: an ordinary hash map that every request thread
reads and writes, guarded by one mutex.

<Sub n="3.1" title="Why it's the right place to start">

It's correct, it's simple, and it's trivially debuggable. [Chapter 13](/topics/13-locks)
showed that an uncontended lock costs a few nanoseconds.

The cost of being wrong is low, too. Replacing it later is a local change
behind one interface. For almost everything, start here and make a
profile tell you to move.

</Sub>

<Sub n="3.2" title="The lock turns the map into a queue">

However many threads you have, only one of them is ever inside the map. Eight
threads can't do more map operations per second than one thread could.

[Chapter 16](/topics/16-contention-tail-latency)'s arithmetic then takes over.
As that one lock gets busier, waiting grows much faster than the load. Past
about two threads of real contention, it's your bottleneck.

<Why>Why do threads wait, if they're touching different keys?</Why>

Look at what those threads are doing. Thread A is updating a user
session, thread B is reading a product, and they never conflict. They only wait
because they share a lock.

</Sub>

<SectionHeading n="04" id="striping">Lock striping</SectionHeading>

So split the lock. That's **lock striping**, and it's the idea behind
`dashmap` and the older `ConcurrentHashMap`.

<Sub n="4.1" title="An array of locks, picked by hash">

Keep an array of, say, sixteen locks, each guarding a slice of the key space,
and let a key's hash pick which one guards it:

```cpp
// Each stripe on its own cache line. Without alignas this reintroduces
// exactly the false sharing chapter 13 measured at 55x.
struct alignas(128) Stripe {
    std::mutex m;
    std::unordered_map<Key, Value> map;
};
std::vector<Stripe> stripes(16);
```

</Sub>

<Sub n="4.2" title="What striping is worth">

<Callout label="The machine" kind="note">
Apple M4, 10 cores, macOS 26.5.1, clang 21 `-O2 -pthread`. Eight threads,
100,000 critical sections each, median of 3. Every stripe is `alignas(128)`. The
critical-section body is a variable number of multiply-add rounds, so the lock's
share of the cost can be varied.
</Callout>

**Striping is worth 16–22× at eight threads**, consistently across
critical-section lengths. That's more than the eightfold ideal, probably from
the coherence traffic you stop paying.

</Sub>

<Sub n="4.3" title="Why 64 stripes is no better than 8">

<Why>If collisions keep getting rarer, why stop at eight?</Why>

Because once collisions are rare, the remaining cost isn't waiting. It's the
**cache line** that holds each lock, bouncing between the cores that use it
([chapter 02](/topics/02-memory-hierarchy) covers how cores pass lines between
each other).

With eight threads, eight stripes already give each thread its own lock.
Stripes beyond your thread count are decoration.

<Callout label="Design implication">
Size the stripe count to your thread count, not your table size. Around eight
for eight threads, maybe sixteen for headroom.
</Callout>

</Sub>

<Sub n="4.4" title="The benchmark that lied to me">

My first version of this benchmark showed striping getting *slower* as stripes
increased: 14.3 ns at one stripe, 25.9 ns at sixteen. That result is wrong, and
how it was wrong is the useful part.

Each thread picked its stripe as `(thread_id * 7919 + i) % stripes`, a different
stripe every iteration. So every thread touched every stripe, no sharding
happened at all, and I measured the cache miss from walking 64 lines instead of
one.

<Why>What was the benchmark missing?</Why>

**Affinity.** Real sharded workloads have it: a thread, or a key, maps to a
stripe and stays there. Change the access to `stripes[thread_id % n]` and the
16× appears.

<Callout label="Common mistake" kind="warn">
A striping benchmark without affinity measures cache misses, not striping. If
more stripes look slower, check how your threads pick them.
</Callout>

</Sub>

<Sub n="4.5" title="Padding each stripe">

Every shared lock or counter wants its own cache line. Miss one and chapter
13's 55× false-sharing penalty lands on an otherwise well-designed structure,
with nothing in the code looking wrong.

The padding is 128 bytes on Apple Silicon because that's the M-series line
size; 64 isn't enough there. Two usual misses: a size counter sitting next to
the buckets, and the head and tail indices of a ring buffer in one struct.

</Sub>

<SectionHeading n="05" id="no-sharing">Not sharing at all</SectionHeading>

The last step is to stop sharing. That removes the concurrent structure entirely.

<Sub n="5.1" title="Per-thread state, merged on read">

For something like a request counter, every thread bumping one number is as
contended as it gets. So give each thread its own counter, and add them up only
when somebody reads the total.

  title="A per-thread counter: cheap writes, a reader that sums"
  lanes={[

    { t: "Thread 1", s: "slot 1", icon: "1" },
    { t: "Thread 7", s: "slot 7", icon: "7" },
    { t: "Reader", s: "wants the total", icon: "Σ" },
    { t: "Result", s: "slightly stale", icon: "≈" },
  ]}
  steps={[
    [0, "Thread 0 handles a request and bumps **its own** slot. No lock, no shared cache line, no synchronisation whatsoever."],
    [1, "Thread 1 does the same, at the same moment, on its own padded slot. The two never interact."],
    [2, "So do the other threads, up to thread 7. Writes scale with the thread count."],
    [3, "Someone asks for the total. The reader walks **every slot** and adds them up, so a read costs O(threads)."],
    [4, "Slots change while it walks, so the sum is a **slightly stale** aggregate. For a counter, that's fine."],
  ]}
/>

The Linux kernel's per-CPU counters work this way, and so do the per-thread
caches in allocators like jemalloc and tcmalloc.

<Why>Why doesn't everything work this way?</Why>

Because the cost moves to the reader, and it only works for data you can merge:
counters, accumulators, statistics, anything commutative. When it applies, it
beats every algorithm in this chapter, and it probably applies more often than
people check.

</Sub>

<Sub n="5.2" title="When one atomic is enough">

Sometimes the right structure is no structure. A counter that's read often
wants `fetch_add`, not a map. A flag wants `fetch_or`. Check for a single
hardware atomic before building anything.

</Sub>

<SectionHeading n="06" id="lock-free">Lock-free structures</SectionHeading>

<Sub n="6.1" title="When blocking is a correctness problem">

[Chapter 14](/topics/14-lock-free) covers lock-free structures in full. The
short version for this decision: reach for one when you can't tolerate a thread
being descheduled while holding something, and not because it sounds faster.

That means signal handlers, interrupt context and hard real-time. Places where
blocking is a correctness problem, not a speed one.

<Why>Aren't lock-free structures faster?</Why>

Not under heavy contention. Chapter 14 measured 162 ns against a mutex's 16 ns
at eight threads. And reclamation, knowing when it's safe to free a node,
becomes a research problem. If you need one, use an existing implementation.

</Sub>

<SectionHeading n="07" id="failure">Where striping undoes itself</SectionHeading>

Striping has two ways to undo itself: one very popular key that everyone
wants, and any operation that needs every stripe at once.

<Sub n="7.1" title="The hot key">

Striping assumes keys spread evenly. Real workloads probably have a key taking 40%
of traffic, and it lives in exactly one stripe. You've built a 64-way concurrent
map that behaves, for your actual traffic, like a map with one lock.

<Why>Why doesn't the aggregate lock profile show it?</Why>

Because an even-looking total can hide a skewed distribution. Compare wait time
*per stripe*, never in aggregate. `perf lock contention` showing one lock
dominating, while throughput doesn't improve with stripe count, is the
signature.

The fix isn't a better structure. If it's a counter, give each thread its own
and sum on read. If it's a cache entry, replicate it per thread and accept some
staleness. Removing the sharing is the answer.

</Sub>

<Sub n="7.2" title="Treating size() as a fact">

`size()` on a striped or lock-free structure has two bad options:

| Approach | What you get |
|---|---|
| Lock every stripe | Your cheapest-looking query becomes the most expensive call in the API, and it blocks all writers |
| Sum per-stripe counters without a global lock | A number that was never simultaneously true: stripes are read at different instants and change in between |

Java documents `ConcurrentHashMap.size()` as an estimate for exactly this
reason. Most people read it as a fact. Using it for a capacity decision means
building on a value that can be wrong in either direction.

</Sub>

<Sub n="7.3" title="Benchmarking with uniform keys">

Uniform keys make every striped structure look excellent, and they hide the one
failure mode that will hit you. Test with a **skewed** distribution:
Zipf, or your real key frequencies taken from a log.

| Symptom | Likely cause | Fix |
|---|---|---|
| Striped map shows 16× in the benchmark, nothing in production | A hot key hashing to one stripe | Per-thread state or per-thread replicas for that key |
| More stripes make the benchmark slower | No affinity: every thread touches every stripe | Map each thread or key to a stable stripe |
| Going from 8 stripes to 64 changes nothing | Stripes already exceed the thread count | Match stripe count to thread count |
| A clean-looking design is mysteriously slow | Two locks or counters sharing a cache line | `alignas` each one to the line size (128 on Apple Silicon) |
| `size()` is slow, or its number doesn't add up | It locks every stripe, or sums them at different instants | Treat it as an estimate; don't make capacity decisions on it |
| Lost updates with a thread-safe map | Check-then-act across two calls | Use `compute_if_absent`, `LoadOrStore` or `entry()` |

</Sub>

<SectionHeading n="08" id="choosing">Choosing a design</SectionHeading>

<Sub n="8.1" title="Five questions">

1. **Can you avoid sharing entirely?** Per-thread state with a periodic merge
   beats every algorithm in this chapter. Check this first, every time.
2. **Is there a single hardware atomic for it?** A counter wants `fetch_add`,
   not a structure. A flag wants `fetch_or`.
3. **Are your keys well distributed?** If yes, stripe, with stripe count ≈
   thread count. If a hot key takes a large share, striping buys you nothing and
   you're back to question 1.
4. **Is blocking a correctness problem?** Signal handler, interrupt, hard
   deadline: then lock-free, and use an existing implementation.
5. **Otherwise use one mutex** and move on. It's probably right more often than
   this chapter's existence suggests.

</Sub>

<Sub n="8.2" title="The four designs side by side">

| Design | Best for | Breaks when |
|---|---|---|
| **One mutex** | Almost everything; start here | Past about two threads of real contention |
| **Lock striping** | Many threads, well-distributed keys, short critical sections: 16× here | A hot key defeats it completely, and `size()` stops being meaningful |
| **Per-thread state** | Counters, accumulators, statistics: anything commutative | Reads become O(threads), and you see a slightly stale aggregate |
| **Lock-free** | Signal handlers, interrupt context, hard real-time | Heavy contention (162 ns against 16 ns in chapter 14), and reclamation |

</Sub>

<Sub n="8.3" title="What production code chose">

| Implementation | Design |
|---|---|
| Java `ConcurrentHashMap`, Java 7 | Explicit segment striping |
| Java `ConcurrentHashMap`, Java 8 | Per-bin locking plus CAS on empty bins, and a striped counter for `size()` |
| Rust `dashmap` | One map sharded across many locks |
| Go `sync.Map` | Tuned for keys that are written once and read often |
| Linux per-CPU counters, jemalloc and tcmalloc caches | Per-CPU or per-thread state, merged on read |
| LMAX Disruptor | A padded ring buffer with preallocated slots; head and tail on separate lines |

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **Thread-safe means each call is atomic**, not that a sequence of calls is.
2. **Check-then-act needs one combined call**, such as `compute_if_absent`,
   `LoadOrStore` or `entry()`.
3. **One mutex is the right starting point**, and it turns the structure into a
   single queue once contention is real.
4. **Striping lets threads on different keys stop waiting for each other**, and
   it was worth 16–22× at eight threads here.
5. **Stripes beyond your thread count are decoration**: 64 stripes measured the
   same as 8.
6. **A striping benchmark needs affinity**, or it measures cache misses instead.
7. **Every stripe and counter needs its own cache line**, 128 bytes on Apple
   Silicon.
8. **Not sharing beats every structure** for anything you can merge on read.
9. **A hot key turns a striped map back into one lock**; look at wait time per
   stripe.
10. **`size()` on a concurrent map is an estimate**, so don't make capacity
    decisions from it.

<SectionHeading n="10" id="build">Build this</SectionHeading>

**Three experiments, and between them they cover every way this goes wrong.**

- Build a `std::unordered_map` behind one mutex, then the same behind N padded
  stripes. Benchmark at 1, 2, 4 and 8 threads and N of 1, 8 and 64. Confirm the
  plateau: past your thread count, more stripes buy nothing.
- Introduce a hot key, sending 40% of operations to one key, and watch the
  entire benefit disappear.
- Remove the `alignas` and measure what you lose.

Then run the first one again with your *real* key distribution instead of a
uniform one. If the answer changes, you've just avoided shipping the wrong
structure.

<SectionHeading n="11" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Your map is thread-safe. Is this correct? if (!m.contains(k)) m.insert(k, v);">
No. Each call is atomic; the pair isn't. Another thread can insert between the
check and the insert, so you overwrite it or double-count.

Every concurrent map API grows a combined method (`compute_if_absent`,
`LoadOrStore`, `entry()`), and those exist specifically to make check-then-act a
single atomic operation.
</QA>

<QA level="intermediate" q="How does lock striping work and what's it worth?">
Replace one lock over the whole structure with N locks, each guarding a slice of
the key space; the key's hash picks the stripe. Two threads on different stripes
never interact.

On an M4 with eight threads I measured 16–22× across a range of
critical-section lengths. Each stripe must be padded to a cache line, or you
reintroduce false sharing and lose most of the gain.
</QA>

<QA level="intermediate" q="You go from 8 stripes to 64 and nothing improves. Why?">
You have eight threads. Once each can hold its own lock, more locks add no
parallelism, only memory and cache pressure. Stripe count should track thread
count, not table size.
</QA>

<QA level="deep" q="Why is size() on a concurrent map problematic?">
Two bad options. Lock every stripe and it becomes the most expensive call in the
API while blocking all writers. Or sum per-stripe counters without a global lock
and return a number that was never simultaneously true: stripes are read at
different instants and mutate in between.

Java documents `ConcurrentHashMap.size()` as an estimate for exactly this reason.
Making a capacity decision from it means building on a value that can be wrong
in either direction.
</QA>

<QA level="deep" q="Your striped map shows 16x in the benchmark and nothing in production. What's different?">
Key distribution. The benchmark used uniform keys; production has a hot key
taking a large share, and it hashes to one stripe. A 64-way map behaves like a
1-way map for that traffic.

Confirm by comparing lock wait *per stripe* instead of in aggregate; an even
total with a skewed distribution is the signature. The fix isn't a better
structure: if it's a counter, give each thread its own and sum on read; if it's
a cache entry, replicate and accept staleness. Removing the sharing beats every
algorithm here.
</QA>

<Quiz>
  <Q q="You have 8 threads. How many stripes?">
    Around 8, maybe 16 for headroom. Past your thread count, extra stripes add
    memory and cache pressure and no parallelism.
  </Q>
  <Q q="Why must each stripe be alignas(128) on Apple Silicon?">
    Otherwise several stripes share a cache line and their mutexes invalidate
    each other: chapter 13's false sharing. 128 because that's the M-series
    line size; 64 isn't enough there.
  </Q>
  <Q q="A striping benchmark shows more stripes are slower. What's wrong with it?">
    No affinity. If each thread touches a random stripe every iteration you
    measure cache misses across N lines, not sharding.
  </Q>
  <Q q="What beats every structure in this chapter, when it applies?">
    Not sharing. Per-thread state merged on read, for anything commutative.
  </Q>
</Quiz>
