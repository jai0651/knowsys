You meet the CPU's inner workings whenever two pieces of code that do the same
work run at very different speeds. A loop gets five times faster after you sort
its input. A reduction gets four times faster after you split one accumulator
into four. Neither change removes any work.

Both effects come from two tricks every modern core plays: it **guesses** which
way each branch will go, and it runs **many instructions at once** when they
don't depend on each other. Neither trick shows up in your source code, so
they catch people out.

This chapter builds a processor from the simplest version up, adds each trick
where the simple version runs out, and measures both on an Apple M4. It also
shows the two times the benchmarks measured nothing because the compiler had
quietly removed the thing being tested.

<SectionHeading n="01" id="pipeline">From one instruction at a time to a pipeline</SectionHeading>

Picture the simplest processor you could build. It fetches an instruction,
works out what it means, does it, writes the result back, and only then fetches
the next one.

It's easy to reason about, and it's slow. Each piece of circuitry sits idle
while the others take their turn.

<Sub n="1.1" title="An assembly line for instructions">

Factories found the first fix: an assembly line. While one
instruction is being executed, the next is being decoded and the one after that
fetched. That's a **pipeline**.

Step through one instruction's trip, and watch what the stages behind it are
doing:

Once the pipeline is full, the processor finishes roughly one instruction every
cycle. Each instruction still takes several cycles from start to end; they just
overlap.

<Why>Why doesn't every processor just add more stages?</Why>

Because a pipeline only pays when the next instruction is known in time to
fetch it. In most programs, every few instructions, it isn't. The next section
is about that problem.

</Sub>

<SectionHeading n="02" id="branch-prediction">Branches, and the predictor that guesses them</SectionHeading>

Pipelines have a problem, and it's in every program you've written: the `if`.

<Sub n="2.1" title="The problem with if">

A pipeline has to fetch the instruction after a branch before the branch has
finished executing. At that moment it doesn't yet know which instruction comes
next.

It has two choices. It can stall and wait, which throws away most of what the
pipeline bought. Or it can guess.

Every modern core guesses, using a **branch predictor** that remembers which
way each branch went recently. It fetches down the predicted path and executes
**speculatively**. A right guess costs nothing. A wrong one means every
instruction fetched down the wrong path is thrown away.

    [0, "Fetch reaches `if (v[i] >= 128)`. The **predictor** looks at this branch's recent history and guesses **taken**."],
    [1, "The front end keeps **fetching down the guessed path** without waiting for the comparison."],
    [2, "Those instructions **execute speculatively**. Their results are held back, not yet made permanent."],
    [3, "The comparison finishes. The branch was **not taken**, so the guess was wrong."],
    [4, "Every instruction behind the branch is **discarded**, and the front end restarts from the right address. On the M4 that costs about **17 cycles**."],

  ]}
/>

Predictors are extremely good, comfortably over 95% on ordinary code. That's
exactly why the misses are expensive enough to see: the core is built to run
far ahead, and a miss throws all of that away.

</Sub>

<Sub n="2.2" title="The data decides the guess">

What decides whether the guess is right? The data.

A branch that tests `x >= 128` over sorted numbers goes the same way for
thousands of iterations in a row, and the predictor hardly ever misses. Over
shuffled numbers it's a coin flip, and it misses about half the time.

Here's the loop. The `noinline` call keeps a real branch in the binary (section
4 explains why that matters):

```cpp
std::vector<int> v(65536);
for (auto& x : v) x = rng() % 256;

long sum = 0;
for (size_t i = 0; i < v.size(); i++)
    if (v[i] >= 128) sum = taken(sum, v[i]);     // noinline, so a real branch
```

Over the shuffled vector it costs **2.724 ns per element**.

<Predict
  q="Now sort the vector first and change nothing else. Same instructions, same element count, same number of calls to taken(). What happens to the time per element?"
  options={[
    "Nothing: the work is identical",
    "It gets slightly slower, because sorting disturbs the cache",
    "It gets about five times faster",
    "It gets about fifty times faster",
  ]}
  answer={2}
>
It drops to **0.556 ns**, 4.9× faster. Cache behaviour is identical,
because the array is the same size either way. All that changed is
that the predictor is now right nearly every time.
</Predict>

<Why>Why does a wrong guess cost 17 cycles?</Why>

Because that's how much work was in flight behind the branch. The gap between the two
runs works out to about 4.3 ns per mispredicted branch, roughly
17 cycles at 4 GHz. That's the depth of the machine, measured from the outside:
what it costs to refill a front end that speculation just emptied.

</Sub>

<Sub n="2.3" title="The security cost of guessing">

Running ahead on a guess has a cost beyond speed. Speculative execution leaves
traces in the cache that survive the rollback. That's what Spectre and
Meltdown exploited in 2018.

Architectural state (registers, memory) was always rolled back correctly.
Microarchitectural state, like which lines are in the cache, was not. Closing
that gap cost real time on every privilege crossing.

<Callout label="Design implication">
If a pre-2018 syscall benchmark won't reproduce on a modern kernel, speculation
mitigations are usually the reason. Chapter 44 covers them in full.
</Callout>

</Sub>

<SectionHeading n="03" id="ilp">Running many instructions at once</SectionHeading>

A second fix was to build several pipelines side by side. A modern core is
**superscalar and out-of-order**: it can decode and retire around eight
instructions per cycle, with several integer units, several load and store
units, and separate vector pipes.

<Sub n="3.1" title="Dependency chains and latency">

It will run instructions out of the order you wrote them when that keeps the
units busy. It can only do that when instructions don't depend on each other.
Look at this loop:

```cpp
for (long i = 0; i < N; i++)
    a = a * K + C;                    // 0.959 ns per operation
```

Each step needs the previous value of `a`, so no amount of hardware can start
step two before step one finishes. That's a **dependency chain**, and the time
one step takes is its **latency**.

<Why>What's the difference between latency and throughput?</Why>

Latency is the time from issuing one operation to getting its result.
Throughput is how many of that operation can *start* per cycle.

A multiply might take three or four cycles of latency with a throughput of one
per cycle. So three or four can be in flight at once, but only if they don't
wait on each other. In a single chain you pay latency, with most of the machine
idle.

</Sub>

<Sub n="3.2" title="Four chains instead of one">

Now split the work into four variables, each with its own chain:

```cpp
for (long i = 0; i < N; i += 4) {
    a = a*K+C;  b = b*K+C;            // 0.228 ns per operation
    c = c*K+C;  d = d*K+C;            // same count of multiply-adds
}
```

Step through what the scheduler does with it:

    { t: "Scheduler", s: "waits for inputs", icon: "▤" },
    { t: "Multiply units", s: "several, pipelined", icon: "⚙" },
    { t: "Retire", s: "in program order", icon: "✓" },

  steps={[
    [0, "The front end decodes `a*K+C`, `b*K+C`, `c*K+C` and `d*K+C` in the same few cycles."],
    [1, "The scheduler checks each one's inputs. **None depends on another**, so all four are ready at once."],
    [2, "All four go to the multiply units back to back. With one chain, the second would have waited for the first result."],
    [1, "The next `a*K+C` needs the new `a`, so it waits in the scheduler. So do the next `b`, `c` and `d`, each on its own chain."],
    [2, "As each result lands, the next step of that chain issues. **Four chains are always in flight**, so the units stay busy."],
    [3, "Results retire in program order. Same number of multiply-adds, and each one costs about a quarter as much."],
  ]}
/>

Four chains cost 0.228 ns per multiply-add against 0.959 ns for one: 4.2×. Eight
chains get to **0.128 ns**, 7.5× for the same arithmetic. Section 6 plots the
whole curve.

<Why>So was it the unrolling that made it faster?</Why>

Not really. It's the four independent dependency chains the unrolling created.
Unroll a loop that still carries one accumulator and you've changed the loop
overhead, not the chain.

<Callout label="Design implication">
Analytical databases like DuckDB and ClickHouse structure their inner loops as
branch-light passes over whole columns for exactly these reasons: predictable
control flow and independent work per element.
</Callout>

</Sub>

<SectionHeading n="04" id="benchmark-traps">When the compiler removes the thing you're measuring</SectionHeading>

Both of the headline numbers in this chapter were wrong when first taken. The
failures teach more than the results.

<Sub n="4.1" title="A branch penalty of exactly 1.0×">

The first branch benchmark used the obvious loop,
`if (d[i] >= 128) sum += d[i]`, and reported a penalty of exactly **1.0×**. The disassembly said why:

<SourceRead
  file="clang++ -O2, if (d[i] >= 128) sum += d[i]"
  repo="aarch64"
  tag="if-conversion"
  href="https://developer.arm.com/documentation/ddi0487/latest/"
>
```asm
    cmp   w10, #0x7f
    csel  w10, w10, wzr, gt     ; conditional select — NO BRANCH EXISTS
    add   x0, x0, x10           ; add unconditionally
```
</SourceRead>

The compiler had removed the branch entirely and turned it into a conditional
select. Nothing to mispredict, so no effect to measure.

<Why>When does the compiler do this?</Why>

Whenever both sides of the condition are cheap. It's called **if-conversion**:
computing both outcomes and picking one is faster than risking a mispredict.
It's a good optimisation, and it silently destroys any branch-prediction
experiment.

This is also why a famous puzzle has aged. Stack Overflow's top-voted question
for years was about a 6× gap between sorted and shuffled input to identical
code. On many modern targets the compiler now removes that branch and the
effect vanishes. The answers are still worth reading, then check whether your
compiler still emits a branch at all.

</Sub>

<Sub n="4.2" title="Zero nanoseconds per add">

An early ILP benchmark reported **0.000 ns per add**. Its loop was `a += i`,
which has a closed form, so the optimiser replaced the loop with a
constant.

Both were fixed the same way. Force a real branch with a `noinline` call, and
use a multiply chain with an opaque seed that can't be folded.

<Callout label="Common mistake" kind="warn">
Trusting a microbenchmark you haven't disassembled. Two of the three
measurements here measured nothing until someone looked at the assembly: a
folded loop, and an if-converted branch. Look for `csel` on ARM or `cmov` on
x86 before you believe a branch result.
</Callout>

</Sub>

<SectionHeading n="05" id="controls">What you can actually control</SectionHeading>

Five things decide how these effects hit your code. Only some of them are yours.

| Variable | Effect | Can you reach it? |
|---|---|---|
| Predictability of your data | Decides the mispredict rate entirely | Yes: sort, partition, or batch by type |
| Whether a branch exists at all | If-conversion removes the question | Indirectly, by keeping both sides cheap |
| Dependency chain length | Latency-bound versus throughput-bound | Yes: unroll, use multiple accumulators |
| Pipeline depth | Sets the misprediction penalty | No. It's the silicon. |
| Issue width | Caps how much overlap helps | No, but you can find it by measuring |

Data predictability and dependency structure are all of this chapter
you can act on. Both are properties of how you arranged your code, not of what
it computes.

<Why>How can one multiply-add take less than a cycle?</Why>

At 4 GHz, 0.128 ns is roughly half a cycle per multiply-add. So the core is
completing more than one per cycle, which needs several multiply units running
at once. Seeing that is how you discover your machine has them.

</Sub>

<SectionHeading n="07" id="act">What to do about it</SectionHeading>

<Sub n="7.1" title="Four moves, in order of payoff">

Ranked by how often they actually pay, not by how clever they look.

1. **Check IPC before anything else.** `perf stat` reports instructions per
   cycle. Modern cores retire six to eight; real code often runs at one or two.
2. **Break dependency chains.** Use multiple accumulators in a reduction, unroll
   a loop, restructure so consecutive operations don't feed each other. Up to
   7.5× is sitting in the measurement above.
3. **Make branches predictable, or remove them.** Sort or partition so a batch
   takes the same path. Where the bodies are cheap, write it branchlessly and
   let the compiler emit a `csel`.
4. **Read the disassembly before concluding anything.**

</Sub>

<Sub n="7.2" title="Reading the symptoms">

IPC far below what the core can issue tells you it's waiting, not working. The
other counters tell you on what.

| Symptom | Likely cause | Fix |
|---|---|---|
| Low IPC, high cache misses | Waiting on memory | Chapter 02; nothing in this chapter will help |
| Low IPC, clean cache counters, high branch misses | Unpredictable branches | Sort or partition the data, or go branchless |
| Low IPC, clean cache and branch counters | A long dependency chain | Multiple accumulators, independent chains |
| Adding a branch made nothing slower | The compiler if-converted it | Check for `csel` / `cmov` in the disassembly |
| A benchmark reports ~0 ns | The loop was folded to a constant | Opaque inputs; read the assembly |

```shell
perf stat -e instructions,cycles ./app      # IPC first
perf stat -e branch-misses ./bench          # then the branch counter
objdump -d ./bench | grep csel              # did the branch survive?
```

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **A pipeline overlaps instructions.** Each takes several cycles, but a full
   pipeline finishes about one per cycle.
2. **Branches break the pipeline, so the core guesses.** A branch predictor
   picks a path and the core runs down it speculatively.
3. **A wrong guess costs a pipeline flush.** About 17 cycles on the M4, 4.3 ns
   per mispredict.
4. **The data decides the mispredict rate.** Sorted input ran at 0.556 ns per
   element; the same input shuffled ran at 2.724 ns.
5. **Speculation has a security cost.** Spectre reads the cache traces it
   leaves, and the mitigations slow every privilege crossing.
6. **A core runs many instructions at once, if they're independent.** One
   dependency chain pays latency; several chains pay throughput.
7. **Independent chains, not unrolling, give the speedup.** Eight chains made
   the same multiply-adds 7.5× faster.
8. **Compilers remove what you're trying to measure.** If-conversion deletes
   branches and constant folding deletes loops.
9. **Check IPC first.** It tells you whether to look at memory, branches or
   dependency chains.
10. **Only two of the five variables are yours.** Data predictability and
    dependency structure; the pipeline depth and issue width are the silicon.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Get it wrong first. That's the part that teaches.**

- Write the sorted-versus-shuffled benchmark naively: `if (x >= 128) sum += x`.
  You'll measure a penalty near 1.0×.
- Disassemble. Find the `csel` on ARM or `cmov` on x86. Your experiment was
  deleted before it ran.
- Force a real branch with a `noinline` call and measure again. Expect roughly
  3–6×, depending on your core's pipeline depth.
- Then sweep dependency chains from 1 to 16 and find where your curve flattens.
  That number is your machine's effective issue width for that operation (or
  probably just a lower bound on it: if the operation is latency-bound you'll
  flatten early for an unrelated reason), and it isn't in any spec sheet in that
  form.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What does 'instructions per cycle' tell you?">
How well the core is being kept busy. A modern core can retire six to eight per
cycle; real code often manages one or two. Low IPC means the core is waiting —
on memory, on a dependency chain, or on recovering from a bad guess.

It's the first number to check because it tells you which chapter to open. Low
IPC with high cache misses is a memory problem; low IPC with clean cache
counters is a control-flow or dependency problem.
</QA>

<QA level="intermediate" q="Why can sorting an array speed up a later loop without changing the loop?">
Branch prediction. A predicate over sorted data goes the same way for long
runs, so the predictor is right nearly always. Over shuffled data it's a coin
flip and every wrong guess discards the speculatively fetched work.

I measured 0.556 ns per element sorted against 2.724 ns shuffled — 4.9×, about
17 cycles per mispredict. The caveat matters: compilers often if-convert such
branches into a conditional select, and then there's no branch and no effect.
</QA>

<QA level="intermediate" q="What's the difference between latency and throughput for an instruction?">
Latency is issue-to-result for one operation. Throughput is how many can start
per cycle. A multiply might have three cycles of latency and one per cycle of
throughput, so three can be in flight simultaneously.

You only reach the throughput number with independent work. I measured 0.959 ns
per multiply-add in a single chain and 0.128 ns across eight independent chains
— 7.5×, with the same instruction count.
</QA>

<QA level="deep" q="Your microbenchmark shows no difference between two implementations. What do you check first?">
The disassembly. By a wide margin the likeliest explanation is that the compiler
deleted whatever you were measuring — folded a loop to a constant, hoisted an
invariant load, or if-converted the branch you wanted to mispredict.

Two of my three measurements in this chapter were wrong initially for exactly
that reason, and only the assembly said so. A benchmark you haven't
disassembled is a benchmark you haven't run.
</QA>

<QA level="deep" q="Why did Spectre mitigations make syscalls slower?">
Because the fix is to stop sharing speculation state across a privilege
boundary. Flushing or partitioning branch predictors on entry, and on some
designs unmapping most of the kernel from the user page table, both add work to
every transition.

Architectural rollback was always correct. What leaked was microarchitectural
state — cache occupancy that survives the squash — and preventing that costs
real time on a path that used to be nearly free.
</QA>
