<SectionHeading n="01" cmd="./bench --sorted --shuffled" id="observe">Two loops, one five times slower</SectionHeading>

Two loops. Same instructions, same element count, same predicate. One runs five
times faster.

```cpp
std::vector<int> v(65536);
for (auto& x : v) x = rng() % 256;

long sum = 0;
for (size_t i = 0; i < v.size(); i++)
    if (v[i] >= 128) sum = taken(sum, v[i]);     // noinline, so a real branch
```

Run that over the shuffled vector: **2.724 ns per element.** Sort the vector
first, change nothing else, and it's **0.556 ns**. Identical work, identical
number of calls to `taken`, identical cache behaviour — the array is the same
size either way.

A second one, no branches involved at all:

```cpp
for (long i = 0; i < N; i++)
    a = a * K + C;                    // 0.959 ns per operation

for (long i = 0; i < N; i += 4) {
    a = a*K+C;  b = b*K+C;            // 0.228 ns per operation
    c = c*K+C;  d = d*K+C;            // same count of multiply-adds
}
```

Four independent chains instead of one, and each multiply-add costs a quarter
as much. Eight chains gets it to 0.128 ns — **7.5× for the same arithmetic.**

Neither result makes sense if you believe a processor executes one instruction
at a time in the order you wrote them. It doesn't, and hasn't since about 1995.

<SectionHeading n="02" cmd="objdump -d ./bench | grep csel" id="mechanism">Speculation, and doing many things at once</SectionHeading>

<Sub n="2.1" title="Your processor is guessing">

At a conditional branch, a modern core doesn't wait to find out which way it
goes. It predicts from history, fetches down that path, and executes
speculatively. Correct guess, nothing lost. Wrong guess, every instruction
behind it is discarded and the front end restarts from the right address.

Predictors are extremely good — comfortably over 95% on ordinary code — and
that's exactly why the misses are expensive enough to see. Sorted data gives
long runs of the same answer and the predictor is right nearly always. Shuffled
data is a coin flip.

</Sub>

<Sub n="2.2" title="And running far more than one thing at once">

Separately, the core is **superscalar and out-of-order**. It can decode and
retire around eight instructions per cycle, with several integer units, several
load and store units, and separate vector pipes.

Those units only stay busy if independent work exists. One dependency chain
means each multiply waits for the previous result — you're paying *latency*,
maybe three or four cycles each, with most of the machine idle. Four chains and
the scheduler interleaves them, so you pay *throughput* instead.

</Sub>

<Sub n="2.3" title="Where my first two measurements went wrong">

Both of the numbers in section 1 were wrong when I first took them, and the
failure is worth more than the result.

My first branch benchmark reported a penalty of exactly **1.0×**. The
disassembly said why:

<SourceRead
  file="clang++ -O2, if (d[i] >= 128) sum += d[i]"
  repo="aarch64"
  tag="if-conversion"
  href="https://developer.arm.com/documentation/ddi0487/latest/"
>
```asm
    cmp   w10, #0x7f
    csel  w10, w10, wzr, gt     ; conditional select — NO BRANCH EXISTS
    add   x0, x0, x10           ; add unconditionally
```
</SourceRead>

The compiler had removed the branch entirely, turning it into a conditional
select. Nothing to mispredict, so no effect to measure. Compilers do this
whenever both sides of the condition are cheap, and it silently destroys any
branch-prediction experiment.

My first ILP benchmark reported **0.000 ns per add**, because `a += i` in a loop
has a closed form, so the optimiser replaced the loop with a constant.

Both were fixed the same way: force a real branch with a `noinline` call, and
use a multiply chain with an opaque seed that can't be folded.

</Sub>

<SectionHeading n="05" cmd="perf stat -e instructions,cycles ./app" id="act">What to do about it</SectionHeading>

Ranked by how often they actually pay, and not by how clever they look.

1. **Check IPC before anything else.** `perf stat` gives you instructions per
   cycle. Modern cores retire six to eight; real code often runs at one or two.
   Low IPC with low cache misses points here; low IPC with high cache misses is
   chapter 02's problem and nothing in this chapter will help.
2. **Break dependency chains.** Multiple accumulators in a reduction, unroll a
   loop, restructure so consecutive operations don't feed each other. Up to 7.5×
   is sitting there in the measurement above.
3. **Make branches predictable, or remove them.** Sort or partition so a batch
   takes the same path. Where the bodies are cheap, write it branchlessly and
   let the compiler emit a `csel`.
4. **Read the disassembly before concluding anything.** Two of my three
   measurements here were measuring nothing until I looked.

<SectionHeading n="06" cmd="make bench && ./bench" id="reproduce">Reproduce it yourself</SectionHeading>

**Get it wrong first — that's the part that teaches.**

- Write the sorted-versus-shuffled benchmark naively: `if (x >= 128) sum += x`.
  You'll measure a penalty near 1.0×.
- Disassemble. Find the `csel` on ARM or `cmov` on x86. Your experiment was
  deleted before it ran.
- Force a real branch with a `noinline` call and measure again. Expect somewhere
  in the 3–6× range depending on your core's pipeline depth.
- Then sweep dependency chains from 1 to 16 and find where your curve flattens.
  That number is your machine's effective issue width for that operation, and
  it isn't in any spec sheet in that form.

<SectionHeading n="08" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What does 'instructions per cycle' tell you?">
How well the core is being kept busy. A modern core can retire six to eight per
cycle; real code often manages one or two. Low IPC means the core is waiting —
on memory, on a dependency chain, or on recovering from a bad guess.

It's the first number to check because it tells you which chapter to open. Low
IPC with high cache misses is a memory problem; low IPC with clean cache
counters is a control-flow or dependency problem.
</QA>

<QA level="intermediate" q="Why can sorting an array speed up a later loop without changing the loop?">
Branch prediction. A predicate over sorted data goes the same way for long
runs, so the predictor is right nearly always. Over shuffled data it's a coin
flip and every wrong guess discards the speculatively fetched work.

I measured 0.556 ns per element sorted against 2.724 ns shuffled — 4.9×, about
17 cycles per mispredict. The caveat matters: compilers often if-convert such
branches into a conditional select, and then there's no branch and no effect.
</QA>

<QA level="intermediate" q="What's the difference between latency and throughput for an instruction?">
Latency is issue-to-result for one operation. Throughput is how many can start
per cycle. A multiply might have three cycles of latency and one per cycle of
throughput, so three can be in flight simultaneously.

You only reach the throughput number with independent work. I measured 0.959 ns
per multiply-add in a single chain and 0.128 ns across eight independent chains
— 7.5×, with the same instruction count.
</QA>

<QA level="deep" q="Your microbenchmark shows no difference between two implementations. What do you check first?">
The disassembly. By a wide margin the likeliest explanation is that the compiler
deleted whatever you were measuring — folded a loop to a constant, hoisted an
invariant load, or if-converted the branch you wanted to mispredict.

Two of my three measurements in this chapter were wrong initially for exactly
that reason, and only the assembly said so. A benchmark you haven't
disassembled is a benchmark you haven't run.
</QA>

<QA level="deep" q="Why did Spectre mitigations make syscalls slower?">
Because the fix is to stop sharing speculation state across a privilege
boundary. Flushing or partitioning branch predictors on entry, and on some
designs unmapping most of the kernel from the user page table, both add work to
every transition.

Architectural rollback was always correct. What leaked was microarchitectural
state — cache occupancy that survives the squash — and preventing that costs
real time on a path that used to be nearly free.
</QA>

<Quiz>
  <Q q="You add a branch and nothing gets slower. Why might that be?">
    The compiler if-converted it into a conditional select. No branch exists in
    the binary. Look for `csel` on ARM or `cmov` on x86.
  </Q>
  <Q q="Unrolling a loop four ways made it 4x faster. Was it the unrolling?">
    Not really — it's the four independent dependency chains you created. Same
    work, but now the core can overlap it.
  </Q>
  <Q q="Roughly how many cycles does a mispredicted branch cost?">
    Around 15–20 on a modern core; I measured about 17 on an M4. That's the
    pipeline depth being refilled.
  </Q>
  <Q q="IPC is 0.4 and branch misses are negligible. Where do you look?">
    Memory, so chapter 02. You're stalling on cache misses, not on control flow.
  </Q>
</Quiz>
