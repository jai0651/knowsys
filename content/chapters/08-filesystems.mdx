Every service reads and writes files, even the ones that think they don't. A
database is slow for twenty minutes after a restart and fine all afternoon. A
pod's memory climbs towards its limit though the heap is small. A config file
comes back empty after a power cut, though the write returned success.

All three come from the same place: the layer the kernel puts between your
`read()` and `write()` calls and the disk. It finds your data by name, and it
hides how slow the disk is by keeping file data in RAM.

This chapter builds that layer up from a bare array of blocks. It covers inodes
and names, the page cache on a read and a write, what `fsync` promises, how
journalling keeps the structure consistent after a crash, and the ways data gets
lost silently, fsyncgate included.

<SectionHeading n="01" id="files-on-blocks">Files on top of blocks</SectionHeading>

To a computer, a disk is one enormous array of numbered blocks, a few kilobytes
each. There are no files in it, no names and no folders.

Everything you think of as "the filesystem" is a data structure the kernel
builds on top of that array. It has two jobs: find your data by name, and hide
how slow the disk is.

<Sub n="1.1" title="Finding a file by name">

You ask for `/home/jai/notes.txt`. Where is it?

The filesystem keeps a small record for every file, called an **inode**, holding
its size, owner, permissions, timestamps and the list of blocks where its bytes
live. A directory is just a file whose contents are a table of names and inode
numbers.

So opening that path means reading the root directory to find `home`, reading
`home` to find `jai`, reading `jai` to find `notes.txt`, and then reading its
inode to learn which blocks to fetch.

<Why>Why doesn't renaming a file touch its data?</Why>

Because the name isn't stored in the file at all. It's an entry in its parent
directory. A rename edits that entry and leaves the inode and its blocks alone.

</Sub>

<Sub n="1.2" title="Inodes, names and extents">

That indirection, names in directories pointing at inodes, explains several
behaviours people find surprising.

<Figure caption="Two names, one inode. Deleting a name decrements a link count; the data goes when the count and the open-descriptor count both reach zero. So deleting a file an open process is using frees no space at all.">

Modern filesystems track data as **extents**, a start block and a length,
instead of listing every block. A contiguous 1 GB file needs one extent, not
250,000 block pointers.

Fragmentation is what turns one extent into thousands. It's usually the
mechanism behind a file that gets slower to read over its lifetime.

</Sub>

<SectionHeading n="02" id="page-cache">The page cache</SectionHeading>

<Sub n="2.1" title="Why the kernel keeps file data in RAM">

The second job, hiding the disk, matters more for performance.

A random 4 KB read that has to reach the SSD on this machine takes about
**45,000 ns**. The same read served from RAM takes about 518 ns, eighty-seven
times less.

So the kernel keeps copies of recently used file data in whatever RAM is free,
in the **page cache**, keyed by inode and offset. Every ordinary `read` checks
there first.

<Why>Why is a database slow for twenty minutes after a restart?</Why>

Because the cache starts empty. Until the working set has been read once from
the device, every read pays the 45,000 ns path.

<Why>Why does free show almost no free memory on a busy box?</Why>

Because the kernel is using it all as cache and will hand it back on demand.
"Free memory" on a healthy server is close to zero by design.

</Sub>

The page stays in the cache afterwards, so the next read of it is a hit. That's
the whole trick.

</Sub>

<Sub n="2.3" title="Writes and dirty pages">

Writes go through the same cache. When `write()` returns, your bytes are in RAM
and the page is marked **dirty**.

The kernel flushes dirty pages to the disk later, in the background, on a timer
or under memory pressure. That's called **writeback**, and Linux can hold dirty
data for up to about 30 seconds by default.

That window is exactly what makes `fsync` necessary.

</Sub>

<SectionHeading n="03" id="durability">Visible is not durable</SectionHeading>

A filesystem promises that a successful `write()` will be visible to any
subsequent `read()`. Note the exact shape of that promise: it's about
*visibility*, not *durability*.

Your bytes are in the page cache. Whether they're on a disk is a separate
question with a separate syscall.

<Sub n="3.1" title="What POSIX guarantees, and what it doesn't">

| Property | Guaranteed? | What it means for you |
|---|---|---|
| A read after a write, in the same or another process, sees the new data | **Yes** | Other processes see your write straight away |
| `rename()` within a directory is atomic | **Yes** | No reader sees a partial state. This is the foundation of safe file updates. |
| Data survives a crash without `fsync` | No | Up to about 30 s of writes can vanish |
| Ordering between writes to different files | No | After a crash, file B can be newer than file A |
| A failed `fsync` can be retried | No | Section 5.1; it's alarming |

</Sub>

<Sub n="3.2" title="fsync, from write() to the device">

`write()` returning means the page cache has your data, marked dirty. Linux can

</Predict>

`fsync` forces the flush and waits for the device to confirm. Here's the whole
path, with the two points that matter marked:

<Callout label="Design implication">
`write()` returning success means the kernel accepted your data. `fsync()`
returning success means the device claims to have it. Postgres writes its log
and calls `fsync` before it tells you a transaction committed. Every database
calls `fsync`. Most application code doesn't, and probably gets away with it.
</Callout>

Kafka goes the other way and leans on the page cache on purpose, keeping
messages there instead of in the JVM heap.

</Sub>

<Sub n="3.3" title="Updating a file safely">

Because `rename` is atomic and `write` is not, the durable-update pattern is
always the same four steps:

```shell
# 1. write the new content to a temporary file in the SAME directory
# 2. fsync the temp file          (data is on the device)
# 3. rename temp over the target  (atomic swap)
# 4. fsync the DIRECTORY          (the rename itself is durable)
```

A half-written file never becomes visible, because readers see either the old
name's target or the new one.

<StepSequence
  title="The rename dance, and what a crash leaves at each step"
  actors={["Your app", "Temp file", "Directory", "Device"]}
  messages={[
    { from: 0, to: 1, label: "write", note: "Write the new content to `config.tmp` in the **same directory** as the target. Readers still see the old `config`." },
    { from: 1, to: 3, label: "fsync(temp)", note: "The new **data** is on the device. A crash now leaves the old file intact, plus a stray temp file." },
    { from: 0, to: 2, label: "rename", note: "`rename(config.tmp, config)` swaps the name **atomically**. Readers see the old file or the new one, never half of each." },
    { from: 2, to: 3, label: "fsync(dir)", note: "The rename is a directory change, and it's sitting in the page cache like anything else. This `fsync` makes the **rename itself** durable." },
  ]}
/>

<Why>Why fsync the directory?</Why>

Because the rename is a directory metadata change, and it sits in the page cache
like anything else. Skip step 4 and a crash can leave you with neither the old
file nor the new one.

<Callout label="Common mistake" kind="warn">
Stopping after the rename. Step 4 is the one everyone forgets, and it's the one
that makes the rename survive a crash.
</Callout>

SQLite's atomic commit documentation is the best free explanation of building
durability on a filesystem that offers so little. It lists which guarantees
SQLite relies on and which it assumes are absent, written by people who had to
make it work everywhere, including on filesystems that lie.

</Sub>

<SectionHeading n="04" id="journalling">Journalling, and what it actually protects</SectionHeading>

<Sub n="4.1" title="Writing intent first">

A crash midway through a multi-block update leaves the filesystem inconsistent:
an inode claiming blocks the allocator thinks are free, a directory entry
pointing at nothing.

A **journal** fixes this by writing intent first. Record what you're about to
do, do it, then clear the record. After a crash, replay or discard.

</Sub>

<Sub n="4.2" title="Metadata only, by default">

<Why>Why can a file hold garbage after a clean journal replay?</Why>

Because ext4's default `data=ordered` journals **metadata only**. Your
filesystem will be structurally consistent after a crash. Your file contents may
be garbage.

Those are different properties and only the first one is being promised.

<Callout label="Common mistake" kind="warn">
Reading "journalled filesystem" as "my data survives crashes". The journal keeps
the filesystem's own structures consistent. Your file's contents are still your
job, with `fsync` and the rename dance.
</Callout>

</Sub>

<SectionHeading n="05" id="failure">fsyncgate, and other silent losses</SectionHeading>

<Sub n="5.1" title="fsyncgate">

In 2018 the Postgres team discovered what Linux does when writeback fails. The
mailing list thread changed how every serious database handles write errors, and
it repays reading in full.

<StepSequence
  title="A failed writeback, reported once"
  actors={["Postgres", "Page cache", "Kernel writeback", "Device"]}
  messages={[
    { from: 0, to: 1, label: "write", note: "Postgres writes data. The pages are dirty in the page cache." },
    { from: 2, to: 3, label: "writeback", note: "The kernel writes the dirty pages back in the background." },
    { from: 3, to: 2, label: "I/O error", note: "The device reports an error. The write failed." },
    { from: 2, to: 1, label: "mark clean", note: "The kernel **marks the pages clean** anyway. The dirty data is gone from memory, and it isn't on the disk." },
    { from: 0, to: 2, label: "fsync", note: "The error goes to **whichever descriptor happens to call `fsync` next**, once. Here, `fsync` fails." },
    { from: 0, to: 2, label: "fsync (retry)", note: "Postgres retries. `fsync` returns **success**, because the error state has been consumed. The data is still lost." },
  ]}
/>

<Why>Why can't you just retry a failed fsync?</Why>

Because the intuitive recovery doesn't merely fail. It converts a reported
failure into a silent one, and the data is already unrecoverable.

Postgres now panics on `fsync` failure, on the grounds that crashing is the only
honest response. The fix across the industry was the same.

<Callout label="Design implication">
If `fsync` fails, you can't retry. Treat it as fatal, and recover from your own
log or a replica.
</Callout>

</Sub>

<Sub n="5.2" title="Directory operations at scale">

A directory with a million entries makes every `open` a lookup in a structure
that may be a linear list. ext4's `dir_index` uses hashed B-trees and handles it;
older filesystems and some network filesystems don't.

The standard fix is sharding by hash prefix, `ab/cd/abcdef...`. That's probably
why every object store, Git, and most cache directories look like that.

</Sub>

<Sub n="5.3" title="Page cache eviction under memory pressure">

The page cache competes with anonymous memory. A large allocation can evict the
file pages your service depends on, and it may not be your allocation. The first symptom is reads that were 518 ns
becoming 45,000 ns with nothing in your code having changed.

On Linux, `vm.swappiness` and cgroup memory limits decide who loses.

<Why>Why does file I/O push a container towards its memory limit?</Why>

Because in a container with a memory limit, the page cache counts against the
limit, which surprises people. Clean cache is mostly harmless: the kernel
reclaims it before it kills anything.

Dirty pages and tmpfs are what get a file-heavy workload OOM-killed, because
neither can be dropped until it's written somewhere.
[The dashboard said 60%](/blog/oom-killed-at-sixty-percent) reproduces both.

</Sub>

<SectionHeading n="06" id="cost">518 nanoseconds against 45,000</SectionHeading>

<Callout label="The machine" kind="note">
Apple M4, macOS 26.5.1, APFS on the internal NVMe. Uncached numbers use a 3 GB
file with `F_NOCACHE` and page-aligned buffers. My first attempt used a 64 MB
file that sat entirely in cache, so it measured RAM and would have called it
disk. Stating it because that mistake is easy and invisible.
</Callout>

**Eighty-seven times.** That single ratio is why the kernel spends every byte of

Nineteen times, and that's on a fast NVMe with APFS. On hardware where the

<Callout label="Design implication">
Group commit is the standard answer: hold transactions for a millisecond, then
`fsync` once for all of them. You trade a little latency for a large amount of
throughput, and it's why database commit latency has a floor around the flush
time of your storage.
</Callout>

</Sub>

<SectionHeading n="07" id="operating">Watching the cache and the writeback</SectionHeading>

<Sub n="7.1" title="Seeing the cache">

```shell
# How much of memory is page cache, and how much is dirty right now
free -h
grep -E 'Dirty|Writeback|^Cached' /proc/meminfo

# Which files are cached, page by page
vmtouch -v /path/to/file

# Is this process doing real I/O or hitting cache?
pidstat -d 1                   # actual device reads/writes
cat /proc/$PID/io              # read_bytes is device; rchar includes cache

# macOS
fs_usage -w -f filesys $PID
sudo purge                     # drop the cache, then re-measure
```

`/proc/$PID/io` is the useful one. `rchar` counts bytes your process asked for;
`read_bytes` counts bytes that reached the device. A large gap between them is
your cache hit rate, expressed in the most direct way available.

</Sub>

<Sub n="7.2" title="Rules that hold up">

1. **Use the rename dance for any file that matters.** Temp file, fsync, rename,
   fsync the directory. All four steps.
2. **Treat `fsync` failure as fatal.** You can't retry it.
3. **Batch your fsyncs** if you control the write pattern. 19× is a lot to pay
   per operation.
4. **Don't fight the page cache.** `O_DIRECT` is for software that maintains its
   own buffer pool (databases) and is a pessimisation everywhere else.
5. **Remember the cache counts against container memory limits.**

</Sub>

<Sub n="7.3" title="What you give up">

| You get | You pay | When the bill arrives |
|---|---|---|
| A page cache worth 87× | It competes with your heap, and counts in cgroup limits | As an OOM kill you didn't expect |
| `write()` returns immediately | Up to 30 s of data in volatile memory | On power loss |
| `fsync`, real durability | 19× per operation | As commit latency with a hard floor |
| Metadata journalling | Structural consistency only, not your file contents | After a crash, as valid files full of garbage |
| Atomic rename | Only if you also fsync the directory | As neither the old nor the new file |

</Sub>

<Sub n="7.4" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| Slow for minutes after a restart, then fine | Cold page cache | Expected; warm it, or wait. Check `read_bytes` against `rchar` |
| Reads suddenly ~100× slower, nothing deployed | Working set evicted from the page cache | Find what allocated memory or what grew; check `/proc/$PID/io` |
| Deleted a large file, no space freed | A process still has it open | Restart or close that process |
| File empty or old after a power cut | No `fsync`, or no directory `fsync` after rename | The four-step rename dance |
| Valid-looking files full of garbage after a crash | `data=ordered` journals metadata only | `fsync` your data; don't rely on the journal |
| Pod OOM-killed doing file I/O | Dirty pages or tmpfs counted against the limit | Flush sooner, move tmpfs data to disk, raise the limit |
| `open` slow in a huge directory | Linear directory lookup | Shard by hash prefix |

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **A disk has no files.** A filesystem is a data structure on an array of
   numbered blocks.
2. **A name is a directory entry, not part of the file.** It points at an inode,
   so a rename doesn't touch the data.
3. **Extents keep big files cheap to describe.** Fragmentation turns one extent
   into thousands.
4. **The page cache is worth about 87×.** 518 ns cached against ~45,000 ns from
   NVMe for a 4 KB random read.
5. **`write()` returning means visible, not durable.** Dirty pages can sit in RAM
   for about 30 seconds.
6. **`fsync` is what asks for durability**, and it cost 19× the write alone.
7. **Safe updates take four steps.** Temp file, fsync, rename, fsync the
   directory.
8. **The default journal protects metadata only.** Your file contents can still
   be garbage after a crash.
9. **A failed `fsync` can't be retried.** Linux reports the error once and marks
   the pages clean.
10. **Group commit makes durability affordable.** 50 transactions per fsync took
    the cost from 18.5% of a core to 0.4%.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Measure the cache cliff yourself, then fall off it.**

- Write a file larger than your RAM. Read 4 KB at random offsets and time it.
- Read the same 64 MB window repeatedly until it's warm, and time that.
- That ratio should land somewhere near two orders of magnitude, maybe more.
- Now `echo 3 > /proc/sys/vm/drop_caches` (or `sudo purge` on macOS) between runs
  and watch the warm number become the cold number.

Then the durability half: time 1,000 small writes with and without `fsync`, and
again with one `fsync` per 50 writes. You'll have derived group commit from
first principles. More convincing than being told about it.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="write() returned success. Is your data safe?">
No. It means the kernel has your data in the page cache and a later read will
see it. It says nothing about the device. Dirty pages are written back on a
timer or under memory pressure, typically within tens of seconds, and a power
cut in that window loses them.

`fsync()` is what asks for durability, and I measured it at about 19× the cost
of the write alone.
</QA>

<QA level="intermediate" q="Describe the safe way to replace a file's contents.">
Four steps. Write the new content to a temporary file in the same directory;
`fsync` that file; `rename` it over the target, which POSIX guarantees is
atomic so no reader sees a partial state; then `fsync` the *directory*.

The fourth step is the one people skip. A rename is a directory metadata change
and it sits in the page cache too. Without that final fsync a crash can leave
you with neither the old file nor the new one.
</QA>

<QA level="intermediate" q="Your reads suddenly got 100x slower and nothing was deployed. What happened?">
Probably the page cache stopped holding your working set. Something
else on the box allocated memory and evicted your file pages, or the file grew
past what the cache holds.

On this hardware I measured 518 ns for a cached 4 KB read and about 45,000 ns
uncached: 87×. Check `read_bytes` in `/proc/$PID/io` against `rchar`: a
widening gap between bytes requested and bytes fetched from the device is the
cache hit rate falling.
</QA>

<QA level="deep" q="What is fsyncgate and why can't you retry a failed fsync?">
Postgres found in 2018 that on Linux a writeback failure is reported to
whichever descriptor calls `fsync` next, exactly once, and the kernel then marks
the pages clean. A second `fsync` returns success, but the dirty data is
already gone.

So retrying converts a loud failure into a silent one over data you have already
lost. No recovery path exists at the application level, so Postgres now panics
on `fsync` failure. Crashing is the only honest response.
</QA>

<QA level="deep" q="Your database does 10,000 commits per second and fsync costs 18 µs. Do the arithmetic.">
Ten thousand fsyncs at 18.5 µs is 185 ms of every second, about 18.5% of a core
doing nothing but flushing, before any actual work.

That's why group commit exists. Hold transactions for a millisecond and fsync
once for the batch: at 50 transactions per flush you make 200 calls instead of
10,000, and the cost drops to roughly 0.4%. You trade a millisecond of latency
for most of a core, and it's why commit latency has a floor set by your
storage's flush time.
</QA>

<SectionHeading n="11" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="You deleted a large file and no space was freed. Why?">
    A process still has it open. The name is gone but the inode's
    open-descriptor count isn't zero, so the blocks stay allocated until that
    process closes it or exits.
  </Q>
  <Q q="ext4 with data=ordered survived a crash. Are your file contents intact?">
    Not necessarily. Default journalling covers metadata only, so the filesystem
    is structurally consistent while individual files may contain garbage.
  </Q>
  <Q q="Roughly how much does the page cache buy you?">
    Around 87× on this hardware: 518 ns cached against ~45,000 ns from NVMe for
    a 4 KB random read.
  </Q>
  <Q q="Should application code use O_DIRECT to avoid double buffering?">
    Almost never. It's for software maintaining its own buffer pool, like
    databases. Everywhere else you lose the 87× and gain nothing.
  </Q>
</Quiz>
