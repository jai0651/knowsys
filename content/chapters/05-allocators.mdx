Your program calls `malloc` or `new` millions of times a second, and almost
never thinks about it. Then a long-running service's memory climbs for hours
and never comes down, with no leak anywhere. Or a profile shows a hot loop
spending its time in `free`.

Both come from the allocator: the code between your `new` and the kernel's
pages. It's why `MALLOC_ARENA_MAX` exists, why Redis ships jemalloc as its
default on Linux, and why nginx gives each request its own memory pool.

This chapter builds an allocator from the simplest possible one, adding a piece
each time the previous version breaks. Then it follows one `malloc` call
through the fast and slow paths, shows where RSS gets stuck, and measures what
all that bookkeeping costs.

<SectionHeading n="01" id="why-an-allocator">Why programs need an allocator</SectionHeading>

Chapter 04 ended with the kernel handing memory to a process in pages, 16 KB at
a time on this machine, through calls like `mmap`. Your program doesn't think
in pages, though.

<Sub n="1.1" title="Pages are the wrong size">

It asks for a 24-byte node, a 100-byte string, a 3 KB buffer, millions of times
a second. Something has to sit between those requests and the kernel's pages.

<Why>Why not ask the kernel for every object?</Why>

Because both costs are absurd. Each request would be a syscall, which chapter
07 measures at around 350 ns. And each 24-byte object would occupy a whole
16 KB page.

So every language runtime puts a middleman in between: the **allocator**, the
code behind `malloc`, `free`, `new` and `delete`. It asks the kernel for big
chunks and cuts them up itself.

</Sub>

<Sub n="1.2" title="What malloc promises">

`malloc(n)` promises a pointer to `n` usable bytes, suitably aligned, that no
other live allocation overlaps. `free(p)` promises that memory becomes
available again.

Read the list of things it doesn't promise, because every one of them is a
production incident someone has had.

| Not promised | What that means in practice |
|---|---|
| **A time bound** | A single `malloc` may take a lock, split a block, walk a free list, or ask the kernel for memory and take microseconds |
| **Return to the OS** | Freed memory usually stays in the allocator's pools. Your RSS doesn't go down, and that isn't a leak |
| **Locality** | Two sequential allocations may land anywhere. Chapter 02 explains why that matters more than the allocation cost |
| **A bound on fragmentation** | Peak RSS can exceed peak live bytes by a lot, permanently |

<Callout label="Design implication">
An allocator spends most of its effort answering "which free block should I
give you, and how do I find it again later". If your program knows the answer
(all objects the same size, or all freed at once), you can skip nearly the
whole mechanism. Section 5 measures that as a **42×** difference.
</Callout>

</Sub>

<SectionHeading n="02" id="building-one">Building an allocator, one problem at a time</SectionHeading>

Each version below fixes the one before it, and each fix brings a new problem.
Real allocators are the sum of all four.

<Sub n="2.1" title="The bump allocator">

The simplest allocator you could write takes one big chunk and keeps a pointer
to the first unused byte. To allocate `n` bytes it returns the pointer and
moves it forward by `n`.

That's a **bump allocator**, and it's probably impossible to beat: a couple of
instructions per allocation.

<Why>What's wrong with it?</Why>

It can't free anything. Once the pointer has passed an object, that memory is
gone until you throw the whole chunk away.

</Sub>

<Sub n="2.2" title="Free lists, and fragmentation">

So the next step is to remember freed pieces. When a program frees a block, put
it on a **free list**, and check that list before bumping the pointer.

Now memory gets reused, and a new problem shows up. Free a 24-byte object and
then ask for 100 bytes, and the 24-byte hole is no use.

Do that for a few hours with mixed sizes and the heap can end up full of free
pieces too small to reuse. That waste is **fragmentation**.

</Sub>

<Sub n="2.3" title="Size classes">

Real allocators handle it with **size classes**. Every request is rounded up to
one of a fixed set of sizes (say 16, 32, 48, 64 bytes, then coarser steps above
that), and each class keeps its own free list.

Any freed 48-byte block fits the next 48-byte request exactly. And "find a
block that fits" turns into an array index.

<Why>What does rounding cost?</Why>

Memory. Under classes of 16 and 32, a 17-byte request gets a 32-byte block, and
nearly half of it is wasted. That sounds bad, but it's usually cheaper than the
fragmentation it prevents.

It also buys speed: allocation becomes a pop from a list, and freeing becomes a
push. No search.

</Sub>

<Sub n="2.4" title="Threads, caches and arenas">

Threads add one more problem. A single free list shared by every thread needs a
lock, and on a busy server that lock can easily become the bottleneck. Chapter
13 measured what that costs under contention.

So every modern allocator (tcmalloc, jemalloc, mimalloc, macOS libmalloc, and
glibc's too) keeps a **per-thread cache** of small blocks. Some add several
independent heaps called **arenas**.

Allocation from a thread cache needs no atomics at all. Only when the cache
empties or overflows does the thread touch shared structures.

| Design | Fast path | What it costs |
|---|---|---|
| One global free list | A lock on every call | Contention on a busy server |
| Per-thread cache | A list pop, no atomics | Blocks freed on one thread aren't available to others until a flush |
| Several arenas | Threads spread over independent heaps | Freed memory can sit in one arena where the others can't reuse it |

That's also why a long-running service's memory can climb without leaking.
Freed memory sits in one thread's cache or one arena, where the others can't
reuse it and the kernel never gets it back. `MALLOC_ARENA_MAX` exists because
of this. So do the allocators people switch to: jemalloc, which Redis ships as
its default on Linux, and Google's tcmalloc.

</Sub>

<SectionHeading n="03" id="malloc-path">One malloc call, step by step</SectionHeading>

With size classes and thread caches in place, most calls finish in a few
nanoseconds. The rest fall through a chain of slower paths.

Notice that the fast path never enters the kernel and never takes a lock. The
cost measured in section 5.1 is almost entirely step 3: a size-class
computation, a list pop, and some bookkeeping.

</Sub>

<Sub n="3.2" title="Freeing on another thread">

`free` is the same path in reverse, and it's fast when the block goes back to
the thread that allocated it. Cross-thread freeing is the slow path in most
allocators. Step through a producer handing objects to a consumer:

/>

<Callout label="Design implication">
Allocate and free on the same thread where you can. A pipeline that allocates
on one stage and frees on another pays the slow path on both ends and strands
memory in between.
</Callout>

</Sub>

<Sub n="3.3" title="Why big allocations behave differently">

Past a threshold (128 KB in glibc by default), allocators stop using their heap
and call `mmap` directly, returning the memory to the OS on `free`.

<Predict
  q="On this machine, malloc + free of 256 bytes costs 9.5 ns. Roughly what does 64 KB cost?"
  options={[
    "About 10 ns: size barely matters",
    "About 15 ns",
    "About 73 ns",
    "About 5 µs",
  ]}
  answer={2}
>
73.4 ns, nearly eight times the 256-byte cost. A 4 KB allocation was still
15.1 ns. The jump is where the kernel starts getting involved: a syscall on
allocation, `munmap` on free, and fresh pages that fault on first touch.
</Predict>

You're paying for a syscall and, later, for a page fault on every page you
touch (chapter 04's 686 ns each). A loop allocating and freeing megabyte
buffers can spend most of its time in the kernel, and the fix is to reuse one
buffer.

</Sub>

<SectionHeading n="04" id="rss">Why RSS never comes down</SectionHeading>

The allocator gets memory from the kernel in pages and hands it out in objects.
Giving it back only works in pages, and that mismatch is behind the most common
allocator complaint.

<Sub n="4.1" title="One survivor pins a page">

Free a million small objects scattered across thousands of pages, and the
allocator can only return a page to the OS if **every** object on it is free.

<Steps
  title="A burst that leaves RSS permanently high"
  lanes={[
    { t: "Burst", s: "many small objects", icon: "◉" },
    { t: "Pages", s: "objects spread out", icon: "▦" },
    { t: "Frees", s: "most objects die", icon: "✕" },
    { t: "Survivors", s: "one per page", icon: "●" },
    { t: "Kernel", s: "gets nothing back", icon: "⌁" },
  ]}
  steps={[
    [0, "A burst of traffic allocates a million small objects."],
    [1, "They're spread across thousands of pages. RSS climbs to cover all of them."],
    [2, "The burst ends and most objects are freed. The allocator puts them back on its free lists."],
    [3, "A few long-lived objects survive, scattered one or two per page. **One survivor pins the whole page.**"],
    [4, "The allocator can only return a page when every object on it is free, so almost nothing goes back. RSS stays at the burst's peak."],
  ]}
/>

That's how a process reaches 4 GB RSS with 400 MB live and stays there. No
leak, no allocator bug, and no statistic in your application will show it. The
usual signature: memory climbs during a burst and never recovers.

<Callout label="Common mistake" kind="warn">
Calling a flat, high RSS a leak. A leak keeps growing; fragmentation climbs
during a burst and then holds. Compare RSS against the sum of live
allocations: a large, stable gap is fragmentation.
</Callout>

<Why>What can you do about it?</Why>

Mitigations, in rough order of practicality:

1. Use an arena for the burst and drop it whole.
2. Use `malloc_trim` if your allocator supports it.
3. Restart the process. Less embarrassing than it sounds, and what many systems
   actually do.

</Sub>

<Sub n="4.2" title="Allocator-induced false sharing">

Two threads allocating small objects concurrently can receive adjacent
addresses in one cache line. Neither thread shares data with the other, and
they hit chapter 13's 55× penalty anyway.

Per-thread caches mostly prevent this, because each thread carves from its own
span. Mostly. If you're padding for concurrency, pad the allocation, not just
the struct.

</Sub>

<Sub n="4.3" title="Realloc in a loop">

`realloc` may extend in place or may copy everything. Growing a buffer by a
fixed increment in a loop is O(n²) in bytes copied and looks perfectly
reasonable in the source.

Growth by a constant *factor*, the doubling every `std::vector` does, is what
makes it amortised O(n).

</Sub>

<SectionHeading n="05" id="cost">Nine nanoseconds, or two tenths</SectionHeading>

<Callout label="The machine" kind="note">
Apple M4, macOS 26.5.1, clang 21 `-O2`, system libmalloc. Two million
allocate-and-immediately-free pairs per size, warmed first. Immediate freeing
keeps everything in the thread cache, so these are best-case numbers. A real
workload holding thousands of live objects will do worse.
</Callout>

<Sub n="5.1" title="malloc by size">

Flat from 16 to 256 bytes, then climbing. Under a few hundred bytes you're
paying for the *mechanism*, not for the memory. So avoiding the mechanism pays
very well.

</Sub>

<Sub n="5.2" title="What you save by knowing the answer in advance">

A bump allocator does one thing: return the current pointer and advance it.
There's no free list, no size class, no thread cache, and no individual `free`.
You drop the whole arena at once.

<Cost items={[
  { what: "malloc + free, 16 bytes", value: "8.5 ns", source: "system libmalloc, 2M iterations" },
  { what: "Bump-pointer arena, 16 bytes", value: "0.2 ns", source: "preallocated arena, same loop" },
  { what: "Difference", value: "42×", source: "derived from the rows above" },
]} />

<Why>Where does a 42× gap come from?</Why>

It's the price of generality. `malloc` doesn't know your objects are all the
same size, or that you'll free them together, or that no other thread will
touch them. When you do know, an arena turns allocation into a pointer
increment.

<Estimate
  rows={[
    { label: "Allocations per request", math: "parse tree nodes for one document", value: "50,000" },
    { label: "With malloc", math: "50,000 × 8.5 ns", value: "425 µs" },
    { label: "With an arena", math: "50,000 × 0.2 ns", value: "10 µs" },
    { label: "Plus one arena reset", math: "a pointer store", value: "~0 ns" },
  ]}
  result={{ label: "saved per request, before any other optimisation", value: "≈ 415 µs" }}
/>

Request-scoped arenas are common in parsers, compilers and web servers for this
reason. The allocation pattern (many small objects, all dead at the same
moment) is exactly the case general allocators handle worst. A web server
freeing every allocation at the end of a request doesn't need a free list at
all, which is roughly why nginx gives each request its own pool.

</Sub>

<SectionHeading n="06" id="choosing">Choosing an allocator</SectionHeading>

<Sub n="6.1" title="Seeing what the allocator is doing">

```shell
# Which allocator, and is it the bottleneck?
perf record -g ./app && perf report | grep -iE 'malloc|free|arena'

# jemalloc's own statistics, if you link it
MALLOC_CONF=stats_print:true ./app

# glibc: arena count, in-use bytes, and what it will not return
# (malloc_stats writes to stderr)

# macOS
MallocStackLogging=1 ./app && leaks --outputGraph app
heap $PID | head -40

# Fragmentation, roughly: RSS against the sum of live allocations
```

</Sub>

<Sub n="6.2" title="The three options">

<Approach
  n="1"
  name="The system allocator"
  breaks="Multi-threaded allocation-heavy workloads, where glibc's arena handling is measurably behind."
  bestFor="Almost everything. Change only when a profile names malloc."
>
Modern system allocators are good. Starting anywhere else is premature, and
the measurement in 5.1 shows that under a few hundred bytes the cost is
single-digit nanoseconds.
</Approach>

<Approach
  n="2"
  name="jemalloc or mimalloc"
  breaks="One more dependency, and different fragmentation behaviour that you will have to learn."
  bestFor="Long-running, heavily threaded services. A drop-in LD_PRELOAD makes it an afternoon experiment."
>
Better arena management, better fragmentation behaviour over long uptimes, and
far better introspection. Often a double-digit percentage win on server
workloads for no code change at all.
</Approach>

<Approach
  n="3"
  name="An arena, scoped to a request"
  breaks="You must be certain nothing outlives the arena. A single escaping pointer is a use-after-free."
  bestFor="Parsers, compilers, request handlers: anywhere a batch of objects all die together."
>
The 42× in 5.2. Allocation becomes a pointer bump and deallocation becomes
resetting one offset.
</Approach>

<Why>Does swapping the allocator ever fix the real problem?</Why>

Sometimes it's the whole fix. Mozilla adopted jemalloc for Firefox largely to
fight fragmentation in a long-running browser process, where RSS climbing over
hours was the user-visible complaint, not allocation speed.

And sometimes the answer is to stop using a general allocator. Many compilers
allocate AST and IR nodes in per-phase arenas and free each phase wholesale. No
individual node is ever freed, and no free list is ever walked. If your objects
have a common death date, a general allocator is solving a problem you don't
have.

</Sub>

<Sub n="6.3" title="What you give up">

| You get | You pay | When the bill arrives |
|---|---|---|
| Allocate anything, any size, any time | ~9 ns of bookkeeping per call | In allocation-heavy inner loops |
| Per-thread caches, no lock | Memory stranded in idle threads' caches | As RSS above what you expect |
| Freed memory reused quickly | It isn't returned to the OS | As RSS that never comes down |
| Size classes, O(1) allocation | A few percent internal fragmentation | Quietly, everywhere |
| An arena at 42× | Nothing may outlive the arena | As a use-after-free, later |

</Sub>

<Sub n="6.4" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| RSS climbs in a burst and never recovers | Fragmentation: survivors pin pages | Arena for the burst, `malloc_trim`, or a restart |
| RSS higher than expected on a many-threaded service | Memory stranded in thread caches or arenas | `MALLOC_ARENA_MAX`, or try jemalloc |
| Profile shows time in `malloc` and `free` in a hot loop | General allocation for objects with a shared lifetime | A request-scoped arena |
| Loop over big buffers spends its time in the kernel | Allocations past the `mmap` threshold | Reuse one buffer |
| Two threads slower than one with no shared data | Allocator-induced false sharing | Pad the allocation to a cache line |
| Buffer growth gets slower as it grows | `realloc` by a fixed increment | Grow by a constant factor |

</Sub>

<SectionHeading n="07" id="summary">Summary</SectionHeading>

1. **The allocator is a middleman.** It gets big chunks from the kernel and
   cuts them into objects, because a syscall per object would be absurd.
2. **`malloc` promises very little.** No time bound, no return to the OS, no
   locality, no bound on fragmentation.
3. **A bump allocator is the fastest possible allocator** and can't free
   anything; every later design pays to fix that.
4. **Size classes trade memory for speed.** Rounding wastes a few percent and
   turns allocation into a list pop.
5. **Per-thread caches remove the lock from the fast path**, at the price of
   memory stranded in other threads' caches.
6. **Allocate and free on the same thread.** Cross-thread freeing is the slow
   path in most allocators.
7. **Big allocations go to `mmap`.** Past 128 KB in glibc you pay a syscall and
   page faults; 64 KB cost 73.4 ns against 9.5 ns at 256 bytes here.
8. **One live object pins a page.** That's how RSS stays high with no leak.
9. **An arena was 42× faster than `malloc`** for 16-byte objects that die
   together: 0.2 ns against 8.5 ns.
10. **Change the allocator only when a profile names it.** Then jemalloc or
    mimalloc is an afternoon `LD_PRELOAD` experiment.

<SectionHeading n="08" id="build">Build this</SectionHeading>

**Write an arena, then find where it stops winning.**

- Fifty lines: a `char*` cursor over a large block, with alignment rounding and
  a `reset()`. (Alignment is the part people get wrong. Round the cursor up
  before you hand it out, not the size afterwards.)
- Benchmark it against `malloc` for 16, 64, 256 and 4,096 byte objects. The
  ratio should shrink as objects get bigger: the arena does roughly the same
  work at every size, so there's less for it to beat.
- Then make it realistic: keep 100,000 objects **live** instead of freeing each
  immediately, and re-measure `malloc`. Its thread cache stops being a free
  win and the gap widens.
- Finally, measure peak RSS for both. The arena probably uses more memory (it
  never reuses a freed slot, so its high-water mark is the sum of everything you
  ever allocated), and seeing that trade in your own numbers is the point.

<SectionHeading n="09" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Your service freed a lot of memory and RSS didn't drop. Is that a leak?">
Probably not. Allocators keep freed memory in their own pools for reuse instead
of returning it, and a page can only go back to the OS when every object on it
is free. One live object pins a whole page.

So a burst that scatters allocations across many pages can leave RSS
permanently high with a small live set. Compare RSS against the sum of live
allocations. A large, stable gap is fragmentation, not a leak.
</QA>

<QA level="intermediate" q="Why do allocators use per-thread caches?">
To avoid a lock on every allocation. A single global free list means every
allocation contends, and chapter 13 measured what that costs. With a per-thread
cache, the fast path is a list pop with no atomics at all, and shared
structures are touched only on refill or overflow.

The cost is that memory freed on one thread sits in that thread's cache and
isn't available elsewhere until a flush, so allocate and free on the same
thread where you can.
</QA>

<QA level="intermediate" q="When is an arena the right choice, and what's the risk?">
When a batch of objects share a lifetime: parse trees, per-request state, a
compiler phase. Allocation becomes a pointer bump (I measured 0.2 ns against
8.5 ns for malloc, about 42×) and deallocation is resetting one offset.

The risk is a pointer escaping the arena's lifetime. There's no per-object
free, so nothing catches it, and you get a use-after-free that reproduces
rarely.
</QA>

<QA level="deep" q="Why does allocation cost jump at large sizes?">
Past a threshold (128 KB in glibc by default) allocators bypass their heap
and call `mmap` directly, so you pay a syscall on allocation and `munmap` on
free. Worse, the returned pages are untouched, so you also pay a minor page
fault on first write to each one: about 570 ns per page on the hardware in
chapter 04.

I measured 9.5 ns for a 256-byte allocation and 73.4 ns at 64 KB. A loop
allocating and freeing large buffers can spend most of its time in the kernel;
reuse one buffer instead.
</QA>

<QA level="deep" q="Two threads allocate small objects and performance is worse than one. Neither shares data.">
Likely false sharing introduced by the allocator. If both threads receive
addresses in the same cache line, their independent writes invalidate each
other's copy: chapter 13's 55× with no shared data and no lock.

Per-thread caches usually prevent it by carving each thread's objects from its
own span, but it still happens near span boundaries and with allocators that
lack them. If a struct is written by exactly one thread and lives next to
another's, pad the allocation to a cache line, not just the struct.
</QA>

<Quiz>
  <Q q="Roughly what does a small malloc+free pair cost?">
    Single-digit nanoseconds on a warm thread cache. I measured 8.5 ns at 16
    bytes on an M4. Under a few hundred bytes the size barely matters.
  </Q>
  <Q q="Why can't the allocator return a mostly-free page to the OS?">
    Because one live object anywhere on it pins the whole page. Pages are the
    unit of return, objects are not.
  </Q>
  <Q q="Growing a buffer by a fixed 1 KB each time. What's the complexity?">
    O(n²) in bytes copied. Grow by a constant factor instead. That's what makes vector's push_back
    amortised O(1).
  </Q>
  <Q q="When does a bump allocator beat malloc by 40x?">
    When every object dies at the same time, so you never free individually.
    Allocation collapses to a pointer increment.
  </Q>
</Quiz>
