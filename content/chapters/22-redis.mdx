Most backend teams meet Redis as a cache in front of Postgres. Then it picks up
more jobs. User sessions live there, `INCR` plus `EXPIRE` makes a rate limiter,
Sidekiq, BullMQ and Celery keep job queues in its lists, and sorted sets give
you a leaderboard in one command.

About a year later the questions change. Why did memory come out so far above
the estimate? Why did one command stall every client? Where did that write go
after the failover?

This chapter answers them from the source. It starts from the design brief
Redis was built to meet, then follows one command through the event loop, looks
at how values are laid out in memory, and ends with durability, eviction and
what to check when it's slow. Every shell block was run on Redis 8.10.2 and
pasted as it came out.

<SectionHeading n="01" id="design">Designing Redis from the brief</SectionHeading>

The brief is simple. Build a shared store that dozens of application servers
can reach over the network, for things that have to be fast: a cache, sessions,
a counter per client. A database query takes milliseconds. This should
take well under one.

<Sub n="1.1" title="Data in RAM, in one hash table">

Speed rules out the disk on the normal path, so the data lives in RAM. The
simplest structure that gives you a value by name is one big hash table from
key to value.

That part's easy. The interesting decision is concurrency, because thousands of
clients will be sending commands at once.

</Sub>

<Sub n="1.2" title="One thread runs every command">

A textbook design gives each client a thread and puts locks around the table.
Chapters 13 and 17 showed what that costs once the locks get busy.

Redis makes the opposite choice. One thread runs every command, one at a time,
each to completion.

<Why>What does one thread buy you?</Why>

Atomicity without a single lock. Remember the lost update from chapter 13, two
threads doing `count++` at once? It can't happen here. `INCR` on a key is one
command, nothing else runs during it, and so it's atomic.

<Why>How does one thread keep up with ten thousand connections?</Why>

With an **event loop**. It asks the kernel which sockets have data ready (the
`epoll` from chapter 07), handles those, and asks again. No thread ever waits
on a slow client, because the loop only touches sockets that are ready.

The price is exactly what you'd guess. One slow command, say `KEYS *` over ten
million keys, and every other client waits behind it.

</Sub>

<Sub n="1.3" title="Three more problems the design has to solve">

That single thread shapes the rest of the design:

| Problem | What Redis does | Section |
|---|---|---|
| A general hash table spends pointers and bookkeeping that dwarf a small value | Stores small hashes, lists and sets as compact flat arrays (**listpacks**) until they pass a size threshold | 4 |
| Rehashing ten million keys at once would freeze the only thread | Keeps the old and new tables side by side and moves one bucket at a time | 5 |
| RAM is gone when the process dies | Snapshots to disk from a `fork()`ed child, an append-only log, and replicas | 7 |

That last row carries the surprise. By default a replica copies the primary's
writes *after* the primary has told the client "OK", so a write you were told
succeeded can be lost in a failover.

</Sub>

<SectionHeading n="02" id="guarantees">What Redis guarantees, and what it doesn't</SectionHeading>

Redis promises you one thing, and people often hear a different one. The
promise is **command atomicity**: while a command runs, no other command runs.

There's no partial state for another client to observe, no isolation level to
pick, and no read that catches a hash halfway through an update.

<Sub n="2.1" title="The guarantees">

| Guarantee | What it means in practice |
|---|---|
| **Atomicity per command** | Every command, including multi-key ones like `MSET` and scripts, runs to completion before the next one starts |
| **Ordering per connection** | Commands from one client execute in the order they were sent. Across clients, there's no ordering beyond serialisation |
| **`MULTI`/`EXEC` without interleaving** | Nothing else runs between the queued commands |

<Callout label="Common mistake" kind="warn">
Saying "Redis is single-threaded." It hasn't been true since Redis 6, which
added **I/O threads** that read and write sockets in parallel. Command
*execution* is still serialised on one thread, and that's the part atomicity
rests on. Parsing and syscalls parallelise; the `dict` lookup doesn't.
</Callout>

</Sub>

<Sub n="2.2" title="What it explicitly does not promise">

This is the half that causes incidents.

| Not promised | What actually happens |
|---|---|
| **Rollback** | If a command inside `MULTI` fails at runtime, the other commands still apply. Redis reports the error and moves on |
| **Durability by default** | Replication is asynchronous. `WAIT numreplicas timeout` blocks until replicas have *acknowledged*, which isn't the same as having *fsynced* |
| **Expired keys leaving memory promptly** | An expired key is never returned to a client, but it can sit in the keyspace for a while (section 8.2) |
| **Isolation between a script and the world** | A Lua script blocks the server for its whole duration. That's atomicity working as designed, and it's also how people take an outage |

<Predict
  q="Inside MULTI you queue SET a 1, then INCR on a key holding the string hello, then SET b 2. You call EXEC. What's in a and b afterwards?"
  options={[
    "Neither is set: the whole transaction rolls back",
    "a is 1 and b is 2; the INCR reports an error",
    "a is 1, and b is unset because execution stopped at the error",
    "EXEC refuses to run anything",
  ]}
  answer={1}
>
`MULTI`/`EXEC` is a batch, not a transaction in the database sense. The `INCR`
fails at runtime on a string that isn't a number, Redis reports the error in
that slot of the reply, and the other two commands still apply.
</Predict>

<Why>Why is the acknowledgement allowed to come before replication?</Why>

Because that's what makes it fast. It isn't a bug and it isn't hidden: the
primary replies as soon as the write is in its own memory, and section 7.1
shows what that costs in a failover.

</Sub>

<SectionHeading n="03" id="event-loop">Following one GET through the event loop</SectionHeading>

For a `GET`, the whole trip is a loop, a parse, a table lookup and a buffered
write. Each step lives in a specific source file.

Step 5 is the only one that touches your data. Everything around it is moving
bytes in and out of buffers.

</Sub>

<Sub n="3.2" title="Why the reply isn't sent immediately">

Step 6 doesn't call `write()`. Replies accumulate in a per-client buffer and go
out in `beforeSleep()`, once, just before the loop blocks again.

<Predict
  q="A client pipelines 100 GET commands in one packet. Roughly how many write() syscalls does Redis make to answer them?"
  options={["100", "About 50", "1", "0: the kernel sends replies on its own"]}
  answer={2}
>
One. Each `GET` appends to the same output buffer, and `beforeSleep()` flushes
it with a single `write`. Pipelining saves the syscalls as well as the network
round trips, and at a few hundred nanoseconds each on a modern kernel, a hundred
avoided syscalls is real.
</Predict>

<Why>Why is a client that stops reading dangerous?</Why>

Because its output buffer grows inside your Redis process.
`client-output-buffer-limit` is the setting that decides whether Redis kills
the client or lets it eat your memory.

</Sub>

<Sub n="3.3" title="Commands that block everything">

Because execution is serialised, any slow command is an outage for every other
client. The usual suspects:

| Command | Why it blocks | What to use |
|---|---|---|
| `KEYS pattern` | Scans the entire keyspace | `SCAN` with a cursor |
| `SMEMBERS` on a huge set | Serialises every member | `SSCAN` |
| `DEL` on a 10M-element hash | Frees every entry inline | `UNLINK` (frees in a background thread) |
| `FLUSHALL` | Synchronous by default | `FLUSHALL ASYNC` |
| A long Lua script | Atomic by design, so nothing preempts it | Split it, or use functions with smaller units |

<Callout label="Design implication">
In Redis, the latency of every command is the latency of the slowest command
running near it. Treat any O(N) command on a big key as a production change,
and prefer the cursor and async variants by default.
</Callout>

</Sub>

<SectionHeading n="04" id="memory-layout">How Redis stores a value</SectionHeading>

A Redis database is two hash tables, and every value in them sits behind a
16-byte header. The header decides how the value is laid out.

<Sub n="4.1" title="Two hash tables per database">

```c
typedef struct redisDb {
    dict *dict;                 /* the keyspace: key -> robj */
    dict *expires;              /* key -> expiry ms, only for keys with a TTL */
    /* ... blocking_keys, watched_keys, id, avg_ttl ... */
} redisDb;
```

Keys live in `dict`. TTLs live in a *separate* `dict` holding only the keys that
have one.

<Why>Why does a TTL cost memory?</Why>

Because setting one adds an entry to the `expires` dict. Removing the TTL gives
that memory back. The split also matters for eviction: the `volatile-*`
policies only look at `expires` (section 8.1).

</Sub>

<Sub n="4.2" title="The object header">

Every value is a `robj`: a small header saying what the value is and how it's
currently laid out.

<SourceRead
  file="src/server.h"
  repo="redis/redis"
  tag="7.2.4"
  href="https://github.com/redis/redis/blob/7.2.4/src/server.h"
>
```c
typedef struct redisObject {
    unsigned type:4;        /* OBJ_STRING, OBJ_LIST, OBJ_HASH, OBJ_ZSET ... */
    unsigned encoding:4;    /* how it is laid out RIGHT NOW */
    unsigned lru:LRU_BITS;  /* clock for LRU, or frequency counter for LFU */
    int refcount;
    void *ptr;              /* the actual payload */
} robj;
```
</SourceRead>

Two four-bit fields, a 24-bit clock, a refcount and a pointer. On x86-64 that
packs into 16 bytes, and you pay those 16 bytes for every value you store.

**The type is what you asked for; the encoding is what Redis decided to give
you.** A hash with six small fields isn't a hash table at all. It's a flat,
cache-friendly array of length-prefixed entries called a
<em className="term">listpack</em>, scanned linearly.

</Sub>

<Sub n="4.3" title="Encodings, and the thresholds that trigger them">

Redis promotes a compact encoding to a real data structure only when it
outgrows a threshold:

<Compare
  cols={["Type", "Compact form", "Promotes to", "Threshold on Redis 8.10"]}
  rows={[
    ["String", "int / embstr", "raw", "45 bytes and up is raw"],
    ["Hash", "listpack", "hashtable", "512 entries, or a 64-byte value"],
    ["Sorted set", "listpack", "skiplist", "128 entries, or a 64-byte value"],
    ["Set", "intset / listpack", "hashtable", "512 ints, or 128 non-ints"],
    ["List", "listpack", "quicklist", "8 KB per node: a size, not a count"],
  ]}
/>

<Callout label="Common mistake" kind="warn">
Quoting 128 as the hash threshold. It's the ziplist-era default that every blog
post repeats, and this chapter's own first draft had it. On Redis 8.10.2 a hash
holds 512 entries before it promotes, four times as many, which is four times
the memory in the range where the compact encoding still applies. Ask your own
build with `CONFIG GET`.
</Callout>

Lists are odd in a different way. `list-max-listpack-size` defaults to
`-2`, and that's not an entry count. Negative values select a *byte* budget per
node, `-2` meaning 8 KB. A thousand short strings in a list stay a listpack;
eighty hundred-byte strings don't.

Two smaller notes. **Listpack replaced ziplist** in Redis 7.0, so a post that
says ziplist predates that, and the config names it quotes no longer exist. And
`CONFIG GET` reports your *running* value, which your distro may have
overridden in `redis.conf`. The values here were checked against a server
started with no config file at all.

<TryIt what="Watch a hash change its own data structure" lang="shell" toolchain="redis 8.10.2, macOS 15">
```shell
# Ask your build what the threshold is. Do not trust a blog post. Including this one.
redis-cli CONFIG GET hash-max-listpack-entries | tail -1   # 512

redis-cli DEL h > /dev/null
redis-cli HSET h a 1 b 2 c 3 > /dev/null
redis-cli OBJECT ENCODING h        # listpack

# Cross the number everyone quotes. Nothing happens.
for i in $(seq 1 130); do redis-cli HSET h "f$i" "$i" > /dev/null; done
redis-cli HLEN h                   # 133
redis-cli OBJECT ENCODING h        # listpack

# Cross the real one.
for i in $(seq 131 520); do redis-cli HSET h "f$i" "$i" > /dev/null; done
redis-cli HLEN h                   # 523
redis-cli OBJECT ENCODING h        # hashtable

# Now shrink it back down to three fields.
redis-cli HDEL h $(seq -f "f%g" 1 520 | tr '\n' ' ') > /dev/null
redis-cli HLEN h                   # 3
redis-cli OBJECT ENCODING h        # hashtable
```

<Output>
A 133-field hash is still a flat array being scanned linearly, and on this
build that's the right call. The listpack stays competitive far longer than the
folk number suggests.

**The conversion only goes one way.** Once a hash is promoted it stays promoted
for the life of the key, however small it shrinks. Three fields, full hash
table overhead.
</Output>
</TryIt>

<Why>Why doesn't a shrunk hash go back to a listpack?</Why>

Because the thresholds are checked on insert, never on delete. Build a hash by
inserting 600 fields and deleting 597 and you keep paying. If that matters,
rebuild the key: `HGETALL` into a new key and `RENAME` over the old one.

Why 512 for hashes when sorted sets and sets sit at 128? The linear scan is over
the same listpack layout in each case. A plausible reason is that hashes are
the type people push hardest for object storage, so the memory win was judged
worth more scanning. That's a guess; I couldn't find it written down.

</Sub>

<SectionHeading n="05" id="rehashing">Growing the table without stopping</SectionHeading>

A hash table has to grow as keys arrive. The normal way is to allocate a bigger
array and move every entry. With one thread and fifty million keys, that move
would freeze the server.

<Sub n="5.1" title="Two tables and a cursor">

A `dict` holds *two* hash tables, not one.

```c
typedef struct dict {
    dictType *type;
    dictEntry **ht_table[2];      /* two tables: old and new */
    unsigned long ht_used[2];
    long rehashidx;               /* -1 when not rehashing, else the bucket index */
    /* ... */
} dict;
```

<Why>Why not rehash everything at once?</Why>

Because a stop-the-world rehash of a 50-million-key table would block the event
loop for seconds. Since command execution is serialised, *blocking the loop is
blocking the database*. Spreading the work one bucket at a time keeps the worst
case bounded.

<Callout label="Design implication">
You pay for it on every read: while a resize is in flight, each lookup checks
two tables. Redis trades a small continuous penalty for never having a
multi-second stall. For a system selling predictable latency, that's the right
way round. Section 6.2 shows a resize caught in the middle.
</Callout>

</Sub>

<SectionHeading n="06" id="cost">What a key really costs</SectionHeading>

Memory is where Redis estimates go wrong most often. The fixed costs are small
but paid per key, and the table itself adds a share that moves as it grows.

<Sub n="6.1" title="The fixed costs">

<Cost items={[
  { what: "Hash table lookup, amortised", value: "O(1)", source: "dict.c: two tables while rehashing" },
  { what: "Strings ≤ 44 bytes (embstr)", value: "1 allocation", source: "OBJ_ENCODING_EMBSTR_SIZE_LIMIT, object.c" },
  { what: "Strings > 44 bytes (raw)", value: "2 allocations", source: "robj and sds allocated separately" },
  { what: "Hash slots in Cluster", value: "16384", source: "CLUSTER_SLOTS, cluster.h" },

<Why>Why 44 bytes, and not a round number?</Why>

An `robj` is 16 bytes and an `sdshdr8` header is 3 bytes plus a null
terminator, so 16 + 3 + 44 + 1 = 64. That's exactly one cache line and exactly
one jemalloc size class.

Cross it by a byte and you get two allocations, two pointer chases, and a size
class with slack in it.

</Sub>

<Sub n="6.2" title="Measuring your own per-key cost">

Key length, value length, encoding and allocator version all move the per-key
overhead, so a number from a blog post (this one included) won't fit your data.
Measure your own shape:

<TryIt what="Measure the real per-key cost of your own data shape" lang="shell" toolchain="redis 8.10.2, macOS 15">
```shell
# Empty baseline
redis-cli FLUSHALL > /dev/null
BEFORE=$(redis-cli INFO memory | awk -F: '/^used_memory:/{print $2+0}')

# 100k keys in the shape you actually store. Note the single quotes around the
# JSON — without them the inline protocol reads the first " as an opening quote
# and the whole pipe dies with "unbalanced quotes in request".
for i in $(seq 1 100000); do
  printf "SET session:%s '{\"uid\":%s,\"role\":\"member\"}'\n" "$i" "$i"
done | redis-cli --pipe

AFTER=$(redis-cli INFO memory | awk -F: '/^used_memory:/{print $2+0}')
echo "bytes per key: $(( (AFTER - BEFORE) / 100000 ))"
redis-cli MEMORY USAGE session:1
redis-cli STRLEN session:1
```

<Output>
```
errors: 0, replies: 100000
bytes per key: 93
64
25
```

A 9-byte key and a 25-byte value. That's 34 bytes of data in 93 bytes of RAM,
about 2.7×, and none of it is waste you can configure away. It's the `robj`
header, the `dictEntry`, the SDS length prefix, and jemalloc rounding each of
those up to a size class.
</Output>
</TryIt>

<Why>Why do MEMORY USAGE and the subtraction disagree?</Why>

`MEMORY USAGE` says 64: one key, its `dictEntry`, its allocator rounding. The
subtraction says 93, because it also carries this key's share of the bucket
array. **Use the subtraction.** The single-key number is honest about the key
and silent about the table.

That share moves with how many keys you have, and not monotonically. Same
measurement at three sizes:

| Keys | Bytes per key |
|---|---|
| 70,000 | 105 |
| 100,000 | 93 |
| 131,000 | 92 |

The obvious guess for 70k is an oversized, half-empty table. That's wrong, and
`DEBUG HTSTATS` shows why (you need `--enable-debug-command local` to run it;
it's off by default since Redis 7):

```
Hash table 0 stats (main hash table):
 table size: 65536
 number of elements: 58460
Hash table 1 stats (rehashing target):
 table size: 131072
 number of elements: 11540
```

At 70k the resize from section 5.2 is still *in flight*. Both arrays exist,
196,608 buckets for 70,000 keys, until the incremental rehash drains table 0. At
100k it has finished: one table, 131,072 buckets, all 100,000 elements. That
12-byte difference is a rehash caught in the middle.

<Callout label="Common mistake" kind="warn">
Benchmarking memory on a keyspace that's actively growing. A reading taken
during a resize measures a transient, and it can be 13% off while looking
perfectly stable.
</Callout>

</Sub>

<SectionHeading n="07" id="durability">Durability: replication and fork()</SectionHeading>

RAM is gone when the process dies. Redis has three answers: replicas that copy
the primary's writes, RDB snapshots written by a forked child, and an
append-only file. Each has a gap you should know about.

<Sub n="7.1" title="The acknowledged write that vanishes">

Replication is asynchronous. The primary replies `OK` to your client and
*then* streams the write to replicas.

<StepSequence
  title="An acknowledged write lost in a failover"
  actors={["Client", "Primary", "Replica"]}
  messages={[
    { from: 0, to: 1, label: "SET k v", note: "The client writes a key. The primary applies it **in its own memory**." },

    { from: 2, to: 2, label: "promoted", note: "Failover promotes the replica. It never received `SET k v`." },
    { from: 0, to: 2, label: "GET k", note: "The client reads the key it was told was written." },
    { from: 2, to: 0, label: "(nil)", note: "The promoted replica **happily serves a read that doesn't include the write**. No error anywhere." },
  ]}
/>

There is a mitigation, but it only goes part of the way:

```
min-replicas-to-write 1
min-replicas-max-lag 10
```

This makes the primary *refuse writes* when fewer than one replica has been seen
within ten seconds. It shrinks the window.

<Why>Why doesn't that close the window?</Why>

Because "a replica was alive recently" and "this specific write reached a
replica" are different claims. A write acknowledged one second before the
primary dies can still be lost. `WAIT` narrows it further, but it counts
replicas that acknowledged receipt, not ones that fsynced.

<Callout label="Design implication">
Treat an acknowledged Redis write as "probably durable". If losing it would be
an incident, the source of truth belongs in a database, and Redis holds a copy.
</Callout>

</Sub>

    { t: "Memory", s: "RSS of both", icon: "▲" },
  ]}
  steps={[
    [0, "`BGSAVE` runs on the main thread, which calls `fork()`."],
    [1, "`fork()` copies the **page tables**, and that time scales with the size of the address space. The event loop is stalled until it returns."],
    [2, "The child walks the dataset and writes it to disk. It sees memory frozen at the moment of the fork."],
    [3, "The parent keeps serving. The first write to any page makes the kernel **copy that page**, so the child's view stays intact."],
    [4, "Extra memory grows with **how many pages the parent writes** during the dump, not with the dataset size."],
    [2, "The child finishes and exits, and its copied pages are freed."],
  ]}
/>

Two failure modes come out of this:

| Failure | Cause | What to do |
|---|---|---|
| **Memory doubling under write load** | COW copies every page the parent writes during the dump. Read-mostly instances probably never notice; one rewriting most of its keyspace can approach 2× | Budget COW headroom (section 6.3); set `vm.overcommit_memory=1` so the kernel doesn't refuse a fork it would never need to back |
| **The fork stalls the loop** | Copying page tables for a large address space | Keep instances smaller, and schedule saves off-peak |

<Why>Where did "disable transparent huge pages" come from?</Why>

Before Linux 5.8, a COW fault on a huge page copied 2 MB instead of 4 KB, which
made the aftermath of a fork far worse. Since
[commit 3917c80280c9](https://github.com/torvalds/linux/commit/3917c80280c93a7123f1a3a6dcdb10a3ea19737d),
whose message names Redis, the kernel splits the page and copies 4 KB.

Compaction stalls are still a reason to be careful, and Redis's startup warning
now asks for `madvise` instead of `never`.

</Sub>

<SectionHeading n="08" id="eviction">Eviction and expiry</SectionHeading>

A cache has to get rid of data two ways: when it's out of memory, and when a
key's TTL passes. Neither works the way most people assume.

<Sub n="8.1" title="Choosing an eviction policy">

`maxmemory-policy` is the setting most often left at its default. The default is
`noeviction`, which means writes start failing when you hit the ceiling. For a
cache that's almost never what you want.

| Policy | How it picks a victim | Breaks when | Best for |
|---|---|---|---|
| **`allkeys-lru`** | Samples `maxmemory-samples` keys (5 by default) and evicts the least recently used | A batch job touching every key evicts your hot set; recency is a weak signal under a scan | A pure cache with a stable working set and no periodic sweeps |
| **`allkeys-lfu`** | Evicts by access *frequency*, from an 8-bit counter in the `robj`'s `lru` field | A key that was hot last week resists eviction today; decay is set by `lfu-decay-time`, which people rarely tune | Caches with a long-lived hot set and periodic scans, the usual production shape |
| **`volatile-ttl`** | Among keys with a TTL, evicts the one expiring soonest | Keys without a TTL are never candidates | A keyspace where every key has a deliberate TTL |

<Why>Why sample instead of tracking exact LRU?</Why>

Real LRU would need a linked list threaded through every object. Sampling five
keys gets close enough, most of the time, for a fraction of the memory.

The LFU counter uses the same trick. Increments get logarithmically less likely
as the counter rises, so a counter of 255 represents roughly a million accesses
in eight bits. That frequency is what makes LFU scan-resistant.

<Callout label="Common mistake" kind="warn">
`volatile-lru` on a keyspace where only some keys have TTLs. It hits
`maxmemory`, finds no eligible victim, and returns `OOM command not allowed when
used memory > 'maxmemory'`, while `INFO` reports gigabytes of evictable-looking
data. None of it is *eligible*: every `volatile-*` policy only considers the
`expires` dict. Check `db0:keys=N,expires=M` in `INFO keyspace`; if `M` is much
smaller than `N`, this is your bug.
</Callout>

</Sub>

<Sub n="8.2" title="How expiry actually runs">

Two mechanisms, and neither is a guarantee:

| Mechanism | When it runs | What it does |
|---|---|---|
| **Lazy** | On every lookup | Checks the `expires` dict first. An expired key is deleted and the lookup reports a miss, so a client never sees stale data |
| **Active** | 20 times a second, in `activeExpireCycle()` | Samples 20 keys from `expires`, deletes the expired ones, and repeats while more than 25% of the sample was expired |

So memory for expired keys is reclaimed *eventually*. A key that nothing reads,
in a database where few keys are expiring, can linger well past its TTL. If
you're sizing memory against a TTL, size against the lingering.

Its tail is hard to model. The 25% rule makes it
self-limiting in aggregate, but I've watched a staging instance hold a few
thousand expired keys for several minutes with no read pressure, and couldn't
reproduce it on demand.

</Sub>

<SectionHeading n="09" id="operating">Running Redis in production</SectionHeading>

<Sub n="9.1" title="What to look at when it's slow">

```shell
redis-cli --latency-history          # round trip over time, cheap, run it first
redis-cli SLOWLOG GET 10             # commands over slowlog-log-slower-than
redis-cli INFO commandstats          # calls, usec, usec_per_call, per command
redis-cli --bigkeys                  # SCAN-based, safe on production
redis-cli INFO keyspace              # keys vs expires — see section 8.1
```

`INFO commandstats` is the one people skip, and it's usually the fastest route
to an answer. It gives total microseconds per command type, so an `HGETALL`
that's individually fast but called 400,000 times a second shows up as the
largest number on the page.

</Sub>

<Sub n="9.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| Every client stalls at once, briefly | One slow command: `KEYS`, a big `DEL`, a long script | `SLOWLOG GET`, then `SCAN`, `UNLINK`, `FLUSHALL ASYNC` |
| Memory far above the estimate | Per-key overhead, promoted encodings that never shrink, a resize in flight | Measure by subtraction; rebuild shrunk keys |
| OOM errors with plenty of data | `volatile-*` policy, few keys with TTLs | Compare `keys` and `expires`; use `allkeys-lfu` |
| Hit rate collapses after a nightly job | `allkeys-lru` evicting the hot set during a scan | Switch to `allkeys-lfu` |
| Memory spikes during saves | COW during `BGSAVE` under write load | Budget headroom; `vm.overcommit_memory=1` |
| A write is missing after failover | Asynchronous replication | `min-replicas-to-write`, `WAIT`, or keep the source of truth elsewhere |
| Memory creeping on the server | A client not reading its replies | `client-output-buffer-limit` |

</Sub>

<SectionHeading n="10" id="summary">Summary</SectionHeading>

1. **One thread executes every command.** That's where atomicity without locks
   comes from, and why one slow command stalls every client.
2. **"Single-threaded" is out of date.** Since Redis 6, I/O threads parallelise
   socket reads and writes; execution stays serialised.
3. **`MULTI`/`EXEC` doesn't roll back.** A failing command reports an error and
   the rest still apply.
4. **Replies are buffered and flushed once per loop.** A hundred pipelined
   commands cost one `write`.
5. **The type is what you asked for; the encoding is what you got.** Small
   hashes are listpacks until 512 entries on Redis 8.10, not the 128 blogs quote.
6. **Promotion is one-way.** A hash that grew and shrank keeps hash-table
   overhead until you rebuild it.
7. **Resizing happens a bucket at a time.** Lookups check two tables during a
   resize, and memory readings taken then are transient.
8. **Measure per-key cost by subtraction.** 34 bytes of data cost 93 bytes of RAM
   in the test here.
9. **An acknowledged write can vanish in a failover.** Replication is
   asynchronous, and `min-replicas-to-write` only narrows the window.
10. **`BGSAVE` memory grows with the write rate**, and `volatile-*` policies
    only see keys with a TTL.

<SectionHeading n="11" id="build">Build this</SectionHeading>

**Implement the listpack-to-hashtable promotion yourself.** Not the whole of
Redis: one type, one threshold, in about 200 lines of C++.

- A `Hash` class with two representations behind one interface: a
  `std::vector<std::pair<std::string,std::string>>` scanned linearly, and a
  `std::unordered_map`.
- Promote when entry count crosses 512 *or* any value exceeds 64 bytes, or
  whatever your own `CONFIG GET hash-max-listpack-entries` says, so the numbers
  are comparable to your build.
- Benchmark `HGET` at 4, 16, 64, 256, 511 and 513 entries. Plot it.

What you're looking for is the crossover: the point where a linear scan of a
contiguous array stops beating a hash lookup with a pointer chase. Redis picked
512 for hashes and 128 for sorted sets, over what looks like the same listpack
layout, and the reasoning isn't written down anywhere I could find. If your
crossover lands nowhere near either number (and on a machine with a 128-byte
cache line it might not), working out *why* will teach you more than this
chapter did.

<SectionHeading n="12" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Is Redis single-threaded?">
Command execution is, and always has been. Since Redis 6 there are also I/O
threads that read from and write to sockets in parallel, controlled by
`io-threads`. The accurate answer is that parsing and syscalls can parallelise
while command execution stays serialised on one thread, and it's the
serialised execution that gives you atomicity for free.
</QA>

<QA level="intermediate" q="You set a TTL on a key. When is the memory actually freed?">
On whichever comes first: the next access to that key, or the active expiry
cycle sampling it. Redis samples 20 keys from the `expires` dict twenty times a
second, deletes the expired ones, and repeats while more than a quarter of the
sample was expired. Neither path is a guarantee, so a key past its TTL can hold
memory for a while. It's never *returned* to a client, though: the lazy check
happens on every read.
</QA>

<QA level="intermediate" q="Why is pipelining faster than sending commands one at a time?">
Two separate savings, and candidates usually name only the first. You avoid the
network round trip per command. You also avoid a `write` syscall per reply,
because `addReply` only appends to a per-client buffer and `beforeSleep`
flushes the whole buffer once per event loop iteration. A hundred pipelined
commands cost one `write`, not a hundred.
</QA>

<QA level="deep" q="Why does BGSAVE sometimes double the memory footprint?">
`BGSAVE` forks. The child shares the parent's pages copy-on-write, so the
initial cost is near zero. Every page the *parent* then writes to has to be
copied, so the extra memory is proportional to the write rate during the dump,
not to the dataset size. A read-mostly instance will probably never notice; one
rewriting most of its keyspace during the dump can approach 2×. This is also
why `vm.overcommit_memory=1` is in every production guide: with the default,
the kernel can refuse a fork it would in practice never need to back. It's also
where "turn THP off" came from: before Linux 5.8, a COW fault on a huge page
copied 2MB instead of 4KB. Newer kernels split the page and copy 4KB, so on a
modern box the remaining THP risk is compaction stalls, not COW.
</QA>

<QA level="deep" q="Your instance is at maxmemory with allkeys-lru and the hit rate collapsed after a nightly batch job. What happened and what do you change?">
That batch job scanned keys nobody will ever read again. Under LRU every one
of those became the most-recently-used thing in the cache, evicting the actual
hot set. Recency is a weak signal when something sweeps the keyspace.

Switch to `allkeys-lfu`. Frequency survives a scan: a key touched once by the
batch job has a counter of roughly 1, while a key served a thousand times a
minute sits far higher, so the scan evicts itself. Check `lfu-decay-time` too:
one minute is probably right for your workload, and probably wrong if your hot
set shifts on a daily cycle.
</QA>

<QA level="deep" q="Explain incremental rehashing and what it costs.">
A `dict` holds two hash tables. On growth, Redis allocates the second at the new
size and sets `rehashidx` to 0 without moving anything. Every subsequent lookup,
insert or delete migrates one bucket and advances `rehashidx`; a background cron
moves a few more. It exists because a stop-the-world rehash of a large table
would block the event loop for seconds, and since execution is serialised,
blocking the loop is blocking the database.

The cost is that while `rehashidx >= 0` every lookup checks both tables, so
reads are measurably slower for the duration. You're trading a small continuous
penalty for the elimination of a multi-second stall. For a system selling
predictable latency, that's the right way round.
</QA>

<SectionHeading n="13" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="A hash grows to 200 fields; you delete 197. A second hash grows to 600 and you delete 597. Both have three fields. Same encoding?">
    No. First one's `listpack`, second one's `hashtable`. 200 never crossed
    `hash-max-listpack-entries`, which is 512 on Redis 8, so nothing was ever
    promoted. 600 did, and promotion is one-way: the thresholds are checked on
    insert, never on delete. Two keys, identical contents, and the second costs
    you full hash table overhead for three fields until you rebuild it. If you
    answered `hashtable` for both, you're carrying the 128 from an old blog post,
    which is exactly the mistake this chapter shipped with.
  </Q>
  <Q q="Why is the embstr threshold 44 bytes and not a round number?">
    16 bytes of `robj` + 3 bytes of `sdshdr8` header + 44 bytes of payload + 1
    null terminator = 64 bytes. One cache line, one jemalloc size class.
  </Q>
  <Q q="You run `WAIT 2 1000` and it returns 2. Is your write durable?">
    No. `WAIT` counts replicas that *acknowledged receipt*, not replicas that
    fsynced to disk. Two replicas holding the write in memory can both lose it
    in a correlated power failure.
  </Q>
  <Q q="INFO keyspace shows db0:keys=8000000,expires=1200. Your policy is volatile-lru. What breaks?">
    Only 1,200 keys are eviction candidates. Once those are gone Redis hits
    `maxmemory` with nothing eligible and starts refusing writes with an OOM
    error, while appearing to hold 8M evictable keys.
  </Q>
</Quiz>
