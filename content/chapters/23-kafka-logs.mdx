A ship's captain keeps a logbook. Entries are only ever added at the end, each on its own numbered line, and nobody rips pages out. The first mate reads up to line 40 and puts a bookmark there. The navigator reads the same book from line 12. Neither reading takes anything away, so a new officer can start at line 1 and replay the whole voyage.

A mailbox works differently. Once someone takes a letter out, it's gone, and no one else can read it. Kafka is the logbook, and treating it as a mailbox is behind most of the surprises people meet with it. You can build the core idea, minus everything that makes it fast and safe, in a few lines.

<SectionHeading n="01" id="toy-log">Build a toy log and read it from two places</SectionHeading>

Save this as `toylog.py`. It's a toy: one file, one process, no replication. It shows only the shape of the idea.

<Sub n="1.1" title="Append, read by number, keep your own bookmark">

<TryIt what="Append four records, let two readers consume at their own pace, append one more, then replay from the start" lang="python" toolchain="Python 3.14, macOS 26.5.1 (a toy, not Kafka)">
```python
import os

path = "orders.log"
if os.path.exists(path): os.remove(path)

def append(record):                              # the only way to write: add to the end
    with open(path, "a") as f: f.write(record + "\n")

def read_from(offset, max_records=10):           # read by record number; nothing is removed
    with open(path) as f: lines = f.read().splitlines()
    return list(enumerate(lines))[offset:offset + max_records]

for order in ("order-1", "order-2", "order-3", "order-4"):
    append(order)

billing_offset, shipping_offset = 0, 0           # each reader remembers its own position
batch = read_from(billing_offset, 2);  billing_offset += len(batch)
print("billing  reads :", batch)
batch = read_from(shipping_offset, 4); shipping_offset += len(batch)
print("shipping reads :", batch)
append("order-5")
print("billing  reads :", read_from(billing_offset), " <- carries on from offset", billing_offset)
print("replay from 0  :", [r for _, r in read_from(0)], " <- nothing was consumed")
```
<Output>
```
billing  reads : [(0, 'order-1'), (1, 'order-2')]
shipping reads : [(0, 'order-1'), (1, 'order-2'), (2, 'order-3'), (3, 'order-4')]
billing  reads : [(2, 'order-3'), (3, 'order-4'), (4, 'order-5')]  <- carries on from offset 2
replay from 0  : ['order-1', 'order-2', 'order-3', 'order-4', 'order-5']  <- nothing was consumed
```
</Output>
</TryIt>

Billing and shipping read the same records at different speeds and never interfered with each other. Billing stopped after two records and picked up later exactly where it left off. The last line replays all five, because reading removed nothing.

</Sub>

<Sub n="1.2" title="What Kafka adds to this">

The toy's whole design is an append, a record number called an **offset**, and a bookmark each reader keeps. That's the heart of Kafka too. The rest of the machinery exists to make the idea survive real conditions: splitting a log into partitions so many machines share the load, copying each partition to several brokers so a crash loses nothing, and batching writes so the disk keeps up.

The chapter builds Kafka up from that one idea. It follows a record onto disk, through replication and out to a consumer, and explains why "acknowledged" doesn't always mean what people think.

</Sub>

<SectionHeading n="02" id="log">The log as a primitive</SectionHeading>

A **log** is the simplest storage structure there is. Jay Kreps, who co-created
Kafka at LinkedIn, put it as "an append-only, totally-ordered sequence of
records ordered by time" in his essay
[The Log](https://engineering.linkedin.com/distributed-systems/log-what-every-software-engineer-should-know-about-real-time-datas-unifying).

<Sub n="2.1" title="Offsets, and readers that keep their own place">

Each record gets the next integer, its **offset**. You can only add at the end.
You read from any offset forward.

That sounds too simple to be interesting. It has one property a queue doesn't:
reading doesn't change the log.

| | A queue (RabbitMQ, SQS) | A log (Kafka) |
|---|---|---|
| **What a read does** | Removes or hides the message | Nothing; the reader advances its own offset |
| **Several readers** | Compete for messages | Each reads everything, at its own pace |
| **Replay** | Gone once acknowledged | Rewind the offset and read again |
| **Ordering** | Usually per queue, weakened by redelivery | Strict, per partition |
| **Deletion** | Per message, on acknowledgement | Whole files, by age or size (section 9) |

<Why>Why is "readers keep their own place" such a big deal?</Why>

Because the broker stops tracking per-message state. It doesn't need to know
who has read record 41,902. A consumer is a number, and adding a tenth consumer
costs the broker almost nothing.

That's also why a log is a good building block for other systems. Databases
already use one: Postgres's write-ahead log (chapter 21) is a log that replicas
replay. Kafka takes the same structure and makes it a service anyone can
append to and replay.

</Sub>

<Sub n="2.2" title="Partitions: many logs, ordered one at a time">

One log on one machine has a ceiling: one disk and one network card. So a Kafka
**topic** is split into **partitions**, and each partition is an independent
log with its own offsets.

Producers pick the partition. With a key, the default is a murmur2 hash of
the key modulo the partition count, so every record for `order-17` lands in the
same partition, in order. Without a key, records are spread across partitions.

<Why>Why only per-partition ordering?</Why>

Because a total order across partitions would need every broker to agree on
every append: a consensus round per record. Kafka gives you ordering
where it's cheap, inside one partition, and lets you choose what shares a
partition by choosing the key.

<Callout label="Design implication">
Pick the key as "the thing whose events must stay in order": an account, an
order, a device. And pick the partition count early. Adding partitions changes
`hash(key) % n`, so records for the same key start landing somewhere new and
the old ordering guarantee no longer holds across the change.
</Callout>

</Sub>

```text
-rw-r--r-- 1 root root       43 Sep 27 04:05 partition.metadata
```

<Sub n="3.1" title="Segments and their two indexes">

Records live in the `.log` file. When it passes `log.segment.bytes` (1 GiB by
default) Kafka closes it and starts a new **segment**, named by the first offset
it holds. A partition is a list of segments; only the newest, the **active
segment**, is written to.

Next to each segment sit two indexes:

| File | Entry | What it maps |
|---|---|---|
| `.index` | 8 bytes: 4-byte offset relative to the segment's base, 4-byte file position | Offset → byte position in the `.log` |
| `.timeindex` | 12 bytes: 8-byte timestamp, 4-byte relative offset | Timestamp → offset, for "seek to 09:00" |

Both are preallocated to `log.index.size.max.bytes` (10 MiB) and memory-mapped,
so a 123-byte log sits next to two 10 MB files. `du` reported 0 KB for
both, because the files are sparse. At 10,485,756 bytes, the time index is the
largest multiple of 12 that fits.

<Why>Why is the index sparse?</Why>

Because it doesn't need an entry per record. Kafka adds one roughly every
`log.index.interval.bytes` (4,096) of log. A lookup binary-searches the index for
the nearest entry at or below the target offset and scans forward from there, at
most a few kilobytes. So the index stays small enough to live in memory.

</Sub>

<Why>Why does the broker keep the producer's batches intact?</Why>

So it doesn't have to touch them. It validates the CRC and assigns
offsets, then writes the bytes as they arrived. On the way out it sends those
same bytes to consumers. Section 6 shows why that matters so much.

</Sub>

<SectionHeading n="04" id="write-path">The write path: batching and acks</SectionHeading>

A call to `producer.send()` doesn't send anything. It appends the record to an
in-memory batch for its partition and returns a future.

<Sub n="4.1" title="The accumulator, batch.size and linger.ms">

The producer's **record accumulator** keeps one open batch per partition. A
background sender thread ships a batch when it's full (`batch.size`, 16,384
bytes) or when it has waited `linger.ms`.

`linger.ms` defaulted to 0 until Kafka 4.0. It's now 5, and the
[upgrade notes](https://kafka.apache.org/documentation/#upgrade) give the
reason: "the efficiency gains from larger batches typically result in similar
or lower producer latency despite the increased linger."

<Why>Why would waiting make things faster?</Why>

Because the broker's cost is mostly per request and per batch, not per byte:
parsing, a CRC check, an append, a replication round. Put 150 records in a batch
and you pay those costs once instead of 150 times.

Here's how much it matters. One producer, 100-byte records, `acks=all`, a
three-partition topic with replication factor 3, as fast as it will go:

<Sub n="4.2" title="acks: when the producer hears back">

`acks` decides when the leader answers the producer:

| `acks` | Leader replies when | You can lose an acknowledged record when |
|---|---|---|
| `0` | Never. The producer doesn't wait | Anything goes wrong, including the request never arriving |
| `1` | The leader has appended to its own log | The leader dies before a follower copies the record |
| `all` (or `-1`) | Every replica in the ISR has it, and the ISR has at least `min.insync.replicas` members | Every in-sync replica is lost at once |

`all` has been the default since Kafka 3.0. Latency at a steady 3,000 records a
second on the same cluster, so queueing doesn't swamp the numbers:

<Compare
  cols={["acks", "p50", "p99", "What the wait covers"]}
  rows={[
    ["0", "1 ms", "20 ms", "Handing the batch to the socket"],
    ["1", "1 ms", "39 ms", "One round trip and a leader append"],
    ["all", "6 ms", "75 ms", "Plus followers fetching the batch and the leader seeing their progress"],
  ]}
/>

<Why>Why does acks=all cost a few milliseconds even on one machine?</Why>

Because followers **pull**. Nobody pushes the record to them. The leader
waits until each follower's next fetch asks for an offset past the record, which
proves the follower has it. Only then does it answer the producer. Section 5.1 follows that exchange in detail.

</Sub>

<SectionHeading n="05" id="replication">Replication: the ISR and the high watermark</SectionHeading>

Each partition has one **leader** and some **followers**; replication factor 3
means one of each plus one more. Producers and consumers talk to the leader.
Followers are just consumers that write what they read into their own copy of
the log.

<Sub n="5.1" title="LEO, HW and committed records">

Every replica tracks its **log end offset** (LEO): the offset the next record
will get. Leaders also track the **high watermark** (HW): the offset below
which every in-sync replica has the data. Records below the HW are
**committed**; only those are shown to consumers.

<Why>Why not let consumers read up to the leader's LEO?</Why>

Because records above the HW might not survive. If the leader died now, a
follower without record 100 could become leader, and 100 would never have
existed. A consumer that had already processed it would have acted on a phantom.
So consumers are held to records that will outlive the leader.

</Sub>

<Sub n="5.2" title="The in-sync replica set">

The **ISR** is the set of replicas the leader waits for. The
[design docs](https://kafka.apache.org/documentation/#replication) give two ways
to leave it:

- **The broker loses its session.** A broker that doesn't heartbeat the
  controller within `broker.session.timeout.ms` (9 s) is fenced and removed
  from every ISR it was in.
- **The follower falls behind.** A replica that hasn't caught up to the
  leader's end within `replica.lag.time.max.ms` (30 s) is dropped by the
  leader.

A replica rejoins when it catches up. In a test, a follower killed with `kill
-9` was out of the ISR roughly 9.5 seconds later, measured by polling
`kafka-topics.sh --describe` (which takes a second or two per call). That
matches the 9-second session timeout.

<Why>Why have an ISR instead of a fixed majority quorum?</Why>

A majority quorum, as in Raft, needs 2f+1 copies to survive f failures. The ISR
needs only f+1, because the leader waits for *all* in-sync replicas and a dead
one is removed from the set. In exchange, the set can shrink, and
you have to say how small you'll let it get. That's what
`min.insync.replicas` is for.

</Sub>

With replication factor 3 and `min.insync.replicas=2`, you survive one broker
loss with no pause and no loss of committed data.

<Callout label="Common mistake" kind="warn">
Setting replication factor 3 and leaving `min.insync.replicas` at its broker
default of **1**. Now the ISR can shrink to the leader alone, `acks=all` means
"the leader has it", and one more failure loses acknowledged data. Use RF 3
with `min.insync.replicas=2` for anything you can't lose.
</Callout>

<Sub n="5.4" title="Leader epochs: truncating a log safely">

When a leader dies, the controller picks a new one from the ISR, and every
replica has to agree on where the log now ends. A follower may hold records the
new leader never got. Those have to be cut off.

Kafka originally truncated followers to their own high watermark. That lost
data or left replicas diverged in some double-failure cases, described in
[KIP-101](https://cwiki.apache.org/confluence/display/KAFKA/KIP-101+-+Alter+Replication+Protocol+to+use+Leader+Epoch+rather+than+High+Watermark+for+Truncation),
because a follower's HW lags the leader's.

KIP-101's fix was the **leader epoch**, a counter that goes up with each new leader
and is stamped on every batch (the `PartitionLeaderEpoch` field above). Each
replica keeps a small file, `leader-epoch-checkpoint`, recording the first
offset of each epoch.

<Why>How does an epoch tell a follower where to cut?</Why>

A returning follower asks the new leader: "where did epoch 4 end for you?" The
leader answers with the first offset of epoch 5 in its own log, and the follower
truncates to that point. Both logs now match up to there, whatever either high
watermark said. Raft solves the same problem with its term numbers.

</Sub>

<Sub n="5.5" title="Unclean leader election">

If every ISR member is gone, you have a choice. Wait for one of them to come
back, or elect a replica that was out of sync and accept the loss of whatever
it didn't have.

`unclean.leader.election.enable` makes that choice, and it defaults to `false`:
the partition stays offline instead of silently losing committed data.

This is where Kafka's replication story started. Kyle Kingsbury's
[Jepsen test of Kafka](https://aphyr.com/posts/293-call-me-maybe-kafka)
(2013), run against a pre-release Kafka 0.8, shrank the ISR to the leader alone, then partitioned it away. Of 987
acknowledged writes, 520 were lost. One of his proposed fixes was a minimum ISR
size, and `min.insync.replicas` is what Kafka later added.

| Setting | Topic stays available when all ISR members die? | Acknowledged data can be lost? |
|---|---|---|
| `unclean.leader.election.enable=false` (default) | No: offline until an ISR member returns | No, while one ISR member's disk survives |
| `unclean.leader.election.enable=true` | Yes: any live replica can lead | Yes, everything it hadn't copied |

</Sub>

<SectionHeading n="06" id="page-cache">The page-cache trick</SectionHeading>

This is the part of the design that surprises people most. Kafka stores
everything on disk, often keeps weeks of data, and is still fast. It gets there
mostly by not doing things.

<Sub n="6.1" title="No cache of its own, and no fsync per write">

Kafka's design docs reject the usual plan, a big in-process cache flushed to
disk "in a panic" when space runs out: "we invert that. All data is immediately
written to a persistent log on the filesystem without necessarily flushing to
disk. In effect this just means that it is transferred into the kernel's
pagecache."

So the broker's `write()` lands in the page cache (chapter 08) and returns, and the
kernel writes it back to disk later. A JVM cache, the same docs note, would
store objects at "often doubling the size of the data" and start cold after
every restart. Page cache survives a broker restart.

<Why>Then what makes an acknowledged record durable?</Why>

Replication. `log.flush.interval.messages` defaults to `Long.MAX_VALUE`, so
Kafka never fsyncs a segment because of a write. A committed record is in the
page cache of every ISR member. You lose it only if all of them lose power
before writeback. That's why ISR members should sit in different racks or
availability zones. Kafka's docs argue that fsync on every write "can reduce
performance by two to three orders of magnitude".

<TryIt what="Which files does a broker fsync while taking writes?" lang="shell" toolchain="Kafka 4.3.1, single broker, strace 6.8, linuxkit 6.10.14 aarch64">
```shell

kafka-producer-perf-test.sh --topic perf --num-records 200000 --record-size 100 \
  --throughput 20000 --producer-props acks=all
```

<Output>

Ten seconds, 200,000 records, about 20 MB into `perf-0`, and **not one fsync
on the topic's segment**. Every fsync went to the KRaft metadata log (section 10), which does sync, and to the checkpoint file where the broker records high
watermarks.
</Output>
</TryIt>

</Sub>

<Sub n="6.2" title="sendfile: from page cache to socket">

Serving a read the ordinary way takes four copies, as the docs spell out: disk
to page cache, page cache to a user buffer, user buffer to socket buffer, socket
buffer to NIC. **`sendfile()`** skips the middle two: an application names a
file range and a socket, and the kernel moves page-cache pages to the socket
itself (chapter 10 follows that path through the stack).

Kafka can do this because of section 3.2: the bytes on disk are already in the
wire format. Here's the call site:

<Why>Why does a lagging consumer hurt everyone?</Why>

A consumer reading the tail gets pages that were written seconds ago and are
still cached. Kafka's docs put it as "on a Kafka cluster where the consumers are
mostly caught up you will see no read activity on the disks whatsoever".

A consumer replaying last week's data forces real disk reads, and those pages
push the tail out of the cache. Now the caught-up consumers and the followers
start missing cache too. One backfill job can raise latency for every client
on the broker.

<Callout label="Design implication">
Size broker RAM for the page cache, not the heap. Keep the JVM heap modest and
leave the rest for the kernel. Watch disk reads on brokers: in a healthy
cluster they're near zero, and a rise usually means a consumer is reading far
behind.
</Callout>

</Sub>

<Sub n="6.3" title="Why TLS turns the trick off">

`sendfile` works because the kernel never has to change the bytes. TLS has to
encrypt them, and Kafka does that in Java with `SSLEngine`. From the docs: "`sendfile` is not used when SSL is enabled." The TLS transport layer
reads the file into a buffer instead:

  file="clients/src/main/java/org/apache/kafka/common/network/SslTransportLayer.java"

  tag="4.3.1"

So with TLS every fetched byte is read into user space in 32 KB pieces,

<Callout label="Common mistake" kind="warn">
Sizing a cluster from a plaintext benchmark and then turning on TLS. Every
fetch now costs CPU for copying and encryption on the broker, and the gap is
widest for fan-out topics with many consumers. Benchmark with the security
settings you'll run in production.
</Callout>

</Sub>

<SectionHeading n="07" id="consumers">Consumers and consumer groups</SectionHeading>

A consumer is a loop around `poll()`. It fetches batches from partition leaders
and occasionally records how far it's got.

<Sub n="7.1" title="Committed offsets">

That position is stored in Kafka itself, in the internal compacted topic
`__consumer_offsets`: one record per group, topic and partition. Committing
means producing to that topic.

Whether you process or commit first decides your delivery guarantee:

| Order | Crash between the two means | Guarantee |
|---|---|---|
| Commit, then process | The records are skipped | At most once |
| Process, then commit | The records are processed again | At least once, the default |
| Commit inside the same transaction as the output | Neither | Exactly once, within Kafka (section 8) |

`enable.auto.commit` is `true` by default and commits in the background
during `poll()`. That's at-least-once as long as you finish processing a batch
before calling `poll()` again.

</Sub>

<Sub n="7.2" title="Groups, and three generations of rebalancing">

Consumers sharing a `group.id` split the partitions between them. Each partition
goes to exactly one member, so the useful number of consumers is at most the
number of partitions.

When members join or leave, partitions move. That's a **rebalance**, and its
design has changed twice:

| Protocol | Where assignment happens | What stops during a rebalance |
|---|---|---|
| **Classic, eager** | A group leader among the clients | Every consumer revokes every partition, then waits for the new plan |
| **Classic, cooperative** ([KIP-429](https://cwiki.apache.org/confluence/display/KAFKA/KIP-429%3A+Kafka+Consumer+Incremental+Rebalance+Protocol), 2.4) | Still the client leader | Only partitions that move are revoked |
| **Consumer protocol** ([KIP-848](https://cwiki.apache.org/confluence/display/KAFKA/KIP-848%3A+The+Next+Generation+of+the+Consumer+Rebalance+Protocol), GA in 4.0) | The broker's group coordinator | Nothing global. Each member reconciles on its own heartbeat |

The KIP-848 [operations guide](https://kafka.apache.org/documentation/#consumer_rebalance_protocol)
says it "no longer relies on a global synchronization barrier". Brokers
enable it by default, but the Java client still defaults to
`group.protocol=classic`, so you have to opt in per application.

<Why>Why does a slow handler cause a rebalance?</Why>

Because the classic protocol treats "hasn't called `poll()` for
`max.poll.interval.ms`" (5 minutes) as dead. A handler stuck on a slow database
call for five minutes gets kicked out, its partitions move, and another consumer
reprocesses the same records. Then the first one comes back and triggers
another rebalance.

<Callout label="Common mistake" kind="warn">
Raising `session.timeout.ms` to stop rebalance storms caused by slow
processing. Heartbeats come from a background thread and keep flowing, so
the session timeout (45 s) isn't what's firing. It's
`max.poll.interval.ms`. Lower `max.poll.records` (500 by default) so each
`poll()` loop finishes sooner, or move slow work off the poll thread.
</Callout>

</Sub>

<SectionHeading n="08" id="exactly-once">Idempotence and exactly-once</SectionHeading>

At-least-once delivery produces duplicates in two places. A producer retries a
batch whose acknowledgement was lost, and the broker writes it twice. Or a
consumer reprocesses after a crash. Kafka closes the first with idempotence and
the second, for Kafka-to-Kafka pipelines, with transactions. Both arrived in
0.11 ([KIP-98](https://cwiki.apache.org/confluence/display/KAFKA/KIP-98+-+Exactly+Once+Delivery+and+Transactional+Messaging)).

<Sub n="8.1" title="The idempotent producer">

Each producer gets a **producer ID** from the broker, and numbers its batches
per partition: 0, 1, 2… The leader remembers the last sequence it accepted for
each producer ID and rejects anything that doesn't follow:

<SourceRead
  file="storage/src/main/java/org/apache/kafka/storage/internals/log/ProducerAppendInfo.java"
  repo="apache/kafka"
  tag="4.3.1"
  href="https://github.com/apache/kafka/blob/4.3.1/storage/src/main/java/org/apache/kafka/storage/internals/log/ProducerAppendInfo.java#L196"
>
```java
    private boolean inSequence(int lastSeq, int nextSeq) {
        return nextSeq == lastSeq + 1L || (nextSeq == 0 && lastSeq == Integer.MAX_VALUE);
    }
```
</SourceRead>

A retried batch that the broker already has is recognised as a duplicate and
acknowledged without being written again. To do that, the broker keeps the
metadata of the last five batches per producer (`NUM_BATCHES_TO_RETAIN = 5` in
`ProducerStateEntry.java`). That's why idempotence requires
`max.in.flight.requests.per.connection` of 5 or less.

<Why>Can idempotence turn itself off?</Why>

Yes, silently. From the producer docs: "If conflicting configurations are set and
idempotence is not explicitly enabled, idempotence is disabled." Setting
`acks=1` is such a conflict. Look back at the dump in section 5.3: those
`acks=1` batches carry `producerId: -1`. It happened in the batching
benchmark too, where `acks` was passed explicitly.

<Callout label="Common mistake" kind="warn">
Setting `acks=1` for speed and assuming you still have Kafka 3.0's
duplicate-free default. You don't: idempotence went away with it. If you want
it, set `enable.idempotence=true` explicitly and the producer will refuse a
conflicting config instead of quietly dropping the guarantee.
</Callout>

</Sub>

<Sub n="8.2" title="Transactions">

A transaction lets a producer write to several partitions, and commit a
consumer's offsets, atomically. It's run by a **transaction coordinator**, a
broker that owns the producer's `transactional.id`, with state kept in another
internal topic, `__transaction_state`.

/>

Markers are real records, and each takes an offset:

also show `producerEpoch` going 1, 2, 3: with transaction version 2

<Callout label="Common mistake" kind="warn">
Computing "records remaining" or checking completeness with offset arithmetic,
like `end offset - committed offset`. On a transactional topic, markers take up
offsets, aborted records stay in the log, and compaction removes others. Offsets
are increasing, not contiguous.
</Callout>

</Sub>

<Sub n="8.3" title="read_committed and the last stable offset">

A `read_committed` consumer reads up to the **last stable offset** (LSO): the
first offset of the oldest transaction still open. Nothing past it is delivered,
even records from producers that aren't transactional at all.

<TryIt what="Hold a transaction open for 40 seconds, then abort" lang="shell" toolchain="Kafka 4.3.1, OpenJDK 21, linuxkit 6.10.14 aarch64">
```shell

kafka-console-consumer.sh --topic txn4 --from-beginning --command-property isolation.level=read_uncommitted | wc -l
kafka-console-consumer.sh --topic txn4 --from-beginning --command-property isolation.level=read_committed | wc -l

```

<Output>
```text
10
0
ProducerId  ProducerEpoch  LatestCoordinatorEpoch  LastSequence  LastTimestamp  CurrentTransactionStartOffset
1003        0              -1                      9             1790482933080  0
```

A default `read_uncommitted` consumer sees all ten records of a transaction
that's about to be aborted. The `read_committed` one sees nothing, and
`CurrentTransactionStartOffset: 0` is what's holding the LSO there. After the
abort, the partition's end offset was 11 (ten records and the ABORT marker), and
`read_committed` still returned 0 records.
</Output>
</TryIt>

<Why>Why is a hanging transaction an outage?</Why>

Because the LSO can't pass it. Until the transaction commits, aborts or times
out (`transaction.timeout.ms`, 60 s by default on the producer), every
`read_committed` consumer on that partition is stuck. `kafka-transactions.sh
find-hanging` and `abort` exist for exactly this case.

</Sub>

<Sub n="8.4" title="What exactly-once covers">

Exactly-once in Kafka means a read-process-write loop where the input offsets
and the output records commit together, all inside Kafka. It doesn't reach
beyond that. In the design docs' words, "Exactly-once delivery for other destination
systems generally requires cooperation with such systems".

| Side effect | Covered by Kafka transactions? | What to do instead |
|---|---|---|
| Records written to Kafka topics | Yes | Transactions with `read_committed` downstream |
| Consumer offsets | Yes | `sendOffsetsToTransaction` |
| A row in Postgres | No | Store the offset in the same database transaction, or an idempotency key |
| An email, a payment call | No | Idempotency keys at the receiver |

<Callout label="Design implication">
Treat "exactly-once" as "exactly-once *inside Kafka*". Anything that leaves the
cluster is at-least-once, and the receiving side needs to deduplicate.
</Callout>

</Sub>

<SectionHeading n="09" id="retention">Retention and compaction</SectionHeading>

A log that only grows fills its disks. Kafka removes data in two ways, and both
work on whole segments, never single records.

<Sub n="9.1" title="Deleting by time and size">

With `cleanup.policy=delete` (the default), a closed segment is deleted once
its newest record is older than `retention.ms` (7 days by default), or once the
partition is over `retention.bytes` (unlimited by default). Active segments
are never deleted.

<Why>Why does retention sometimes keep data far longer than configured?</Why>

Because the active segment doesn't close until it reaches `segment.bytes` or
`segment.ms`. On a quiet partition with 1 GiB segments, a segment can take weeks
to fill, and none of it is eligible for deletion until it rolls. Lower
`segment.ms` for quiet topics; `segment.bytes` can't go below 1 MiB since
Kafka 4.0.

</Sub>

<Sub n="9.2" title="Compaction: the latest value per key">

With `cleanup.policy=compact`, Kafka keeps at least the last record for each
key and throws older ones away. `__consumer_offsets` works this way: only the
latest committed offset per partition matters.

<TryIt what="Write 61 versions of three keys, then let the cleaner run" lang="shell" toolchain="Kafka 4.3.1, linuxkit 6.10.14 aarch64">
```shell
kafka-topics.sh --create --topic users2 --config cleanup.policy=compact \
  --config segment.ms=3000 --config min.cleanable.dirty.ratio=0.01
# alice, bob and carol, versions v1..v61, in three bursts: 183 records
ls data1/users2-0/          # before, then again 45 s later
kafka-console-consumer.sh --topic users2 --from-beginning --formatter-property print.offset=true ...
```

<Output>
```text
00000000000000000000.log  00000000000000000090.log  00000000000000000180.log     # before
00000000000000000000.log  00000000000000000180.log  (and *.deleted files)        # after
Offset:177  alice  v60
Offset:178  bob    v60
Offset:179  carol  v60
Offset:180  alice  v61
Offset:181  bob    v61
Offset:182  carol  v61
```

183 records became 6. Kafka's cleaner merged the two closed segments into one that
holds only offsets 177 to 179. Each surviving record **keeps its original
offset**, so the log now has a gap from 0 to 176. Segment 180, still active,
wasn't touched; compaction never cleans it.
</Output>
</TryIt>

To delete a key, write a **tombstone**: the key with a null value. Tombstones are
kept for `delete.retention.ms` so that consumers reading slowly
still see the delete, then drops them.

</Sub>

<SectionHeading n="10" id="kraft">KRaft: the metadata is a log too</SectionHeading>

Someone has to decide which broker leads each partition, who's in each ISR and
which brokers are alive. For most of Kafka's life that was ZooKeeper.
[KIP-500](https://cwiki.apache.org/confluence/display/KAFKA/KIP-500%3A+Replace+ZooKeeper+with+a+Self-Managed+Metadata+Quorum)
replaced it with a Raft quorum of controllers, and Kafka 4.0 removed ZooKeeper
mode entirely.

<Sub n="10.1" title="A Raft log named __cluster_metadata">

Controllers keep cluster state as a log: topic created, partition
reassigned, ISR changed, broker fenced. That log is a Kafka partition,
`__cluster_metadata-0`, with the same segment files as any other.

One active controller appends to it, the other controllers replicate it with
Raft, and brokers fetch it like followers to keep their own copy of the
metadata up to date.

<Why>Why does the metadata log fsync when topic data doesn't?</Why>

Because Raft's safety depends on a voter not forgetting what it acknowledged.
A Raft majority that loses unsynced writes in a power cut can elect a leader
missing committed entries. That's why the strace in section 6.1 found 50 fsyncs
on `__cluster_metadata-0` and none on the topic. Metadata is small and changes rarely, so
the cost probably never shows up in your latency.

A small test cluster shows the quorum:

```text
$ kafka-metadata-quorum.sh describe --status
LeaderId:               1
LeaderEpoch:            1
HighWatermark:          66
MaxFollowerLag:         0
CurrentVoters:          [{"id": 1, ...}, {"id": 2, ...}, {"id": 3, ...}]
```

</Sub>

<Sub n="10.2" title="What changed for operators">

| | ZooKeeper era | KRaft |
|---|---|---|
| **Metadata store** | A separate ZooKeeper ensemble | A Raft log inside Kafka's controllers |
| **Broker liveness** | ZooKeeper session | Heartbeats to the controller, `broker.session.timeout.ms` (9 s) |
| **Controller failover** | New controller reloads all state from ZooKeeper | Standby controllers already have the log |
| **Brokers learn metadata** | RPCs from the controller | Fetching the metadata log |
| **Supported** | Up to 3.9 | Only option since 4.0 |

</Sub>

<SectionHeading n="11" id="operating">Running Kafka: what to watch and what to fix</SectionHeading>

<Sub n="11.1" title="Settings that decide your guarantees">

| Setting | Default | Set it to | Why |
|---|---|---|---|
| Replication factor | Per topic | 3 | Survive a broker loss with a spare |
| `min.insync.replicas` | 1 | 2 with RF 3 | Otherwise `acks=all` can mean one copy |
| `acks` | `all` | Leave it | `1` also silently disables idempotence |
| `enable.idempotence` | `true` | `true`, explicitly | Fail loudly on a conflicting config |
| `unclean.leader.election.enable` | `false` | Leave it, except for topics that prefer availability | Prevents silent loss |
| `isolation.level` | `read_uncommitted` | `read_committed` downstream of transactional producers | Otherwise consumers see aborted data |
| `group.protocol` | `classic` (client) | `consumer` on 4.x clusters | Incremental, broker-driven rebalances |

</Sub>

<Sub n="11.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| `NOT_ENOUGH_REPLICAS` with one broker down | ISR below `min.insync.replicas` | Restore the broker; check RF and replica placement |
| `acks=1` writes succeed but consumers see nothing | HW frozen while the ISR is under min ISR | Same; it's the KIP-966 guard working |
| `UnderReplicatedPartitions` above 0 | A follower is slow or down | Check its disk, network and GC; look for a hot partition |
| Consumer group keeps rebalancing | Processing exceeds `max.poll.interval.ms` | Lower `max.poll.records`, move slow work off the poll loop, or use the consumer protocol |
| `read_committed` consumers stall on one partition | A hanging transaction pins the LSO | `kafka-transactions.sh find-hanging`, then `abort` |
| Produce latency rises when a backfill job starts | Old segments evicting the tail from page cache | Throttle the backfill, add RAM, or serve history from tiered storage |
| Broker CPU jumps after enabling TLS | No more `sendfile`; the JVM copies and encrypts | Budget for it, or terminate TLS elsewhere where policy allows |
| Disk usage far above `retention.ms × write rate` | Active segments too big to roll on quiet partitions | Lower `segment.ms` or `segment.bytes` for those topics |
| Duplicates after producer retries | Idempotence disabled by `acks=1` or `max.in.flight` above 5 | `acks=all`, `enable.idempotence=true` |

<Callout label="Design implication">
Of the broker metrics, the ISR ones matter most:
`UnderReplicatedPartitions`, `UnderMinIsrPartitionCount` and
`OfflinePartitionsCount`. Alert on the second, because that's when `acks=all`
writes start failing, and the first is the warning before it.
</Callout>

</Sub>

<SectionHeading n="12" id="summary">Summary</SectionHeading>

1. **Kafka is a log, not a queue.** Reads don't remove anything; each consumer
   keeps its own offset, so extra readers are nearly free.
2. **Ordering is per partition.** The key picks the partition, so choose it as
   the thing whose events must stay in order.
3. **A partition is a directory of segments.** Each has a sparse offset index
   and time index; a lookup is a floor search, a binary search and a short scan.
4. **The batch is the unit of everything.** Batching was worth about 60× in
   throughput here, and `linger.ms` now defaults to 5 for that reason.
5. **`acks=all` waits for the ISR, and the ISR can shrink.** Pair RF 3 with
   `min.insync.replicas=2`, or `acks=all` can mean one copy.
6. **Consumers only see records below the high watermark.** Since KIP-966 the
   HW stops moving when the ISR is under min ISR, even for `acks=1` writes.
7. **Durability comes from replication, not fsync.** The broker left 20 MB of
   writes in the page cache; only the KRaft metadata log was synced.
8. **`sendfile` sends fetches from page cache to socket.** TLS turns it off, and
   a lagging consumer can evict everyone else's cache.
9. **Idempotence and transactions give exactly-once inside Kafka only.**
   `acks=1` silently turns idempotence off, and transaction markers use offsets.
10. **Retention and compaction work on closed segments.** The active segment is
    never deleted or compacted.

<SectionHeading n="13" id="build">Build this</SectionHeading>

**A one-partition log server in about 400 lines.** Pick any language with
`sendfile` access (Go, Rust, C, or Java's `FileChannel.transferTo`).

- An append endpoint that writes length-prefixed batches to a segment file and
  returns the base offset. Roll to a new file at 64 MB, named by base offset.
- A sparse index: one (relative offset, position) pair every 4 KB, in an
  `mmap`ed file. Implement "fetch from offset N" as floor search, binary search,
  forward scan.
- Serve fetches with `sendfile`. Then serve them with read-into-buffer-and-write
  and compare CPU per GB with `perf stat`.
- Add one follower that pulls from the leader, a high watermark, and an
  `acks=all` mode. Kill the follower and watch your own HW stop.

<SectionHeading n="14" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What's the difference between a Kafka topic and a message queue?">
A queue removes a message once it's consumed, and several consumers compete for
messages. A Kafka topic is a set of append-only logs; reading doesn't change
them, and each consumer group tracks its own offset. So several groups can each
read everything, you can replay by resetting an offset, and data is removed only
by retention or compaction, a whole segment at a time.
</QA>

<QA level="beginner" q="What do acks=0, acks=1 and acks=all mean?">
When the leader answers the producer: never, after the leader's own append, or
after every in-sync replica has the record and the ISR has at least
`min.insync.replicas` members. `acks=1` loses acknowledged records if the
leader dies before a follower copies them. `acks=all` is the default since 3.0.
</QA>

<QA level="intermediate" q="What is the high watermark, and why can't consumers read past it?">
It's the offset below which every ISR member has the data. Records above it exist
only on some replicas and could vanish if the leader fails, so showing them
would let a consumer act on a record that later never existed. A leader learns
followers' progress from the offsets in their next fetch requests, and since
KIP-966 it only advances the HW while the ISR is at least `min.insync.replicas`.
</QA>

<QA level="intermediate" q="Your consumer group rebalances every few minutes. What do you check?">
Whether processing a batch takes longer than `max.poll.interval.ms` (5 minutes
by default). If it does, the consumer is treated as dead even though its
heartbeats are fine. Lower `max.poll.records`, move slow work off the poll
thread, or raise the interval. Also check for frequent deploys or autoscaling,
and consider cooperative assignment or the KIP-848 consumer protocol so each
rebalance only moves the partitions that need to move.
</QA>

<QA level="intermediate" q="Why is Kafka fast even though it stores everything on disk?">
Appends are sequential and go to the page cache, not straight to disk; Kafka
doesn't fsync per write and relies on replication for durability. Batches are
stored in the wire format, so fetches go from page cache to socket with
`sendfile` and never enter the JVM. Batching amortises per-request costs.
Caught-up consumers are served from memory. TLS removes the `sendfile` part.
</QA>

<QA level="deep" q="How does Kafka prevent duplicates when a producer retries?">
An idempotent producer gets a producer ID and numbers its batches per
partition. Its leader keeps the last sequence and the metadata of the last five
batches per producer ID. A retry that matches a stored batch is acknowledged
without being written; a gap raises `OutOfOrderSequenceException`. That
five-batch window is why `max.in.flight.requests.per.connection` must be at most
5. Idempotence is disabled without warning if you set a conflicting config like
`acks=1` without setting `enable.idempotence=true`.
</QA>

<QA level="deep" q="A read_committed consumer is stuck on one partition, and lag keeps rising. Other partitions are fine. What's going on?">
Probably an open transaction. A `read_committed` consumer can't read past the
last stable offset, the start of the oldest open transaction on that partition.
A producer that began a transaction and died or hung pins it until the
transaction times out, or indefinitely if markers were never written.
`kafka-transactions.sh describe-producers` shows the `CurrentTransactionStartOffset`,
`find-hanging` lists stuck ones, and `abort` clears them.
</QA>

<QA level="deep" q="Why does Kafka use leader epochs for truncation instead of the high watermark?">
A follower's high watermark lags the leader's, because it only learns the HW in
the next fetch response. Truncating to it after a leader change could throw away
committed records or leave replicas with different data at the same offset,
which KIP-101 documents. Leader epochs, stamped on every batch and checkpointed
per replica, let a follower ask the new leader exactly where its previous
epoch ended and truncate to that point.
</QA>

<SectionHeading n="15" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="Three transactions of 1,000 records each commit on one partition. What's the end offset?">
    3,003. Each commit writes a control record into the partition, and it takes
    an offset like any other record.
  </Q>
  <Q q="Why is a new segment's .index file 10 MB when the log is 123 bytes?">
    Index files are preallocated to `log.index.size.max.bytes` and memory-mapped.
    They're sparse on disk, and trimmed when the segment rolls.
  </Q>
  <Q q="RF 3, min.insync.replicas=2, two brokers down. Can acks=1 producers still write? Can consumers read what they write?">
    Yes, and no. Leaders accept `acks=1` writes, but the high watermark can't
    move while the ISR is under min ISR, so the new records stay invisible.
  </Q>
  <Q q="What happens to sendfile when you enable TLS on the listener?">
    It's not used. Kafka's TLS transport reads the file into a 32 KB direct buffer,
    encrypts in the JVM and writes it out.
  </Q>
</Quiz>
