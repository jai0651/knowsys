I wrote a service that catches `SIGTERM`, prints "ignoring", and goes back to
sleep. Then I ran `systemctl stop` on it and waited.

It came back **90.22 seconds** later. Nothing was hung, nothing was
wrong with the machine. That's the default: systemd sends `SIGTERM`, waits a
minute and a half, then sends `SIGKILL`. If you've ever watched "A stop job is
running for..." tick up on a shutdown screen, you've met this number.

That was the second experiment. The first was smaller. I ran `sleep 600` as
PID 1 in a plain Ubuntu container, spawned five short-lived children under it,
and listed the processes. Five zombies. `sleep` doesn't call `wait()`, and
nobody else will. `docker stop` on that container took **10.16 s**; the same
container started with `--init` stopped in **0.093 s**.

Both numbers come from the same fact, more or less. Something has to be PID 1, and PID 1 has
responsibilities that ordinary processes don't. Everything else in this chapter
is what systemd builds on top of those.

<SectionHeading n="01" cmd="man 7 pid_namespaces" id="contract">What PID 1 owes the kernel</SectionHeading>

Two things, and the kernel won't do either for you.

- **Reap orphans.** When a process dies, its parent gets `SIGCHLD` and must
  `wait()` for it, or the entry stays in the process table as a zombie. When the
  parent dies first, the orphan is reparented to init. So init has to reap
  children it never started.
- **Handle signals deliberately.** The kernel won't deliver a signal to init
  unless init installed a handler for it. [pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)
  spells it out for namespaces: from inside, only signals with an established
  handler reach PID 1; from an ancestor namespace, `SIGKILL` and `SIGSTOP` still
  work. That's the whole 10 seconds above. `sleep` has no `SIGTERM` handler, so
  Docker's `SIGTERM` is dropped, and Docker falls back to `SIGKILL` when its
  grace period runs out.

There's a third rule, stated less often. If PID 1 on the host exits or crashes,
the kernel panics. That's why a crash in systemd isn't a service outage but a
machine outage, and it's why the CVEs in section 4.6 matter.

<Callout label="Why the zombies in that container never went away">
A zombie holds no memory, just a slot in the process table and an exit status
nobody collected. Each `docker exec sh -c 'sleep 0.1 & exit'` left one behind,
because the `sh` exited before its child, the child got reparented to `sleep`
(PID 1 in that namespace), and `sleep` never calls `wait()`. With `--init`,
PID 1 is `docker-init` (tini), a program whose entire purpose is to call
`wait()` in a loop and forward signals. That's the minimum viable init.
</Callout>

<Sub n="1.1" title="From pidfiles to supervisors">

System V init ran shell scripts that daemonized a program, wrote its PID to a
file, and forgot about it. Stopping meant reading the pidfile and hoping the
number still referred to the same process. Nothing noticed a crash.

Supervision grew out of that, roughly in this order:

- **daemontools** (Dan Bernstein, late 1990s). `supervise` runs a program in
  the foreground, as its direct child, and restarts it on exit. Programs are
  told *not* to daemonize, so the supervisor always knows the PID.
- **runit** (Gerrit Pape). The daemontools idea, small enough to be PID 1, and
  used as init by Void Linux.
- **Upstart** (Ubuntu, 2006). Event-driven: jobs start when events fire. It
  tracked forking daemons by following `fork()` with ptrace, which was fragile.
- **systemd** (Lennart Poettering and Kay Sievers, announced in
  [Rethinking PID 1](http://0pointer.de/blog/projects/systemd.html), April 2010).
  Dependency-based instead of event-based, socket activation borrowed from
  inetd and launchd, and cgroups to track processes. From that post: "cgroup
  membership is securely inherited by child processes, they cannot escape."

</Sub>

<Sub n="1.2" title="What systemd promises, and what it doesn't">

systemd promises that it'll start units in an order consistent with their
declared dependencies, computed as one transaction; that every process a
service spawns is attributed to that service, however it forks; that it'll
restart per the policy you wrote; and that stdout and stderr end up in the
journal with trusted metadata.

It doesn't promise that a unit reported **active** is ready to serve. It
doesn't promise that `After=` pulls anything in. And it definitely doesn't
promise that a service that keeps restarting is healthy. Each of those turns up
in a transcript below.

</Sub>

<SectionHeading n="02" cmd="systemctl list-jobs" id="layout">Units, jobs, and one cgroup per service</SectionHeading>

A **unit** is a named object loaded from a file: `foo.service`, `foo.socket`,
`foo.timer`, `home.mount`, `multi-user.target`, `system.slice`. The file is
INI syntax, but what systemd keeps in memory is a graph node with two sets of
edges, and the whole design depends on them being separate.

<Compare

    ["Wants=", "Should X start when I do?", "Yes", "No"],
    ["Requires=", "Should I fail if X fails to start?", "Yes", "No"],
    ["BindsTo=", "Should I stop whenever X stops?", "Yes", "No"],
    ["After= / Before=", "If both are starting, who waits?", "No", "Yes"],
  ]}
/>

That table is probably the chapter's most expensive line, and it's in section 3.3 with a
transcript. Requirement and ordering are orthogonal. `Requires=db.service`
without `After=db.service` starts both **at the same time**.

<Sub n="2.1" title="Jobs and the transaction">

You never start a unit directly. `systemctl start app` asks the manager, over
D-Bus, to enqueue a **job**: a (unit, type) pair like `app.service/start`. The
manager builds a <em className="term">transaction</em> around that anchor job:
walk the requirement edges, add a job for every unit pulled in, merge
duplicates, then walk the ordering edges looking for cycles. Only a consistent
transaction gets committed to the run queue.

I caught one mid-flight. `db.service` takes three seconds to report ready, and
`app-good.service` has `Requires=` and `After=` on it:

```shell
$ systemctl start --no-block app-good; sleep 0.3; systemctl list-jobs
JOB UNIT             TYPE  STATE
734 app-good.service start waiting
796 db.service       start running

2 jobs listed.
```

Two jobs, one `waiting` on an ordering edge, one `running`. Nothing in the
unit files mentioned "wait". That's the ordering graph at work.

</Sub>

<Sub n="2.2" title="What the engine does with a cycle">

What does it do when the ordering graph has a loop? I expected an error, probably a loud one. I built
three units, `cyc-a` → `cyc-b` → `cyc-c` → `cyc-a`, each with `Wants=` and
`After=` on the next, and started `cyc-a`:

```shell
$ systemctl start cyc-a; echo rc=$?
rc=0
$ journalctl -o cat | grep -A3 "ordering cycle"
cyc-a.service: Found ordering cycle on cyc-b.service/start
cyc-a.service: Found dependency on cyc-c.service/start
cyc-a.service: Found dependency on cyc-a.service/start
cyc-a.service: Job cyc-b.service/start deleted to break ordering cycle starting with cyc-a.service/start
$ systemctl is-active cyc-a cyc-b cyc-c
active
inactive
inactive
```

Exit code zero. systemd silently dropped a unit from the boot and carried on,
and `cyc-c` went with it because nothing else wanted it. Swap `Wants=` for
`Requires=` and the same start fails with `Transaction order is cyclic`. Here's
the loop that decides:

  file="src/core/transaction.c — transaction_verify_order_one()"

  href="https://github.com/systemd/systemd/blob/v255/src/core/transaction.c#L366-L392"

```c
/* Have we seen this before? */
if (j->generation == generation) {
        Job *k, *delete = NULL;
        ...
        /* So, the marker is not NULL and we already have been here. We have a cycle. Let's try to
         * break it. We go backwards in our path and try to find a suitable job to remove. */
        for (k = from; k; k = ((k->generation == generation && k->marker != k) ? k->marker : NULL)) {
                ...
                if (!delete && hashmap_contains(tr->jobs, k->unit) && !job_matters_to_anchor(k))
                        /* Ok, we can drop this one, so let's do so. */
                        delete = k;

                /* Check if this in fact was the beginning of the cycle */
                if (k == j)
                        break;
        }
```
</SourceRead>

`job_matters_to_anchor` is the whole policy. A job pulled in by `Requires=`
matters to the anchor, so it can't be dropped. A job pulled in by `Wants=`
doesn't, so the first one found walking back along the cycle gets deleted. On a
real machine that shows up as `SKIP` on the console at boot, and a service that
just isn't running afterwards.

</Sub>

<SectionHeading n="03" cmd="strace -f -e trace=accept4,execve /usr/local/bin/echo-activated" id="hot-path">One connection, from socket to accept()</SectionHeading>

Here's the operation to trace. A TCP connection arrives on a port where no
service process is running yet. What has to happen between the SYN and the
service's `accept()` returning?

<Sub n="3.1" title="The fd that PID 1 was holding">

The socket unit is four lines, and the service unit is two:

```ini
# /etc/systemd/system/hello.socket
[Socket]
ListenStream=127.0.0.1:7777

# /etc/systemd/system/hello.service
[Service]
ExecStart=/usr/local/bin/echo-activated
```

After `systemctl start hello.socket`, the service isn't running, and the
listening socket belongs to PID 1:

```shell
$ systemctl is-active hello.service; ss -ltnp | grep 7777
inactive
LISTEN 0  4096  127.0.0.1:7777  0.0.0.0:*  users:(("systemd",pid=1,fd=47))
```

Meanwhile the kernel completes the handshake into that socket's backlog whether or not
anyone's accepting. PID 1 has the fd in its event loop, sees it go readable,
and enqueues `hello.service/start`. As far as the client knows, it's connected and just
waiting for bytes.

</Sub>

<Sub n="3.2" title="Getting fd 47 to become fd 3">

systemd 255 changed how children are spawned. Earlier versions forked PID 1 and
did all the sandbox setup in the child; the [v255 NEWS](https://github.com/systemd/systemd/blob/v255/NEWS)
explains that this ran glibc code that isn't safe between `fork` and `exec`, and
that from now on "the new process is spawned using CLONE_VM and CLONE_VFORK
semantics via posix_spawn(3), and it immediately execs a new internal binary,
systemd-executor". The executor receives the configuration over a memfd, sets
up namespaces, credentials and fds, then execs your binary.

passed sockets always start at 3, the constant `SD_LISTEN_FDS_START`. Then the
environment is built:

Why `LISTEN_PID` at all? Environment variables are inherited. If your service
runs a shell script that forks a helper, the helper sees `LISTEN_FDS=1` too, and
without the PID check it'd start calling `accept()` on an fd it doesn't own.
`getpid_cached()` runs in the executor, and that's the same process that execs the
service, so the PID is exactly right. On the library side, it's the first thing checked:

Note the `fd_cloexec` loop. The fds arrive *without* close-on-exec, because they
had to survive one `execve`, and the library turns it back on so they don't
survive a second. It's a small enough protocol to do by hand, so I did, in C++
with no libsystemd:

<TryIt what="A socket-activated server that reads the protocol itself" lang="cpp" toolchain="g++ 13.3 -O2, Ubuntu 24.04 in Docker, aarch64">
```cpp
#include <cstdio>
#include <cstdlib>
#include <string>
#include <unistd.h>
#include <sys/socket.h>

int main() {
    const char* pid = getenv("LISTEN_PID");
    const char* n   = getenv("LISTEN_FDS");
    const char* nm  = getenv("LISTEN_FDNAMES");
    if (!pid || !n || atoi(pid) != getpid()) {
        fprintf(stderr, "not socket-activated\n");
        return 1;
    }
    int listen_fd = 3;                      // SD_LISTEN_FDS_START
    fprintf(stderr, "LISTEN_PID=%s LISTEN_FDS=%s LISTEN_FDNAMES=%s, my pid=%d\n",
            pid, n, nm ? nm : "-", getpid());
    for (;;) {
        int c = accept(listen_fd, nullptr, nullptr);
        if (c < 0) { perror("accept"); return 1; }
        std::string msg = "hello from pid " + std::to_string(getpid()) + "\n";
        (void)!write(c, msg.data(), msg.size());
        close(c);
    }
}
```

<Sub n="3.3" title="Started is not ready, and After= is not Wants=">

When does systemd consider a service "started"? It depends on `Type=`, and it's
the setting that decides whether `After=` means anything.

- **`Type=simple`** (the default): started the moment the manager has forked
  the process. Before `execve`, even.
- **`Type=exec`**: started once `execve` succeeds. Catches a missing binary;
  says nothing about readiness.
- **`Type=forking`**: started when the original process exits, the old
  double-fork daemon convention. You'll usually want a `PIDFile=` too.
- **`Type=notify`**: started when the process sends `READY=1` over the socket in
  `$NOTIFY_SOCKET`.

`sd_notify` is one `sendto()` of a datagram on a Unix socket. Here's a fake
database that takes three seconds to warm up:

```cpp
// notify-slow.cpp: Type=notify by hand
static void notify(const char* msg) {
    const char* path = getenv("NOTIFY_SOCKET");
    if (!path) return;
    int fd = socket(AF_UNIX, SOCK_DGRAM | SOCK_CLOEXEC, 0);
    sockaddr_un sa{};
    sa.sun_family = AF_UNIX;
    strncpy(sa.sun_path, path, sizeof sa.sun_path - 1);
    if (sa.sun_path[0] == '@') sa.sun_path[0] = '\0';   // abstract namespace
    sendto(fd, msg, strlen(msg), 0, (sockaddr*)&sa, sizeof sa);
    close(fd);
}

int main() {
    sleep(3);                                   // load a cache, open a DB...
    notify("READY=1\nSTATUS=serving");
    for (;;) pause();
}
```

I ran it twice, as `db.service` with `Type=notify` and as `db-simple.service`
with `Type=simple`. Then four one-shot "apps" that print the database's state
at the moment they run:

```shell
app-bad:        Requires=db.service                          → "db is activating"   start took 0.02s
app-good:       Requires=db.service  After=db.service        → "db is active"       start took 3.03s
app-simple:     Requires=db-simple   After=db-simple         → "db-simple is active" start took 0.01s
app-after-only:                      After=db.service        → "db is inactive"
```

Four units, four different failures of intuition:

- **`app-bad`** is the bug everyone writes. `Requires=` pulled the database in,
  and with no ordering edge both jobs ran in parallel. The app ran while the
  database was still `activating`.
- **`app-good`** is correct. The 3.03 s is the database's warm-up, spent in the
  `waiting` state you saw in section 2.1.
- **`app-simple`** has the right dependencies and still loses. The database
  reported `active` 0.01 s after launch, three seconds before it could serve,
  because `Type=simple` defines "started" as "forked".
- **`app-after-only`** didn't start the database at all. `After=` only orders
  jobs that are already in the transaction.

<Callout label="The two-line rule, and the one line after it">
`Wants=` or `Requires=` decides *whether*. `After=` decides *when*. You almost
always want both, and then `After=` only waits as long as the dependency's
`Type=` says it should. A `Type=simple` dependency is "ready" the instant it's
forked, so ordering after it buys you nothing.
</Callout>

How does the manager know the datagram came from the service and not some
other process? The notify socket has `SO_PASSCRED` set, so each message
arrives with the sender's PID, and `service_notify_message_authorized()` in
[src/core/service.c](https://github.com/systemd/systemd/blob/v255/src/core/service.c#L4295)
checks it against `NotifyAccess=` (the main PID only, by default for
`Type=notify`). Messages from anyone else get logged and dropped.

</Sub>

<SectionHeading n="04" cmd="journalctl -u crashy -o short-monotonic" id="failure">How supervision fails</SectionHeading>

<Sub n="4.1" title="The restart loop that looks healthy">

A crashing service with `Restart=on-failure` and default settings:

```ini
[Service]
ExecStart=/bin/sh -c "echo starting; sleep 0.2; echo segfault-ish >&2; exit 139"
Restart=on-failure
```

It restarts every 100 ms (`DefaultRestartUSec=100ms`), and the start limit
of 5 starts in 10 s stops it after about two seconds:

```shell
[27299.110431] crashy.service: Failed with result 'exit-code'.
[27299.395354] crashy.service: Scheduled restart job, restart counter is at 5.
[27299.395995] crashy.service: Start request repeated too quickly.
[27299.396213] crashy.service: Failed with result 'exit-code'.
$ systemctl show crashy -p NRestarts -p Result -p StartLimitBurst -p StartLimitIntervalUSec
NRestarts=5
Result=exit-code
StartLimitBurst=5
StartLimitIntervalUSec=10s
```

I expected `Result=start-limit-hit`, and the manpage says that's a possible
value. What stuck was the first failure. `service_enter_dead()` only
overwrites the result `if (s->result == SERVICE_SUCCESS)`, and the start-limit
check in `service_can_start()` runs before the start path resets it. So if your
alerting greps for `start-limit-hit` on a unit that crashed its way there, it
won't find it. `systemctl --failed` will.

Now the variant that matters. Same crash, but after one second of uptime, with
`RestartSec=2`:

```shell
$ systemctl start crashy-slow; sleep 32
$ systemctl show crashy-slow -p NRestarts -p ActiveState -p SubState
NRestarts=10
ActiveState=active
SubState=running
$ systemctl --failed
  UNIT           LOAD   ACTIVE SUB    DESCRIPTION
● crashy.service loaded failed failed crashy.service
```

Ten crashes in 32 seconds, and it's `active (running)` and missing from
`--failed`. A three-second cycle only fits three or four starts into any
ten-second window, so the limit never trips. I left it running and later saw
`restart counter is at 58` go past in the journal. That's how a service that
segfaults every few seconds stays green for weeks. Chris Siebenmann wrote up a
real one, a [Prometheus host agent](https://utcc.utoronto.ca/~cks/space/blog/linux/SystemdRestartHidesProblems)
crashing with a Go runtime error that went unnoticed partly because of
`Restart=always`.

**`NRestarts` is the number to alert on, not `ActiveState`.** It survives `daemon-reload` (it's serialized with the rest of the unit's
state) and resets on the next manual start or a `systemctl reset-failed`.

</Sub>

<Sub n="4.2" title="The socket that dies with its service">

This one I found by accident. My cold-start benchmark stopped `hello.service`
thirty times in a tight loop so each connection would trigger a fresh start.
Partway through, connections started getting refused:

```shell
hello.service: Start request repeated too quickly.
hello.service: Failed with result 'start-limit-hit'.
Failed to start hello.service.
hello.socket: Failed with result 'service-start-limit-hit'.
```

When the service hits its start limit, the socket unit goes down with it and
**closes the listening socket**. After I lifted the service limit with
`StartLimitIntervalSec=0`, the socket hit its own, separate limit
(`TriggerLimitBurst=20` per `TriggerLimitIntervalSec=2s`) and failed with
`trigger-limit-hit`. Either way, the port is now refusing connections. Socket activation was
supposed to prevent exactly that. A crash-looping
socket-activated service turns from "slow" into "down" at the sixth crash.

</Sub>

<Sub n="4.3" title="The 90-second stop">

Back to the opening. The defaults, read from the running manager:

```shell
$ systemctl show stubborn -p TimeoutStopUSec -p KillMode -p KillSignal -p FinalKillSignal
TimeoutStopUSec=1min 30s
KillMode=control-group
KillSignal=15
FinalKillSignal=9
$ time systemctl stop stubborn
stop took 90.22 s
[27351.722146] python3[479]: got SIGTERM, ignoring
[27441.908849] stubborn.service: State 'stop-sigterm' timed out. Killing.
[27441.910632] stubborn.service: Killing process 479 (python3) with signal SIGKILL.
[27441.913059] stubborn.service: Failed with result 'timeout'.
```

At shutdown, units stop in reverse dependency order, so one stubborn service
blocks everything ordered before it for the full 90 seconds. Fedora 38 accepted
a [change](https://fedoraproject.org/wiki/Changes/Shorter_Shutdown_Timer) to cut
it to 45 s and, via `TimeoutStopFailureMode=abort`, to send `SIGABRT` first so
the hang leaves a core dump. That's the better fix in your own units too: a
core of the thing that wouldn't stop tells you why.

</Sub>

<Sub n="4.4" title="KillMode and the processes left behind">

`KillMode=control-group` (the default) signals every process in the cgroup.
`KillMode=process` signals only the main PID. I ran a service that starts two
`setsid` background children, in both modes:

```shell
$ systemd-cgls -u system.slice | grep -A3 forker-process
├─forker-process.service
│ ├─614 sleep 1000
│ ├─616 sleep 1001
│ └─617 sleep 1002
$ systemctl stop forker-control-group forker-process
$ ps -eo pid,ppid,args | grep "sleep 100"
    616       1 sleep 1001
    617       1 sleep 1002
$ cat /proc/617/cgroup
0::/docker/990fb6a9.../system.slice/forker-process.service
```

`setsid` didn't help the control-group version escape: all three died. In
process mode the children survived, and they **stayed in the service's cgroup**.
Starting the unit again gave:

```shell
forker-process.service: Found left-over process 616 (sleep) in control group while starting unit. Ignoring.
forker-process.service: Found left-over process 617 (sleep) in control group while starting unit. Ignoring.
```

Five processes in the unit now, two of them from the last run. Some units ship
`KillMode=process` on purpose (sshd, so a restart doesn't kill your login
sessions), but I'd guess most uses are a leak.

</Sub>

<Sub n="4.5" title="The watchdog">

`WatchdogSec=2` puts `WATCHDOG_USEC=2000000` in the environment and expects
`WATCHDOG=1` over the notify socket more often than that. My test program
pinged every second, six times, then pretended to deadlock:

```shell
[27477.808096] wd[732]: deadlocked (pretend)
[27479.905676] systemd[1]: wd.service: Watchdog timeout (limit 2s)!
[27479.905749] systemd[1]: wd.service: Killing process 732 (wd) with signal SIGABRT.
[27479.905950] systemd[1]: wd.service: Failed with result 'watchdog'.
[27480.143467] systemd[1]: wd.service: Scheduled restart job, restart counter is at 1.
```

`SIGABRT`, not `SIGTERM`, so you get a core of the stuck state. Where you put the ping
matters more than the interval, I think. Sent from a dedicated timer thread, it proves the
process is alive and nothing more. Sent from the event loop after real work, it
proves the event loop isn't wedged, and that's probably what you care about.

</Sub>

<Sub n="4.6" title="When PID 1 is the thing that breaks">

A bug in a service kills that service. A bug in PID 1 panics the kernel, and
PID 1 parses input unprivileged users can influence.

- **[CVE-2021-33910](https://www.qualys.com/2021/07/20/cve-2021-33910/denial-of-service-systemd.txt)**
  (Qualys, July 2021). systemd reads `/proc/self/mountinfo` and escapes each
  mount path with `unit_name_path_escape()`, which used `strdupa()`, an
  `alloca()` on the stack. A path over 8 MB (the default stack limit), mounted
  by an unprivileged user via FUSE, crashed PID 1 and with it the machine.
  Qualys traced it to v220, April 2015, where a heap `strdup()` became
  `strdupa()`.
- **[CVE-2018-15686](https://ubuntu.com/security/notices/USN-3816-1)** (Jann
  Horn, Google Project Zero). Across `daemon-reexec`, systemd serializes its
  state to a text file and reads it back. Reading used `fgets()` with a fixed
  buffer, so an overlong status line written through `NotifyAccess` got split,
  and the second half was parsed as a fresh serialized field. That was state
  injection into PID 1, with a path to root. Versions up to 239 were affected.

Both are roughly the same shape. Attacker-controlled bytes (a mount path, a status
string) reached code in PID 1 that assumed a size bound.

</Sub>

A few things fall out of that. Supervision adds about a millisecond of manager
work per start over a bare `fork+exec`, and most of what you see from
`systemctl` is the client itself: `systemctl show`, which changes nothing, costs
2.5 ms. If a deploy script calls `systemctl` in a loop over 500 units, that's
over a second in client startup alone, and `systemctl start a b c ...` in one
call is the fix.

Socket activation's cold path is a couple of milliseconds. That seems cheap enough
for an SSH daemon or a metrics exporter, and it's why Ubuntu has shipped `sshd`
[socket-activated by default](https://discourse.ubuntu.com/t/sshd-now-uses-socket-based-activation-ubuntu-22-10-and-later/30189) since 22.10. It isn't cheap enough to do per request,
and `Accept=yes` (one instance per connection, inetd style) does exactly that.

<Sub n="5.1" title="The journald burst that wasn't 10,000">

journald's default rate limit is `RateLimitBurst=10000` per
`RateLimitIntervalSec=30s`, per service. I had a service print 50,000 lines as
fast as Python could. **37,500** made it in. Where does 37,500 come from? The
burst is scaled by free disk space, in
[journald-rate-limit.c](https://github.com/systemd/systemd/blob/v255/src/journal/journald-rate-limit.c#L159-L185):

```c
k = log2u64(available);
if (k <= 20)            /* 1MB */
        return burst;
burst = (burst * (k-16)) / 4;
```

The disk had 402 GB free, which would give k = 38 and a burst of 55,000. My
reading is that "available" is measured against journald's `SystemMaxUse=`
budget (10% of the filesystem, capped at 4 GiB) minus what's used, which lands
just under 2^32. I checked the arithmetic, not that code path. Dropped
lines don't announce themselves at the time: a
`Suppressed 62502 messages from chatty.service` line only appeared when the
service logged again, after the window, and it counted this run's 12,500 plus
all 50,002 lines of a second run I'd started inside the same 30 s.

</Sub>

<Sub n="5.2" title="What the sandbox costs, and a number I got wrong first">

2.5 ms plain, 30.6 ms with the drop-in from section 6.3. I believed it for a
while. Then I reran it on a second Linux box (the shared lab container, same
kernel and systemd, 4 CPUs) and got a *plain* unit at 17 to 60 ms, which made no

It was the harness, as far as I can tell. For the hardened run I'd added a 150 ms sleep

people were using.

<SectionHeading n="06" cmd="systemd-analyze security hello.service" id="operating">Operating it</SectionHeading>

<Sub n="6.1" title="Seeing where boot time goes">

`blame` sorts units by their own start time; `critical-chain` shows the path that
actually gated the target. That's usually the one you want.

```shell
$ systemd-analyze
Startup finished in 192ms (userspace)
$ systemd-analyze blame | head -3
32ms systemd-resolved.service
25ms systemd-tmpfiles-setup-dev.service
14ms systemd-journald.service
$ systemd-analyze critical-chain
graphical.target @188ms
└─multi-user.target @188ms
  └─systemd-logind.service @176ms +11ms
    └─basic.target @155ms
      └─sysinit.target @154ms
        └─systemd-resolved.service @121ms +32ms
          └─systemd-tmpfiles-setup.service @112ms +6ms
            └─local-fs.target @109ms
```

On a real server the usual top of that chain is `network-online.target`, and
the usual cause is a unit that asked for it without needing it. The
[systemd.io page](https://systemd.io/NETWORK_ONLINE/) is blunt about the
distinction. `network.target` means the network manager has started, and
"whether any network interfaces are already configured when it is reached is not
defined"; it matters mostly at shutdown. `network-online.target` actively waits
for a routable address, and it "will time out after 90s". If you really need the
network up, you need both lines:

```ini
[Unit]
Wants=network-online.target
After=network-online.target
```

`After=network-online.target` on its own is the section 3.3 bug again. If
nothing else pulls the target in, the ordering edge points at a job that isn't
there, and your service starts as early as it always did.

</Sub>

<Sub n="6.2" title="The journal is a socket, then a file">

A service's stdout and stderr are a Unix stream socket to journald. That's
why fd 1 and 2 showed up as `socket:[480492]` in section 3.2. journald reads
the peer's credentials and cgroup off that socket and stamps them on every line.
Those `_`-prefixed fields are *trusted*: the client can't forge them.

```shell
$ journalctl -u hello.service -o verbose -n 1
    _TRANSPORT=stdout
    _SYSTEMD_UNIT=hello.service
    _SYSTEMD_CGROUP=/system.slice/hello.service
    _PID=847
    _UID=61895
    _CAP_EFFECTIVE=0
    _SYSTEMD_INVOCATION_ID=e84a97bb23a44ec5be6cb9d03a26f215
    MESSAGE=LISTEN_PID=847 LISTEN_FDS=1 LISTEN_FDNAMES=hello.socket, my pid=847
```

`_SYSTEMD_INVOCATION_ID` changes on every start, so `journalctl
_SYSTEMD_INVOCATION_ID=...` gives you the logs of exactly one run of a
crash-looping service. It's also asynchronous: querying immediately
after my 50,000-line burst showed 8,363 lines, and the full 37,500 a few seconds
later. Don't assert on the journal in a test without waiting for it.

</Sub>

<Sub n="6.3" title="Hardening, and the score">

Every custom unit I'd written scored **9.6 UNSAFE** in `systemd-analyze
security`, the same as most units shipped by packages. systemd's own daemons sit
between 2.1 and 4.3. I added one drop-in to `hello.service`:

```ini
# /etc/systemd/system/hello.service.d/harden.conf
[Service]
DynamicUser=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
NoNewPrivileges=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6
RestrictNamespaces=yes
LockPersonality=yes
MemoryDenyWriteExecute=yes
SystemCallFilter=@system-service
SystemCallArchitectures=native
CapabilityBoundingSet=
```

```shell
$ systemd-analyze security hello.service | tail -1
→ Overall exposure level for hello.service: 2.0 OK :-)
$ ps -o user,pid,args -p 847
USER         PID COMMAND
hello        847 /usr/local/bin/echo-activated
$ grep -E "NoNewPrivs|Seccomp:|CapEff" /proc/847/status
CapEff:	0000000000000000
NoNewPrivs:	1
Seccomp:	2
$ nsenter -t 847 -m sh -c "touch /usr/x; touch /tmp/x && ls /tmp"
touch: cannot touch '/usr/x': Read-only file system
x
```

Same binary, unchanged. It now runs as a throwaway UID, with no capabilities,
a seccomp filter, a read-only `/usr`, and a `/tmp` nobody else can see. The
listening socket still works because PID 1 opened it before any of that applied.
That's the quiet advantage of socket activation: the service never needs the
privilege to bind port 443.

It isn't free at start time: the whole drop-in added about 9 ms to a cold
activation, and section 5.2 has the per-directive numbers. For a long-running
daemon that's nothing. For `Accept=yes`, which spawns per connection, it's the
whole budget.

</Sub>

<CardGrid>
  <WildCard name="Kubernetes kubelet — the systemd cgroup driver" verdict="If your nodes run systemd, the kubelet and the container runtime should both say cgroupDriver: systemd, and match.">
    The [container runtime docs](https://kubernetes.io/docs/setup/production-environment/container-runtimes/)

  </WildCard>
  <WildCard name="network.target vs network-online.target" verdict="Look for After=network-online.target without Wants=: it's in more vendor units than you'd hope.">
    The upstream [explanation](https://systemd.io/NETWORK_ONLINE/) exists
    because this is systemd's most-asked question. Services that bind
    `0.0.0.0` don't need either target. Services that connect to a remote

  </WildCard>
  <WildCard name="Fedora 38 — the shorter shutdown timer" verdict="A distro deciding that 90 seconds of silence on shutdown was worse than a core dump.">

  </WildCard>
  <WildCard name="CVE-2021-33910 — a long mount path" verdict="An unprivileged user could panic the machine with a FUSE mount.">

  </WildCard>
  <WildCard name="Restart=always without a limit" verdict="Still an open upstream issue: systemd doesn't warn you.">

<SectionHeading n="10" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What does PID 1 have to do that other processes don't?">
Reap orphaned children, since they're reparented to it, and install handlers
for any signal it wants to receive, because the kernel drops the rest. I ran
`sleep` as PID 1 in a container: five zombies after five orphaned children, and
`docker stop` took 10.16 s because `SIGTERM` was ignored until Docker sent
`SIGKILL`. With `--init` it stopped in 0.09 s.
</QA>

<QA level="beginner" q="What's the difference between Requires= and After=?">
`Requires=` pulls the other unit into the transaction and fails you if it
fails. `After=` only orders two jobs that are both already queued. With only
`Requires=`, both start in parallel; I measured an app seeing its database as
`activating`. With only `After=`, the database isn't started at all.
</QA>

<QA level="intermediate" q="Your unit has Requires= and After= on the database and still connects too early. Why?">
Check the database's `Type=`. With `Type=simple`, systemd calls it started as
soon as it's forked, so ordering after it waits for nothing. It needs
`Type=notify` and a `READY=1` once it can accept connections (or a
`Type=forking` daemon that only exits its parent when ready).
</QA>

<QA level="intermediate" q="How does a socket-activated service get its socket?">
PID 1 creates and binds the socket and holds it. On the first connection it
spawns the service; the executor dups the fd to 3, sets `LISTEN_PID` to the
child's own PID and `LISTEN_FDS` to the count, then execs. The service checks
the PID matches, so forked helpers don't also grab the fd, and accepts on fd 3.
</QA>

<QA level="intermediate" q="A service shows active (running) but users report errors every few seconds. What do you look at?">
`systemctl show -p NRestarts`. A crash cycle slower than 5 starts per 10 s
never trips the start limit, so the unit stays green. I had one at 10 restarts
in 32 s, `active` and absent from `systemctl --failed`. Then the journal for one
invocation with `_SYSTEMD_INVOCATION_ID=`.
</QA>

<QA level="deep" q="Why does KillMode=process exist, and why is it usually a mistake?">
It signals only the main PID, which sshd uses so restarting the daemon doesn't
kill live sessions. For most services it leaks children. They stay in the
unit's cgroup, and the next start logs "Found left-over process ... in control
group" and carries on with the old ones still there.
</QA>

<QA level="deep" q="Why is a memory-safety bug in systemd worse than one in a service?">
Because PID 1 exiting panics the kernel. CVE-2021-33910 was an `alloca` sized
by a mount path; a FUSE mount over 8 MB from an unprivileged user crashed PID 1
and the machine. CVE-2018-15686 was state injection through the text
serialization used on `daemon-reexec`, where an overlong line got split and
parsed as a new field.
</QA>

<QA level="deep" q="Why should kubelet use the systemd cgroup driver on a systemd host?">
Otherwise two things write to the cgroup tree with different views of it:
systemd for services, kubelet and the runtime via `cgroupfs` for pods. The
Kubernetes docs say such nodes can become unstable under resource pressure. With
the systemd driver, the runtime asks systemd to create a scope per container
under `kubepods.slice`, and there's one owner.
</QA>

<SectionHeading n="11" cmd="cat REFERENCES.md" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="You add After=network-online.target and the service still starts before the network is up. Why?">
    Nothing pulled the target into the transaction. Add Wants=network-online.target;
    After= only orders jobs that already exist.
  </Q>
  <Q q="Three units have Wants= and After= on each other in a cycle. What does systemctl start return?">
    Zero. systemd deletes one Wanted job to break the cycle and logs it. With
    Requires= it fails with "Transaction order is cyclic".
  </Q>
  <Q q="Why does sd_listen_fds check LISTEN_PID before anything else?">
    Environment is inherited. Without the check, a forked child of the service
    would also think fd 3 was its listening socket.
  </Q>
  <Q q="Your service logged 50,000 lines in a burst and 37,500 are in the journal. Bug?">
    Rate limiting. The 10,000 default burst is scaled by (log2(available) − 16) / 4,
    and the dropped lines are only reported when the service logs again.
  </Q>
</Quiz>
