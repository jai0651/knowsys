Every service you deploy to a Linux server is started, watched and stopped by
something. On most servers that something is systemd. The unit files that ship
with Postgres, nginx and Redis are systemd units, and Kubernetes' kubelet places
pods in the same cgroup tree systemd builds.

You mostly notice it when it surprises you. An app connects to its database
before the database can serve. A deploy hangs for a minute and a half on one
service. A service that crashes every few seconds shows green on every
dashboard for weeks.

This chapter starts from the simplest way to keep a program running and fixes
it one step at a time, up to PID 1. Then it covers units and jobs, the gap
between started and ready, one connection through socket activation, the ways
supervision fails, and what it all costs.

<SectionHeading n="01" id="why-supervisor">Why a service needs a supervisor</SectionHeading>

You've written a web service, and it runs fine when you start it by hand. Now
it has to live on a server. How do you keep it running?

<Sub n="1.1" title="Running it by hand, and the init script">

Everyone first tries `./server &` over ssh. It goes wrong in four
ways:

| What happens | Result |
|---|---|
| You log out | The shell's hangup signal may take the server with it |
| It crashes at 3am | It stays down |
| The machine reboots | Nothing starts it again |
| It writes output | The output goes to a terminal that no longer exists |

For decades the classic Unix answer was an init script. It started
the program, and the program **daemonized**: it forked, detached from the
terminal and let its parent exit. Then it wrote the program's PID to a file so that
"stop" could find it later.

<Why>What's wrong with a pidfile?</Why>

Nothing is watching. If the daemon crashes, nobody finds out.

And the pidfile holds a number, not a process. After a crash, that number can
belong to something else entirely by the time you try to kill it.

</Sub>

<Sub n="1.2" title="From pidfiles to supervisors">

What fixes it is a **supervisor**: a program that runs your service as its own
direct child, in the foreground. The kernel tells a parent whenever a child
exits, so the supervisor always knows when the service died, and can restart
it.

Supervision grew roughly in this order:

| System | Idea |
|---|---|
| **System V init** | Shell scripts that daemonize a program, write a pidfile and forget about it. Nothing notices a crash. |
| **daemontools** (Dan Bernstein, late 1990s) | `supervise` runs the program in the foreground as its direct child and restarts it on exit. Programs are told *not* to daemonize, so the supervisor always knows the PID. |
| **runit** (Gerrit Pape) | The daemontools idea, small enough to be PID 1. Void Linux uses it as init. |
| **Upstart** (Ubuntu, 2006) | Event-driven: jobs start when events fire. It tracked forking daemons by following `fork()` with ptrace, which was fragile. |
| **systemd** (Lennart Poettering and Kay Sievers, 2010) | Dependency-based, socket activation borrowed from inetd and launchd, and cgroups to track processes. |

systemd was announced in [Rethinking PID 1](http://0pointer.de/blog/projects/systemd.html),
April 2010. One line from that post matters most for this chapter is about
cgroups: "cgroup membership is securely inherited by child processes, they
cannot escape."

</Sub>

<Sub n="1.3" title="What systemd promises, and what it doesn't">

Everything systemd manages is a **unit**: a service, a socket, a mount, a
timer. Units declare dependencies, every service gets its own cgroup, and all
their output goes to one journal.

| systemd promises | systemd doesn't promise |
|---|---|
| Units start in an order consistent with their declared dependencies, computed as one transaction | That a unit reported **active** is ready to serve |
| Every process a service spawns is attributed to that service, however it forks | That `After=` pulls anything in |
| It restarts per the policy you wrote | That a service that keeps restarting is healthy |
| stdout and stderr reach the journal with trusted metadata | That every line you log is kept |

Each item in the right-hand column turns up in a transcript later in the
chapter.

</Sub>

<SectionHeading n="02" id="pid1">What PID 1 owes the kernel</SectionHeading>

Which raises the next question: who supervises the supervisor? At the top of
that chain is **PID 1**, the one process the kernel starts itself at boot.
Every other process descends from it.

PID 1 has two jobs the kernel won't do for anyone else, and a third rule that
makes its bugs expensive.

<Sub n="2.1" title="Reaping orphans">

When a process dies, its parent gets `SIGCHLD` and must `wait()` for it.
Until it does, the dead process stays in the process table as a **zombie**.

When the parent dies first, the orphan is reparented to init. So init has to
reap children it never started.

<Why>Why do zombies pile up in containers?</Why>

In a container, whatever your Dockerfile's `CMD` runs becomes PID 1 of its
namespace. If that program never calls `wait()`, every orphan it inherits
stays a zombie.

<Callout label="Why the zombies in that container never went away">
A zombie holds no memory, just a slot in the process table and an exit status
nobody collected. Each `docker exec sh -c 'sleep 0.1 & exit'` left one behind,
because the `sh` exited before its child, the child got reparented to `sleep`
(PID 1 in that namespace), and `sleep` never calls `wait()`. With `--init`,
PID 1 is `docker-init` (tini), a program whose entire purpose is to call
`wait()` in a loop and forward signals. That's the minimum viable init.
</Callout>

</Sub>

<Sub n="2.2" title="Signals only reach PID 1 through a handler">

The kernel won't deliver a signal to init unless init installed a handler for
it. [pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)
spells it out for namespaces: from inside, only signals with an established
handler reach PID 1. From an ancestor namespace, `SIGKILL` and `SIGSTOP` still
work.

<Why>Why does docker stop sometimes take ten seconds?</Why>

Because `docker stop` sends `SIGTERM` to PID 1 and waits out a grace period
before sending `SIGKILL`. If PID 1 has no `SIGTERM` handler, the first signal
is silently dropped, and all you see is the wait.

In a test with `sleep` as PID 1, then with `--init` in front of it:

| PID 1 | `docker stop` took | Zombies left |
|---|---|---|
| `sleep` (no `SIGTERM` handler, never calls `wait()`) | **10.16 s** | Five, from the processes spawned under it |
| `docker-init` (tini), via `--init` | **0.093 s** | None |

</Sub>

<Sub n="2.3" title="When init dies, the machine dies">

There's a third rule, stated less often. If PID 1 on the host exits or
crashes, the kernel panics.

So a crash in systemd isn't a service outage. It's a machine outage, and it's
why the CVEs in section 6.6 matter more than bugs in any one service.

</Sub>

<SectionHeading n="03" id="units">Units, jobs and the transaction</SectionHeading>

A **unit** is a named object loaded from a file: `foo.service`, `foo.socket`,
`foo.timer`, `home.mount`, `multi-user.target`, `system.slice`. It's written in INI
syntax. What systemd keeps in memory is a node in a graph.

<Sub n="3.1" title="Two kinds of edge">

Each unit node has two sets of edges, and the whole design depends on them
being separate:

<Compare
  cols={["Edge", "Question it answers", "Pulls the other unit in?", "Orders the start?"]}
  rows={[
    ["Wants=", "Should X start when I do?", "Yes", "No"],
    ["Requires=", "Should I fail if X fails to start?", "Yes", "No"],
    ["BindsTo=", "Should I stop whenever X stops?", "Yes", "No"],
    ["After= / Before=", "If both are starting, who waits?", "No", "Yes"],
  ]}
/>

Requirement and ordering are orthogonal. `Requires=db.service` without
`After=db.service` starts both **at the same time**. That's probably the most
expensive line in this chapter, and section 4.3 shows it with a transcript.

</Sub>

<Sub n="3.2" title="Jobs, and how one start becomes a plan">

You never start a unit directly. `systemctl start app` asks the manager to
enqueue a **job**: a (unit, type) pair like `app.service/start`. The manager
builds a <em className="term">transaction</em> around that anchor job before
anything runs.

    [5, "Only a consistent transaction is committed. `db.service/start` runs, and `app-good.service/start` sits `waiting` on its ordering edge."],
  ]}
/>

You can catch that last step mid-flight. Here `db.service` takes three seconds
to report ready, and `app-good.service` has `Requires=` and `After=` on it:

```shell
$ systemctl start --no-block app-good; sleep 0.3; systemctl list-jobs
JOB UNIT             TYPE  STATE
734 app-good.service start waiting
796 db.service       start running

2 jobs listed.
```

Two jobs, one `waiting` on an ordering edge, one `running`. Nothing in the unit
files mentioned "wait". That's the ordering graph at work.

</Sub>

<Sub n="3.3" title="What the engine does with a cycle">

What happens when the ordering graph has a loop? The test: three units,
`cyc-a` → `cyc-b` → `cyc-c` → `cyc-a`, each with `Wants=` and `After=` on the
next.

<Predict
  q="You run systemctl start cyc-a on those three units. What happens?"
  options={[
    "It fails with a non-zero exit code and starts nothing",
    "It succeeds; all three units end up active",
    "It succeeds; one or more units are silently left out",
    "systemctl hangs, waiting on the cycle forever",
  ]}
  answer={2}
>
systemd deletes a job to break the cycle, logs it, and starts the rest. The
exit code is zero. With `Wants=` edges, the dropped unit takes anything only it
wanted along with it.
</Predict>

```shell
$ systemctl start cyc-a; echo rc=$?
rc=0
$ journalctl -o cat | grep -A3 "ordering cycle"
cyc-a.service: Found ordering cycle on cyc-b.service/start
cyc-a.service: Found dependency on cyc-c.service/start
cyc-a.service: Found dependency on cyc-a.service/start
cyc-a.service: Job cyc-b.service/start deleted to break ordering cycle starting with cyc-a.service/start
$ systemctl is-active cyc-a cyc-b cyc-c
active
inactive
inactive
```

systemd dropped `cyc-b` from the start and carried on. `cyc-c` went with it,
because nothing else wanted it. Swap `Wants=` for `Requires=` and the same
start fails with `Transaction order is cyclic`.

<Why>How does it choose which job to drop?</Why>

Here's the loop that decides:

<SourceRead
  file="src/core/transaction.c — transaction_verify_order_one()"
  repo="systemd/systemd"
  tag="v255"
  href="https://github.com/systemd/systemd/blob/v255/src/core/transaction.c#L366-L392"
>
```c
/* Have we seen this before? */
if (j->generation == generation) {
        Job *k, *delete = NULL;
        ...
        /* So, the marker is not NULL and we already have been here. We have a cycle. Let's try to
         * break it. We go backwards in our path and try to find a suitable job to remove. */
        for (k = from; k; k = ((k->generation == generation && k->marker != k) ? k->marker : NULL)) {
                ...
                if (!delete && hashmap_contains(tr->jobs, k->unit) && !job_matters_to_anchor(k))
                        /* Ok, we can drop this one, so let's do so. */
                        delete = k;

                /* Check if this in fact was the beginning of the cycle */
                if (k == j)
                        break;
        }
```
</SourceRead>

`job_matters_to_anchor` is the whole policy. A job pulled in by `Requires=`
matters to the anchor, so it can't be dropped. A job pulled in by `Wants=`
doesn't, so the first one found walking back along the cycle gets deleted.

On a real machine that shows up as `SKIP` on the console at boot, and a service
that just isn't running afterwards.

</Sub>

<Why>Why does a cgroup beat a pidfile?</Why>

A `fork()` inherits the cgroup, and a double-fork doesn't escape it. So "which
processes belong to this service" is a directory listing, not a guess.

This is also what the Kubernetes kubelet leans on (section 12).

</Sub>

<SectionHeading n="04" id="readiness">Started versus ready</SectionHeading>

`After=` makes one job wait for another to be "started". What "started" means
is set by the dependency's `Type=`, and that setting decides whether `After=`
means anything at all.

<Sub n="4.1" title="What Type= means by started">

| `Type=` | The service counts as started when… | What that tells you |
|---|---|---|
| **`simple`** (the default) | The manager has forked the process. Before `execve`, even. | Nothing about the program |
| **`exec`** | `execve` succeeds | It catches a missing binary; nothing about readiness |
| **`forking`** | The original process exits, the old double-fork convention | Ready, if the daemon only exits its parent when ready. You'll usually want `PIDFile=` too. |
| **`notify`** | The process sends `READY=1` over the socket in `$NOTIFY_SOCKET` | Ready, because the service said so |

</Sub>

<Sub n="4.2" title="sd_notify by hand">

`sd_notify` is one `sendto()` of a datagram on a Unix socket. Here's a fake
database that takes three seconds to warm up:

```cpp
// notify-slow.cpp: Type=notify by hand
static void notify(const char* msg) {
    const char* path = getenv("NOTIFY_SOCKET");
    if (!path) return;
    int fd = socket(AF_UNIX, SOCK_DGRAM | SOCK_CLOEXEC, 0);
    sockaddr_un sa{};
    sa.sun_family = AF_UNIX;
    strncpy(sa.sun_path, path, sizeof sa.sun_path - 1);
    if (sa.sun_path[0] == '@') sa.sun_path[0] = '\0';   // abstract namespace
    sendto(fd, msg, strlen(msg), 0, (sockaddr*)&sa, sizeof sa);
    close(fd);
}

int main() {
    sleep(3);                                   // load a cache, open a DB...
    notify("READY=1\nSTATUS=serving");
    for (;;) pause();
}
```

What stops another process from sending `READY=1`? The notify socket has `SO_PASSCRED` set, so each message arrives with the
sender's PID. `service_notify_message_authorized()` in
[src/core/service.c](https://github.com/systemd/systemd/blob/v255/src/core/service.c#L4295)
checks it against `NotifyAccess=`, which for `Type=notify` defaults to the main
PID only. Messages from anyone else get logged and dropped.

</Sub>

<Sub n="4.3" title="Requires= without After=, and After= without Wants=">

That database ran twice in the test: as `db.service` with `Type=notify`, and as
`db-simple.service` with `Type=simple`. Then four one-shot "apps" printed the
database's state at the moment they ran:

```shell
app-bad:        Requires=db.service                          → "db is activating"   start took 0.02s
app-good:       Requires=db.service  After=db.service        → "db is active"       start took 3.03s
app-simple:     Requires=db-simple   After=db-simple         → "db-simple is active" start took 0.01s
app-after-only:                      After=db.service        → "db is inactive"
```

Four units, four different failures of intuition:

| Unit | What went wrong |
|---|---|
| **`app-bad`** | The bug everyone writes. `Requires=` pulled the database in, and with no ordering edge both jobs ran in parallel. The app ran while the database was still `activating`. |
| **`app-good`** | Correct. The 3.03 s is the database's warm-up, spent in the `waiting` state from section 3.2. |
| **`app-simple`** | Right dependencies, and it still loses. The database reported `active` 0.01 s after launch, three seconds before it could serve, because `Type=simple` defines "started" as "forked". |
| **`app-after-only`** | Didn't start the database at all. `After=` only orders jobs that are already in the transaction. |

<Callout label="Design implication">
`Wants=` or `Requires=` decides *whether*. `After=` decides *when*. You almost
always want both, and then `After=` only waits as long as the dependency's
`Type=` says it should. A `Type=simple` dependency is "ready" the instant it's
forked, so ordering after it buys you nothing. Services you write that others
depend on should be `Type=notify`.
</Callout>

</Sub>

<Sub n="4.4" title="network.target and network-online.target">

There's a famous special case of the same trap. The
[systemd.io page](https://systemd.io/NETWORK_ONLINE/) is blunt about the
distinction:

| Target | What reaching it means |
|---|---|
| `network.target` | The network manager has started. "Whether any network interfaces are already configured when it is reached is not defined." It matters mostly at shutdown. |
| `network-online.target` | Actively waits for a routable address, and "will time out after 90s". |

If you really need the network up, you need both lines:

```ini
[Unit]
Wants=network-online.target
After=network-online.target
```

<Callout label="Common mistake" kind="warn">
`After=network-online.target` on its own. If nothing else pulls the target in,
the ordering edge points at a job that isn't there, and your service starts as
early as it always did. It's the `app-after-only` bug with a more convincing
name.
</Callout>

</Sub>

<SectionHeading n="05" id="socket-activation">Socket activation, one connection at a time</SectionHeading>

Here's the operation to trace. A TCP connection arrives on a port where no
service process is running yet. What has to happen between the SYN and the
service's `accept()` returning?

<Sub n="5.1" title="The fd that PID 1 was holding">

A socket unit here is four lines, and the service unit is two:

```ini
# /etc/systemd/system/hello.socket
[Socket]
ListenStream=127.0.0.1:7777

# /etc/systemd/system/hello.service
[Service]
ExecStart=/usr/local/bin/echo-activated
```

After `systemctl start hello.socket`, the service isn't running, and the
listening socket belongs to PID 1:

```shell
$ systemctl is-active hello.service; ss -ltnp | grep 7777
inactive
LISTEN 0  4096  127.0.0.1:7777  0.0.0.0:*  users:(("systemd",pid=1,fd=47))
```

So the first client isn't refused: the kernel completes the handshake into that socket's backlog whether
or not anyone is accepting. As far as the client knows, it's connected and just
waiting for bytes.

</Sub>

<Sub n="5.2" title="From fd 47 to fd 3">

systemd 255 changed how children are spawned. Earlier versions forked PID 1 and
did all the sandbox setup in the child. The [v255 NEWS](https://github.com/systemd/systemd/blob/v255/NEWS)
explains that this ran glibc code that isn't safe between `fork` and `exec`.

From v255, "the new process is spawned using CLONE_VM and CLONE_VFORK semantics
via posix_spawn(3), and it immediately execs a new internal binary,
systemd-executor". Step through one cold connection:

<Sub n="5.3" title="LISTEN_PID, and the protocol by hand">

<Why>Why pass LISTEN_PID at all?</Why>

Environment variables are inherited. If your service runs a shell script that
forks a helper, the helper sees `LISTEN_FDS=1` too. Without the PID check it'd
start calling `accept()` on an fd it doesn't own.

`getpid_cached()` runs in the executor, the same process that execs the
service, so the PID matches. On the library side, it's the first thing
checked:

<SourceRead
  file="src/libsystemd/sd-daemon/sd-daemon.c — sd_listen_fds()"
  repo="systemd/systemd"
  tag="v255"
  href="https://github.com/systemd/systemd/blob/v255/src/libsystemd/sd-daemon/sd-daemon.c#L42-L90"
>
```c
_public_ int sd_listen_fds(int unset_environment) {
        ...
        e = getenv("LISTEN_PID");
        if (!e) { r = 0; goto finish; }

        r = parse_pid(e, &pid);
        if (r < 0)
                goto finish;

        /* Is this for us? */
        if (getpid_cached() != pid) { r = 0; goto finish; }

        e = getenv("LISTEN_FDS");
        ...
        for (int fd = SD_LISTEN_FDS_START; fd < SD_LISTEN_FDS_START + n; fd ++) {
                r = fd_cloexec(fd, true);
                if (r < 0)
                        goto finish;
        }
        r = n;
finish:
        unsetenv_all(unset_environment);
        return r;
}
```
</SourceRead>

Note the `fd_cloexec` loop. The fds arrive *without* close-on-exec, because
they had to survive one `execve`. `sd_listen_fds` turns it back on so they don't
survive a second.

It's a small enough protocol to do by hand, in C++ with no libsystemd:

<TryIt what="A socket-activated server that reads the protocol itself" lang="cpp" toolchain="g++ 13.3 -O2, Ubuntu 24.04 in Docker, aarch64">
```cpp
#include <cstdio>
#include <cstdlib>
#include <string>
#include <unistd.h>
#include <sys/socket.h>

int main() {
    const char* pid = getenv("LISTEN_PID");
    const char* n   = getenv("LISTEN_FDS");
    const char* nm  = getenv("LISTEN_FDNAMES");
    if (!pid || !n || atoi(pid) != getpid()) {
        fprintf(stderr, "not socket-activated\n");
        return 1;
    }
    int listen_fd = 3;                      // SD_LISTEN_FDS_START
    fprintf(stderr, "LISTEN_PID=%s LISTEN_FDS=%s LISTEN_FDNAMES=%s, my pid=%d\n",
            pid, n, nm ? nm : "-", getpid());
    for (;;) {
        int c = accept(listen_fd, nullptr, nullptr);
        if (c < 0) { perror("accept"); return 1; }
        std::string msg = "hello from pid " + std::to_string(getpid()) + "\n";
        (void)!write(c, msg.data(), msg.size());
        close(c);
    }
}
```

```shell
$ nc -q1 127.0.0.1 7777 </dev/null
hello from pid 177
$ journalctl -u hello.service -o cat
Started hello.service.
LISTEN_PID=177 LISTEN_FDS=1 LISTEN_FDNAMES=hello.socket, my pid=177
$ ls -l /proc/177/fd | grep -E " [0-3] "
lr-x------ 1 root root 64 Sep 25 13:06 0 -> /dev/null
lrwx------ 1 root root 64 Sep 25 13:06 1 -> socket:[480492]
lrwx------ 1 root root 64 Sep 25 13:06 2 -> socket:[480492]
lrwx------ 1 root root 64 Sep 25 13:06 3 -> socket:[482356]
```

<Output>
First connection: it started the service and was served by it. Fd 3 is the
listening socket PID 1 had been holding. Fds 1 and 2 are a socket too, a stream
connection to journald (section 8.2).

Then the service got `kill -9`. It went `failed`, the socket stayed up, and the
next `nc` started a fresh instance, PID 206, with no refused connection in
between. The listening socket never closed, because the process that owned it
was never the one that died.
</Output>
</TryIt>

<Callout label="Design implication">
Socket activation separates owning the port from serving it. Restarts and
crashes don't refuse connections, and because PID 1 binds the socket, the
service never needs the privilege to bind port 443 (section 8.3 takes every
other privilege away too). The one exception is section 6.2.
</Callout>

</Sub>

<SectionHeading n="06" id="failure">How supervision fails</SectionHeading>

A supervisor restarts what dies and stops what it's told to. Each of those has
a failure mode that looks like success from the outside.

<Callout label="Common mistake" kind="warn">
Alerting on `ActiveState`. Alert on `NRestarts`. It survives `daemon-reload`
(it's serialized with the rest of the unit's state) and resets on the next
manual start or a `systemctl reset-failed`.
</Callout>

</Sub>

<Sub n="6.2" title="The socket that dies with its service">

This one turned up by accident. A cold-start benchmark stopped `hello.service`
thirty times in a tight loop, so each connection would trigger a fresh start.
Partway through, connections started getting refused:

```shell
hello.service: Start request repeated too quickly.
hello.service: Failed with result 'start-limit-hit'.
Failed to start hello.service.
hello.socket: Failed with result 'service-start-limit-hit'.
```

When the service hits its start limit, the socket unit goes down with it and
**closes the listening socket**.

<Why>Doesn't lifting the service's limit fix it?</Why>

No. With `StartLimitIntervalSec=0` on the service, the socket hit its own,
separate limit (`TriggerLimitBurst=20` per `TriggerLimitIntervalSec=2s`) and
failed with `trigger-limit-hit`.

Either way, the port now refuses connections, which is what socket activation
was supposed to prevent. A crash-looping socket-activated service turns from
"slow" into "down" at the sixth crash.

</Sub>

<Why>Why does one stubborn service slow the whole shutdown?</Why>

At shutdown, units stop in reverse dependency order. One stubborn service

Fedora 38 accepted a [change](https://fedoraproject.org/wiki/Changes/Shorter_Shutdown_Timer)

too: a core of the thing that wouldn't stop tells you why.

</Sub>

<Sub n="6.4" title="KillMode and the processes left behind">

`KillMode=` decides who gets the stop signal:

| `KillMode=` | Signals | Children after stop |
|---|---|---|
| `control-group` (the default) | Every process in the cgroup | All dead, even ones that called `setsid` |
| `process` | Only the main PID | Alive, and **still in the service's cgroup** |

A test service started two `setsid` background children, in both modes:

```shell
$ systemd-cgls -u system.slice | grep -A3 forker-process
├─forker-process.service
│ ├─614 sleep 1000
│ ├─616 sleep 1001
│ └─617 sleep 1002
$ systemctl stop forker-control-group forker-process
$ ps -eo pid,ppid,args | grep "sleep 100"
    616       1 sleep 1001
    617       1 sleep 1002
$ cat /proc/617/cgroup
0::/docker/990fb6a9.../system.slice/forker-process.service
```

Starting the process-mode unit again gave:

```shell
forker-process.service: Found left-over process 616 (sleep) in control group while starting unit. Ignoring.
forker-process.service: Found left-over process 617 (sleep) in control group while starting unit. Ignoring.
```

Five processes in the unit now, two of them from the last run. Some units ship
`KillMode=process` on purpose (sshd, so a restart doesn't kill your login
sessions), but most other uses are probably a leak.

</Sub>

<Sub n="6.5" title="The watchdog">

`WatchdogSec=2` puts `WATCHDOG_USEC=2000000` in the environment and expects
`WATCHDOG=1` over the notify socket more often than that. The test program
pinged every second, six times, then pretended to deadlock:

```shell
[27477.808096] wd[732]: deadlocked (pretend)
[27479.905676] systemd[1]: wd.service: Watchdog timeout (limit 2s)!
[27479.905749] systemd[1]: wd.service: Killing process 732 (wd) with signal SIGABRT.
[27479.905950] systemd[1]: wd.service: Failed with result 'watchdog'.
[27480.143467] systemd[1]: wd.service: Scheduled restart job, restart counter is at 1.
```

It sends `SIGABRT`, not `SIGTERM`, so you get a core of the stuck state.

Where you put the ping matters more than the interval. Sent from a dedicated timer
thread, it proves the process is alive and nothing more. Sent from the event
loop after real work, it proves the event loop isn't wedged, and that's
probably what you care about.

</Sub>

<Sub n="6.6" title="When PID 1 is the thing that breaks">

A bug in a service kills that service. A bug in PID 1 panics the kernel, and
PID 1 parses input unprivileged users can influence.

| CVE | What reached PID 1 | What went wrong |
|---|---|---|
| **[CVE-2021-33910](https://www.qualys.com/2021/07/20/cve-2021-33910/denial-of-service-systemd.txt)** (Qualys, July 2021) | A mount path over 8 MB (the default stack limit), mounted by an unprivileged user via FUSE | systemd reads `/proc/self/mountinfo` and escapes each path with `unit_name_path_escape()`, which used `strdupa()`, an `alloca()` on the stack. PID 1 crashed, and the machine with it. Qualys traced it to v220, April 2015, where a heap `strdup()` became `strdupa()`. |
| **[CVE-2018-15686](https://ubuntu.com/security/notices/USN-3816-1)** (Jann Horn, Google Project Zero) | An overlong status line written through `NotifyAccess` | Across `daemon-reexec`, systemd serializes its state to a text file and reads it back with `fgets()` and a fixed buffer. The line got split, and the second half was parsed as a fresh serialized field: state injection into PID 1, with a path to root. Versions up to 239 were affected. |

Both are roughly the same shape. Attacker-controlled bytes, a mount path or a
status string, reached code in PID 1 that assumed a size bound.

</Sub>

Most of that time goes into the client. Supervision adds about a millisecond of manager work

instance per connection, inetd style) does exactly that.

</Sub>

<Sub n="7.2" title="The journald burst that wasn't 10,000">

journald's default rate limit is `RateLimitBurst=10000` per
`RateLimitIntervalSec=30s`, per service. A test service printed 50,000 lines as
fast as Python could, and **37,500** made it in.

Where does 37,500 come from? The burst is scaled by free disk space, in
[journald-rate-limit.c](https://github.com/systemd/systemd/blob/v255/src/journal/journald-rate-limit.c#L159-L185):

```c
k = log2u64(available);
if (k <= 20)            /* 1MB */
        return burst;
burst = (burst * (k-16)) / 4;
```

<Estimate
  rows={[
    { label: "Lines kept", math: "measured", value: "37,500" },
    { label: "Solve for k", math: "10,000 × (k − 16) / 4 = 37,500", value: "k = 31" },
    { label: "So journald saw 'available' as", math: "2^31 ≤ available < 2^32", value: "2–4 GiB" },
    { label: "Disk actually free", math: "df /var/log/journal", value: "402 GB" },
  ]}
  result={{ label: "Consistent with 'available' being journald's own size cap, not the disk", value: "k = 31" }}
/>

Yet the disk had 402 GB free, which would give k = 38 and a burst of 55,000. The
likeliest reading is that "available" is measured against journald's
`SystemMaxUse=` budget (10% of the filesystem, capped at 4 GiB) minus what's
used, which lands just under 2^32. That's checked against the arithmetic, not
the code path.

Nothing said lines were dropped, because the report is deferred. A `Suppressed 62502 messages from
chatty.service` line only appeared when the service logged again, after the
window. It counted this run's 12,500 plus all 50,002 lines of a second run
started inside the same 30 s.

</Sub>

The first measurement of hardening said it cost about **28 ms** per cold start:

<Sub n="8.1" title="Seeing where boot time goes">

On a real server the usual top of that chain is `network-online.target`, and

</Sub>

<Sub n="8.2" title="The journal is a socket, then a file">

A service's stdout and stderr are a Unix stream socket to journald. That's why
fds 1 and 2 showed up as `socket:[480492]` in section 5.3.

journald reads the peer's credentials and cgroup off that socket and stamps
them on every line. Those `_`-prefixed fields are *trusted*: the client can't
forge them.

```shell
$ journalctl -u hello.service -o verbose -n 1
    _TRANSPORT=stdout
    _SYSTEMD_UNIT=hello.service
    _SYSTEMD_CGROUP=/system.slice/hello.service
    _PID=847
    _UID=61895
    _CAP_EFFECTIVE=0
    _SYSTEMD_INVOCATION_ID=e84a97bb23a44ec5be6cb9d03a26f215
    MESSAGE=LISTEN_PID=847 LISTEN_FDS=1 LISTEN_FDNAMES=hello.socket, my pid=847
```

`_SYSTEMD_INVOCATION_ID` changes on every start, so `journalctl
_SYSTEMD_INVOCATION_ID=...` gives you the logs of exactly one run of a
crash-looping service.

It's also asynchronous. Querying immediately after the 50,000-line
burst showed 8,363 lines, and the full 37,500 a few seconds later. Don't
assert on the journal in a test without waiting for it.

</Sub>

<Sub n="8.3" title="Hardening, and the score">

Every custom unit written for this chapter scored **9.6 UNSAFE** in
`systemd-analyze security`, the same as most units shipped by packages.
systemd's own daemons sit between 2.1 and 4.3. One drop-in for
`hello.service`:

```ini

```

```shell

$ ps -o user,pid,args -p 847

hello        847 /usr/local/bin/echo-activated

```

Same binary, unchanged. It now runs as a throwaway UID, with no capabilities, a
seccomp filter, a read-only `/usr`, and a `/tmp` nobody else can see.

The listening socket still works because PID 1 opened it before any of that
applied. That's the quiet advantage of socket activation: the service never
needs the privilege to bind port 443.

It isn't free at start time. All of it together added about 9 ms to a cold
activation (section 7.3 has the per-directive numbers). For a long-running
daemon that's nothing. For `Accept=yes`, which spawns per connection, it's the
whole budget.

</Sub>

<Sub n="8.4" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| `active (running)`, but users see errors every few seconds | A crash cycle slower than 5 starts per 10 s | Alert on `NRestarts`; read one run with `_SYSTEMD_INVOCATION_ID=` |
| App connects to its database before it's ready | `Requires=` without `After=`, or a `Type=simple` database | Add `After=`; make the database `Type=notify` |
| Service starts before the network is up | `After=network-online.target` without `Wants=` | Add both lines, or retry the connection |
| A unit silently isn't running after boot | A `Wants=` ordering cycle broken by deleting its job | `journalctl` for "ordering cycle"; remove one edge |
| `systemctl stop` or shutdown takes 90 s | The service ignores `SIGTERM` | Handle `SIGTERM`; `TimeoutStopFailureMode=abort` for a core |
| `docker stop` takes 10 s | PID 1 has no `SIGTERM` handler | Install one, or run with `--init` |
| A socket-activated port refuses connections | The service hit its start limit and took the socket down | Fix the crash loop; check the socket unit's `Result` |
| "Found left-over process" on start | `KillMode=process` | Use the default, `control-group` |
| Log lines missing after a burst | journald's rate limit | Look for `Suppressed N messages`; raise `RateLimitBurst=` |

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **A supervisor runs your service as its direct child.** The kernel tells a
   parent when a child exits, which a pidfile never could.
2. **PID 1 must reap orphans and handle signals deliberately.** Without a
   handler, `SIGTERM` to PID 1 is dropped: 10.16 s to `docker stop` with
   `sleep` as PID 1, 0.093 s with `--init`.
3. **If PID 1 dies, the kernel panics.** A bug in systemd is a machine outage.
4. **Requirement and ordering are separate edges.** `Wants=` or `Requires=`
   decides whether, `After=` decides when, and you almost always want both.
5. **A `Wants=` cycle doesn't fail the start.** systemd deletes a job, logs it
   and exits zero.
6. **Started is not ready.** `Type=simple` counts as started once forked; only
   `Type=notify` waits for the service to say `READY=1`.
7. **Socket activation separates the port from the process.** PID 1 holds the
   listening fd, hands it over as fd 3, and a crash refuses no connections,
   until the start limit closes the socket.
8. **A slow crash loop never trips the start limit.** Alert on `NRestarts`, not
   `ActiveState`.
9. **Ignoring `SIGTERM` costs 90 seconds per stop** under the defaults, and
   blocks shutdown behind it.
10. **Supervision costs about a millisecond per start; full hardening about
    9 ms more.** The seccomp filter is the largest single part.

<SectionHeading n="10" id="build">Build this</SectionHeading>

**A socket-activated, `Type=notify`, watchdog-supervised service in about 80
lines of C++, with no libsystemd.**

- Take the `LISTEN_FDS` server from section 5.3 and add the `notify()` helper
  from 4.2. Send `READY=1` after your setup and `WATCHDOG=1` from the accept
  loop, not from a timer thread.
- Run systemd as PID 1 to test it:
  `docker run -d --privileged --cgroupns=host -v /sys/fs/cgroup:/sys/fs/cgroup:rw --tmpfs /run ubuntu-with-systemd /lib/systemd/systemd`
  (install `systemd` in `ubuntu:24.04` first).
- Kill it with `-9` under a steady stream of `nc` connections and count refused
  ones. There should be none.
- Then crash-loop it on purpose and find the connection that gets refused. It's
  the one after the start limit.
- Add the hardening drop-in from 8.3 and time cold activation with and without
  each line. Then add a 150 ms sleep before each connection and watch it get ten
  times slower. If you can say why, you've answered the question section 7.3
  couldn't.

<SectionHeading n="12" id="in-the-wild">Where you meet this in the wild</SectionHeading>

<CardGrid>
  <WildCard name="Kubernetes kubelet — the systemd cgroup driver" verdict="If your nodes run systemd, the kubelet and the container runtime should both say cgroupDriver: systemd, and match.">
    The [container runtime docs](https://kubernetes.io/docs/setup/production-environment/container-runtimes/)
    warn that `cgroupfs` alongside systemd gives "two views of the available and
    in-use resources", and that such nodes can "become unstable under resource
    pressure". With the systemd driver, pods live under `kubepods.slice` and the
    runtime asks systemd over D-Bus to create a scope per container, so there's
    one manager. kubeadm has defaulted to it since
    [v1.22](https://github.com/kubernetes/kubernetes/pull/99471).
  </WildCard>
  <WildCard name="network.target vs network-online.target" verdict="Look for After=network-online.target without Wants=: it's in more vendor units than you'd hope.">
    The upstream [explanation](https://systemd.io/NETWORK_ONLINE/) exists
    because this is systemd's most-asked question. Services that bind
    `0.0.0.0` don't need either target. Services that connect to a remote
    database at startup need both lines, or better, retry.
  </WildCard>
  <WildCard name="Fedora 38 — the shorter shutdown timer" verdict="A distro deciding that 90 seconds of silence on shutdown was worse than a core dump.">
    The accepted [change](https://fedoraproject.org/wiki/Changes/Shorter_Shutdown_Timer)
    cut the stop timeout to 45 s and used `TimeoutStopFailureMode=abort`, so a
    service that won't stop produces a core instead of a wait. Concerns in the
    discussion included libvirt needing time to shut VMs down.
  </WildCard>
  <WildCard name="CVE-2021-33910 — a long mount path" verdict="An unprivileged user could panic the machine with a FUSE mount.">
    Qualys' [advisory](https://www.qualys.com/2021/07/20/cve-2021-33910/denial-of-service-systemd.txt)
    traces it to a 2015 commit that swapped a heap `strdup()` for a stack
    `strdupa()` in `unit_name_path_escape()`. Every mount the kernel reports
    goes through PID 1.
  </WildCard>
  <WildCard name="Restart=always without a limit" verdict="Still an open upstream issue: systemd doesn't warn you.">
    [systemd #30804](https://github.com/systemd/systemd/issues/30804) asks for a
    warning on units that restart forever, citing gdm3, lightdm and openssh.
    v254 added `RestartSteps=` and `RestartMaxDelaySec=` for exponential
    backoff, per the [NEWS](https://github.com/systemd/systemd/blob/v255/NEWS).
  </WildCard>
</CardGrid>

<SectionHeading n="13" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What does PID 1 have to do that other processes don't?">
Reap orphaned children, since they're reparented to it, and install handlers
for any signal it wants to receive, because the kernel drops the rest. With
`sleep` as PID 1 in a container: five zombies after five orphaned children, and
`docker stop` took 10.16 s because `SIGTERM` was ignored until Docker sent
`SIGKILL`. With `--init` it stopped in 0.09 s.
</QA>

<QA level="beginner" q="What's the difference between Requires= and After=?">
`Requires=` pulls the other unit into the transaction and fails you if it
fails. `After=` only orders two jobs that are both already queued. With only
`Requires=`, both start in parallel; in the test, the app saw its database as
`activating`. With only `After=`, the database isn't started at all.
</QA>

<QA level="intermediate" q="Your unit has Requires= and After= on the database and still connects too early. Why?">
Check the database's `Type=`. With `Type=simple`, systemd calls it started as
soon as it's forked, so ordering after it waits for nothing. It needs
`Type=notify` and a `READY=1` once it can accept connections (or a
`Type=forking` daemon that only exits its parent when ready).
</QA>

<QA level="intermediate" q="How does a socket-activated service get its socket?">
PID 1 creates and binds the socket and holds it. On the first connection it
spawns the service; the executor dups the fd to 3, sets `LISTEN_PID` to the
child's own PID and `LISTEN_FDS` to the count, then execs. The service checks
the PID matches, so forked helpers don't also grab the fd, and accepts on fd 3.
</QA>

<QA level="intermediate" q="A service shows active (running) but users report errors every few seconds. What do you look at?">
`systemctl show -p NRestarts`. A crash cycle slower than 5 starts per 10 s
never trips the start limit, so the unit stays green. In the test, one reached
10 restarts in 32 s, `active` and absent from `systemctl --failed`. Then the
journal for one invocation with `_SYSTEMD_INVOCATION_ID=`.
</QA>

<QA level="deep" q="Why does KillMode=process exist, and why is it usually a mistake?">
It signals only the main PID, which sshd uses so restarting the daemon doesn't
kill live sessions. For most services it leaks children. They stay in the
unit's cgroup, and the next start logs "Found left-over process ... in control
group" and carries on with the old ones still there.
</QA>

<QA level="deep" q="Why is a memory-safety bug in systemd worse than one in a service?">
Because PID 1 exiting panics the kernel. CVE-2021-33910 was an `alloca` sized
by a mount path; a FUSE mount over 8 MB from an unprivileged user crashed PID 1
and the machine. CVE-2018-15686 was state injection through the text
serialization used on `daemon-reexec`, where an overlong line got split and
parsed as a new field.
</QA>

<QA level="deep" q="Why should kubelet use the systemd cgroup driver on a systemd host?">
Otherwise two things write to the cgroup tree with different views of it:
systemd for services, kubelet and the runtime via `cgroupfs` for pods. The
Kubernetes docs say such nodes can become unstable under resource pressure. With
the systemd driver, the runtime asks systemd to create a scope per container
under `kubepods.slice`, and there's one owner.
</QA>

<SectionHeading n="14" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="You add After=network-online.target and the service still starts before the network is up. Why?">
    Nothing pulled the target into the transaction. Add Wants=network-online.target;
    After= only orders jobs that already exist.
  </Q>
  <Q q="Three units have Wants= and After= on each other in a cycle. What does systemctl start return?">
    Zero. systemd deletes one Wanted job to break the cycle and logs it. With
    Requires= it fails with "Transaction order is cyclic".
  </Q>
  <Q q="Why does sd_listen_fds check LISTEN_PID before anything else?">
    Environment is inherited. Without the check, a forked child of the service
    would also think fd 3 was its listening socket.
  </Q>
  <Q q="Your service logged 50,000 lines in a burst and 37,500 are in the journal. Bug?">
    Rate limiting. The 10,000 default burst is scaled by (log2(available) − 16) / 4,
    and the dropped lines are only reported when the service logs again.
  </Q>
</Quiz>
