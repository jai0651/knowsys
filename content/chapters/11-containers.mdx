You meet containers far more often than you type `docker run`. Every
Kubernetes pod is one, set up by runc. Every systemd service gets its own
cgroup, and `PrivateTmp=` is a mount namespace. Chrome's sandbox on Linux uses
PID, network and user namespaces.

When a container misbehaves, the symptoms look like magic: exit code 137 with
nothing in the logs, a `docker stop` that always takes ten seconds, a first
request that takes four. Each one has a plain cause in a kernel mechanism you
can read and poke.

This chapter takes the magic apart. It builds a container by hand with
`unshare`, `pivot_root`, overlayfs, a veth pair and a cgroup, then again in 98
lines of C, and compares both with what runc does. Then it covers what breaks,
what each layer costs, and how to look inside a running one.

<SectionHeading n="01" id="what-a-container-is">What a container is</SectionHeading>

Suppose you have one Linux machine and two applications to run on it. One needs
Python 3.8 and an old OpenSSL, the other needs Python 3.12. Both want to listen
on port 8080. One leaks memory, and you'd rather it didn't take the other down.
And neither should be able to see, or kill, the other's processes.

The heavyweight answer is a virtual machine each, with its own kernel and its
own slice of RAM. That works, and [chapter 47](/topics/47-virtualization)
covers it. But it's a lot of machinery for what is really a problem of
*perception*.

<Why>What would you change about one process so it believes it's alone?</Why>

Go through it one thing at a time. It sees files, so give it a different root
directory, with its own `/usr` and its own Python. It sees other processes, so
give it a process list in which it's PID 1 and nothing else exists.

It sees network interfaces and ports, so give it its own set, with its own port
8080. It sees a hostname, so give it its own. Linux has a mechanism for each of
these, and together with two more pieces they're all a container is.

| Piece | What it controls | Kernel feature |
|---|---|---|
| **Namespaces** | What the process can *see* | `clone(2)` / `unshare(2)` with `CLONE_NEW*` flags |
| **A cgroup** | What it can *use* | Files under `/sys/fs/cgroup` |
| **A layered root filesystem** | Which files it has | overlayfs, plus `pivot_root` |

<Sub n="1.1" title="Namespaces: a separate view">

A **namespace** is a separate view of one kind of kernel object, such as the
mount table, the process IDs or the network stack. A process can be in a
different one of each kind.

| Namespace | What it hides |
|---|---|
| **pid** | Process IDs. Its first process becomes PID 1 and can't see its parent. |
| **mnt** | The mount table. This is what makes a different `/` possible. |
| **uts** | Hostname and domain name. Tiny, and roughly the one every tutorial starts with. |
| **ipc** | System V semaphores, message queues and shared memory. |
| **net** | Interfaces, routes, iptables rules, sockets, the port space. |
| **user** | UID and GID mappings, and which capabilities mean anything. |
| **cgroup** | Which part of the cgroup tree looks like the root. |

There's an eighth, the `time` namespace (Linux 5.6), which almost nobody uses.
So there are seven or eight kinds, depending how you count.

Docker doesn't create `user` or `time` namespaces by default. User
namespace remapping is [opt-in](https://docs.docker.com/engine/security/userns-remap/).

</Sub>

<Sub n="1.2" title="cgroups: a budget">

Namespaces handle what a process can see. What it can *use* is a separate
problem, and the answer is a **cgroup**.

cgroups v2 is a tree of directories under `/sys/fs/cgroup`, whose files set
limits for the processes in them. Write `64M` into `memory.max` and the kernel
will reclaim memory, and then OOM-kill something, before that subtree's usage
passes 64 MiB. The leaky application can now only hurt itself.

</Sub>

<Sub n="1.3" title="overlayfs: a layered root">

The last piece is the files. Shipping a full root filesystem per application
would be wasteful when most of them share a base image.

So images are stacked in layers with **overlayfs**: read-only layers
underneath, one writable layer on top, merged into a single view. Section 2.2
shows what that looks like on disk.

</Sub>

<Sub n="1.4" title="What's missing: a second kernel">

Notice what isn't on the list. Every container on a host makes its syscalls
into the same kernel, with the same scheduler, the same page cache and the same
bugs.

<Why>Why does sharing the kernel matter so much?</Why>

It's what makes containers cheap: `unshare` with six namespaces starts in about
0.76 ms (section 5.2). It's also what makes them weaker. A kernel bug reachable
from one container is reachable from all of them.

<Callout label="Design implication">
A container isn't a security boundary in the sense a VM is. A VM gives the
guest its own kernel and exposes a small emulated device interface to the host.
A container exposes the host kernel's entire syscall surface, filtered by
seccomp, capabilities and LSMs. That's why Firecracker, gVisor and Kata exist,
why AWS runs Lambda functions in Firecracker microVMs instead of plain
containers, and why [chapter 47](/topics/47-virtualization) is a separate
chapter.
</Callout>

</Sub>

<SectionHeading n="02" id="kernel-layout">How the kernel stores it</SectionHeading>

Each of the three pieces has a concrete home: a struct of pointers in the
kernel, directories on disk, and a tree of files under `/sys/fs/cgroup`.

<Sub n="2.1" title="A struct of pointers">

A task's namespaces live in one `struct nsproxy`, and `unshare(2)` or
`clone(2)` with `CLONE_NEW*` flags builds a new one. Here's the function that
does it, at the tag matching the kernel used here (the `//` comments are
added):

<SourceRead

  tag="v6.10"
  href="https://github.com/torvalds/linux/blob/v6.10/kernel/nsproxy.c#L67"
>
```c
static struct nsproxy *create_new_namespaces(unsigned long flags,
	struct task_struct *tsk, struct user_namespace *user_ns,
	struct fs_struct *new_fs)
{
	new_nsp = create_nsproxy();
	// each copy_*() takes a reference on the old namespace, or allocates
	// a new one if its CLONE_NEW* bit is set in flags
	new_nsp->mnt_ns = copy_mnt_ns(flags, tsk->nsproxy->mnt_ns, user_ns, new_fs);
	new_nsp->uts_ns = copy_utsname(flags, user_ns, tsk->nsproxy->uts_ns);
	new_nsp->ipc_ns = copy_ipcs(flags, user_ns, tsk->nsproxy->ipc_ns);
	new_nsp->pid_ns_for_children =
		copy_pid_ns(flags, user_ns, tsk->nsproxy->pid_ns_for_children);
	new_nsp->cgroup_ns = copy_cgroup_ns(flags, user_ns,
					    tsk->nsproxy->cgroup_ns);
	new_nsp->net_ns = copy_net_ns(flags, user_ns, tsk->nsproxy->net_ns);
	new_nsp->time_ns_for_children = copy_time_ns(flags, user_ns,
					tsk->nsproxy->time_ns_for_children);
	// error unwinding elided
	return new_nsp;
}
```
</SourceRead>

Two details in there are easy to miss.

There's no `user_ns` field. The user namespace hangs off the task's
credentials, not the nsproxy, and it's passed *in* as the owner of every
namespace created here.

And the PID field is called `pid_ns_for_children`, because unsharing a PID namespace doesn't move you. It changes where your next
child lands, and that child becomes PID 1. That's why `unshare --pid` needs
`--fork`.

</Sub>

<Sub n="2.2" title="On disk: lower, upper, work">

A container's filesystem is an **overlayfs** mount with three directories:

| Directory | Role |
|---|---|
| `lowerdir` | The image, read-only |
| `upperdir` | Where every write goes |
| `workdir` | Scratch space the kernel needs for atomic renames |

Deleting a file that exists only in the read-only lower layer is impossible, so overlayfs writes a **whiteout** instead: a character device with
device number 0,0 in the upper layer that hides the lower file.

```shell
$ rm /ks/merged/etc/motd
$ stat -c "%n %F %t,%T" /ks/upper/etc/motd
/ks/upper/etc/motd character special file 0,0
$ ls /ks/lower/etc/motd
/ks/lower/etc/motd           # still there, just hidden
```

That's what a Docker image layer is on disk: a directory of files plus
whiteouts, stacked. Nothing more exotic.

</Sub>

<SectionHeading n="03" id="by-hand">Building one by hand</SectionHeading>

The transcripts in this section come from a privileged Ubuntu 24.04 container
on Docker Desktop's linuxkit 6.10.14 kernel. It adds one namespace at a time,
then does the whole thing in C.

<Sub n="3.1" title="A PID namespace, and the first surprise">

Start with the smallest thing. Ask for a PID namespace and print your PID:

```shell
$ unshare --pid --fork bash -c 'echo $$; ps -o pid,comm | head -5'
1
fatal library error, lookup self
```

`$$` is 1, as promised. `ps` is broken.

<Why>Why can't ps find itself?</Why>

`ps` reads `/proc`, and `/proc` is still the parent namespace's procfs. So `ps`
can't find the process it's running as. A PID namespace without a new `/proc`
is only half a PID namespace. Add a mount namespace and remount it:

```shell
$ unshare --pid --fork --mount-proc bash -c 'echo $$; ps -o pid,comm'
1
  PID COMMAND
    1 ps
```

PID 1 is `ps`, not bash. Bash `exec`s the last command of a `-c` string, so
`ps` inherited the PID. Keep that in mind for section 4.2, where PID 1 turns
out to be special in ways that bite.

</Sub>

<Sub n="3.2" title="A root filesystem and a cgroup">

Next, a rootfs. `docker export` of an Alpine container gave an 8.9 MB tar,
unpacked as the lower layer onto a tmpfs:

```shell
mount -t tmpfs tmpfs /ks
mkdir -p /ks/lower /ks/upper /ks/work /ks/merged
tar -xf /w/alpine.tar -C /ks/lower
mount -t overlay overlay \
  -o lowerdir=/ks/lower,upperdir=/ks/upper,workdir=/ks/work /ks/merged

cd /sys/fs/cgroup
mkdir init && for p in $(cat cgroup.procs); do echo $p > init/cgroup.procs; done
echo "+memory +cpu +pids" > cgroup.subtree_control
mkdir box
echo 64M            > box/memory.max
echo 0              > box/memory.swap.max
echo "50000 100000" > box/cpu.max      # 50 ms of CPU per 100 ms period
echo 64             > box/pids.max
```

The loop moving every process into `init` isn't decoration. cgroup v2 won't enable controllers for the children of a cgroup that still
holds processes of its own. The kernel docs call it the no-internal-process
constraint.

A real root cgroup is exempt. But this "root" is Docker's `/docker/<id>`
cgroup seen through a cgroup namespace, so the rule applies. On a systemd host
you rarely meet it, because systemd already keeps processes in leaves.

</Sub>

<Sub n="3.3" title="pivot_root, and a cached path">

Here's what the process that will become the container runs. It starts as PID
1 in fresh mount, UTS, IPC, net and cgroup namespaces, but it can still see
every host file. This is the script, lightly trimmed:

```bash
#!/bin/bash
set -e
hostname box
mount --make-rprivate /            # stop our mounts leaking back to the host
cd /ks/merged
mkdir -p .old
pivot_root . .old                  # the overlay becomes /, the host moves to /.old
cd /; hash -r                      # bash cached /usr/bin/mount from the host
mount -t proc proc /proc
mount -t sysfs sysfs /sys
mount -t cgroup2 cgroup2 /sys/fs/cgroup
mount -t tmpfs -o size=1m,mode=755 tmpfs /dev
mknod -m 666 /dev/null c 1 3
umount -l /.old && rmdir /.old     # and now the host is gone
until ip link show c0 >/dev/null 2>&1; do sleep 0.05; done
ip link set c0 name eth0
ip addr add 10.99.0.2/24 dev eth0 && ip link set eth0 up && ip link set lo up
exec "$@"
```

The first version didn't have `hash -r`, and it died right after `pivot_root`
with `/usr/bin/mount: No such file or directory`. Bash had looked up `mount`
once, before the pivot, and remembered the host's path. Alpine keeps it in
`/bin`. It's maybe the nicest demonstration that `pivot_root` really does swap the world
out from under a running process.

<Why>Why pivot_root and not chroot?</Why>

A chroot changes one process's idea of `/` and leaves the old root mounted in
its namespace. A root process can walk back out with the well-known
double-chroot trick.

After `pivot_root` and a lazy unmount of `/.old`, the host tree isn't in the
mount namespace at all. There's nothing to walk back to.

| | `chroot` | `pivot_root` + `umount -l` |
|---|---|---|
| What changes | One process's root directory | The root mount of the whole mount namespace |
| Old root | Still mounted | Detached |
| Escape by root | Double-chroot trick | No path back |

</Sub>

<Sub n="3.4" title="Wiring the network, and looking inside">

On the host side, the script joins the cgroup first, so the child and its
cgroup namespace are rooted there. Then it unshares and plugs in a veth pair.
The peer is named `c0` and created directly in the child's namespace, so
there's nothing to collide with:

```bash
echo $$ > /sys/fs/cgroup/box/cgroup.procs
unshare --pid --fork --mount --uts --ipc --net --cgroup /w/inner.sh "$@" &
sleep 0.2
CPID=$(pgrep -P $!)                     # the container's PID 1, as the host sees it
ip link add veth-host type veth peer name c0 netns $CPID
ip addr add 10.99.0.1/24 dev veth-host && ip link set veth-host up
wait
```

<Callout label="Common mistake" kind="warn">
Moving the host's own interface into the new namespace. The first version of
this script moved Docker's `eth0` into the toy namespace, and when the toy
exited, the network went with it. At the kernel level there's no "inside" and
"outside", only namespaces. Create a veth pair and move only the peer.
</Callout>

Then, from outside, `nsenter -a` into it and look around:

<TryIt what="mini.c — clone, a cgroup, overlayfs, pivot_root, a veth, seccomp" lang="c" toolchain="gcc 13.3 -O2 · linux 6.10.14 aarch64 · run as root">
```c
// mini.c: a container in about a hundred lines. Linux 5.x+, run as root.
// usage: ./mini <lowerdir> <cmd> [args...]
#define _GNU_SOURCE
#include <fcntl.h>
#include <linux/audit.h>
#include <linux/filter.h>
#include <linux/seccomp.h>
#include <sched.h>
#include <signal.h>
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mount.h>
#include <sys/prctl.h>
#include <sys/stat.h>
#include <sys/syscall.h>
#include <sys/sysmacros.h>
#include <sys/wait.h>
#include <unistd.h>

#define CG "/sys/fs/cgroup/mini"
#define DIE(what) do { perror(what); exit(1); } while (0)
static char **argv_; static int sync_pipe[2];

static void put(const char *path, const char *val) {        // echo val > path
  int fd = open(path, O_WRONLY);
  if (fd < 0 || write(fd, val, strlen(val)) < 0) DIE(path);
  close(fd);
}

static void deny_mount(void) {       // seccomp: mount(2) returns EPERM, even for root
  struct sock_filter f[] = {
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, arch)),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_AARCH64, 1, 0),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_mount, 0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | 1 /* EPERM */),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
  };
  struct sock_fprog prog = { sizeof f / sizeof f[0], f };
  if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) ||
      prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog)) DIE("seccomp");
}

static int child(void *arg) {
  char c;                                     // wait until the parent has put us
  close(sync_pipe[1]);                        // in the cgroup and made our veth
  if (read(sync_pipe[0], &c, 1) != 1) DIE("sync");
  if (unshare(CLONE_NEWCGROUP)) DIE("cgroupns");   // root it at /mini, not /
  if (sethostname("mini", 4)) DIE("uts");
  if (mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL)) DIE("private");
  mkdir("/tmp/mini", 0755);                   // overlay: image read-only, writes to tmpfs
  if (mount("tmpfs", "/tmp/mini", "tmpfs", 0, NULL)) DIE("tmpfs");
  mkdir("/tmp/mini/up", 0755); mkdir("/tmp/mini/work", 0755); mkdir("/tmp/mini/root", 0755);
  char opts[512];
  snprintf(opts, sizeof opts, "lowerdir=%s,upperdir=/tmp/mini/up,workdir=/tmp/mini/work", (char *)arg);
  if (mount("overlay", "/tmp/mini/root", "overlay", 0, opts)) DIE("overlay");
  if (system("ip link set c0 name eth0 && ip addr add 10.99.1.2/24 dev eth0 &&"
             "ip link set eth0 up && ip link set lo up")) DIE("net");
  if (chdir("/tmp/mini/root") || mkdir(".old", 0700) < 0) DIE("chdir");
  if (syscall(SYS_pivot_root, ".", ".old")) DIE("pivot_root");
  if (chdir("/") || umount2("/.old", MNT_DETACH) || rmdir("/.old")) DIE("old root");
  if (mount("proc", "/proc", "proc", 0, NULL)) DIE("proc");
  mount("sysfs", "/sys", "sysfs", MS_RDONLY, NULL);
  mount("cgroup2", "/sys/fs/cgroup", "cgroup2", 0, NULL);
  mount("tmpfs", "/dev", "tmpfs", 0, "size=1m,mode=755");
  mknod("/dev/null", S_IFCHR | 0666, makedev(1, 3));
  mknod("/dev/zero", S_IFCHR | 0666, makedev(1, 5));
  deny_mount();
  execvp(argv_[0], argv_);
  DIE("exec");
}

int main(int argc, char **argv) {
  if (argc < 3) { fprintf(stderr, "usage: %s lowerdir cmd...\n", argv[0]); return 2; }
  argv_ = argv + 2;
  mkdir(CG, 0755);                                        // cgroup v2 limits
  put(CG "/memory.max", "64M"); put(CG "/memory.swap.max", "0");
  put(CG "/cpu.max", "50000 100000"); put(CG "/pids.max", "64");
  if (pipe(sync_pipe)) DIE("pipe");
  static char stack[1 << 20];
  int flags = CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWNET | SIGCHLD;
  pid_t pid = clone(child, stack + sizeof stack, flags, argv[1]);
  if (pid < 0) DIE("clone");
  char buf[256];
  snprintf(buf, sizeof buf, "%d", pid); put(CG "/cgroup.procs", buf);
  snprintf(buf, sizeof buf, "ip link add vm%1$d type veth peer name c0 netns %1$d && "
           "ip addr add 10.99.1.1/24 dev vm%1$d && ip link set vm%1$d up", pid);
  if (system(buf)) DIE("veth");
  close(sync_pipe[0]);
  if (write(sync_pipe[1], "g", 1) != 1) DIE("release");
  int status; waitpid(pid, &status, 0);
  if (rmdir(CG)) perror("rmdir " CG);          // the veth dies with the netns
  if (WIFSIGNALED(status)) fprintf(stderr, "mini: killed by signal %d\n", WTERMSIG(status));
  return WIFEXITED(status) ? WEXITSTATUS(status) : 128 + WTERMSIG(status);
}
```

```
Seccomp:	2
```

Busybox asks "are you root?". It is: UID 0 with every capability. The seccomp
filter answered `EPERM` before the kernel ever checked. (The `hello` line comes
first only because stderr and stdout interleave.) And that `CapEff` line is
the honest weakness of `mini`: it never drops capabilities. A plain
`docker run alpine` on the same VM shows `CapEff: 00000000a80425fb`, 14 of them.
</Output>
</TryIt>

<Why>Why does the child wait on a pipe?</Why>

It's the one ordering decision that matters. `child()` blocks until the parent
has written its PID into `cgroup.procs` and created the veth end in its network
namespace. Here's the exchange:

<StepSequence
  title="The parent and child of mini, in order"
  actors={["Parent (host)", "Kernel", "Child (PID 1)"]}
  messages={[
    { from: 0, to: 1, label: "clone(CLONE_NEW*)", note: "The parent asks for a child in new PID, mount, UTS, IPC and network namespaces. **No cgroup namespace yet.**" },
    { from: 2, to: 2, label: "read(sync_pipe)", note: "The child starts and blocks on the pipe straight away. It has done nothing that depends on its cgroup or its network." },
    { from: 0, to: 1, label: "write cgroup.procs", note: "The parent moves the child into `/sys/fs/cgroup/mini`. The limits now apply to it." },

    { from: 0, to: 2, label: "write \"g\"", note: "One byte on the pipe releases the child." },
    { from: 2, to: 1, label: "unshare(NEWCGROUP)", note: "Only now does the child create its cgroup namespace, so its root is `/mini` and `/proc/self/cgroup` reads `0::/`." },
    { from: 2, to: 1, label: "pivot_root · execvp", note: "It builds its root filesystem, installs seccomp and runs your command." },
  ]}
/>

Put `CLONE_NEWCGROUP` in the `clone` flags instead, and the child's cgroup root
is wherever the parent was sitting. Then `/proc/self/cgroup` shows
`0::/../init`, a path climbing out of its own root.

</Sub>

<Sub n="3.6" title="What runc does, and why it's so much longer">

runc solves the same ordering problem with three processes, not two, and its
authors are candid about how that went:

<SourceRead
  file="libcontainer/nsenter/nsexec.c"
  repo="opencontainers/runc"
  tag="v1.3.1"
  href="https://github.com/opencontainers/runc/blob/v1.3.1/libcontainer/nsenter/nsexec.c#L772"
>
```c
	/*
	 * Okay, so this is quite annoying.
	 *
	 * [...] if we unshare(2) the user namespace *before* we clone(2), then
	 * all hell breaks loose.
	 *
	 * The parent no longer has permissions to do many things (unshare(2) drops
	 * all capabilities in your old namespace), and the container cannot be set
	 * up to have more than one {uid,gid} mapping. This is obviously less than
	 * ideal. In order to fix this, we have to first clone(2) and then unshare.
	 *
	 * Unfortunately, it's not as simple as that. We have to fork to enter the
	 * PID namespace (the PID namespace only applies to children). Since we'll
	 * have to double-fork, this clone_parent() call won't be able to get the
	 * PID of the _actual_ init process [...]
	 *
	 * -- Aleksa "what has my life come to?" Sarai
	 */
```
</SourceRead>

| Stage | What it does |
|---|---|
| `STAGE_PARENT` | Writes the child's `uid_map`, because the child can't |
| `STAGE_CHILD` | Unshares the user namespace, asks the parent for a mapping over a socket, then unshares everything else |
| `STAGE_INIT` | The grandchild, and the only one actually inside the new PID namespace |

`mini` skips all of it by not supporting user namespaces. That's the part that
makes a real runtime hard.

</Sub>

<SectionHeading n="04" id="failures">What goes wrong</SectionHeading>

Three kinds of failure show up again and again: a memory limit that kills, a
PID 1 that won't die, and escapes through `/proc`.

<Sub n="4.1" title="An OOM test that didn't OOM">

The first memory test inside the box piped 200 MB through `tail` against a
64 MB limit, from a shell entered with `nsenter -a`.

<Predict
  q="You nsenter -a into a container whose memory.max is 64M and run a command that needs 200 MB. What happens?"
  options={[
    "The kernel OOM-kills it, exit 137",
    "It completes normally; the limit doesn't apply",
    "malloc fails with ENOMEM",
    "The whole container is killed",
  ]}
  answer={1}
>
It exited 0, and `memory.events` said `oom_kill 0`. In the entered shell,
`/proc/self/cgroup` said `0::/../init`. `nsenter` joins namespaces; it doesn't
move you into a cgroup. The process was never under the limit.
</Predict>

`docker exec` doesn't have this problem, because runc writes the exec'd process
into the container's cgroup. Bare `nsenter` doesn't. Joining the cgroup first,
and using `dd` with a 100 MB buffer so the allocation is certain:

```shell
$ echo $$ > /sys/fs/cgroup/box/cgroup.procs
$ nsenter -t $CPID -a sh -c 'dd if=/dev/zero of=/dev/null bs=100M count=1; echo exit=$?;
    cat /sys/fs/cgroup/memory.events'
Killed
exit=137
low 0
high 0
max 37
oom 1
oom_kill 1
oom_group_kill 0

$ dmesg | tail -1          # wrapped here for width
Memory cgroup out of memory: Killed process 91997 (dd) total-vm:104076kB,
  anon-rss:63664kB, file-rss:0kB, shmem-rss:844kB, UID:0 pgtables:164kB oom_score_adj:0
```

Exit 137 is 128 + SIGKILL, the same number Kubernetes shows as `OOMKilled`.

<Callout label="Common mistake" kind="warn">
Testing limits from a shell entered with `nsenter`. It joins every namespace
but not the cgroup, so your test process runs outside the limit and proves
nothing. Write your PID into the container's `cgroup.procs` first, or use
`docker exec`.
</Callout>

The PID in `dmesg` is 91997, the VM's view of a process whose PID inside the box was two digits
long. There were two levels of PID namespace between them: the VM's, Docker's,
and the box's.

<Why>Which process gets killed?</Why>

That's a policy question, and Kubernetes changed its answer. On cgroup v2,
since 1.28, the kubelet sets **`memory.oom.group=1`** on every container, so an
OOM kills *every* process in the container, not the one the kernel picked.

For a web server that's what you want. For a Jupyter kernel under a notebook
server it isn't. [2i2c hit this](https://2i2c.org/blog/kubernetes-cgroup-changes/)
when their clusters moved to AL2023 images with cgroup v2: a user who blew
through memory used to lose one kernel and now lost the whole pod. They fixed
it with the kubelet's `singleProcessOOMKill` option, added in 1.32.

</Sub>

<Sub n="4.2" title="PID 1 ignores you">

A PID namespace's init gets special treatment from the kernel. Here's `mini`
running a PID 1 that never calls `wait()`, with two short-lived children:

<TryIt what="Zombies, and a SIGTERM that goes nowhere" lang="shell" toolchain="linuxkit 6.10.14 aarch64 · recorded transcript">
```shell

$ sleep 1; P=$(pgrep -f '^sleep 1000')
$ nsenter -t $P -a ps -o pid,ppid,stat,comm
$ kill -TERM $P; sleep 1; ps -o pid,stat,comm -p $P
$ kill -KILL $P; sleep 0.3; ps -o pid,stat,comm -p $P || echo gone
```

<Output>
```
PID   PPID  STAT COMMAND
    1     0 S    sleep
    8     1 Z    sleep
    9     1 Z    sleep

    PID STAT COMMAND
```

Two zombies, one orphaned into PID 1 and one its direct child, because `sleep`
never reaps. And `SIGTERM` from the host did nothing at all.

The kernel drops it:

<SourceRead
  file="kernel/signal.c"
  repo="torvalds/linux"
  tag="v6.10"
  href="https://github.com/torvalds/linux/blob/v6.10/kernel/signal.c#L81"
>
```c
static bool sig_task_ignored(struct task_struct *t, int sig, bool force)
{
	void __user *handler;

	handler = sig_handler(t, sig);

	/* SIGKILL and SIGSTOP may not be sent to the global init */
	if (unlikely(is_global_init(t) && sig_kernel_only(sig)))
		return true;

	/* a container's init is SIGNAL_UNKILLABLE: with no handler
	 * installed, a signal is dropped, not given its default action */
	if (unlikely(t->signal->flags & SIGNAL_UNKILLABLE) &&
	    handler == SIG_DFL && !(force && sig_kernel_only(sig)))
		return true;
```
</SourceRead>

A normal process with no SIGTERM handler dies. PID 1 with no handler ignores
it, and only `SIGKILL` from an ancestor namespace gets through. Here's what
that looks like from `docker stop`:

<StepSequence
  title="docker stop, when PID 1 has no SIGTERM handler"
  actors={["docker stop", "Kernel", "Your app (PID 1)"]}
  messages={[
    { from: 0, to: 1, label: "SIGTERM", note: "Docker sends SIGTERM to the container's PID 1 and starts a 10-second timer." },
    { from: 1, to: 1, label: "sig_task_ignored()", note: "PID 1 of a namespace is `SIGNAL_UNKILLABLE`. Its handler is `SIG_DFL`, so the kernel **drops the signal** instead of applying the default action." },
    { from: 2, to: 2, label: "keeps running", note: "Your app never sees anything. In-flight requests carry on, no shutdown code runs." },
    { from: 0, to: 1, label: "SIGKILL (after 10 s)", note: "The timer expires. SIGKILL comes from an ancestor namespace, so it isn't filtered." },
    { from: 1, to: 2, label: "killed", note: "The app dies without cleanup, and the container exits with 137." },
  ]}
/>

That's what `docker stop` hitting its 10-second timeout usually is: your app
didn't install a handler, so SIGTERM vanished, and Docker waited and then sent
SIGKILL.

[tini](https://github.com/krallin/tini) exists for exactly these two jobs:
forward signals to the real process and reap zombies. It has shipped inside
Docker since 1.13 as `docker run --init`. The Docker container used to write
this chapter had `sleep infinity` as its PID 1, and after a few failed runs `ps`
showed a small graveyard of `<defunct>` `pkill` and `run.sh` processes
reparented onto it.

<Callout label="Design implication">
Whatever runs as PID 1 in your image has two jobs the kernel won't do for it:
handle SIGTERM and reap zombies. Either install a SIGTERM handler in your app
and reap children, or put tini (or dumb-init) in front of it. If `docker stop`
takes exactly ten seconds, look at PID 1 first.
</Callout>

</Sub>

<Sub n="4.3" title="Breakouts through /proc">

Both famous runc escapes go through the same door: `/proc/self` magic links,
which let a process reach an object that a path lookup would never find.

| CVE | What leaked | Affected | Fixed or disclosed |
|---|---|---|---|
| **CVE-2019-5736** ([disclosure](https://www.openwall.com/lists/oss-security/2019/02/11/2)) | The host's runc binary, through `/proc/self/exe` | — | Disclosed 11 February 2019 |
| **CVE-2024-21626**, "Leaky Vessels" ([advisory](https://github.com/opencontainers/runc/security/advisories/GHSA-xr7r-f8xq-vfvv)) | An open fd for the host's `/sys/fs/cgroup` | 1.0.0-rc93 to 1.1.11 | 1.1.12, 31 January 2024 |

<Why>How did a container overwrite runc?</Why>

When runc `exec`s into a container, for a moment the process in the container
*is* the host's runc binary. A malicious container could open
`/proc/self/exe`, wait for the binary to stop being busy, and overwrite runc on
the host. Next `docker exec`, root on the host. It was found by Adam Iwaniuk and
Borys Popławski.

Leaky Vessels was simpler. runc leaked the cgroup fd into `runc init`, so an
image with `WORKDIR /proc/self/fd/7` started life with its working directory on
the host filesystem. It was found by Rory McNamara at Snyk, plus two others.

That 2019 fix is still in runc, and the current version comments on its own
cost:

<SourceRead
  file="libcontainer/exeseal/cloned_binary_linux.go"
  repo="opencontainers/runc"
  tag="v1.3.1"
  href="https://github.com/opencontainers/runc/blob/v1.3.1/libcontainer/exeseal/cloned_binary_linux.go"
>
```go
// CloneSelfExe makes a clone of the current process's binary (through
// /proc/self/exe). This binary can then be used for "runc init" in order to
// make sure the container process can never resolve the original runc binary.
// For more details on why this is necessary, see CVE-2019-5736.
func CloneSelfExe(tmpDir string) (*os.File, error) {
	// Try to create a temporary overlayfs to produce a readonly version of
	// /proc/self/exe that cannot be "unwrapped" by the container. [...]
	//
	// Based on some basic performance testing, the overlayfs approach has
	// effectively no performance overhead (it is on par with both
	// MS_BIND+MS_RDONLY and no binary cloning at all) while memfd copying adds
	// around ~60% overhead during container startup.
	overlayFile, err := sealedOverlayfs("/proc/self/exe", tmpDir)
```
</SourceRead>

The original fix copied the whole runc binary into a sealed memfd on every
start. Today's version mounts a throwaway read-only overlay over it and falls
back to the copy.

</Sub>

<Why>Why is a network namespace roughly a hundred times slower?</Why>

A new netns runs every registered per-namespace init hook: loopback, IPv4 and

first `hyperfine` run of `mini` aborted on a non-zero exit, and the fixed veth
name was the likely culprit: the previous run's `veth-mini` still existed, so
`ip link add` failed. Naming it after the PID made the benchmark run clean.

<Sub n="5.4" title="What a CPU limit feels like">

`cpu.max = 50000 100000` means 50 ms of CPU per 100 ms period. A busy loop for
3 seconds:

```shell
real 0m 3.00s   user 0m 1.51s
cpu.stat delta: nr_periods 30   nr_throttled 30   throttled_usec 1,488,738
```

Every single period throttled.

On average that's half a core. The reality is 50 ms of running then 50 ms of being frozen.
For a request handler, that means a 50 ms stall appears in your tail latency
whenever a request straddles the boundary.
[Chapter 16](/topics/16-contention-tail-latency) has more on why the average
hides this.

</Sub>

<Sub n="5.5" title="An unexplained tail">

That netns `max` column is ugly: 17 to 40 ms in every run, against a 266 µs
median. And the first batch of netns creations in each run was consistently
slower (319–363 µs) than a second identical batch later in the same process
(244–261 µs). That's also why "all seven" beats "net" alone in the table.

The best guess, and it's only a guess, is contention with the asynchronous
cleanup of namespaces just destroyed. `cleanup_net` runs from a workqueue and
takes `rtnl_lock`, and so does registering the new namespace's devices. That
would explain both the tail and a warm-up effect if the backlog drains.

It isn't proven. What would settle it is an off-CPU profile of `copy_net_ns`
with bpftrace, run once with a 20 ms gap between creations and once without.
An attempt at the gapped run was cut short when the Docker VM went away
mid-run.

</Sub>

<SectionHeading n="06" id="operating">Operating containers</SectionHeading>

<Sub n="6.1" title="Seeing inside a running container">

```shell
lsns -p $PID                          # which namespaces, by inode
readlink /proc/$PID/ns/*              # same, raw; equal inodes = shared namespace
nsenter -t $PID -a sh                 # enter all of them (but NOT its cgroup)
grep -E 'Seccomp|CapEff|NoNewPrivs' /proc/$PID/status
cat /proc/$PID/cgroup                 # 0::/kubepods.slice/...

cd /sys/fs/cgroup/<container>
cat memory.events                     # max, oom, oom_kill counters
cat memory.pressure cpu.pressure      # PSI: time stalled waiting for the resource
grep throttled cpu.stat               # nr_throttled, throttled_usec
cat memory.stat | grep -E '^(anon|file) '   # is it heap or page cache?
```

<Why>What should you look at first when a container is slow?</Why>

Three things. `cpu.stat` for throttling. `memory.pressure` for reclaim stalls:
a container near `memory.max` spends its time evicting its own page cache long
before any OOM. And `Seccomp` in `/proc/PID/status`.

On the privileged container used here, that field was `0`. `--privileged`
switches off seccomp, keeps every capability and exposes host devices. It's the
right tool for writing this chapter and the wrong one for anything else.

</Sub>

<Sub n="6.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| Exit code 137, nothing in the app's logs | `memory.max` hit, OOM kill | Check `oom_kill` in `memory.events` and `dmesg`; raise the limit or fix the leak |
| `docker stop` always takes 10 seconds | PID 1 has no SIGTERM handler | Install a handler, or run with `--init` / tini |
| `<defunct>` processes pile up | PID 1 doesn't reap | tini, dumb-init, or `waitpid` in your init |
| First request after deploy takes seconds | overlayfs copy-up of a big image file | Put mutable data on a volume |
| p99 has 50 ms stalls, average CPU looks fine | CFS throttling by `cpu.max` | Check `nr_throttled` in `cpu.stat`; raise the quota |
| Memory limit test doesn't trigger OOM | Test shell entered with `nsenter`, outside the cgroup | Write your PID to `cgroup.procs` first |
| JVM OOM-killed after a node image change | Old JDK can't read cgroup v2 limits | JDK 11.0.16+ or 8u372+ (section 6.3) |

</Sub>

<Sub n="6.3" title="cgroup v1 to v2">

cgroup v1 gave every controller its own hierarchy. A process could be in `/a`
for memory and `/b` for CPU, and nobody could reason about the result.

v2 has one tree, the no-internal-process rule from 3.2, pressure stall
information, and `memory.high` as a soft limit that throttles before it kills.
The migration took years, and it's now pretty much over:

| Milestone | What changed |
|---|---|
| **Kubernetes 1.25** (August 2022) | cgroup v2 support [GA](https://kubernetes.io/blog/2022/08/31/cgroupv2-ga-1-25/) |
| **systemd 258** | Removed v1 support entirely ([NEWS](https://github.com/systemd/systemd/blob/v258/NEWS)) |
| **Kubernetes 1.35** | kubelets refuse to start on a v1 host unless you set `failCgroupV1: false` ([KEP-5573](https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/5573-remove-cgroup-v1/README.md)) |

Where it bites is usually the JVM. OpenJDK before 11.0.16 and 8u372 can't read v2 limits, so on a
v2 node it sizes its heap from the host's memory and can get OOM-killed
([JDK-8230305](https://bugs.openjdk.org/browse/JDK-8230305)).

Kubernetes' [cgroup v2 page](https://kubernetes.io/docs/concepts/architecture/cgroups/)
lists the minimum versions for Java, Node and other runtimes. Check before the
node image changes under you, not after.

</Sub>

<Sub n="6.4" title="Rootless, and user namespaces">

User namespaces are the one piece that changes what root inside means. As an
unprivileged user `u1`, in the same Ubuntu container:

```shell
$ id
uid=1001(u1) gid=1001(u1) groups=1001(u1)
$ unshare --user --map-root-user --mount --pid --fork --mount-proc sh
# id; cat /proc/self/uid_map
uid=0(root) gid=0(root) groups=0(root)
         0       1001          1
# touch /etc/owned-by-host-root
touch: cannot touch '/etc/owned-by-host-root': Permission denied
# mount -t tmpfs x /mnt && echo mounted a tmpfs
mounted a tmpfs
# ls -ln /etc/shadow
-rw-r----- 1 65534 65534 526 Sep 25 13:13 /etc/shadow
```

Root inside, UID 1001 outside. It can mount a tmpfs, because it has
`CAP_SYS_ADMIN` over its own mount namespace. It can't touch host-root files,
which show up as 65534, the overflow ID for anything unmapped.

<Why>What do user namespaces fix, and what don't they?</Why>

They **fix** the "root in the container is root on the host" class of bug.
CVE-2019-5736's own disclosure says the attack fails when host root isn't
mapped into the container, since overwriting runc needs host root. Kubernetes
[enabled user namespaces for pods](https://kubernetes.io/blog/2025/04/25/userns-enabled-by-default/)
(`hostUsers: false`) by default in 1.33; it needs Linux 6.3+ and runc 1.2+.

They **don't** fix the shared kernel. They make its reachable surface bigger. An
unprivileged user can now reach code paths that used to require real root.

CVE-2022-0185, a heap overflow in filesystem-context parsing, was exploitable by
an unprivileged user precisely because user namespaces handed them a namespaced
`CAP_SYS_ADMIN` ([Ubuntu's notice](https://ubuntu.com/security/CVE-2022-0185)).
That's why Ubuntu added an AppArmor restriction on unprivileged user namespaces
([opt-in in 23.10](https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces),
on by default from 24.04).

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **A container is a process, not a machine.** Namespaces set what it sees, a
   cgroup sets what it can use, and overlayfs gives it a root filesystem.
2. **Every container shares the host kernel.** That makes startup cost
   milliseconds, and makes a reachable kernel bug everyone's problem.
3. **Unsharing a PID namespace moves your children, not you.** The next child
   becomes PID 1, and it needs its own `/proc`.
4. **`pivot_root` removes the host tree; `chroot` only hides it.** After a lazy
   unmount of the old root there's no path back.
5. **Order matters when you build one.** Join the cgroup and wire the network
   before creating the cgroup namespace, or the paths come out wrong.
6. **`nsenter` doesn't join the cgroup.** Tests run from it escape the limits.
7. **Exit 137 means SIGKILL**, almost always an OOM kill at `memory.max`, and
   Kubernetes 1.28+ kills the whole container cgroup.
8. **PID 1 drops signals it has no handler for.** That's the 10-second
   `docker stop`; tini or a handler fixes it.
9. **The network namespace is the expensive one.** About 266 µs against a few
   microseconds for the rest, with asynchronous teardown.
10. **The first write to a big image file copies all of it.** Put mutable data
    on a volume, and watch `cpu.stat` for throttling that averages hide.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Make `mini` into something you'd let a stranger run code in, then attack it.**

- Add user namespace support: clone with `CLONE_NEWUSER`, have the parent write
  `uid_map` and `gid_map`, and discover for yourself why runc has three stages.
- Drop capabilities to Docker's default 14 with `capset`, and replace the
  one-rule seccomp filter with a real allowlist.
- Make PID 1 a 20-line init that reaps with `waitpid(-1, ..., WNOHANG)` and
  forwards SIGTERM. Rerun the zombie transcript from 4.2.
- Then try to escape: write the Leaky Vessels bug on purpose by leaking a
  host directory fd without `O_CLOEXEC`, and `chdir("/proc/self/fd/N")` from
  inside. It's a short program, and it's alarming how well it works.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What's the difference between a container and a VM?">
A VM runs its own kernel on virtual hardware; a container is a set of host
processes in namespaces and a cgroup, making syscalls to the host kernel. So a
container starts in milliseconds (6.7 ms for the hand-built one here) and
a kernel bug is shared by every container on the host. See
[chapter 47](/topics/47-virtualization) for the other side.
</QA>

<QA level="beginner" q="Your container exits with code 137. What happened?">
It got SIGKILL: 128 + 9. Almost always the cgroup's `memory.max` was hit and
the kernel OOM-killed it. Confirm with `oom_kill` in `memory.events` or
`dmesg`, which shows `CONSTRAINT_MEMCG` and the cgroup path. The other common
source is `docker stop` escalating after its timeout.
</QA>

<QA level="intermediate" q="Why does docker stop sometimes take exactly ten seconds?">
It sends SIGTERM to the container's PID 1, waits 10 seconds, then sends
SIGKILL. A PID namespace's init is `SIGNAL_UNKILLABLE`: with no handler
installed, the kernel drops SIGTERM without applying the default action. So an
app that never installs a handler ignores it. Fix it with a handler, or
`--init`/tini.
</QA>

<QA level="intermediate" q="Why pivot_root and not chroot?">
chroot changes one process's root directory but leaves the old root mounted
in its namespace, and a root process can escape with the double-chroot trick.
pivot_root swaps the root mount of the whole mount namespace; after a lazy
unmount of the old root, the host tree isn't reachable by any path.
</QA>

<QA level="intermediate" q="A container's first request after deploy takes four seconds, later ones take milliseconds. Where do you look?">
Overlayfs copy-up. The first open-for-write of a lower-layer file copies the
whole file into the upper layer inside `open()`. It measured 4 seconds for a
1 GiB file on an ext4 upper. Put mutable data on a volume, not in the image.
</QA>

<QA level="deep" q="Why does creating a network namespace cost 100× more than a UTS namespace?">
A UTS namespace is a struct copy, about a microsecond. A netns runs every
registered pernet init: loopback, IPv4/IPv6 state, netfilter, and fallback
tunnel devices for loaded modules. It measured 266 µs median, with a
multi-millisecond tail, and teardown is asynchronous, so the veth lingers ~75 ms.
</QA>

<QA level="deep" q="What do rootless containers protect against, and what don't they?">
With a user namespace, container root maps to an unprivileged host UID, so
bugs that give "root in container" (CVE-2019-5736 overwriting runc) don't give
host root. They don't shrink the shared kernel; they widen it, since
unprivileged users gain namespaced capabilities that reach code like the
CVE-2022-0185 overflow.
</QA>

<QA level="deep" q="How did CVE-2024-21626 let a container reach the host filesystem?">
runc leaked a file descriptor for the host's `/sys/fs/cgroup` into `runc
init`, without close-on-exec. An image with `WORKDIR /proc/self/fd/7` started
with its cwd on the host mount, outside the pivot_root. Fixed in runc 1.1.12
by making sure the fd is closed before the container process runs, plus
checks on the working directory.
</QA>

<SectionHeading n="11" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="You enter a container with nsenter -a and run a memory hog. It exceeds the limit and isn't killed. Why?">
    nsenter joins namespaces, not cgroups. Your process is still in the cgroup
    you started in. Write your PID to the container's cgroup.procs first.
  </Q>
  <Q q="Why does ps fail after unshare --pid --fork without --mount-proc?">
    /proc is still the parent's procfs, so ps can't find itself by PID. A
    PID namespace needs its own /proc mount.
  </Q>
  <Q q="Why can't you enable controllers in cgroup.subtree_control on a cgroup with processes in it?">
    cgroup v2's no-internal-processes rule: controllers apply to leaves, so
    move the processes into a child cgroup first.
  </Q>
  <Q q="What is a whiteout?">
    A 0,0 character device in the upper layer that hides a lower-layer file,
    because overlayfs can't delete from the read-only lower.
  </Q>
</Quiz>
