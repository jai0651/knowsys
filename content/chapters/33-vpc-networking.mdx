Every service you deploy on AWS runs inside a VPC, whether you drew one or took
the default. Most of the time it stays out of the way. Then a request times out
with no error anywhere, two teams discover they can't connect their networks,
or the bill shows thousands a month for traffic between zones.

Those surprises have one root. A VPC isn't a network with cables and routers.
It's a lookup table, consulted by a card in the server your instance runs on.
Once you see it that way, the failures stop looking arbitrary.

This chapter builds a VPC from the provider's side, then walks through the
pieces you configure, one packet's trip between zones, the failures that
produce no error message, and what it all costs.

<Callout label="How this chapter was built" kind="note">
Every other chapter here is measured on a machine I own. I don't have an AWS
account with Nitro instances to break, so this one is built from the
documentation, the ENA driver's counter names, AWS talks and public
postmortems. Wherever I show output I haven't run, I say so.
</Callout>

<SectionHeading n="01" id="overlay">A private network on shared hardware</SectionHeading>

Put yourself in a cloud provider's position. You have a building full of
physical servers on one shared physical network. Every customer wants a private
network of their own.

<Sub n="1.1" title="The provider's problem">

Customer A wants a private network. So does customer B, and both want the
addresses `10.0.0.0` to `10.0.255.255`, because that's what every tutorial
says. Neither may ever see the other's packets.

<Why>Why not give each customer their own switches?</Why>

Because customers create networks by clicking a button, thousands of times a
day. You can't run separate cables and switches for every one of them. The
isolation has to come from software, on hardware everyone shares.

</Sub>

<Sub n="1.2" title="Fake it in the network card">

You fake it in the one place every packet has to pass through: the network card
of the host it's leaving. Chapter 47 described those hosts, running customers'
VMs on a hypervisor, with a card (AWS calls it **Nitro**) that handles
networking for all of them.

Give each card a table. For every VM, it knows which customer's network the VM
belongs to. For every address in that network, it knows which physical host
the VM is on.

When customer A's VM sends a packet to `10.0.2.9`, the card looks up where
*A's* `10.0.2.9` lives. It wraps the packet in an outer packet addressed to that
physical host, tagged with A's network, and sends it across the shared network.
The card at the other end unwraps it and delivers it only to A's VM.

B's `10.0.2.9` is a different entry in the table, and it never sees the packet.

<Callout label="Design implication">
There is no router. The "VPC router" at `x.x.x.1` in every subnet isn't a
device; it's a convention. Routing decisions are made by the network card on
the *sending* host, before the packet leaves. So you can't log in to it,
can't saturate it, and can't make it a bottleneck.
</Callout>

</Sub>

<SectionHeading n="02" id="pieces">The pieces you configure</SectionHeading>

That's a **VPC**. Each piece you configure in the console is really an entry in
that table, pushed out to the cards that need it.

<Sub n="2.1" title="CIDR blocks and subnets">

A **CIDR block** is your address range. `10.0.0.0/16` means the first 16 bits
are fixed, which leaves 65,536 addresses.

A **subnet** is a slice of that range pinned to one **availability zone**, one of
the separate data centres in a region.

<Why>Why does subnet size matter on Kubernetes?</Why>

On EKS, the default VPC CNI gives every pod its own VPC address. So the number
of pods you can run is tied to how big your subnets are, and a subnet carved
small on day one caps the cluster later.

</Sub>

<Sub n="2.3" title="Route tables, gateways and security groups">

Three more pieces decide where a packet may go:

| Piece | What it does |
|---|---|
| **Route table** | Says where packets for each destination go: stay inside the VPC, out through an internet gateway, or through a NAT gateway |
| **NAT gateway** | Swaps in a public source address for servers that shouldn't be reachable directly |
| **Security group** | A set of allow rules the card checks before it sends or delivers anything. It remembers connections, so replies get through |

</Sub>

<SectionHeading n="03" id="guarantees">Isolation, and what it isn't</SectionHeading>

From inside, a VPC behaves like a flat routed network you own. Two instances in
the same VPC can reach each other by private IP with no configuration beyond a
permissive security group.

What you're sold is isolation. What you get is **a distributed lookup table**:
no cable between your two instances, no switch, no VLAN. Each packet is
wrapped, shipped across a shared physical substrate, and unwrapped by hardware
on the far side.

<Sub n="3.1" title="What it guarantees">

| Guarantee | What it means |
|---|---|
| **L3 isolation** | Packets don't leak between VPCs without explicit peering, a transit gateway, or an endpoint |
| **Stable private addressing** | An ENI's private IP is yours for the life of the interface |
| **Stateful filtering by default** | Security groups track connections, so return traffic is allowed without a matching rule |

</Sub>

<Sub n="3.2" title="What it does not">

| Not provided | Consequence |
|---|---|
| **Broadcast or multicast** | ARP is emulated. Anything built on broadcast discovery, like old clustering software and some licence servers, won't work |
| **Guaranteed bandwidth between two instances** | You get an allowance tied to instance size, and it's a ceiling, not a reservation |
| **Overlapping CIDRs** | Two VPCs with overlapping ranges can't peer, ever |

<Why>Why can't overlapping VPCs peer?</Why>

Because the table can't tell their addresses apart. If both VPCs contain
`10.0.2.9`, a lookup for that address has two answers, and the card has no way
to choose.

<Callout label="Common mistake" kind="warn">
Typing `10.0.0.0/16` without thinking. It's the decision that's hardest to
reverse, and it's made on day one. Years later two teams that both took the
default need to peer, and the fix is renumbering a production VPC.
</Callout>

</Sub>

<Sub n="4.2" title="The mapping service">

Step 3 is where the interesting behaviour comes from. The sending card asks a
**mapping service**, described publicly in AWS's re:Invent networking talks,
which physical host currently holds that private IP. It gets back a substrate
address and wraps the packet.

<Why>Why is the first packet to a new destination slower?</Why>

Because mapping entries are cached on the card, and a miss costs a lookup. It's
probably single-digit milliseconds, though I've never managed to measure it
cleanly. You'll occasionally see it as first-connection latency that never
reproduces under load.

<Why>How can an instance move hosts and keep its IP?</Why>

Live migration is a mapping update, not a renumbering. Your IP follows you
because it was never bound to hardware in the first place.

</Sub>

<Sub n="4.3" title="Security groups against NACLs">

A security group is evaluated on the Nitro card of the *sending* and
*receiving* hosts, before the packet reaches any guest. There's no appliance to
route through, and no throughput cost that scales with rule count the way an
iptables chain does.

| | Security group | NACL |
|---|---|---|
| **State** | Stateful: tracks connections | Stateless: every packet judged alone |
| **Where** | The Nitro card of each instance | The subnet boundary |
| **Rules** | A set of allow rules | An ordered rule list |
| **Return traffic** | Allowed automatically | Needs its own rule |

That difference in state causes more outages than any other VPC feature. Here's
the same request through each:

  actors={["Client", "Security group", "NACL"]}

    { from: 1, to: 0, label: "SYN-ACK from :443", note: "The reply is allowed with no outbound rule, because the connection is tracked." },
    { from: 0, to: 2, label: "SYN → :443", note: "Now the same request through a NACL with the same inbound rule. The SYN gets in." },
    { from: 2, to: 0, label: "SYN-ACK from :443", dashed: true, note: "**Dropped.** The reply goes to the client's ephemeral port, and there's no outbound rule for `:32768-60999`. The NACL has no memory of the SYN." },
  ]}
/>

<Callout label="Common mistake" kind="warn">
Adding a NACL that mirrors your security group's inbound rules and nothing
else. The responses are silently dropped, and a dropped response looks exactly
like an application hang. Give every NACL an outbound rule for the ephemeral
port range.
</Callout>

</Sub>

<SectionHeading n="05" id="silent-failures">Failures with no error message</SectionHeading>

Because a VPC is a table, most of its failures are an entry that says "drop"
or a ceiling that's quietly hit. Nothing replies, so the instance sees a
timeout and nothing else.

<Sub n="5.1" title="The blackhole route">

<Predict
  q="You delete a NAT gateway, but a route in a private subnet still points at it. What do instances in that subnet see when they connect out?"
  options={[
    "The API refuses to delete the gateway",
    "The route is removed automatically",
    "An ICMP unreachable, so connections fail fast",
    "Nothing: packets vanish and connections time out",
  ]}
  answer={3}
>
The route is just an entry, and now it points at nothing. It stays, its state
becomes `blackhole`, and matching packets are dropped with no ICMP unreachable,
no log line, and no error on the instance beyond a timeout.
</Predict>

Find them with one query:

```shell
aws ec2 describe-route-tables \
  --query 'RouteTables[].Routes[?State==`blackhole`].[DestinationCidrBlock,GatewayId]' \
  --output text
```

Run that after any teardown. It takes a second and it's the highest-yield VPC
check I know.

</Sub>

<Sub n="5.2" title="NAT gateway port exhaustion">

A NAT gateway rewrites source addresses, so every outbound connection consumes
a source port *per unique destination*. AWS documents the ceiling as roughly
55,000 simultaneous connections to a single destination IP and port, and
returns `ErrorPortAllocation` past it.

<Why>Why do unrelated services fail at the same time?</Why>

Because the limit is per destination, on a gateway everyone shares. Everything
works, then a batch job fans out to one third-party API, and other services
start failing to connect. Nothing in your application changed. You ran out of
tuples.

Mitigations, in order of how much they help:

| Fix | Why it helps |
|---|---|
| **Don't route it through NAT** | A VPC endpoint for S3, DynamoDB and the rest keeps that traffic off the gateway entirely, and off your bill |
| **More NAT gateways** | One per AZ is the default advice, and it also halves cross-AZ charges |
| **Fewer connections** | Connection pooling and keep-alive |

</Sub>

<Sub n="5.3" title="Allowances you didn't know you had">

Instance network performance is a set of ceilings. Crossing one shows up as
packet loss with no error anywhere in your application. The ENA driver counts
them, and almost nobody looks:

```shell
ethtool -S eth0 | grep -E 'allowance_exceeded'
```

You get five counters back. These are made-up values to show the shape; I don't
have a Nitro instance to paste a real run from:

```
bw_in_allowance_exceeded: 0
bw_out_allowance_exceeded: <n>
pps_allowance_exceeded: 0
conntrack_allowance_exceeded: <n>
linklocal_allowance_exceeded: 0
```

They're counters, so any non-zero value is cumulative since boot and tells you
nothing about *when*. Sample them on an interval, or you can't tell a burst
last Tuesday from a problem happening now.

A non-zero `conntrack_allowance_exceeded` means the Nitro card's connection
tracking table is full, usually from a scan, a huge fan-out, or half-open
connections piling up.

<Callout label="Design implication">
`conntrack_allowance_exceeded` isn't in CloudWatch by default. The instance
drops packets, the application sees timeouts, and every dashboard you'd
normally reach for looks fine. Ship the `ethtool -S` counters yourself.
</Callout>

</Sub>

<Sub n="5.4" title="MTU, and the 9001 you probably aren't getting">

Inside a VPC the MTU is 9001 bytes. Traffic leaving through an internet gateway
drops to 1500, and paths through some gateway types drop further.

<Why>Why do small requests work while large ones hang?</Why>

A packet with DF set that's too large for the path gets an ICMP
fragmentation-needed response. Plenty of security groups and on-prem firewalls
drop that ICMP, and the result is the classic **PMTU black hole**: small
requests work, large ones hang forever.

```shell
# Find the real path MTU, without trusting anyone's documentation
tracepath 10.0.2.47
ping -M do -s 8973 10.0.2.47      # 8973 + 28 bytes of header = 9001
```

</Sub>

Traffic between availability zones leaves one data centre for another, so it
shows up on the bill. The rates are small; the volumes aren't.

<SectionHeading n="07" id="operating">Debugging and monitoring a VPC</SectionHeading>

<Sub n="7.1" title="Answering 'why can't A reach B'">

There's an order that resolves this fastest, and it isn't the order most people
use. Work from the cheapest check to the most expensive:

1. **Reachability Analyzer.** It evaluates route tables, SGs, NACLs and gateways
   statically and names the blocking component. No packets sent.
2. **Blackhole routes.** The query in 5.1.
3. **NACLs, both directions.** Stateless means the return path needs its own
   rule, and the ephemeral range is the usual gap.
4. **Flow logs, filtered to REJECT.** These tell you *that* something was
   dropped, and by which ENI.
5. **Only then, tcpdump on the instance.**

<Why>Why not start with flow logs?</Why>

They're where people start, and they're the slowest useful step. They show
rejects but not *why*: a REJECT line doesn't say whether the SG or the NACL did
it.

</Sub>

| Symptom | Likely cause | Fix |
|---|---|---|
| Outbound connections time out after a teardown | Blackhole route | Query for `blackhole` routes; repoint or delete them |

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **A VPC is a lookup table, not a network.** The card on each host maps your
   private IPs to physical hosts and wraps every packet.
2. **There is no router.** The `.1` address is a convention; routing happens on
   the sending host.
3. **Every subnet loses five addresses.** A `/24` holds 251 instances, a `/28`
   holds 11.
4. **Overlapping CIDRs can never peer.** The table can't tell the addresses
   apart, so choose ranges on day one.
5. **Security groups are stateful; NACLs aren't.** A NACL needs an outbound rule
   for the ephemeral range, or responses vanish.
6. **Deleted targets leave blackhole routes.** Packets are dropped with no
   error; query for them after every teardown.
7. **NAT gateways run out of ports per destination.** About 55,000 connections
   to one IP and port, shared by everything behind the gateway.
8. **Allowance counters live in `ethtool -S`**, not CloudWatch. Sample them, or
   the drops stay invisible.
9. **The VPC MTU is 9001, but paths out are smaller.** Blocked ICMP turns that
   into a PMTU black hole.
10. **Cross-AZ traffic is billed in both directions.** One chatty service pair
    can cost about $4,200 a month; zone-aware routing removes most of it.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Build the overlay yourself, on one laptop.** Two network namespaces, a VXLAN
tunnel between them, and a tiny userspace "mapping service" that resolves an
overlay IP to a tunnel endpoint.

- Create two netns, give each a veth with an overlay address in `10.99.0.0/24`.
- Bridge them with VXLAN over loopback, so the encapsulation is real.
- Write 30 lines that maintain the FDB from a dictionary, and ping across.
- Then delete an entry and watch the ping stop with no ICMP error at all.

That last step is the whole chapter in one experiment. A blackhole route and a
missing mapping entry fail identically, silently, and once you've caused it
yourself the AWS behaviour stops feeling mysterious.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="How many usable addresses are in a /28 subnet on AWS?">
Eleven. Sixteen addresses minus five reserved: the network address, the implied
router at `.1`, the DNS resolver at `.2`, one reserved for future use at `.3`,
and the broadcast address at the end, reserved even though broadcast doesn't
function in a VPC.
</QA>

<QA level="intermediate" q="Security groups versus NACLs: when does the difference actually bite?">
Statefulness. A security group tracks connections, so allowing inbound 443
automatically permits the response. A NACL is stateless and evaluates each
packet independently, so the same setup needs an explicit *outbound* rule
covering the ephemeral port range or every response is dropped.

What makes it nasty is the symptom: a silently dropped response is
indistinguishable from an application hang. A connection establishes, the
request is delivered, and the client just waits.
</QA>

<QA level="intermediate" q="A deleted NAT gateway left traffic failing with no errors. What happened?">
That route survived the gateway and moved to `blackhole` state. Matching packets
are discarded with no ICMP unreachable, so instances see a timeout and nothing
else. Query route tables for routes in `blackhole` state after any teardown.
</QA>

<QA level="deep" q="Two instances in the same VPC, different AZs. Describe the packet path.">
A guest writes to a socket; the ENA driver hands the frame to the Nitro card.
Security group rules are evaluated there, in hardware, before anything leaves
the host. That card resolves the destination private IP to a physical host
address through the mapping service, encapsulates the packet, and sends it over
the AWS substrate: a real network, with real routers, that has never heard of
your `10.0.0.0/16`. On the far side, a card decapsulates, applies the
destination security group, and delivers to the target ENI.

Two things follow. There's no router device to become a bottleneck, because
routing decisions happen on the sending host. And your private IP isn't bound to
hardware, and that's what makes live migration possible.
</QA>

<QA level="deep" q="Outbound connections start failing across several services at once. Nothing was deployed. Where do you look first?">
NAT gateway port exhaustion. Check `ErrorPortAllocation` on the NAT gateway in
CloudWatch. Blast radius is the giveaway: NAT is shared infrastructure, so
one service fanning out to a single third-party endpoint consumes the source
port space that every other service in the subnet depends on.

Then check `conntrack_allowance_exceeded` in `ethtool -S` on the busiest
instances, because a connection-tracking overflow presents almost identically
and isn't in CloudWatch at all. A VPC endpoint is usually the durable fix,
taking that traffic off the gateway and off the bill together.
</QA>

<SectionHeading n="11" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="Why can't you ping the VPC router at x.x.x.1?">
    Because it isn't a device. Routing is applied on the sending host's Nitro
    card; the `.1` address is a reserved convention with nothing listening.
  </Q>
  <Q q="A security group allows inbound 443 and has no outbound rules. Do responses get out?">
    Yes. Security groups are stateful, so the tracked connection's return
    traffic is allowed. A NACL in the same position would drop them.
  </Q>
  <Q q="Small HTTP requests work, large uploads hang forever. First guess?">
    A PMTU black hole. Path MTU drops below 9001, the sender gets an ICMP
    fragmentation-needed that something along the way is dropping, and packets
    with DF set vanish. Test with `ping -M do -s 8973`.
  </Q>
  <Q q="Two VPCs, both 10.0.0.0/16, need to talk. What are your options?">
    Not peering: overlapping CIDRs can't peer. You're left with renumbering
    one, a private NAT layer, or a PrivateLink endpoint that exposes specific
    services instead of joining the networks.
  </Q>
</Quiz>
