You text a friend and hear nothing back for an hour. They might have lost their phone, fallen asleep, gone into a tunnel, or be in trouble. From your side, all of those look the same: silence. You have to decide when to worry, and if you decide too early you'll call the police on someone who was at the cinema.

Every cluster of servers makes the same guess many times a second about its own members, and it can only go on silence. A monitor that declares a healthy node dead can trigger a failover while the old node is still running. You can watch that mistake happen in forty lines of Python.

<SectionHeading n="01" id="wrongly-dead">Watch a monitor declare a healthy worker dead</SectionHeading>

Save this as `hb.py`. A worker sends a heartbeat every 100 ms. A monitor declares it dead if it hears nothing for 300 ms. One second in, the worker pauses for a full second, as a long garbage-collection pause or a stalled disk would.

<Sub n="1.1" title="A pause that looks like a crash">

<TryIt what="Run a heartbeating worker and a 300 ms timeout monitor, and pause the worker for one second" lang="python" toolchain="Python 3.14, macOS 26.5.1, Apple M4">
```python
import threading, time

last_beat = time.monotonic()
start = time.monotonic()
stop = False

def say(msg): print(f"  t={time.monotonic() - start:4.1f}s  {msg}", flush=True)

def worker():                                  # a healthy service that sends a heartbeat every 100 ms
    global last_beat
    while not stop:
        last_beat = time.monotonic()
        time.sleep(0.1)
        if 1.0 <= time.monotonic() - start < 1.05:
            say("worker: entering a 1.0 s pause (a long GC, a stalled disk)")
            time.sleep(1.0)
            say("worker: pause over, still alive")

def monitor(timeout=0.3):                      # declares the worker dead after 300 ms of silence
    dead = False
    while not stop:
        silent = time.monotonic() - last_beat
        if silent > timeout and not dead:
            say(f"monitor: no heartbeat for {silent:.1f}s -> declares the worker DEAD"); dead = True
        elif silent <= timeout and dead:
            say("monitor: heartbeat is back -> the worker was never dead"); dead = False
        time.sleep(0.02)

threading.Thread(target=worker, daemon=True).start()
threading.Thread(target=monitor, daemon=True).start()
time.sleep(3)
stop = True
```
<Output>
```
  t= 1.0s  worker: entering a 1.0 s pause (a long GC, a stalled disk)
  t= 1.3s  monitor: no heartbeat for 0.3s -> declares the worker DEAD
  t= 2.0s  worker: pause over, still alive
  t= 2.1s  monitor: heartbeat is back -> the worker was never dead
```
</Output>
</TryIt>

The monitor declared the worker dead 0.3 seconds into the pause, and the verdict was wrong: the worker resumed a second later, fully alive. A second run declared it dead at 1.2 s instead of 1.3 s.

</Sub>

<Sub n="1.2" title="What went wrong">

Nothing was broken. The monitor followed its rule exactly, and the rule can't distinguish a dead worker from a slow one. If the monitor had also promoted a replacement, there would now be two workers doing the same job.

Raising the timeout reduces false alarms and slows down real recoveries, so no value is right for everyone. The chapter starts with why certainty is impossible, measures how long a healthy process can go quiet, and then builds better detectors and the tools that stop a wrong verdict from corrupting data.

</Sub>

<SectionHeading n="02" id="impossible">Why you can't know a node is dead</SectionHeading>

On one machine, a crashed process is a fact: the kernel reaps it and tells its
parent. Across a network there's no such signal. All you ever have is messages
that did or didn't arrive.

<Sub n="2.1" title="Four failures that look identical">

| What happened | What the observer sees |
|---|---|
| The process crashed | No replies |
| The machine is up but the process is paused (GC, swap, a stuck disk) | No replies, then a burst of late ones |
| The network between you dropped or delayed packets | No replies, while others may hear it fine |
| Your *own* process was paused, and the peer is fine | No replies arrived while you weren't looking |

The last row is the one that bites. A detector that's itself paused for three
seconds will wake up, see three seconds of silence from everyone, and conclude
the whole cluster died.

<Why>Why can't a smarter protocol tell them apart?</Why>

Because in an asynchronous network, where messages can be delayed by any amount,
a slow process and a crashed one produce exactly the same observations. Fischer,
Lynch and Paterson's [FLP result](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)
(1985) follows from this: no deterministic protocol can guarantee consensus if
even one process may crash, because it can never be sure whether to keep
waiting.

So real systems give up on certainty and add timing assumptions. Chandra and
Toueg's [unreliable failure detectors](https://www.cs.utexas.edu/~lorenzo/corsi/cs380d/papers/p225-chandra.pdf)
(1996) formalised the trade with two properties:

- **Completeness:** every crashed process is eventually suspected.
- **Accuracy:** correct processes aren't suspected (or eventually aren't).

Completeness is easy: suspect everyone who's quiet. Accuracy is the hard part,
and every design in this chapter is a way of buying more of it.

</Sub>

<Sub n="2.2" title="Gray failure: alive to one observer, dead to another">

Real failures are often partial. A node answers health checks but times out on
real requests; it reaches the coordinator but not its peers. Huang et al. call
this [gray failure](https://www.microsoft.com/en-us/research/publication/gray-failure-achilles-heel-cloud-scale-systems/)
(HotOS 2017): the failure detector and the application disagree about whether a
component is healthy.

Bailis and Kingsbury's
[The Network is Reliable](https://queue.acm.org/detail.cfm?id=2655736)
(ACM Queue, 2014) collects public postmortems of partial partitions,
asymmetric links and switches that dropped some traffic and not other traffic.
It's the best argument against assuming failures are clean.

<Callout label="Design implication">
Health checks should exercise the path real requests take. A `/healthz` that
returns 200 from a thread that doesn't touch the database, the disk or the
downstream service is measuring that the process exists, and that's the
failure you least need help detecting.
</Callout>

</Sub>

<SectionHeading n="03" id="timeouts">Heartbeats and timeouts</SectionHeading>

The basic detector is simple. Each node sends a heartbeat every interval `Δ`.
The monitor declares a node failed if nothing arrives for a timeout `T`. Every
other design is a refinement of that.

<Sub n="3.1" title="The trade you can't avoid">

Choosing `T` is choosing between two kinds of error:

| | Short timeout | Long timeout |
|---|---|---|
| **Detection time** | Fast | Slow: every real crash costs `T` of unavailability |
| **False positives** | Frequent: pauses and jitter look like death | Rare |
| **Cost of each false positive** | A failover, a rebalance, maybe split brain | — |

There's no setting that's good on both rows. That's what the hook of this
chapter means by "a timeout is a design choice": you're picking which failure
you'd rather have, and how often.

<Why>Why not use TCP to tell you the peer is gone?</Why>

Because TCP's defaults are tuned for patience, not detection. On Linux 6.10,
read from the lab container:

| Setting | Default | What it means |
|---|---|---|
| `tcp_keepalive_time` | 7,200 s | Idle time before the first keepalive probe (only if `SO_KEEPALIVE` is set) |
| `tcp_keepalive_intvl` | 75 s | Between probes |
| `tcp_keepalive_probes` | 9 | Probes before giving up: about 11 more minutes |
| `tcp_retries2` | 15 | Retransmissions of unacknowledged data before the connection dies: at least 924.6 s, per the [kernel docs](https://docs.kernel.org/networking/ip-sysctl.html) |

An idle connection to a machine that lost power stays "established" for over
two hours by default. A connection with unacknowledged data in flight takes over
15 minutes to fail. Applications that care set their own heartbeats, or
`TCP_USER_TIMEOUT`, or both.

</Sub>

A garbage collector does much worse. The next test runs a heartbeat thread
sleeping 100 ms inside a JVM whose main thread churns roughly 800 MB (estimated) of live

| Run | Full collections | Longest GC pause | Median heartbeat gap | Worst heartbeat gap |
|---|---|---|---|---|
| 1 | 34 | 2,781 ms | 609 ms | **2,884 ms** |
| 2 | 51 | 660 ms | 584 ms | 936 ms |
| 3 | 50 | 769 ms | 592 ms | 943 ms |

That's a deliberately unhappy JVM, close to its heap limit. But it's a
realistic one, and it shows the point: a live process with a 100 ms heartbeat
went silent for **almost three seconds**. A detector with a one-second timeout
would have declared it dead, and it would have woken up still believing it was
the leader.

<Callout label="Common mistake" kind="warn">
Setting a failure timeout from the heartbeat interval ("three missed
heartbeats") without measuring pauses. The right input is the worst gap a
*healthy* process produces under load, including GC and the scheduler, and it's
usually far longer than three intervals. Measure it, the way section 3.2 does,
on the machines you'll run on.
</Callout>

</Sub>

<Why>Why wait five minutes when the node was declared unreachable at 50 seconds?</Why>

Because declaring a node unreachable is cheap and reversible, and evicting its
pods isn't. A node that was merely partitioned from the API server is still
running its pods; evicting them early starts a second copy of every pod while
the first may still be serving. Kubernetes separates *suspecting* from
*acting*, and gives acting a much longer fuse. Workloads that need faster
failover set a smaller `tolerationSeconds` on their own pods.

It also refuses to act on a mass failure. If more than 55% of nodes in a zone
are unhealthy (`--unhealthy-zone-threshold`), the controller slows evictions
sharply, on the theory that the problem is more likely the controller's own
connectivity than half the zone dying at once
([nodes docs](https://kubernetes.io/docs/concepts/architecture/nodes/)).

</Sub>

<Sub n="3.4" title="Consensus timeouts: etcd and Raft">

Leader-based consensus uses the same mechanism at a smaller scale. A Raft leader
sends heartbeats; a follower that hears nothing for its election timeout starts
an election. etcd's [tuning guide](https://etcd.io/docs/v3.5/tuning/) sets the
defaults at a **100 ms** heartbeat and a **1,000 ms** election timeout, and gives
two rules: the heartbeat should be around the round-trip time between members,
and the election timeout "at least 10 times the round-trip time".

The [Raft paper](https://raft.github.io/raft.pdf) adds one more trick:
randomise each follower's election timeout (its example is 150–300 ms). Then
one follower usually times out first and wins before the others start competing
elections. The [consensus chapter](/topics/27-consensus) follows an election
message by message.

</Sub>

<SectionHeading n="04" id="accrual">Accrual detectors: a suspicion level instead of a verdict</SectionHeading>

A fixed timeout throws information away. It treats a node that's normally as
regular as a clock the same as one whose heartbeats always wander, and it gives
the application one bit: alive or dead.

<Sub n="4.1" title="The phi accrual detector">

Hayashibara, Défago, Yared and Katayama's
[φ accrual failure detector](https://doi.org/10.1109/RELDIS.2004.1353004)
(SRDS 2004) outputs a number instead. It keeps a window of recent heartbeat
inter-arrival times, fits a distribution to them, and asks: given how long it's
been since the last heartbeat, how unlikely is it that one is still coming?

`φ = −log10(P(a heartbeat arrives later than now))`

So φ is on a log scale of mistake probability. The paper puts it plainly: if
you suspect a node when φ ≥ 1, "the likeliness that we will make a mistake …
is about 10%. The likeliness is about 1% with Φ = 2, 0.1% with Φ = 3, and so
on." A threshold of 8, the default in both Cassandra and Akka, means a
one-in-a-hundred-million chance, *if* the model is right.

</Sub>

<Sub n="4.2" title="Akka's version, and why it floors the deviation">

<SourceRead
  file="akka-remote/src/main/scala/akka/remote/PhiAccrualFailureDetector.scala"
  repo="akka/akka"
  tag="v2.6.20"
  href="https://github.com/akka/akka/blob/v2.6.20/akka-remote/src/main/scala/akka/remote/PhiAccrualFailureDetector.scala#L173"

```scala
  private def phi(timestamp: Long): Double = {
    val oldState = state.get
    val oldTimestamp = oldState.timestamp

    if (oldTimestamp.isEmpty) 0.0 // treat unmanaged connections, e.g. with zero heartbeats, as healthy connections
    else {
      val timeDiff = timestamp - oldTimestamp.get

      val history = oldState.history
      val mean = history.mean
      val stdDeviation = ensureValidStdDeviation(history.stdDeviation)

      phi(timeDiff, mean + acceptableHeartbeatPauseMillis, stdDeviation)
    }
  }
  /* ... */
  private[akka] def phi(timeDiff: Long, mean: Double, stdDeviation: Double): Double = {
    val y = (timeDiff - mean) / stdDeviation
    val e = math.exp(-y * (1.5976 + 0.070566 * y * y))
    if (timeDiff > mean)
      -math.log10(e / (1.0 + e))
    else
      -math.log10(1.0 - 1.0 / (1.0 + e))
  }
```
</SourceRead>

Two lines there carry lessons from production. `acceptableHeartbeatPauseMillis`
is added to the mean, so the detector expects pauses of that length as normal.
And `ensureValidStdDeviation` never lets the deviation drop below
`min-std-deviation`.

Cassandra's gossip detector keeps the name and drops the normal distribution:

</SourceRead>

`phi` here is just elapsed time over the mean interval, and `PHI_FACTOR` is
`1 / ln(10)`, which converts it to the log10 scale of an exponential
distribution. So a node is convicted when silence exceeds `8 × ln(10) ≈ 18.4`
times its mean heartbeat interval. With gossip running once a second
(`Gossiper.intervalInMillis = 1000`), that's around 18 seconds.

<Why>Why check for a local pause first?</Why>

Because of the last row of the table in section 2.1. If `interpret` itself
hasn't run for more than 5 seconds (`DEFAULT_MAX_PAUSE`), the silence it's
about to judge is probably *its own* fault: a GC pause or a stalled VM on this
node. Cassandra logs "Not marking nodes down due to local pause" and refuses to
convict anyone until the pause is 5 seconds behind it. Every failure detector
should have this check, and most home-grown ones don't.

</Sub>

<SectionHeading n="05" id="gossip">Membership at scale: gossip and SWIM</SectionHeading>

Heartbeats answer "is that node alive?" for one monitor. A cluster needs every
member to agree, roughly, on the whole membership list. The naive approach, all
nodes heartbeating all nodes, sends `n²` messages per interval: a million a
second for a thousand nodes.

<Sub n="5.1" title="Gossip: spreading news like an epidemic">

In a gossip protocol each node periodically picks a few random peers and
exchanges what it knows. News spreads like an infection: each round roughly
multiplies the number of nodes that have it, so it reaches everyone in
`O(log n)` rounds, while each node sends a constant number of messages per
round.

Cassandra gossips once a second to a random live peer (and sometimes a seed or
an unreachable node). Each node's state carries a heartbeat counter it
increments itself, so a peer knows a node is alive when that counter keeps going
up, even if it heard it second- or third-hand.

</Sub>

<Sub n="5.2" title="SWIM: probe, ask for help, then suspect">

Das, Gupta and Motivala's [SWIM](https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf)
(DSN 2002) separates two jobs that gossip mixes together: *detecting* failures
and *disseminating* membership changes. Detection is a randomised probe;
dissemination piggybacks on the probes' own messages.

    { from: 2, to: 1, label: "ping", note: "Each helper pings N over its own network path. If any gets an ack, it relays it to M, and N is fine." },
    { from: 0, to: 3, label: "suspect N (inc 7)", note: "No acks at all. M doesn't declare N dead; it marks N **suspect** and spreads that, tagged with N's current **incarnation number**, piggybacked on its next pings." },
    { from: 1, to: 3, label: "alive N (inc 8)", note: "If N is alive and hears the rumour, it **refutes** it by gossiping `alive` with a higher incarnation. Only N can increment its own incarnation, so that message wins over the suspicion." },
    { from: 0, to: 3, label: "dead N", note: "If the suspicion timeout expires without a refutation, N is declared **dead**, and that spreads the same way." },
  ]}
/>

<Why>Why does the load stay constant as the cluster grows?</Why>

Because each member sends one probe per period, plus at most k indirect
requests when a probe fails, whatever the group size. The SWIM paper shows the
expected time until *some* member first detects a crash is at most `e/(e−1)`,
about 1.58 protocol periods, also independent of group size. Picking probe
targets round-robin from a shuffled list, instead of at random, bounds the worst
case: every member is probed by each other member within `2n − 1` periods.

</Sub>

<Sub n="5.3" title="memberlist: SWIM in production">

HashiCorp's [memberlist](https://github.com/hashicorp/memberlist) is the SWIM
implementation inside Consul, Nomad and Serf. Its LAN defaults, from `config.go`
at v0.5.1:

| Setting | Default | Meaning |
|---|---|---|
| `ProbeInterval` | 1 s | One probe per period |
| `ProbeTimeout` | 500 ms | Before falling back to indirect probes |

| `SuspicionMult` | 4 | Scales the suspicion timeout |
| `SuspicionMaxTimeoutMult` | 6 | Upper bound, as a multiple of the minimum |
| `GossipInterval` / `GossipNodes` | 200 ms / 3 | Dissemination of updates |
| `AwarenessMaxMultiplier` | 8 | How far a struggling node slows its own probing |

reach a node in a big cluster, and a suspect needs time to hear and refute its
own suspicion. From `util.go`, the minimum is

nodes; the formula in `util.go` gives 96.)

</Sub>

<Sub n="5.4" title="Lifeguard: when the prober is the problem">

SWIM's weakness is the one Cassandra guards against: a node that's slow to
process messages misses acks, suspects healthy peers, and spreads false
rumours. Dadgar, Phillips and Currey's
[Lifeguard](https://arxiv.org/abs/1707.00788) extensions to memberlist fix that
in two ways.

First, **local health awareness**. A node that has to refute suspicions about
itself, or whose probes keep failing, raises its own "awareness" score and
stretches its probe interval, up to 8× by default. A struggling node becomes a
more patient judge.

Second, **suspicion that accelerates with independent confirmations**. The
suspicion timer starts at the maximum and shrinks as other members
independently confirm the suspicion:

<SourceRead
  file="suspicion.go"
  repo="hashicorp/memberlist"
  tag="v0.5.1"
  href="https://github.com/hashicorp/memberlist/blob/v0.5.1/suspicion.go#L85"
>
```go
// remainingSuspicionTime takes the state variables of the suspicion timer and
// calculates the remaining time to wait before considering a node dead. The
// return value can be negative, so be prepared to fire the timer immediately in
// that case.
func remainingSuspicionTime(n, k int32, elapsed time.Duration, min, max time.Duration) time.Duration {
	frac := math.Log(float64(n)+1.0) / math.Log(float64(k)+1.0)
	raw := max.Seconds() - frac*(max.Seconds()-min.Seconds())
	timeout := time.Duration(math.Floor(1000.0*raw)) * time.Millisecond
	if timeout < min {
		timeout = min
	}

	// We have to take into account the amount of time that has passed so
	// far, so we get the right overall timeout.
	return timeout - elapsed
}
```
</SourceRead>

`k` is `SuspicionMult − 2`, so 2 confirmations by default. With none, a
suspect in a 100-node cluster gets the full 48 seconds to refute. Each
independent confirmation moves the timer logarithmically toward the 8-second
minimum. One confused node alone can't kill anyone quickly; several agreeing
nodes can.

<Callout label="Design implication">
Lifeguard's two ideas generalise. Make a detector distrust itself when it's
unhealthy, and require independent witnesses before acting fast. Redis Cluster
does the second too: a node's local `PFAIL` becomes a cluster-wide `FAIL` only
when a majority of masters report it within `2 × NODE_TIMEOUT`
([cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)).
</Callout>

</Sub>

<SectionHeading n="06" id="split-brain">Split brain: when the verdict is wrong</SectionHeading>

A false positive in a load balancer costs a little capacity. A false positive in
a leader election costs much more: the old leader is still alive, still
believes it's the leader, and now there are two.

<Sub n="6.1" title="What a 43-second partition did at GitHub">

On 21 October 2018, routine maintenance to replace failing optical equipment
cut connectivity between GitHub's US East Coast network hub and its primary
East Coast data center.
[Connectivity came back in 43 seconds](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/).
In that window, their MySQL failover tool, Orchestrator, promoted primaries on
the West Coast.

When the network healed, both coasts held writes the other didn't have:
several seconds of East Coast writes that hadn't replicated west, and, by the
time the team came to rebuild the topology, nearly 40 minutes of application
writes on the West Coast primaries. Failing back wasn't safe, and the incident ran to **24 hours and 11
minutes** of degraded service while they reconciled.

<Why>Why was 43 seconds enough to cause a day of damage?</Why>

Because the failover's timeout was shorter than the partition, and the action it
triggered wasn't reversible. The detector was right that the East Coast was
unreachable *from where it stood*. It was wrong about what that meant, and
promotion across regions turned a 43-second network event into divergent
histories.

</Sub>

<Sub n="6.2" title="The tools that stop two leaders">

| Tool | How it works | Examples |
|---|---|---|
| **Majority quorum** | A leader must be able to reach a majority. At most one side of a partition has one | Raft, ZooKeeper, etcd, Redis Cluster's master votes |
| **Leases** | Leadership expires after a fixed time unless renewed; a new leader waits it out | etcd leases, Chubby, ZooKeeper sessions |
| **Epochs / terms** | Each new leader gets a higher number; followers reject older ones | Raft terms, Kafka leader epochs, Redis `configEpoch` |
| **Fencing tokens** | The *storage* rejects writes carrying an older token | ZooKeeper `zxid`, etcd revisions used as tokens |
| **STONITH** | Power off or isolate the old node before promoting | Pacemaker [fencing](https://clusterlabs.org/projects/pacemaker/doc/2.1/Pacemaker_Explained/html/fencing.html), cloud API "stop instance" |

<Why>Why isn't a lease enough on its own?</Why>

Because a lease is a promise about time, and the process holding it can lose
track of time. A leader that's paused for longer than its lease wakes up,
doesn't know how long it was out, and writes as if it still holds the lease. The
JVM in section 3.2 paused for 2.9 seconds; Martin Kleppmann's
[analysis of distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
notes HBase GC pauses that lasted minutes, and a GitHub incident where packets
were delayed about 90 seconds.

The fix is to make the thing being protected check, instead of trusting the
lock holder:

<StepSequence
  title="A fencing token stops a paused leader's write"
  actors={["Client 1", "Lock service", "Client 2", "Storage"]}
  messages={[
    { from: 0, to: 1, label: "acquire", note: "Client 1 takes the lease. The lock service returns a **fencing token**, a number that increases with every grant: **33**." },
    { from: 0, to: 0, label: "GC pause", dashed: true, note: "Client 1 stops for longer than the lease. It doesn't know; to it, no time has passed." },
    { from: 2, to: 1, label: "acquire", note: "The lease expired, so the lock service grants it to Client 2, with token **34**." },
    { from: 2, to: 3, label: "write (34)", note: "Client 2 writes with token 34. Storage records **34** as the highest token it has seen." },
    { from: 0, to: 3, label: "write (33)", note: "Client 1 wakes and sends its delayed write with token 33." },
    { from: 3, to: 0, label: "rejected", note: "33 is lower than 34, so **storage rejects it**. The stale leader can't do damage, however long it slept." },
  ]}
/>

<Callout label="Common mistake" kind="warn">
Using a distributed lock for correctness without fencing. If the resource can't
check a token (a legacy database, an external API), a lease only makes
conflicts less likely. Either add the check at the resource, or design the
operation to be safe when two holders run it at once.
</Callout>

</Sub>

<SectionHeading n="07" id="choosing">Choosing a timeout on purpose</SectionHeading>

<Sub n="7.1" title="Defaults across real systems">

| System | Heartbeat | Declared failed after | What happens then |
|---|---|---|---|
| etcd / Raft | 100 ms | 1 s election timeout | New election |
| Akka Cluster | 1 s | φ > 8 ≈ 4.5 s of silence | Unreachable; downing is a separate decision |
| memberlist (Consul) | 1 s probe | 8–48 s suspicion at 100 nodes | Marked dead, removed from catalog |
| Cassandra | 1 s gossip | φ > 8 ≈ 18 × mean interval | Marked down; no data moves |
| Redis Cluster | `cluster-node-timeout`, 15 s by default | Majority of masters within 2 × timeout | Replica promoted |
| ZooKeeper sessions | Client pings | Negotiated, 2–20 × `tickTime` | Ephemeral nodes deleted |
| Kubernetes nodes | 10 s lease | 50 s | Tainted; pods evicted 300 s later |

The spread is three orders of magnitude, and each is reasonable for what it
triggers. etcd's timeout is short because an election is cheap and safe. A
Kubernetes eviction is slow because rescheduling a node's worth of pods is
expensive and may duplicate them.

</Sub>

<Sub n="7.2" title="A worksheet">

1. **Measure the healthy gap distribution** on your real machines under real
   load, including GC. Take the worst gap, not the p99.
2. **Price both errors.** What does a missed crash cost per second? What does
   one false positive cost: a failover, a cold cache, a rebalance, a
   possible second leader?
3. **Split suspect from act.** Suspect early and cheaply (stop routing reads
   there); act late and expensively (promote, evict, move data).
4. **Require independent witnesses** for expensive actions: a quorum, indirect
   probes, confirmations from other nodes.
5. **Guard against your own pauses.** If the detector itself was stalled,
   don't convict anyone.
6. **Rate-limit actions.** If many nodes look dead at once, the observer is the
   likeliest suspect.
7. **Fence** anything that must have one owner.

</Sub>

<Sub n="7.3" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| Nodes flap between up and down | Timeout below the healthy gap distribution | Lengthen it, raise φ threshold, add acceptable pause |
| Many nodes marked down at once, then back | The *observer* paused or lost its network | Local-pause guard; Lifeguard-style awareness; rate-limit actions |
| Failover takes minutes | Long chain of timeouts (e.g. Kubernetes defaults) | Shorter `tolerationSeconds` for that workload; app-level health checks |
| Two primaries after a network blip | Failover without quorum or fencing | Majority quorum, fencing tokens, STONITH |
| Dead peer's TCP connections stay open for hours | Kernel keepalive defaults | App heartbeats, `TCP_USER_TIMEOUT`, shorter keepalive on those sockets |
| Healthy node repeatedly suspected by one peer only | Asymmetric path or gray failure | Indirect probes; require multiple witnesses |
| `Not marking nodes down due to local pause` in Cassandra logs | GC or VM stall on that node | Fix the pause; the detector is protecting you |

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **A dead node and a slow one look the same.** Across a network, failure
   detection is always a guess made from silence.
2. **Every timeout trades detection time for false positives.** There's no
   setting that's good at both, so pick by what each error costs.
3. **Healthy processes go quiet for surprisingly long.** A 100 ms heartbeat ran
   up to 46% late on a shared box and 2.9 s late in a GC-bound JVM.
4. **TCP won't tell you in time.** Default keepalive takes over two hours to
   notice an idle dead peer.
5. **Accrual detectors output a suspicion level.** φ is a log10 mistake
   probability, and each consumer can pick its own threshold.
6. **Fitted distributions are overconfident in the tail.** That's why Akka
   floors the standard deviation and adds an acceptable pause.
7. **SWIM keeps per-node load constant.** Direct probe, indirect probes through
   k helpers, then suspicion that the suspect can refute with a higher
   incarnation.
8. **Detectors must distrust themselves.** Cassandra's local-pause guard and
   Lifeguard's awareness score stop a stalled node from convicting everyone.
9. **Separate suspecting from acting.** Kubernetes marks a node unreachable at
   50 s and evicts its pods only after 300 more.
10. **A wrong verdict becomes split brain without quorums and fencing.** Leases
    alone fail when the holder pauses; storage that checks tokens doesn't.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why can't a distributed system reliably detect that a node has crashed?">
Because it only sees messages, and a crashed node, a paused one and one behind a
broken link all produce the same silence. Any detector either waits (and is slow
on real crashes) or guesses (and sometimes convicts a healthy node). FLP makes
this formal for asynchronous systems.
</QA>

<QA level="beginner" q="What's the trade-off in choosing a heartbeat timeout?">
A short timeout detects crashes quickly and produces more false positives from
GC pauses, scheduling delay and network jitter. A long one is accurate and slow.
Pick it from the measured worst gap of a healthy process and from what each kind
of error costs.
</QA>

<QA level="intermediate" q="How does the phi accrual failure detector work?">
It records heartbeat inter-arrival times in a sliding window, fits a
distribution (normal in Akka, exponential in Cassandra), and computes φ =
−log10 of the probability that a heartbeat would still arrive given the time
since the last one. φ = 1 means about a 10% chance of a mistake, φ = 2 about 1%.
Applications choose thresholds; 8 is the common default.
</QA>

<QA level="intermediate" q="Walk through SWIM's failure detection.">
Each period a member pings one random (or round-robin) peer. If no ack arrives
within the probe timeout, it asks k other members to ping that peer. If none
succeed, it marks the peer suspect and gossips that with the peer's incarnation
number. The peer can refute by gossiping alive with a higher incarnation. If the
suspicion timeout passes without refutation, the peer is declared dead.
Updates piggyback on probe messages, so load per member is constant.
</QA>

<QA level="intermediate" q="A Kubernetes node loses power. How long until its pods run elsewhere, and why?">
About six minutes with defaults. The kubelet renews a Lease every 10 s; after
50 s without one (`node-monitor-grace-period`) the node goes `Unknown` and gets
an `unreachable:NoExecute` taint. Pods tolerate that taint for 300 s by default,
then are evicted and rescheduled. The long toleration exists because a merely
partitioned node may still be running its pods.
</QA>

<QA level="deep" q="Why does Akka enforce a minimum standard deviation in its phi detector?">
Because a very regular heartbeat gives a tiny standard deviation, and a normal
distribution with a tiny deviation calls any small delay astronomically
unlikely. Using the gaps measured here (mean 101 ms, σ 2.4 ms), φ would cross 8
at 114 ms, and a real 146 ms scheduling hiccup would score about 214. The floor
(100 ms by default) plus an acceptable heartbeat pause (3 s) keeps ordinary
jitter from convicting healthy nodes.
</QA>

<QA level="deep" q="A leader holds a 10-second lease. Why can it still corrupt data, and what fixes it?">
It can pause (GC, VM stall) for longer than the lease, wake without knowing time
passed, and write while a new leader also writes. Clocks and leases can't fix
that from the holder's side. The fix is at the resource: every grant carries a
monotonically increasing fencing token, and storage rejects any write with a
token lower than the highest it has seen. Consensus-based stores provide
suitable tokens (ZooKeeper zxid, etcd revision).
</QA>

<QA level="deep" q="What went wrong in GitHub's October 2018 incident, in failure-detection terms?">
A 43-second partition exceeded the failover tool's detection threshold, so
Orchestrator promoted West Coast primaries while East Coast ones still held
unreplicated writes. The detector was locally correct and globally wrong, and
the action (cross-region promotion) wasn't reversible. Both sides then had
writes the other lacked, and recovery took over 24 hours. The lessons: price the
action, not just the detection, and don't let a short partition trigger an
irreversible topology change.
</QA>

<Quiz>
  <Q q="φ = 3. What's the probability the detector is wrong, according to the paper's model?">
    About 0.1%: each unit of φ is a factor of ten.
  </Q>
  <Q q="Cassandra with phi_convict_threshold 8 and 1-second gossip. Roughly how long a silence convicts a node?">
    About 18 seconds: phi is t / mean scaled by 1/ln 10, so conviction needs
    t above 8 × ln 10 ≈ 18.4 mean intervals.
  </Q>
  <Q q="In SWIM, who can increment a node's incarnation number?">
    Only the node itself, when it refutes a suspicion. That's why its alive
    message always overrides the suspect rumour.
  </Q>
  <Q q="Why does Kubernetes slow evictions when more than 55% of a zone looks unhealthy?">
    Because a mass failure is more likely a problem with the controller's own
    view, such as a partition, than half the zone dying at once. Evicting
    everything would make it worse.
  </Q>
</Quiz>
