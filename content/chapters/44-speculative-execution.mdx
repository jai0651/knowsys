Every modern core guesses. It reaches an `if`, predicts which way it'll go, and
runs ahead on the guess. When the guess is wrong it throws the extra work away,
and for about twenty-five years everyone treated that throwing-away as complete.

It isn't. In 2018 Spectre and Meltdown showed that speculative work leaves a
trace in the cache, and that a program can read someone else's memory from
that trace. Fixes landed in every kernel, compiler and browser, and they
cost time on every syscall.

That's why this comes up in design reviews. Should the database fleet boot with
`mitigations=off`? Is that safe on dedicated hardware? This chapter builds the
two ingredients of the attack, walks one through step by step, covers the
variants and their mitigations, and measures what the mitigations cost.

<SectionHeading n="01" id="speculation">Speculation, and what it leaves behind</SectionHeading>

A core that waited for every branch to resolve would spend most of its time
idle. So it doesn't wait. It predicts, runs ahead, and checks its work later.

<Sub n="1.1" title="The window where nothing is real yet">

A modern core doesn't execute your program in order. It fetches far ahead,
issues instructions as their inputs become ready, and holds the results in a
<em className="term">reorder buffer</em> (the ROB) until it's sure they should
have happened.

On Apple's M-series the ROB is hundreds of entries deep. So hundreds of
instructions can be in flight, none of them yet *architecturally* real.

<Why>When does an instruction become real?</Why>

At retirement. Instructions leave the ROB in program order, and only then do
their effects become official: registers commit, stores drain, exceptions fire.
Anything the core did speculatively and shouldn't have gets squashed here, as if
it never ran.

</Sub>

<Sub n="1.2" title="Architectural state and microarchitectural state">

Registers roll back. Flags roll back. What doesn't roll back is the cache: a
line pulled in during the speculative detour stays pulled in. So the core forgets
it did the work, but not that it touched the memory.

<Why>Why didn't anyone treat that as a bug before 2018?</Why>

Because for correctness it isn't one. Architectural state, the registers and
memory your program can name, is restored perfectly on a bad guess. Speculation
was always understood to be invisible, and for what a program *computes*, it is.

<Callout label="Design implication">
Spectre's whole insight is that <strong>microarchitectural state is not
architectural state</strong>. Cache occupancy survives the squash. The CPU
cleans up everything it promised to clean up, and the one thing it never
promised, which lines are warm, is exactly the thing that leaks. Any shared
structure a program can time is a possible channel.
</Callout>

</Sub>

<SectionHeading n="02" id="ingredients">The two ingredients</SectionHeading>

Spectre needs two things: a branch predictor the attacker can train, and a
clock fine enough to tell a cache hit from a miss. Both are observable on their
own, before you combine them into an attack.

<Sub n="2.1" title="The predictor memorises, it doesn't just lean">

A branch predictor that only tracked "which way does this branch usually go"
would be beaten by a coin flip. Modern ones keep *history*. Feed a branch a
fixed but random-looking pattern that repeats, and the predictor learns the
whole sequence, not the average.

In a test on the M4, a buffer of 2<sup>20</sup> branches was filled by tiling a
period-N pattern, with both arms of the branch doing identical work. Only the
period changes, so the only variable is how often the predictor guesses wrong.

<Figure caption="Apple M4, clang 21 -O2, both branch arms noinline and equal-cost. A period-2 pattern (strict alternation, a 50/50 bias) predicts perfectly at 0.75 ns. The M4 keeps learning fixed patterns out past period 1024, still 2.6x faster than unlearnable random data at 3.24 ns/branch.">
<Plot
  xLabel="pattern period (branches)"
  yLabel="ns per branch"

  series={[{ name: "period learned", points: [[2, 0.746], [8, 0.929], [32, 0.990], [64, 1.013], [128, 1.136], [256, 1.167], [1024, 1.227]] }]}
/>
</Figure>

Strict alternation is a 50/50 branch with no bias at all, and the M4 predicts it
at **0.746 ns**. That's a state machine that has seen `taken, not-taken, taken,
not-taken` and extrapolated.

Push the period to 1024 and it still runs at **1.227 ns**, well under the
**3.239 ns** of data with no learnable pattern. It's a small,
trainable memory, maybe a few thousand entries, sitting in front of your
instruction stream.

<Why>Why is trainability a security problem?</Why>

Because the predictor is shared state. If you can train it, so can code that
runs just before yours, and it can train it to guess wrong in exactly the place
it wants.

</Sub>

<Sub n="2.2" title="A cache hit and a cache miss are different sizes in time">

Spectre's second ingredient is older and duller: a load that hits L1 is much faster
than one that misses to DRAM. On the M4, a randomised pointer chase measures
it, with dependent loads so each one's latency lands on the critical path.

<Compare
  cols={["Working set", "ns per dependent load", "Where it lives"]}
  rows={[

Ninety-odd nanoseconds against one. **That 90x ratio is the whole covert
channel.** If code touches memory at an address that depends on a secret, and
you can tell afterwards which line is warm, you've read the secret without
anyone handing it to you.

</Sub>

<SectionHeading n="03" id="spectre-v1">Spectre v1, step by step</SectionHeading>

Put the two ingredients together and you get the first variant: a bounds check
that the core skips speculatively.

<Sub n="3.1" title="The victim">

Here's the victim, in the pattern every writeup uses:

```cpp
uint8_t array1[16];              // the "public" array, size 16
uint8_t array2[256 * 512];       // the covert channel, one page per byte value

void victim(size_t x) {
    if (x < array1_size)                       // the guard
        temp &= array2[array1[x] * 512];       // read, then use as an index
}
```

That guard is correct. Architecturally, an out-of-bounds `x` never reads
anything. Spectre works in the window before the guard resolves.

    { from: 1, to: 3, label: "load array2[83*512]", note: "Speculatively, it reads the secret `array1[x]` = 83 and uses it to load one line of `array2`. **That line is now in cache.**" },

  ]}
/>

<Why>Why multiply by 512?</Why>

So each possible byte value lands on its own cache line, and far enough apart
that loading one doesn't pull its neighbours in. So the probe array has 256 slots,
one per value a byte can take.

</Sub>

<Sub n="3.2" title="Reading the byte back">

Last comes the receiver. It needs every probe line cold before the
attack, and a clock that can tell a 1 ns hit from a 93 ns miss afterwards.

On x86 both are easy. `clflush` is a user instruction that evicts a line, and
`rdtsc` resolves single cycles. That's why the textbook proof of concept, in
Appendix C of Kocher's paper, is written for x86.

<Predict
  q="A process on the M4 has a clock that ticks every 42 ns and no flush instruction. L1 hits take about 1 ns, DRAM misses about 93 ns. What does a naive Spectre receiver see?"
  options={[
    "The secret line clearly faster than the other 255",
    "Every line looks like a hit",
    "Every line looks like a miss",
    "A random byte each run",
  ]}
  answer={1}
>
A DRAM miss is only about two ticks, and an L1 hit is zero. Without a flush,
the receiver can only evict lines by streaming a big buffer, so most "misses"
stop in a nearer cache and read the same as a hit. Section 6 shows the run:
all 256 lines score as hits.
</Predict>

</Sub>

<SectionHeading n="04" id="variants">One idea, many variants</SectionHeading>

Spectre v1 mistrains a conditional branch. Once researchers saw that
speculation leaves footprints, they found other ways to steer it and other
buffers to sample.

<Sub n="4.1" title="The family, 2018 to 2023">

Dates matter here, because the mitigation each one forced is still running on
your machine today.

    ["Inception (SRSO)", "CVE-2023-20569", "Aug 2023", "Phantom recursive calls overflow the return stack buffer"],

/>

<Why>Why do the mitigations keep piling up?</Why>

Because they don't retire when the next bug lands. They stack. A 2024 kernel
carries the fixes for all nine rows, and section 7 adds up what they cost.

And the gap from 2019 to 2022 wasn't quiet, either. Researchers were realising that
every predictor and every internal buffer is fair game, and vendors were
patching microcode faster than the papers came out.

</Sub>

<Sub n="4.2" title="The ones that name Apple silicon">

Most of that table is Intel and AMD. Apple silicon has its own:

| Attack | When | What it abuses | Shown on |
|---|---|---|---|
| **GoFetch** | March 2024, no CVE | The <em className="term">data memory-dependent prefetcher</em> (DMP), which prefetches values that look like pointers | M1, M2, M3 |
| **SLAP** | January 2025, no CVE | The load *address* predictor | M2 and later, stealing data from Safari |
| **FLOP** | January 2025, no CVE | The load *value* predictor | M3 and later, from Safari and Chrome |

GoFetch feeds the DMP crypto key material shaped like a pointer, and the
prefetch leaks the key through the cache. Its authors never tested the M4,
which didn't exist yet, so where it stands on that chip isn't known.

SLAP and FLOP are prediction mechanisms newer than branch prediction, doing the
same trick one level down: guess a load's result, and speculate on the guess.

<Callout label="Design implication">
This pattern has held for a decade. Any structure that predicts, to run ahead of
certainty, is a structure you can mistrain into running ahead into somebody
else's data. New predictors in new chips should be expected to bring new
variants.
</Callout>

</Sub>

<SectionHeading n="05" id="mitigations">The mitigations, and which you can reach</SectionHeading>

The fix can't be "stop speculating", because speculation is most of why a
modern core is fast. So the fixes are patches around the edges, divided by which
prediction they break.

<Sub n="5.1" title="What the kernel and compiler do">

| Mitigation | Fixes | How it works |
|---|---|---|
| **KPTI / PTI** (kernel page-table isolation) | Meltdown | The kernel stops mapping most of itself into your process's page tables, so a speculative load can't reach kernel memory. Mainline Linux 4.15, 28 January 2018. |
| **Retpoline** | Spectre v2 | Invented by Paul Turner at Google: "return" plus "trampoline". Replaces an indirect branch with a return sequence that steers speculation into a dead `pause` loop. |
| **IBRS / eIBRS** | Spectre v2, Retbleed | Indirect Branch Restricted Speculation, a hardware control; eIBRS is the enhanced, always-on form. |
| **STIBP** | Cross-thread v2 | Single Thread Indirect Branch Predictors: stops one SMT sibling training the other's predictor. |
| **SSBD** | Spectre v4 | Speculative Store Bypass Disable: turns off the reordering behind v4. |
| **`__user` pointer sanitization** | Spectre v1 | A barrier the kernel puts on untrusted array indices. |

KPTI is the one every syscall pays for. Here's what it adds to a crossing:

  ]}
/>

<Why>Why wasn't retpoline the end of Spectre v2?</Why>

Retpoline assumes the return predictor is trustworthy. Retbleed, in 2022,
showed that on some Intel and AMD parts, return instructions could still take
their target from the branch predictor. ETH Zürich, who found it, put the
mitigation cost at **12 to 28%**.

</Sub>

<Sub n="5.2" title="Reading the state from inside a container">

Linux exposes what's mitigated at `/sys/devices/system/cpu/vulnerabilities/`,
added in 4.15 alongside KPTI. Read from a plain Ubuntu container on the M4, the
kernel is Docker Desktop's linuxkit VM, aarch64, so this is Linux looking at an
Apple core:

```shell
docker run --rm ubuntu:24.04 sh -c \
  'for f in /sys/devices/system/cpu/vulnerabilities/*; do
     printf "%-22s %s\n" "$(basename $f):" "$(cat $f)"; done'
```

<Panel label="linuxkit 6.10.14, aarch64, on Apple M4">
```text

mds:                   Not affected
meltdown:              Not affected

```
</Panel>

Meltdown, L1TF, MDS, Downfall and Retbleed are all "Not affected", because they
were Intel or AMD microarchitecture, not this ARM core. Spectre v1 gets the
software fix. Spectre v2 is "Not affected".

<Why>Why does spec_store_bypass say Vulnerable?</Why>

Because the kernel decided the fix wasn't worth the cost on this part in this
configuration. "Vulnerable" is a policy choice, not an oversight. On a
bare-metal Intel Xeon the same file is a wall of `Mitigation:` lines, and every
one of them is spending time.

</Sub>

<Sub n="5.3" title="What the browser does">

Kernels handle process boundaries. A browser has a harder job: it runs
attacker JavaScript on purpose, all day. Its defence has two parts.

| Defence | What it does | What it costs |
|---|---|---|
| **Site isolation** | Chrome puts each site in its own process, so a Spectre read inside a tab only reaches that site's memory | Memory: a process per site |
| **Coarse clocks** | `performance.now()` coarsened to microseconds; `SharedArrayBuffer` disabled by default after 2018 | Getting `SharedArrayBuffer` back needs **COOP and COEP** headers, which put the page in its own isolated browsing context |

<Why>Why disable SharedArrayBuffer?</Why>

Because a second thread incrementing a counter in shared memory is a home-made
nanosecond timer. Coarsening `performance.now()` is pointless if a page can
build its own clock.

Reduced timer precision is a strange mitigation. It doesn't fix the leak; it
blinds the reader. The next section shows that blinding from the attacker's
side.

</Sub>

<SectionHeading n="06" id="the-attack-on-an-m4">Running the textbook attack on an M4</SectionHeading>

<Sub n="6.1" title="Zero of forty bytes">

In a test on the M4, the Kocher Appendix C proof of concept was typed out and
run with its full logic: mistrain the branch, then time all 256 channel lines.
`_mm_clflush` became a big eviction loop and `rdtsc` became `mach_absolute_time`.

<Panel label="Apple M4, macOS 26.5.1, clang 21 -O2">
```text
[diag] of 256 channel lines, 256 scored >=900/999 -- no line stands out
  byte  0: got 0xff  score 999/999  weak  (want 'T')
  byte  1: got 0xff  score 999/999  weak  (want 'h')
  byte  2: got 0xff  score 999/999  weak  (want 'e')
  ...
recovered 0/40 bytes correctly
```
</Panel>

Every line scores 999 out of 999, so the receiver thinks all 256 are cache hits.
It recovered **0 of 40 bytes**.

<Why>Did speculation not happen?</Why>

It did. But the timer can't see the result:

<Cost items={[
  { what: "mach_absolute_time granularity", value: "41.67 ns", source: "M4, 24 MHz counter; smallest non-zero back-to-back delta is one tick" },
  { what: "L1 hit", value: "~1 ns", source: "dependent-load measurement, section 2.2" },
  { what: "DRAM miss", value: "~93 ns", source: "same measurement, 256 MB working set" },
]} />

What needs reading is a gap of 1 ns against 93 ns, with a ruler whose ticks are 42 ns
apart. A DRAM miss is barely two ticks; an L1 hit is zero.

And a normal user process on macOS has no cache-flush instruction. Evicting
lines meant streaming a 24 MB buffer, slow enough that the timing probably
washes out further. The x86 proof of concept works because `rdtsc` resolves
single cycles and `clflush` is a user instruction. Neither holds here.

</Sub>

<Sub n="6.2" title="The blinding is the mitigation">

<Callout label="Design implication">
This is the defence browsers ship, met from the other side. Real M4-class
attacks, GoFetch, SLAP and FLOP, don't rely on the coarse system clock; they
build their own timing primitives and amplify a weak signal over many trials.
A naive port doesn't, so it saw nothing. <strong>The leak is real, and failing
to read it is exactly what a coarsened timer is designed to produce.</strong>
</Callout>

The experiment reproduced the *cause*, speculation past a bounds check, and
could not reproduce the *read*. It doesn't prove a patient attacker fails. It
only shows that the easy version does.

<Callout label="Common mistake" kind="warn">
Reading a failed proof of concept as "this machine isn't vulnerable". A PoC
that scores every line alike has usually hit the timer wall, not a fixed
CPU. Check the clock's resolution against the hit/miss gap before drawing any
conclusion.
</Callout>

</Sub>

<SectionHeading n="07" id="cost">What the mitigations cost</SectionHeading>

<Sub n="7.1" title="The syscall tax">

Mitigations can't be toggled on Docker's shared kernel: `mitigations=off` is a
boot parameter, and that VM's boot isn't under the user's control. So the
with-and-without numbers here are attributed, and the baseline is measured.

A real `getpid` syscall under that linuxkit kernel on the M4 costs **132 ns**
(5M calls, the actual `SYS_getpid` trap, not the libc wrapper). For the
mitigation cost itself, the best source is probably still Brendan Gregg's 2018
analysis for Netflix:

<Compare
  cols={["Measured / reported", "Overhead", "Source"]}
  rows={[
    ["getpid syscall, M4, linuxkit 6.10.14", "132 ns (baseline)", "Docker run, 5M iterations"],
    ["KPTI at ~50k syscalls/sec/CPU", "~2%", "Gregg, Netflix, 2018"],
    ["KPTI, Netflix production range", "0.1–6%", "Gregg, depends on syscall rate"],
    ["KPTI + PCID, 100 MB working set", "2.1% → 0.5%", "Gregg: PCID cuts the TLB cost"],
    ["Retbleed mitigation", "12–28%", "ETH Zürich, 2022"],
  ]}
/>

<Why>Why does the overhead range so widely?</Why>

Because the tax is per crossing, so it tracks syscall rate roughly linearly.
Gregg's headline is that Netflix expected "between 0.1% and 6% overhead with
KPTI due to our syscall rates". A service doing 5k syscalls/sec/CPU barely
notices, maybe half a percent; one doing 500k pays real money.

PCID softens the worst of it by letting the TLB survive the page-table swap, so
Gregg's 2.1% falls to 0.5% once it's on.

</Sub>

<Sub n="7.2" title="Turning the tax into dollars">

Chapter 07 measured a `write` to `/dev/null` at 348 ns on this Mac, and showed a
busy service can burn 17% of a core just crossing the boundary. Layer the
mitigation tax on top and the arithmetic is unforgiving for syscall-heavy work:

<Estimate
  rows={[

A tenth of a core per node sounds small until it's multiplied by ten thousand

mitigations off" argument.

</Sub>

<SectionHeading n="08" id="what-to-do">What to do about it</SectionHeading>

There are two levers: turn mitigations off, or make the taxed path shorter. Most
teams should reach for the second and leave the first alone.

<Sub n="8.1" title="When mitigations=off is defensible">

`mitigations=off` disables every optional CPU mitigation in one boot flag: no
PTI, no retpoline, no MDS clearing. It's a real lever with a narrow use.

<Compare
  cols={["Situation", "mitigations=off?", "Why"]}
  rows={[
    ["Single-tenant box, no untrusted code, ever", "Defensible", "No attacker shares the hardware; the leak has no reader"],
    ["HPC / batch node you own end to end", "Often yes", "Trusted code only, and the tax hits tight syscall loops hard"],
    ["Anything running other people's code", "No", "That's the whole threat model: a tenant, a Lambda, a browser tab"],
    ["Kubernetes multi-tenant nodes", "No", "A pod is untrusted code by definition"],
    ["A laptop with a browser", "No", "JavaScript is untrusted code you invite in hourly"],
  ]}
/>

<Why>So why not flip it everywhere and reclaim the tax?</Why>

Because most hardware isn't single-tenant. On a box running one trusted
workload, the mitigations defend against a threat that can't reach you, and
turning them off is a rational reclaim of that 2–28%.

A system that runs other people's code in one process, like Cloudflare Workers,
has to treat this as part of its design, not a boot flag.

<Callout label="Common mistake" kind="warn">
Setting `mitigations=off` on shared hardware because a benchmark looked slow.
On a multi-tenant node it converts a hardware bug into a data breach, and the
person who flips it usually isn't the person who gets paged.
</Callout>

</Sub>

<Sub n="8.2" title="Make the boundary rare instead">

The tax is per crossing, so the highest-leverage move is crossing less.
Everything chapter 07 says about syscall reduction pays double once
mitigations are in the price. Ranked by what it returns:

1. **Buffer.** One `write` per 4 KB instead of per line. Forty crossings become
   one, and each one now carries the KPTI tax too, so the win is bigger than it
   was in 2017.
2. **Batch.** `writev`, `sendmmsg`, `recvmmsg`: many items, one crossing.
3. **Amortise with shared memory.** io_uring moves submission and completion
   into rings both sides read, so a busy server can run the data path with
   almost no syscalls. A path you don't cross pays no tax.
4. **Keep PCID on.** It is by default on anything modern. On a custom kernel,
   don't disable it to "simplify"; it's most of what makes KPTI affordable.

Batching and PCID are the ones people forget. A syscall you didn't make is the
only one that's reliably free, mitigations or not.

</Sub>

<Sub n="8.3" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| A pre-2018 syscall benchmark won't reproduce | KPTI on every crossing | Check PCID is on; buffer and batch syscalls |
| Kernel-heavy workload 12–28% slower after a kernel update on Intel or AMD | Retbleed mitigation | Accept it on shared hardware; consider `mitigations=off` only on single-tenant boxes |
| `vulnerabilities/*` shows `Vulnerable` | The kernel chose not to mitigate on this part | Decide whether untrusted code ever shares the host |
| `SharedArrayBuffer` is undefined in your page | Page isn't cross-origin isolated | Serve COOP and COEP headers |
| A Spectre PoC scores every probe line as a hit | Timer too coarse, or no flush instruction | Measure clock resolution against the hit/miss gap |

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **Speculation is rolled back architecturally, not microarchitecturally.**
   Registers and flags are restored after a bad guess; cache lines stay warm.
2. **Branch predictors are trainable memories.** The M4 learns fixed patterns
   past period 1024, and code that runs before yours can train them too.
3. **The covert channel is a timing gap.** On the M4, 1 ns for an L1 hit
   against about 93 ns for a DRAM miss.
4. **Spectre v1 turns a skipped bounds check into a read.** The secret picks
   which probe line is loaded, and timing the 256 lines recovers it.
5. **The variants keep coming and the mitigations stack.** A 2024 kernel
   carries fixes for everything from Meltdown to Inception.
6. **Apple silicon has its own.** GoFetch, SLAP and FLOP abuse the prefetcher
   and load predictors instead of branch prediction.
7. **Coarse clocks blind the reader; they don't fix the leak.** A naive PoC on
   the M4 recovered 0 of 40 bytes against a 42 ns timer.
8. **KPTI's cost tracks syscall rate.** Netflix saw 0.1–6%, and PCID cut one
   case from 2.1% to 0.5%.
9. **`mitigations=off` is only safe where no untrusted code shares the
   hardware.** Pods, Lambdas and browser tabs all count as untrusted.
10. **Crossing the boundary less beats removing the tax.** Buffer, batch, use
    io_uring, and keep PCID on.

<SectionHeading n="10" id="build">Build this</SectionHeading>

**Get it wrong the way the test above did. The failure is the lesson.**

- Take the Kocher Appendix C proof of concept and compile it on an Apple Mac
  with `clang++ -O2`. Swap `_mm_clflush` for a big eviction loop and `rdtsc`
  for `mach_absolute_time`.
- Run it. Expect **0 bytes** and every channel line scoring alike. You didn't
  break the attack; you hit the timer wall.
- Prove the wall is real. Read `mach_absolute_time` twice back to back in a
  tight loop and look at the smallest non-zero delta. You'll find one tick,
  about 42 ns, so a DRAM miss is only about two ticks and a miss that stops in
  a nearer cache is less than one.
- Now watch the *cause* work anyway: a randomised dependent pointer-chase across
  16 KB versus 256 MB gives you the 1 ns / 93 ns gap the attack depends on. The
  ingredient is there; only the reader is blind.

What's still open is the counter-thread timer, amplified over many trials the
way the real Apple-silicon papers do it. A naive counter thread was throttled
by cross-core coherency, and macOS gives no thread-affinity API to pin it. A
patient attacker probably recovers the byte on this M4; the test here didn't.

<CardGrid>
  <WildCard name="GoFetch, March 2024" verdict="The first Spectre-class break that names Apple silicon specifically. No microcode fix exists for M1/M2; the DMP can't be disabled from software there.">

    instead.
  </WildCard>
  <WildCard name="SLAP & FLOP, January 2025" verdict="Load prediction is the new branch prediction. Same trick, one layer deeper, and demonstrated against shipping browsers.">
    Georgia Tech's team abused the load-address predictor (M2+) and the
    load-value predictor (M3+) to read data out of Safari and Chrome. The
    predictors guess a load's address or result and speculate on the guess,
    exactly the mistrainable structure Spectre needs.
  </WildCard>
  <WildCard name="KPTI at Netflix, 2018" verdict="If a pre-2018 syscall benchmark won't reproduce, page-table isolation is the usual reason.">
    Brendan Gregg measured Meltdown's fix across production and found overhead
    tracking syscall rate: 0.1% to 6%, about 2% at 50k syscalls/sec per CPU. The
    write-up is still the clearest public account of the tax landing on real
    traffic.
  </WildCard>
  <WildCard name="Chrome Site Isolation" verdict="The industrial response to a bug that can't be fully patched in silicon: make the leak read only your own site's memory.">
    After Spectre, Chrome moved every site into its own renderer process and
    coarsened its timers. It's expensive in memory, and it shipped anyway,
    because the browser runs hostile code by design and can't trust the CPU to

  </WildCard>

<SectionHeading n="12" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Speculation is supposed to be invisible. How does Spectre see it?">
Architectural state is invisible: registers and flags roll back perfectly on a
bad guess. Microarchitectural state doesn't. A cache line pulled in during the
speculative detour stays warm after the squash.

Spectre reads that warmth. The secret never appears in any register you can name;
it appears as which cache line is fast, and a timer recovers it. The rollback is
complete for everything the CPU promised to undo, and cache occupancy was never
on that list.
</QA>

<QA level="beginner" q="What's the difference between Meltdown and Spectre v1?">
Meltdown (CVE-2017-5754) reads kernel memory from user space: a faulting load
grabs privileged data before the fault retires. Its fix is KPTI: unmap the
kernel from user page tables.

Spectre v1 (CVE-2017-5753) stays within one privilege level and mistrains a
bounds check so the CPU speculatively reads past an array. No page-table trick
stops it; the fix is a barrier on untrusted indices. Meltdown was mostly Intel;
Spectre v1 hits nearly every speculating core.
</QA>

<QA level="intermediate" q="Why did syscalls get slower in 2018, and by how much?">
KPTI. Meltdown's fix stops mapping the kernel into your process, so every
syscall swaps page tables entering and leaving the kernel, and that costs TLB
work on top of the trap.

Brendan Gregg measured 0.1% to 6% at Netflix, roughly 2% at 50k syscalls/sec per
CPU, scaling with syscall rate. PCID cuts it substantially (his 2.1% case fell
to 0.5% with PCID on) because the TLB no longer flushes on every crossing.
</QA>

<QA level="intermediate" q="You ran the textbook Spectre PoC on an M4 and it recovered nothing. Bug or defence?">
Defence, mostly. The out-of-bounds read still happens speculatively; the problem
is reading the cache footprint back. macOS gives user code a 42 ns timer and no
flush instruction. Even a full DRAM miss is only about two ticks of that
timer, and without a flush the probe lines probably never get evicted that far,
so most "misses" land in a nearer cache and read the same as a hit.

That's the same coarse-timer mitigation browsers ship, met from the attacker's
side. A serious attack builds a finer timer (a counter thread) and averages many
trials; the naive port doesn't, so it's blind.
</QA>

<QA level="deep" q="When is mitigations=off a reasonable choice?">
When no untrusted code shares the hardware. A single-tenant box running one
trusted workload, or an HPC node you own end to end, gets no protection from
mitigations against an attacker who can't reach it, so reclaiming the 2–28% is
rational.

It stops being reasonable the instant someone else's code runs on that silicon:
a Kubernetes pod, a Lambda, a browser tab. There the flag turns a hardware bug
into a data breach. The threat model is "shared hardware", and the flag is only
safe where that's false.
</QA>

<QA level="deep" q="Retpoline mitigated Spectre v2. Why did Retbleed need more?">
Retpoline replaces indirect branches with a return sequence that steers
speculation into a safe loop. It assumes the return predictor is trustworthy.

Retbleed (2022) broke that assumption: on some Intel and AMD parts, return
instructions could take their speculative target from the branch target buffer,
not the return stack, so a poisoned BTB defeats the trampoline. The fix moved to
hardware controls (IBRS/eIBRS), and ETH measured the cost at 12–28%, much
steeper than retpoline, and that's why it was contentious.
</QA>

<SectionHeading n="13" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="A secret never lands in a register the attacker can read. How does the byte escape?">
    As a cache line. The speculative load uses the secret to pick which line of a
    probe array to touch; that line stays warm after the squash, and its access
    time reveals the byte. The channel is timing, not data.
  </Q>
  <Q q="Your Spectre PoC scores every channel line as a hit. What's the first thing to check?">
    Timer resolution. If a single hit and a single miss both fit inside one clock
    tick, the receiver is blind. On the M4 that tick is ~42 ns and a full DRAM
    miss is ~90 ns, right at the edge. Without a flush instruction the lines
    rarely get that far out, and a naive single-shot read loses.
  </Q>
  <Q q="Two identical single-tenant boxes; one has mitigations=off. Is that a bug?">
    Not necessarily. With no untrusted code on the hardware, the mitigations
    defend against an attacker who can't reach it, so turning them off to reclaim
    syscall throughput is defensible. The same flag on a multi-tenant node is a
    breach waiting to happen.
  </Q>
  <Q q="Why did browsers disable SharedArrayBuffer after Spectre?">
    Because a second thread incrementing a counter is a home-made high-resolution
    timer, and Spectre needs one. Coarsening performance.now() is pointless if
    you can build your own clock. COOP/COEP isolation is now required to get it
    back.
  </Q>
</Quiz>
