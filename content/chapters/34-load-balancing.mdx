At a supermarket with ten checkouts, you can choose a queue in different ways. You could pick one at random and hope. You could walk to the next one in order. You could glance at two queues and join the shorter. Or, if you could see all ten at once, you could join the shortest of them all. The shoppers, the tills and the speed of the cashiers are the same in every case, but you'll wait for very different amounts of time.

A load balancer makes that choice for every request, thousands of times a second. The rule it uses matters more than most people expect, and you can measure how much in a short simulation.

<SectionHeading n="01" id="four-ways-to-pick">Simulate four ways to pick a server</SectionHeading>

Save this as `lb.py`. Ten servers each take about 1 ms per request, on average, and requests arrive at random so the fleet is 80% busy. The script sends 200,000 requests using each rule and reports the mean and p99 time, which includes waiting in the server's queue.

<Sub n="1.1" title="Same fleet, four rules">

<TryIt what="Send 200,000 requests to 10 servers at 80% load using four balancing rules" lang="python" toolchain="Python 3.14, macOS 26.5.1, fixed random seed">
```python
import random

def simulate(policy, servers=10, requests=200_000, load=0.8, seed=3):
    rng = random.Random(seed)
    free_at = [0.0] * servers                      # when each server finishes its queue
    t, lat = 0.0, []
    rate = load * servers                          # arrivals per ms (mean service time = 1 ms)
    for i in range(requests):
        t += rng.expovariate(rate)
        if policy == "random":
            s = rng.randrange(servers)
        elif policy == "round robin":
            s = i % servers
        elif policy == "two random choices":
            a, b = rng.sample(range(servers), 2)
            s = a if free_at[a] <= free_at[b] else b
        else:                                      # least loaded: the server that frees up first
            s = min(range(servers), key=free_at.__getitem__)
        start = max(t, free_at[s])
        free_at[s] = start + rng.expovariate(1.0)
        lat.append(free_at[s] - t)
    lat.sort()
    return sum(lat) / len(lat), lat[int(0.99 * len(lat))]

print(f"{'policy':<20}{'mean':>9}{'p99':>10}")
for p in ("random", "round robin", "two random choices", "least loaded"):
    m, q = simulate(p)
    print(f"{p:<20}{m:7.2f} ms{q:8.2f} ms")
```
<Output>
```

random                 5.12 ms   23.85 ms
round robin            2.91 ms   13.20 ms
two random choices     1.75 ms    6.21 ms
least loaded           1.21 ms    4.93 ms
```
</Output>
</TryIt>

Random assignment gave a p99 of 23.85 ms and least-loaded gave 4.93 ms, nearly five times better, with the same servers and the same traffic. Round robin sits in between. Looking at just two random servers and picking the shorter queue got most of the way to the best result: 6.21 ms.

</Sub>

<Sub n="1.2" title="What the rules assume">

Least-loaded is the best rule here because the simulation lets it see every server's backlog for free. A real balancer often can't: knowing every queue at every moment means asking every server, and the answer is stale by the time it arrives. Two random choices needs to look at only two, so balancers such as Envoy and HAProxy offer it.

Every rule here also assumes the servers are equally healthy. When one is slow or broken, the rule decides how much damage it does. The chapter starts from the job a load balancer does, then follows traffic down two layers: packets spread by routers and L4 balancers, and requests spread by L7 proxies.

</Sub>

<SectionHeading n="02" id="the-job">What a load balancer decides</SectionHeading>

A load balancer owns one address that clients know, a **VIP** (virtual IP),
and a set of **backends** that do the work. For each new unit of work it makes
one decision: which backend gets it.

<Sub n="2.1" title="Three jobs in one decision">

That decision carries three different jobs:

| Job | What it means | What goes wrong without it |
|---|---|---|
| **Spread load** | Keep every backend about equally busy | One server saturates while others idle |
| **Hide failures** | Stop sending work to backends that can't do it | Some fraction of users see errors |
| **Allow change** | Add, remove and replace backends without clients noticing | Every deploy or scale-down drops connections |

They pull against each other. Hiding failures means reacting fast to
bad signals, and allowing change means *not* moving traffic that's
fine where it is. Most of this chapter is about that tension.

</Sub>

<Sub n="2.2" title="Layer 4 or layer 7">

Your biggest design choice is what the balancer looks at.

| | Layer 4 (transport) | Layer 7 (application) |
|---|---|---|
| **Sees** | IP addresses, ports, TCP/UDP | HTTP method, path, headers, gRPC service |
| **Unit it balances** | A connection (a flow of packets) | A request |
| **TLS** | Passes it through | Usually terminates it |
| **Cost per unit** | Tiny: a hash and a table lookup per packet | Parse, maybe decrypt, route, re-encrypt |
| **Examples** | AWS NLB, Google Maglev, Facebook Katran, IPVS, kube-proxy | AWS ALB, Envoy, nginx, HAProxy in `mode http` |
| **Can do** | Millions of packets a second per core, any protocol | Retries, path routing, header rewrites, per-request balancing |

<Why>Why do large sites run both?</Why>

Because each is good at what the other can't do. An L4 tier can take a huge
packet rate and spread it across a fleet of L7 proxies without understanding
any of it. Those L7 proxies then make the per-request decisions. Google's
[Maglev paper](https://www.usenix.org/conference/nsdi16/technical-sessions/presentation/eisenbud)
describes exactly that stack, and Cloudflare, Facebook and GitHub run the same
shape.

<Callout label="Design implication">
Match the balancer's unit to your traffic's unit. Long-lived, multiplexed
connections (gRPC, HTTP/2, WebSockets, database pools) need L7 balancing or
client-side balancing; an L4 balancer spreads the connections evenly and the
work however it happens to fall.
</Callout>

</Sub>

<SectionHeading n="03" id="layer-4">Layer 4: spreading packets</SectionHeading>

Start at the bottom. A VIP might receive tens of gigabits a second, more than
any one machine can handle. So the first spreading happens in the network
itself.

<Sub n="3.1" title="ECMP: the router spreads the load">

Routers support **equal-cost multi-path** routing (ECMP): if several next hops
reach a destination at the same cost, the router picks one per packet by
hashing the packet's **5-tuple** (source IP, source port, destination IP,
destination port, protocol). The same flow always hashes to the same next hop,
so a TCP connection's packets arrive in order. [RFC 2992](https://datatracker.ietf.org/doc/html/rfc2992)
analyses the common "hash-threshold" method.

So a whole fleet of load balancers can announce the same VIP over BGP, each
at equal cost, and the router spreads flows across them. Maglev's authors
describe moving to this from active-passive pairs: "we can multiply the
capacity of a VIP by the maximum ECMP set size of the routers, and all
machines can be fully utilized."

<Sub n="3.2" title="Three ways to deliver a packet to a backend">

| Method | How it works | Client IP at the backend | Return traffic |
|---|---|---|---|
| **NAT** (IPVS NAT, kube-proxy, NLB by default) | Rewrite the destination to the backend's IP | Preserved, unless source NAT is added too | Must come back through the balancer to be un-rewritten |
| **Tunnel + DSR** (Maglev, Katran, GLB) | Encapsulate (GRE, IP-in-IP, GUE); backend decapsulates | Preserved | Direct to the client |
| **Proxy** (any L7, and L4 proxies like HAProxy `mode tcp`) | Terminate the connection, open a new one | Lost; pass it in `X-Forwarded-For` or the PROXY protocol | Through the proxy |

<Why>Why doesn't the load balancer need to see replies?</Why>

With DSR, a load balancer only handles the small inbound half of each
connection. Maglev's paper puts the reason plainly: DSR means "Maglev does not
need to handle returning packets, which are typically larger in size." It
also means the balancer can't observe the connection's end, which matters
for the next problem.

</Sub>

<Sub n="3.3" title="The problem: the set changes">

ECMP keeps a flow on one load balancer only while the set of next hops is
stable. Add a load-balancer machine, or lose one, and the router's hash maps
some existing flows to a *different* machine. That machine has never seen the
connection.

It happens one level down too. If each load balancer picks a backend
with `hash(5-tuple) % N`, removing one backend changes `N` and moves almost
every connection.

<Why>Can't the new machine just look up the connection?</Why>

Only if connection state is shared, and sharing per-connection state between
load balancers at millions of packets a second is what these designs avoid. So
they make the backend choice a *function of the packet* that every load
balancer computes identically, and they choose that function so a change in
the backend set moves as few flows as possible. Maglev combines both: a local
connection table for flows it has seen, and consistent hashing so a
*different* Maglev machine makes the same choice for flows it hasn't.

</Sub>

<Sub n="3.4" title="Maglev hashing">

Maglev builds a lookup table of prime size `M` (65,537 in the paper's
experiments) and fills every slot with a backend. Each backend has its own
pseudo-random permutation of slot numbers, derived from two hashes of its name:
an `offset` and a `skip`. Backends take turns claiming their next preferred
slot that's still empty, until the table is full.

Envoy's implementation of the paper's Pseudocode 1 is short enough to read:

```cpp
                                     (HashUtil::xxHash64(key_to_hash, 1) % (table_size_ - 1)) + 1,

  // ...
  // Iterate through the table build entries as many times as it takes to fill up the table.
  uint64_t table_index = 0;
  for (uint32_t iteration = 1; table_index < table_size_; ++iteration) {
    for (uint64_t i = 0; i < table_build_entries.size() && table_index < table_size_; i++) {

        entry.next_++;
        c = permutation(entry);

      table_[c] = entry.host_;
      entry.next_++;
      entry.count_++;
      table_index++;
    }

uint64_t MaglevTable::permutation(const TableBuildEntry& entry) {
  return (entry.offset_ + (entry.skip_ * entry.next_)) % table_size_;
}
```
</SourceRead>

A lookup is then `table[hash(5-tuple) % M]`: one hash and one array read per
new flow. Because `M` is prime and `skip` is between 1 and `M − 1`, each
backend's permutation visits every slot. Each backend ends up, the paper notes,
with either ⌊M/N⌋ or ⌈M/N⌉ slots, and recommends "M to be larger than 100 × N to
ensure at most a 1% difference". Envoy's default table size is also 65,537
([`maglev.proto`](https://github.com/envoyproxy/envoy/blob/v1.31.0/api/envoy/extensions/load_balancing_policies/maglev/v3/maglev.proto)).

Here's how it compares with plain modulo and with a classic consistent-hash
ring, on 500,000 random flow hashes, when one backend is removed:

<TryIt what="Modulo, ring and Maglev hashing: balance, and flows moved when one backend leaves" lang="python" toolchain="Python 3.14.6, Apple M4">
```python
def maglev(backends, M=65537):
    offset = {b: h(b, 1) % M for b in backends}
    skip   = {b: h(b, 2) % (M - 1) + 1 for b in backends}
    nxt = {b: 0 for b in backends}; table = [None] * M; filled = 0
    while True:
        for b in backends:                      # Pseudocode 1 in the Maglev paper
            c = (offset[b] + nxt[b] * skip[b]) % M
            while table[c] is not None:
                nxt[b] += 1; c = (offset[b] + nxt[b] * skip[b]) % M
            table[c] = b; nxt[b] += 1; filled += 1
            if filled == M: return lambda k: table[k % M]

for f in flows:                                 # 500,000 random 64-bit flow hashes
    a, b = before(f), after(f)                  # tables built with and without one backend
    if a != b:
        moved += 1
        if a != gone: needless += 1             # moved although its backend is still alive
```

<Why>Why would Maglev accept moving any flows needlessly?</Why>

Because uneven load costs money every second, and disruption only costs when
the set changes. Its authors say so directly: earlier schemes "prioritize minimal
disruption over load balancing", and "Maglev takes the opposite approach". A
backend that gets 1.32× its share forces you to overprovision the whole fleet by
that much. Those few flows Maglev moves needlessly are caught by the connection
table on the machine that already has them.

</Sub>

<Sub n="3.5" title="Other L4 designs">

| System | Data plane | Keeping connections through changes |
|---|---|---|
| **Maglev** (Google, [NSDI 2016](https://www.usenix.org/conference/nsdi16/technical-sessions/presentation/eisenbud)) | Kernel-bypass user-space forwarder; the paper reports saturating 10 Gbit/s with small packets | Maglev hashing plus a local connection table |
| **Katran** (Facebook, [2018](https://engineering.fb.com/2018/05/22/open-source/open-sourcing-katran-a-scalable-network-load-balancer/)) | XDP in the kernel driver | "An extended version of the Maglev hash" plus an LRU connection table |
| **GLB Director** (GitHub, [2018](https://github.blog/engineering/infrastructure/glb-director-open-source-load-balancer/)) | DPDK | Rendezvous hashing picks a primary and a secondary; a packet the primary doesn't know gets a "second chance" at the secondary |
| **Unimog** (Cloudflare, [2020](https://blog.cloudflare.com/unimog-cloudflares-edge-load-balancer/)) | XDP on every edge server, no separate tier | "Daisy chaining" from the Beamer paper: a server forwards packets for connections it doesn't own to the previous owner |

Every one of them solves the same problem from section 3.3: the set of
servers changes all the time, and existing connections must not notice.

</Sub>

<SectionHeading n="04" id="layer-7">Layer 7: choosing a backend per request</SectionHeading>

An L7 proxy terminates the client's connection and sends each request to a
backend over its own pool of connections. Now the unit is a request, and the
proxy can see how each backend is doing.

<Sub n="4.1" title="The algorithms">

| Algorithm | Picks | Uses | Weakness |
|---|---|---|---|
| **Round robin** (weighted) | The next backend in turn | Nothing about the backends | Keeps feeding a slow backend its full share |
| **Least connections / least request** | The backend with the fewest in flight | A counter per backend | Needs a global view; a fast-failing backend looks idle |
| **Power of two choices** (P2C) | The less loaded of two random backends | The same counter, for two backends | Slightly less exact than least-request |
| **Consistent hash** (ring, Maglev) | A backend determined by a key (user, session) | The key | Hot keys make hot backends |
| **Peak EWMA** (Finagle, Linkerd) | Lowest recent latency × load | Latency history | Needs tuning; reacts to noise |

<Why>Why pick from two random backends instead of the best one?</Why>

Because "the best one" needs a fresh global view, and when many proxies share
one stale view, they all pick the same "best" backend at once and overload it.
Picking two at random and taking the less loaded avoids the worst choices
without a herd. Michael Mitzenmacher's
[The Power of Two Choices in Randomized Load Balancing](https://www.eecs.harvard.edu/~michaelm/postscripts/tpds2001.pdf)
shows the second choice cuts the expected maximum load roughly exponentially, from
about `log n / log log n` to `log log n / log 2`.

Envoy's `LEAST_REQUEST` does exactly this: its `choice_count` "Defaults to 2
so that we perform two-choice selection"
([`least_request.proto`](https://github.com/envoyproxy/envoy/blob/v1.31.0/api/envoy/extensions/load_balancing_policies/least_request/v3/least_request.proto)).
HAProxy's `balance random(2)` picks "the least loaded of these servers" after
two draws.

</Sub>

<Why>Why is round robin's median four times worse, when three servers are fast?</Why>

Because wrk is a closed loop: 32 connections, each sending its next request only
after the last one returns. Round robin keeps handing the slow server a quarter
of the requests, so connections spend most of their time waiting on it, and
the whole fleet runs at the slow server's pace. That's also true of any client
pool with a fixed concurrency, such as a thread pool calling a service.

Least-connections notices that requests pile up on the slow server and sends it
2% of the traffic. `random(2)` sits between the two: with four servers, the
slow one is in half of all random pairs, and it only loses the comparison when
it has more in flight. The uneven `s1`/`s2`/`s3` counts under
`random(2)` come from HAProxy drawing through a consistent-hash map, which it
documents; `hash-balance-factor` evens it out. And the p99 of every algorithm stays
at 51 ms, because the slow server still gets *some* requests. Only removing it
fixes the tail.

<Callout label="Design implication">
Round robin is fine when backends are identical and healthy, which is exactly
when you don't need a clever balancer. On the day one backend degrades, a
load-aware algorithm (least-request or P2C) is the difference between one sick
server and a slow fleet. Make it the default.
</Callout>

</Sub>

<SectionHeading n="05" id="health-checks">Health checks that lie</SectionHeading>

Load-aware algorithms move traffic away from slow servers. Taking servers out
entirely is the job of health checks, and it's where load balancers most
often get it wrong.

<Sub n="5.1" title="Active and passive checks">

| | Active health check | Passive (outlier detection) |
|---|---|---|
| **How** | The balancer probes `GET /health` every few seconds | The balancer watches real responses: 5xx, resets, timeouts |
| **Sees** | Whatever `/health` checks | What users get |
| **Blind spot** | Anything `/health` doesn't exercise | Backends with no traffic yet |
| **Examples** | ALB/NLB target health, Kubernetes readiness probes, HAProxy `check` | Envoy outlier detection, HAProxy `observe layer7`, Linkerd failure accrual |

</Sub>

    [1, "Every real request to s4 now fails with a 500. But `/health` only checks that the process can answer HTTP."],
    [2, "The balancer's probe gets **200 OK** every second, so s4 stays marked healthy."],
    [3, "The balancer keeps sending s4 its share. With round robin that's a quarter of all traffic."],
    [4, "A quarter of users get errors, and every dashboard of **backend health** shows green."],
  ]}
/>

Measured with the same HAProxy setup, s4 now answering 500 to real requests
and 200 to `/health`:

<TryIt what="A lying health check, with and without passive observation" lang="shell" toolchain="HAProxy 2.8.16, wrk 4.1, linuxkit 6.10.14 aarch64">
```shell
#   server s4 127.0.0.1:18404 check inter 1s                    # first run
#   server s4 127.0.0.1:18404 check inter 1s \
#          observe layer7 error-limit 10 on-error mark-down     # second run
wrk -t2 -c32 -d10s http://127.0.0.1:18400/
```

<Output>
```text

  Non-2xx or 3xx responses: 19691
```

Without observation, 25% of requests failed while s4 reported `L7OK`. Watching
real responses cut the errors to 104. A second run of the observed setup

ten more errors.
</Output>

<Callout label="Common mistake" kind="warn">
Letting a passive check and a lying active check fight. Your server flaps: passive
detection ejects it, the active check readmits it, and users pay a burst of
errors each cycle. Either make `/health` reflect the thing that broke, or use
ejection with backoff, as Envoy does: the ejection time "is equal to the base
time multiplied by the number of times the host has been ejected"
([`outlier_detection.proto`](https://github.com/envoyproxy/envoy/blob/v1.31.0/api/envoy/config/cluster/v3/outlier_detection.proto)).
</Callout>

</Sub>

<Sub n="5.3" title="The black hole">

It gets worse with a load-aware algorithm. A server that fails *fast*, because
it rejects requests before doing any work, finishes requests sooner than its
healthy neighbours. To least-connections, that looks like the least busy server
in the fleet.

David Yanacek describes this in the Amazon Builders' Library article
[Implementing health checks](https://aws.amazon.com/builders-library/implementing-health-checks/):
"some load-balancing algorithms, such as 'least requests,' give more work to
the fastest server. When a server fails, it often begins failing requests
quickly, creating a 'black hole' in the service fleet by attracting more
requests than healthy servers."

<Predict
  q="Four backends behind HAProxy. s4's database is down, so it answers every request with an immediate 500; the other three take 2 ms to answer correctly. The health check passes on all four. What share of requests does leastconn send to s4?"
  options={["About 2%", "About 25%", "About 50%", "0%: HAProxy notices the 500s"]}
  answer={2}
>
About half. In three 10-second runs, leastconn sent s4 51.6%, 51.9% and 48.4%
of all requests, where round robin sent it exactly 25%. The failing server
never has requests in flight, so it always looks least loaded. The same
algorithm that protected the fleet from a slow server in section 4.2 doubles
the damage from a fast-failing one.
</Predict>

<Why>So is least-connections a bad idea?</Why>

No. It's the right default for slow servers, which are the common case. It needs
a partner that counts *failures*, not just load: outlier detection that
ejects a backend on consecutive 5xx. Yanacek also mentions a blunter fix used at
Amazon: "slowing down failed requests to match the average latency of
successful requests", so a broken server stops looking attractive.

</Sub>

<Sub n="5.4" title="The check that takes everyone out">

An obvious fix for a shallow check is a **deep** one: have `/health` query the
database too. Now the lie is gone, but a new failure appears. When the database
has a bad minute, *every* server's deep check fails at once, and a balancer
that believes them removes the whole fleet, turning a partial outage into a
total one.

| Check depth | Catches | Risk |
|---|---|---|
| **Liveness**: the process answers | Crashed or hung processes | Misses everything else (section 5.2) |
| **Local health**: disk writable, config loaded, workers alive | Problems on this one server | Misses broken dependencies |
| **Dependency health**: can reach the database, caches, downstreams | Server-specific connectivity failures | A shared dependency failing fails every server's check together |

Balancers defend against the last row by refusing to believe that everything
is broken:

| Balancer | Behaviour when too many backends look unhealthy |
|---|---|
| AWS NLB, ALB | **Fail open**: "when all servers fail health checks at the same time, the load balancer fails open, allowing traffic to all servers" (Yanacek; for ALB see [target health checks](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html)) |
| Envoy | **Panic mode**: below 50% healthy by default, it balances across all hosts, healthy or not ([`cluster.proto`](https://github.com/envoyproxy/envoy/blob/v1.31.0/api/envoy/config/cluster/v3/cluster.proto)) |
| Envoy outlier detection | Never ejects more than 10% of a cluster by default (`max_ejection_percent`) |

<Callout label="Design implication">
Make health checks precise about *this server*, and let the balancer's fail-open
or panic threshold handle *everyone*. A good `/health` checks the things only
this instance can get wrong (its own pool to the database, its disk, its
config) and treats a shared dependency's outage as "not my fault". Then a
database blip doesn't empty the fleet, and one server's broken pool still gets
it removed.
</Callout>

Envoy's outlier-detection defaults, all from `outlier_detection.proto` at
v1.31.0, show what a reasonable passive check looks like:

| Setting | Default | Meaning |
|---|---|---|
| `consecutive_5xx` | 5 | Consecutive errors before ejection |
| `interval` | 10 s | How often ejections are analysed |
| `base_ejection_time` | 30 s | Ejection length, multiplied by the number of times ejected |
| `max_ejection_percent` | 10% | Ceiling on how much of the cluster can be ejected |

</Sub>

<SectionHeading n="06" id="draining">Draining: removing a server without dropping requests</SectionHeading>

Allowing change was the third job. Every deploy removes every server at least
once, so how you remove one decides whether deploys are invisible.

<Sub n="6.1" title="What draining means">

**Draining** a backend means: stop sending it new work, let in-flight work
finish, then stop it. It sounds simple. It's hard because "stop sending it new
work" has to reach every balancer, proxy and client-side pool that knows about
the backend, and they don't all find out at the same moment.

| Layer | How it drains | Default wait |
|---|---|---|
| AWS ALB / NLB target groups | Target goes to `draining`; no new requests or connections | `deregistration_delay.timeout_seconds`: 300 s ([docs](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html)) |
| HAProxy | `set server be/s1 state drain` on the runtime API | Until connections close |
| Kubernetes | Pod marked `Terminating`; endpoint marked not ready | `terminationGracePeriodSeconds`: 30 s |
| Your process | Stop accepting, finish requests, close keep-alive connections | Whatever you code |

</Sub>

<Sub n="6.2" title="The Kubernetes race">

On Kubernetes, two things happen when a pod is deleted, and the
[pod lifecycle docs](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination)
are explicit that they happen "at the same time": the kubelet starts shutting
the pod down, and the control plane starts removing it from the Service's
EndpointSlices.

<StepSequence
  title="Why a pod gets requests after it's told to stop"
  actors={["API server", "Kubelet", "Your pod", "Proxies & LBs"]}
  messages={[
    { from: 0, to: 1, label: "pod Terminating", note: "A rollout deletes the pod. The API server records a deletion deadline, 30 seconds by default." },
    { from: 1, to: 2, label: "SIGTERM", note: "The kubelet runs any `preStop` hook, then sends **SIGTERM**. A naive server exits within milliseconds." },
    { from: 0, to: 3, label: "endpoint not ready", note: "In parallel, the EndpointSlice is updated. kube-proxy on every node, ingress controllers and mesh sidecars each learn about it **in their own time**." },
    { from: 3, to: 2, label: "new request", dashed: true, note: "Until they've all updated, some still send new connections to the pod. If it has already exited, those requests get **connection refused or reset**." },
    { from: 2, to: 2, label: "preStop: sleep", note: "The fix: delay shutdown. A `preStop` sleep of a few seconds keeps the pod serving while the endpoint removal propagates." },
    { from: 2, to: 3, label: "drain, then exit", note: "Then on SIGTERM, stop accepting, finish in-flight requests, close idle keep-alive connections, and exit well inside the grace period." },
  ]}
/>

<Callout label="Common mistake" kind="warn">
Treating SIGTERM as "exit now". SIGTERM arrives before the rest of the
cluster has stopped routing to you. Keep serving for a few seconds after
SIGTERM (or add a `preStop` sleep, which Kubernetes supports natively as a
`sleep` hook action since 1.30), then drain. Keep the total below `terminationGracePeriodSeconds`,
or the kubelet sends SIGKILL.
</Callout>

</Sub>

<Sub n="6.3" title="Keep-alive connections don't drain themselves">

An L7 balancer that marks a backend as draining stops sending *new* requests.
But clients talking to your server directly, or proxies holding a pool of
keep-alive connections to it, will keep reusing connections they already have.

<Why>How does a server tell a keep-alive client to go away?</Why>

By saying so in the protocol, on the next response. HTTP/1.1 has
`Connection: close`: send it on each response while draining, and the client
opens its next request on a new connection, which the balancer sends
elsewhere. HTTP/2 and gRPC have `GOAWAY`, which tells the client the highest
stream ID the server will process and that it should open new streams on a new
connection. Most servers probably send it on graceful shutdown, but check that yours does.

</Sub>

<Sub n="6.4" title="Filling: the other half of a deploy">

A freshly started server is probably slower than its neighbours for a while: cold caches, a
JIT that hasn't compiled the hot paths, connection pools still empty. A
least-connections balancer sees it idle and sends it a flood.

**Slow start** ramps a new backend's share up over time. In HAProxy,
`slowstart` makes the weight grow "linearly from 0 to 100%" over the given
time ([configuration manual](https://docs.haproxy.org/2.8/configuration.html)).
ALB target groups and Envoy have equivalents.

</Sub>

<SectionHeading n="07" id="operating">Running it</SectionHeading>

<Sub n="7.1" title="What to watch">

| Signal | Why it matters |
|---|---|
| Per-backend request rate and error rate | A black hole shows as one backend with a high share *and* a high error rate |
| Per-backend latency, not just the aggregate | The fleet p99 hides which server is slow |
| Health-check state changes per minute | Flapping means an active and a passive check disagree |
| 5xx generated by the balancer itself (ALB `HTTPCode_ELB_5XX_Count`, Envoy `upstream_cx_none_healthy`) | Distinguishes "no healthy backend" from "the backend errored" |
| Errors during deploys | Non-zero means draining is broken somewhere |

</Sub>

<Sub n="7.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| p50 fine, p90/p99 bad, one backend slow | Round robin feeding a degraded backend | Least-request or P2C; per-backend latency alerts |
| Error rate exactly 1/N, all health checks green | Shallow health check on a broken server | Check what the server needs; add outlier detection |
| One backend has far more traffic and far more errors | Black hole: least-request attracted to fast failures | Outlier ejection on 5xx; slow down failures |
| All backends removed during a database blip | Deep dependency health checks | Local-only checks; rely on fail-open or panic threshold |
| A backend bounces in and out every few seconds | Passive ejection and active check disagree | Fix `/health`, or ejection with backoff |
| Errors on every deploy | Process exits on SIGTERM before endpoints update | `preStop` sleep, graceful drain, `Connection: close` or `GOAWAY` |
| One pod hot, others idle, with gRPC | L4 balancing of multiplexed connections | L7 balancing or client-side balancing |
| Connections reset when an L4 balancer scales | ECMP set change without consistent hashing | Maglev-style hashing plus connection tracking |
| A new instance overloaded right after it starts | Least-connections sending a cold server a burst | Slow start |

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **A load balancer spreads load, hides failures and allows change**, and those
   jobs pull against each other.
2. **L4 balances connections; L7 balances requests.** Multiplexed protocols like
   gRPC need L7 or client-side balancing.
3. **ECMP lets routers spread a VIP across a fleet of balancers**, as long as the
   fleet doesn't change.
4. **Consistent hashing keeps flows in place when backends change.** Removing one
   of 100 backends moved 99% of flows with modulo and 1.6% with Maglev.
5. **Maglev chooses even load over minimal disruption**, and relies on its
   connection table for the difference.
6. **Load-aware algorithms matter when one server is sick.** With one 25× slower
   backend, leastconn cut p50 from 13.4 to 3.0 ms and gave it 2% of traffic.
7. **Power of two choices gets most of the benefit without a herd**, which is why
   it's Envoy's default for least-request.
8. **A shallow health check hides a broken server**, and a deep one can take out
   the fleet. Check what's local, and let fail-open handle the rest.
9. **Least-connections turns fast failures into a black hole.** It sent about
   half of all traffic to a server answering instant 500s.
10. **Draining is a race between shutdown and routing updates.** Keep serving
    after SIGTERM, then close keep-alive connections deliberately.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**A load balancer you can break.**

- Write a small L7 proxy in the language you use at work, with round robin,
  least-request and P2C, and per-backend counters for in-flight requests,
  errors and latency.
- Put four backends behind it with injectable faults: extra latency, instant
  500s, and a `/health` that lies. Reproduce section 4.2's table and section 5.3's black hole.
- Add outlier detection with an ejection time that doubles on each ejection,
  and a cap on how much of the fleet can be ejected. Show that it stops the
  black hole without flapping, and that a failure on all four backends doesn't
  eject them all.
- Add draining: an admin endpoint that stops new requests to a backend and sends
  `Connection: close` on its responses. Run a rolling restart under load and
  get the error count to zero.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What's the difference between an L4 and an L7 load balancer?">
L4 works on connections: it sees IPs and ports, picks a backend when a flow
starts, and forwards packets without parsing them. It's cheap and
protocol-agnostic. L7 terminates the connection and parses the application
protocol, usually HTTP, so it can balance per request, route on path or
headers, retry, and terminate TLS, at a much higher cost per unit of work.
</QA>

<QA level="beginner" q="What does connection draining do?">
It stops sending new work to a backend while letting in-flight work finish,
before the backend is stopped. On AWS target groups the default deregistration
delay is 300 seconds. On Kubernetes, draining has to cover the gap between
SIGTERM and every proxy removing the endpoint, usually with a `preStop` sleep
and graceful shutdown in the server.
</QA>

<QA level="intermediate" q="Why is round robin a poor default?">
It ignores backend state, so a degraded backend keeps receiving its full
share. Any client with bounded concurrency then spends most of its time waiting
on that backend. In the test here, one 25× slower backend of four took round
robin's p50 to 13.4 ms against 3.0 ms for least-connections, which sent it 2%
of traffic. Least-request or power of two choices are better defaults.
</QA>

<QA level="intermediate" q="Explain the power of two choices.">
Pick two backends at random and send the request to the one with fewer
requests in flight. It avoids the worst backends without every balancer
herding onto the same "best" one from a stale view. Mitzenmacher showed the
second choice reduces the maximum load exponentially compared with a single
random choice. Envoy's least-request uses two choices by default.
</QA>

<QA level="intermediate" q="A service has a 25% error rate and all four backends pass health checks. What's going on?">
Probably one backend is broken in a way `/health` doesn't test, such as a lost
database connection, and round robin keeps giving it a quarter of the traffic.
Look at per-backend error rates. Fix the health check to cover what that server
needs, and add passive outlier detection on 5xx so the balancer reacts to what
users see.
</QA>

<QA level="deep" q="How does Maglev hashing work, and why is it preferred over a hash ring for L4 balancing?">
Each backend gets a permutation of the slots of a prime-sized table, derived
from an offset and a skip hashed from its name. Backends take turns claiming
their next free preferred slot until the table is full, so each gets ⌊M/N⌋ or
⌈M/N⌉ slots. Lookup is one hash and one array read. A ring with virtual nodes
moves fewer flows on changes but balances unevenly; in the simulation here, the
ring's busiest of 100 backends carried 1.32× its share against 1.03× for Maglev.
Maglev covers its extra disruption with a connection-tracking table.
</QA>

<QA level="deep" q="What's a load-balancing black hole?">
A backend that fails fast, returning errors without doing work, looks idle to a
least-connections or least-request balancer, so it attracts more traffic than
healthy backends. In the test here, leastconn sent about half of all requests to
the failing one of four servers. Defences are outlier ejection on consecutive
errors, slowing failures down to normal latency, and alerting on
per-backend share combined with error rate.
</QA>

<QA level="deep" q="Should a health check test the database?">
Test this server's ability to use it, not the database's health. If every
server's check fails when the shared database blips, the balancer removes the
whole fleet and a partial outage becomes total. Check local things (own pool,
disk, config, worker threads), and rely on the balancer's fail-open or panic
threshold, such as NLB failing open or Envoy's 50% panic threshold, for failures
that hit every server at once.
</QA>

<SectionHeading n="11" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="Removing one of 100 backends with hash % N moves how many flows?">
    About 99% in the simulation. Every flow whose hash modulo 100 differs from its
    hash modulo 99 moves, which is nearly all of them.
  </Q>
  <Q q="Why is Maglev's table size prime?">
    So that any skip between 1 and M − 1 generates a permutation that visits
    every slot exactly once.
  </Q>
  <Q q="Envoy is ejecting hosts for 5xx. How much of a cluster can it eject by default?">
    10%, set by max_ejection_percent. Below 50% healthy, the panic threshold
    makes it balance across all hosts anyway.
  </Q>
  <Q q="A pod exits within 50 ms of SIGTERM. Why do some requests fail?">
    Endpoint removal happens in parallel with SIGTERM, so proxies and nodes keep
    routing to the pod until they catch up. Keep serving for a few seconds first.
  </Q>
</Quiz>
