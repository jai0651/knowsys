You meet the memory model when multithreaded code that passed every test on an
Intel laptop starts failing on Graviton or an M-series Mac. You also use it every
time you copy a `std::shared_ptr` or a Rust `Arc`, probably without thinking
about it.

The problem is that neither your compiler nor your processor runs your code in
the order you wrote it. A single thread can't tell. A second thread can, and it
may see your writes in a different order from the one in your source.

This chapter shows where the reordering comes from, then builds the rulebook
that says what another thread is allowed to see: happens-before, and five
orderings. It looks at what each ordering compiles to on ARM, what they cost,
and the ways people get them wrong.

<SectionHeading n="01" id="reordering">Why your code doesn't run in the order you wrote it</SectionHeading>

Most of us carry a simple model of how a program runs: statements execute in
the order you wrote them, and each one finishes before the next starts.

For a single thread that model is never wrong in any way you can detect. It's
also not what happens. Two separate layers reorder your code.

<Sub n="1.1" title="The compiler moves code">

The compiler moves your code around whenever the result is the same for the
thread running it. It keeps a variable in a register instead of writing it back
every iteration, or it hoists a load out of a loop.

Its only obligation is that a single thread can't tell. Nothing obliges it to
consider what another thread might see.

</Sub>

<Sub n="1.2" title="The processor parks stores in a buffer">

The processor does its own version. Chapter 02 showed that a store to a line
that isn't in cache can take about 83 ns to reach it, and no core is going to
stall for that. Here's what it does instead:

/>

<Why>Why doesn't your own thread ever notice?</Why>

Because it checks the store buffer before it reads memory. Everything looks in
order *from the inside*. It's other threads, reading through the cache, that see
stores late, and possibly in a different order.

</Sub>

<SectionHeading n="02" id="publication">The publication problem</SectionHeading>

Now add a second thread, and the illusion breaks.

<Sub n="2.1" title="Data, then a flag">

One thread fills in an object and then sets a flag to say it's ready:

```cpp
data  = compute();   // A
ready = true;        // B
```

The other thread waits for `ready` and then reads `data`.

<Predict
  q="The reader sees ready == true. Is it guaranteed to read the new value of data?"
  options={[
    "Yes: A was written before B",
    "Yes on every architecture, as long as both are plain ints",
    "No: it can see ready == true and still read the old data",
    "Only if the two variables share a cache line",
  ]}
  answer={2}
>
It can see the old `data`. Suppose `data`'s line wasn't in cache and `ready`'s
was. B lands first, and the other core sees it first. On ARM that's allowed. On
x86 the hardware happens to keep stores in order, and the compiler may still
reorder A and B on either.
</Predict>

Step through how it happens on ARM:

  ]}
/>

This bug often turns up only after a move to Graviton or Apple Silicon, months
after the code shipped.

</Sub>

<Sub n="2.2" title="Worse than a stale read">

<Why>Isn't the worst case just reading an old value?</Why>

No. Two threads touching one ordinary location, at least one writing, with no
synchronisation between them, is a **data race**. In C++ a data race is
*undefined behaviour*.

The compiler is entitled to assume races can't happen and transform surrounding
code on that basis. That's why racy programs work for years and then break on a
compiler upgrade with no source change.

<Callout label="Design implication">
You need a way to say "this ordering matters", and the language has to know you
said it. That's what **atomic** variables with an **ordering** are for. The
**memory model** is the rulebook that says which values a read is allowed to
return.
</Callout>

</Sub>

<SectionHeading n="03" id="model">Happens-before, and five orderings</SectionHeading>

The whole model rests on one relation.

<Sub n="3.1" title="Happens-before">

If action X **happens-before** action Y, then everything X wrote is visible to
Y. If no such relation exists between two conflicting accesses, you have a data
race and the program has no defined meaning.

Happens-before is built from two sources: program order within a thread, and
**synchronises-with** edges between threads. Atomics are how you create those
edges. Nothing else does.

</Sub>

<Sub n="3.2" title="The orderings, and what each edge costs">

| Ordering | Guarantees | Creates an edge? |
|---|---|---|
| **relaxed** | Atomicity only. No ordering with anything. | No |
| **acquire** (load) | Nothing after it moves before it | Yes, with a matching release |
| **release** (store) | Nothing before it moves after it | Yes, with a matching acquire |
| **acq_rel** | Both, on a read-modify-write | Yes |
| **seq_cst** | The above, plus one global order all threads agree on | Yes, and transitively |

If you store to `ready` with **release**, you're promising that everything you
wrote before it becomes visible no later than it does. If the reader loads
`ready` with **acquire** and sees `true`, it's guaranteed to see those earlier
writes too.

<Why>What does an acquire do on its own?</Why>

Nothing. Acquire and release **only work in pairs, on the same variable**. An
acquire load with no matching release store compiles perfectly and guarantees
nothing.

<Callout label="Common mistake" kind="warn">
An unpaired acquire or release. It's the single most common way this model is
misused, and it compiles without a warning. Write the pairing in a comment next
to both halves.
</Callout>

</Sub>

<Sub n="3.3" title="The one pattern you'll actually write">

Roughly ninety percent of real atomic usage is publication:

```cpp
Config* cfg = new Config{...};                  // 1. construct
ready.store(cfg, std::memory_order_release);    // 2. publish

// another thread
Config* c = ready.load(std::memory_order_acquire);
if (c) use(c->field);                           // 3. safe to read
```

/>

</Sub>

<Sub n="3.4" title="Where you already use it">

You meet this model every time you use a reference-counted pointer.
`std::shared_ptr` and Rust's `Arc` decrement their counts with a release, then
use an acquire before freeing:

    { from: 2, to: 2, label: "delete", note: "The thread that frees the object has now **seen every other thread's last write to it**. No write can land in freed memory." },
  ]}
/>

The Linux kernel spells the same pair `smp_store_release` and
`smp_load_acquire`.

</Sub>

<SectionHeading n="04" id="codegen">What the orderings compile to</SectionHeading>

<Sub n="4.1" title="A description of hardware, generalised">

The model didn't come from theory hunting for an application. C++11 needed one
abstraction that could be implemented efficiently on x86, ARM, POWER and
Itanium, all of which reorder differently.

Instead of exposing each architecture's barriers, the committee defined the
*weakest useful* guarantees and let each backend emit whatever its hardware
needs.

<Why>So does release mean "insert a fence"?</Why>

Not really. It means "establish this edge", and what the compiler emits depends
entirely on the target.

</Sub>

<Sub n="4.2" title="On ARMv8, there's no barrier at all">

Most explanations picture acquire and release inserting a barrier instruction.
On ARMv8 that's simply wrong, and the disassembly settles it:

<SourceRead
  file="clang++ -O2 -c, objdump"
  repo="aarch64"
  tag="Apple M4, ARMv8.6"
  href="https://developer.arm.com/documentation/ddi0487/latest/"
>
```asm
ld_rlx:  ldr   x0, [x8]        ; relaxed load  — an ordinary load
ld_acq:  ldapr x0, [x8]        ; acquire load  — Load-Acquire RCpc
st_rlx:  str   x0, [x8]        ; relaxed store — an ordinary store
st_rel:  stlr  x0, [x8]        ; release store — Store-Release
st_sc:   stlr  x0, [x8]        ; seq_cst store — THE SAME INSTRUCTION
```
</SourceRead>

Three things in five lines:

| What you see | What it means |
|---|---|
| **No `dmb` anywhere** | Ordering is encoded in the load and store opcodes, not bolted on as a separate barrier |
| **seq_cst store = release store** | Paired with acquire-family loads, `stlr` already gives sequential consistency, so the compiler has nothing extra to emit |
| **`ldapr`, not `ldar`** | The ARMv8.3 RCpc variant: a weaker, cheaper acquire that Apple's cores implement |

</Sub>

<SectionHeading n="05" id="x86-vs-arm">x86 hides the bug ARM will find</SectionHeading>

<Sub n="5.1" title="The model is fine. Your testing hardware isn't.">

Architectures differ in how much they reorder on their own:

| Architecture | Reorders | Consequence |
|---|---|---|
| **x86-64 (TSO)** | Store→load only | Most under-synchronised code accidentally works |
| **ARMv8 / AArch64** | Almost anything | The same code fails, months later |
| **POWER, RISC-V** | Even more freely | Rare in production, brutal when hit |

Code missing acquire/release can pass every test on an Intel laptop and fail on
Graviton, an M-series Mac or an Ampere server:

```cpp
// WRONG — and it passes everything on x86-64
data = compute();                             // plain store
ready.store(true, std::memory_order_relaxed);
```

<Why>Why does this work on x86?</Why>

Total store order (TSO) won't reorder those two stores, so an x86 reader
observing `ready` also sees `data`. ARM reorders happily. Same source, same
compiler, and the bug waits for different silicon.

<Callout label="Design implication">
Run your test suite on ARM routinely. A Graviton instance or an M-series laptop
exposes a class of bug that x86 structurally can't. More ordering bugs are
probably found by changing hardware than by reading code.
</Callout>

The classic casualty is **double-checked locking**. The lazy-singleton idiom was
widely published in a form broken on any reordering machine: a reader can see a
non-null pointer to a half-constructed object. Java fixed it in the 1.5 memory
model; C++ needs acquire/release or `std::call_once`.

</Sub>

<Sub n="5.2" title="volatile is not part of this model">

`volatile` tells the compiler not to elide or cache an access. It says nothing
about the processor, nothing about atomicity, and nothing about ordering between
different variables. It creates no happens-before edge at all.

| | Java `volatile` | C/C++ `volatile` | C++ `std::atomic` |
|---|---|---|---|
| Stops the compiler caching the access | Yes | Yes | Yes |
| Orders other memory accesses | Roughly sequential consistency | No | Yes, per the ordering you choose |
| Meant for | Thread synchronisation | Device registers, signal handlers | Thread synchronisation |

Java's meaning is where the confusion comes from.

<Callout label="Common mistake" kind="warn">
Using `volatile` for a flag shared between C++ threads. It stops compiler
caching and does nothing else. Use `std::atomic`.
</Callout>

</Sub>

<SectionHeading n="06" id="cost">What it costs in practice</SectionHeading>

A natural question is what the guarantee costs. Isn't the strongest ordering,
`seq_cst`, supposed to be slow?

<Callout label="The machine, and a caveat" kind="note">
Apple M4, clang 21 `-O2`. Read-modify-write numbers are medians of 3 × 50M
iterations. I deliberately don't publish per-load and per-store timings: at
0.2–0.4 ns they're at the edge of what the harness resolves, and my first
attempt had the compiler hoist the plain load out of the loop. The disassembly
in 4.2 is the trustworthy evidence, not those timings.
</Callout>

<Sub n="6.1" title="What the strongest ordering costs">

<Cost items={[
  { what: "fetch_add, relaxed", value: "1.596 ns", source: "median of 3 × 50M, single thread" },
  { what: "fetch_add, seq_cst", value: "1.592 ns", source: "same harness — indistinguishable" },
  { what: "Difference", value: "~0%", source: "both compile to one LSE atomic instruction" },
]} />

**Sequential consistency is free here, uncontended.** Both compile to a single
ARMv8.1 atomic, and the stronger ordering is a different opcode, not extra work.

On older ARM without LSE, or on x86 where a `seq_cst` store needs `xchg` or
`mfence`, there's a real gap. It's probably smaller than you'd assume, and dwarfed by
contention.

</Sub>

<Sub n="6.2" title="Contention costs far more">

Chapter 14 has the comparison that matters, measured in its own harness:

| Operation | Cost |
|---|---|
| `fetch_add`, uncontended | 3.0 ns |
| `fetch_add`, eight threads | 18.4 ns |
| Compare-exchange loop, under the same contention | 162 ns |

Contention costs 10–100× what ordering does. Fix that first.

<Callout label="Common mistake" kind="warn">
Dropping `seq_cst` to `relaxed` because it's "faster", without measuring. It's
probably the most common way to introduce a race that survives review, and on
this machine it saved nothing.
</Callout>

</Sub>

<SectionHeading n="07" id="apply">Rules, and how to find the bugs</SectionHeading>

<Sub n="7.1" title="Five rules">

1. **Default to `seq_cst`.** It's the C++ default because reasoning about
   anything weaker is genuinely hard, and section 6 says it's usually free.
2. **Use relaxed for counters whose value never gates control flow.** Metrics,
   progress indicators, statistics.
3. **Use acquire/release in pairs, and write the pairing in a comment.** An
   unpaired acquire is a bug that compiles.
4. **Never use `volatile` for thread synchronisation.**
5. **Test on ARM.**

</Sub>

<Sub n="7.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| Passes on x86, fails on ARM | Missing acquire/release; TSO was hiding it | Release store, acquire load; run tests on ARM |
| Reader sees a non-null pointer to a half-built object | Publication with a relaxed or plain store | Release the pointer, acquire it on the reader |
| Racy code broke after a compiler upgrade | Data race is UB; the optimiser used that | Make the shared variable atomic |
| A `volatile` flag between threads misbehaves | `volatile` orders nothing | `std::atomic` |
| Atomics are slow under load | Contention, not ordering | Reduce sharing before weakening ordering |

```shell
clang++ -fsanitize=thread -O1 -g app.cpp        # finds what review doesn't
clang++ -O2 -S -o - app.cpp | grep -E 'ldar|ldapr|stlr|dmb|lock'
```

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **Neither the compiler nor the CPU runs your code in order.** They only
   promise that one thread can't tell.
2. **Store buffers let later stores become visible first.** Your own thread
   reads through the buffer; other threads don't.
3. **A data race is undefined behaviour in C++.** Not a stale read: the
   optimiser may assume it never happens.
4. **Happens-before is the whole model.** It comes from program order plus
   synchronises-with edges, and only atomics create those edges.
5. **Acquire and release only work in pairs, on the same variable.** An
   unpaired acquire compiles and guarantees nothing.
6. **Publication is most of real atomic use.** Construct, release-store the
   pointer, acquire-load it on the reader.
7. **On ARMv8, orderings are opcodes, not barriers.** A `seq_cst` store is the
   same `stlr` as a release store.
8. **x86 hides ordering bugs that ARM exposes.** TSO keeps stores in order, so
   test on ARM.
9. **`volatile` isn't synchronisation in C or C++.** Use `std::atomic`.
10. **Ordering is cheap; contention isn't.** `fetch_add` cost 1.596 ns relaxed
    and 1.592 ns `seq_cst`, and 18.4 ns across eight threads.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Reproduce store-buffer reordering yourself.** Two threads, the Dekker shape:

```
thread 1:  x = 1;  r1 = y;
thread 2:  y = 1;  r2 = x;
```

Sequential consistency forbids `r1 == 0 && r2 == 0`: one store must come first.

- Run it a few million times with relaxed atomics on an ARM machine and count how
  often that impossible result appears.
- Then add `seq_cst`, and watch the count go to zero.
- Disassemble both to find the instruction that changed.

Seeing an impossible outcome happen on hardware you own is what stops this being
abstract.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What is a data race, and why is it worse than a stale read?">
Two threads accessing one location, at least one writing, with no
synchronisation between them. In C++ it's undefined behaviour — the compiler may
assume it can't happen and optimise on that basis.

So the outcome isn't "you read an old value"; surrounding code may be
transformed in ways that make no sense. That's why racy programs work for years
and then break on a compiler upgrade.
</QA>

<QA level="intermediate" q="What do acquire and release actually guarantee?">
Release on a store means nothing before it in program order moves after it.
Acquire on a load means nothing after it moves before it. Pair them on the same
variable and everything the releasing thread wrote before the store is visible
to the acquiring thread after the load.

They only work in pairs. An acquire load with no matching release store compiles
fine and guarantees nothing at all.
</QA>

<QA level="intermediate" q="Is volatile enough for sharing a flag between threads in C++?">
No. It stops the compiler eliding or caching the access and does nothing else —
no processor ordering, no atomicity for wide types, no happens-before edge.

Java's `volatile` does imply ordering, which is where the confusion comes from.
In C++ use `std::atomic`. `volatile` is for device registers and signal
handlers.
</QA>

<QA level="deep" q="Your code passes on x86 and fails on ARM. What's the likely class of bug?">
Missing acquire/release. x86-64 is total-store-ordered — it only reorders a
store followed by a load to a different address — so a plain store then a flag
store stays in order and most under-synchronised code accidentally works. ARM
reorders far more freely.

Concretely: `data = compute(); ready.store(true, relaxed);` is fine on x86 and
broken on ARM, because a reader can observe `ready` before `data`. Use a release
store and an acquire load, and run your test suite on ARM routinely.
</QA>

<QA level="deep" q="How much does seq_cst cost compared to relaxed?">
Less than people assume, and you should measure instead of guessing. On an M4 I
measured `fetch_add` at 1.596 ns relaxed and 1.592 ns seq_cst — indistinguishable,
because both compile to a single ARMv8.1 LSE atomic with the ordering encoded in
the opcode. The disassembly shows a seq_cst store emitting exactly the same
`stlr` as a release store.

Contention is the expensive thing. The same operation reaches 18.4 ns across
eight threads and a compare-exchange loop 162 ns. Reduce sharing before
weakening ordering.
</QA>
