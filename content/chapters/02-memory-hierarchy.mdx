<SectionHeading n="01" cmd="./reproduce --show" id="observe">What you observe</SectionHeading>

Here is a loop that does nothing but follow pointers:

```cpp
void** p = (void**)a[0];
for (long i = 0; i < REPS; i++) p = (void**)*p;   // one load, repeated
```

One instruction in the body. Run it over an 8 KB array of pointers and each
iteration costs **1.48 ns**. Run the identical loop over a 128 MB array and it
costs **82.92 ns**.

Sixty-eight times, from the same instruction. Nothing about the code changed.
Nothing about the work changed — it's still one dependent load. Only the size of
the array moved.

<Callout label="Why this matters more than algorithmic complexity">
A cache-friendly O(n²) routinely beats a cache-hostile O(n log n) at real sizes,
because asymptotic analysis assumes every memory access costs the same. That
assumption has been wrong since roughly 1990 and gets wronger every generation.
Sixty-eight times is a lot of constant factor to hide inside a big-O.
</Callout>

<SectionHeading n="02" cmd="objdump -d ./explain" id="mechanism">Why it happens</SectionHeading>

<Sub n="2.1" title="Caches, and the unit they work in">

Between the core and DRAM sit two or three levels of progressively larger,
slower cache. A load checks each in turn.

Critically, caches don't store bytes — they store **lines**. Touch one byte and
128 of them move on this machine, 64 on most x86. Coherence is tracked per line.
Prefetching predicts in lines. Eviction happens per line. There is no such thing
as reading one byte.

<Sub n="2.2" title="Why the benchmark chases pointers">

Measuring this honestly is harder than it looks, and a naive attempt measures
something else entirely.

A loop of *independent* loads measures **bandwidth**: the core issues many
concurrently and the prefetcher runs ahead guessing the next line. You can get
twenty times the apparent speed and it's a different property.

For latency each load must depend on the last. A random permutation linked into
a cycle does it — the address of the next load is the value of the current one,
so exactly one miss is outstanding and the prefetcher has nothing to predict.

</Sub>

<Sub n="2.3" title="Coherence, and why writes are different">

Several cores caching one line must agree. MESI and its descendants give each
cached line a state, and a core wanting to **write** must first invalidate every
other copy.

Reads share freely. **Writes serialise**, because ownership can only be in one
place — and that's the entire explanation for false sharing.

</Sub>

<SectionHeading n="04" cmd="./sweep | tee curve.dat" id="measurements">The measurements</SectionHeading>

<Callout label="The machine" kind="note">
Apple M4, macOS 26.5.1, clang 21 `-O2`. Dependent pointer chase through a random
permutation, working set swept from 8 KB to 128 MB. The permutation defeats the
prefetcher; the dependency defeats out-of-order overlap.
</Callout>

Notice how **flat each plateau is**. Within a level, size barely matters. Across
a boundary, it's everything. That shape is why "make the working set fit" is the
highest-leverage change available, and why halving a struct can double your
throughput with no algorithmic change at all.

<Sub n="4.2" title="What sharing costs on top">

Chapter 13 measured the coherence side directly: eight threads incrementing
separate counters that happen to share one cache line ran at 14.6 ns per
operation against 0.27 ns when padded apart. **55×**, with no lock and no shared
data — purely the invalidation traffic from 2.3.

</Sub>

<SectionHeading n="05" cmd="patch -p1 < fix.diff" id="act">What to do about it</SectionHeading>

Three interventions, in descending order of what they typically pay.

1. **Make it smaller.** Shrink structs, use narrower types, drop padding,
   replace 8-byte pointers with 4-byte indices. This moves you left on the
   curve, and the curve is steep. Halving a 128 MB working set to 32 MB is
   roughly 2× from the measurement above, before any other change.
2. **Make it contiguous.** Array-of-structs to struct-of-arrays when you only
   touch some fields. Sequential access recruits the prefetcher, which is the
   difference between the curve above and a much flatter one.
3. **Make it unshared.** Pad anything two threads write with `alignas`, using
   your platform's real line size. 55× is waiting otherwise.

<SectionHeading n="06" cmd="make bench && ./bench" id="reproduce">Reproduce it yourself</SectionHeading>

**Measure your own curve.** Forty lines, and you'll use the result for years.

- Build a random permutation of pointers linked into one cycle, for working sets
  from 4 KB to 256 MB.
- Chase it. Plot ns per access against size, log x-axis.
- Read your cache sizes off the cliffs, then check them against `sysctl -a | grep
  cachesize` or `lscpu`.

Then run it again with a **sequential** permutation instead of a random one and
watch the whole curve flatten. That second run is the prefetcher, and seeing its
effect as a before-and-after teaches more than any description.

```shell
# Line size — query it, never assume
getconf LEVEL1_DCACHE_LINESIZE      # Linux
sysctl -n hw.cachelinesize          # macOS

# Is it memory, and which level?
perf stat -e cache-references,cache-misses,LLC-load-misses ./app
perf record -e cache-misses -g ./app && perf report
```

<SectionHeading n="08" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why is iterating an array faster than a linked list with the same elements?">
Two reasons, the second mattering more. An array is contiguous, so each line
fetch brings several elements you're about to use. And the addresses are
predictable, so the prefetcher loads them before you ask.

A linked list gives a dependent load per node — you can't compute the next
address until the current one arrives — and nodes may be scattered. Past cache
size that's the difference between roughly 1 ns and 80 ns per step.
</QA>

<QA level="intermediate" q="How would you measure memory latency, and what's the trap?">
Chase pointers through a random permutation sized to the level you're probing.
Each load's address comes from the previous load's value, so one miss is
outstanding and the prefetcher has nothing to predict.

The trap is measuring independent loads. The core issues many concurrently and
you measure bandwidth — a different property, and potentially twenty times
better.
</QA>

<QA level="intermediate" q="What is false sharing and how do you fix it?">
Two threads writing different variables in one cache line. Coherence works per
line, so each write invalidates the other core's copy and they serialise despite
sharing no data.

Pad each onto its own line with `alignas`, using the real line size. It's 128
bytes on Apple Silicon and 64 on x86-64, so padding to 64 on an M-series chip
fixes nothing. Chapter 13 measured the penalty at 55× across eight threads.
</QA>

<QA level="deep" q="An O(n log n) algorithm is losing to an O(n²) one on real data. How?">
Constant factors, specifically cache behaviour. If the n² version walks
contiguous memory and the n log n version chases pointers, each step of the
better algorithm can cost seventy times more. I measured 1.22 ns for an
L1-resident dependent access against 82.92 ns at a 128 MB working set.

Asymptotic analysis assumes uniform access cost. That stopped being true around
1990 and the gap widens with every generation.
</QA>

<QA level="deep" q="Your matrix code is fast at 1023×1023 and slow at 1024×1024. Explain.">
Cache set aliasing. Caches are set-associative and the set index comes from
middle address bits. With a power-of-two row stride, the same column across many
rows maps to one set, so you exhaust associativity and evict lines you're about
to reuse — even though the data would fit.

Pad the row length so the stride isn't a power of two. One extra element per
row, which looks like waste and is the optimisation.
</QA>

<Quiz>
  <Q q="Roughly how much slower is DRAM than L1?">
    Around 60–70×. I measured 1.22 ns against 82.92 ns on an M4 — same
    instruction, different working set size.
  </Q>
  <Q q="You pad a struct to 64 bytes on an M-series Mac. Did it stop false sharing?">
    No. Lines are 128 bytes there, so two 64-byte-padded fields still share one.
    Query the size instead of assuming it.
  </Q>
  <Q q="Why does a benchmark of independent loads not measure latency?">
    The core issues many at once and the prefetcher runs ahead, so you measure
    bandwidth. Latency needs a dependent chain.
  </Q>
  <Q q="Your working set is 20 MB and random access is slow. Cheapest fix?">
    Make it smaller. Getting under about 16 MB moves you from ~42 ns to ~10 ns
    on the measured curve, with no algorithmic change.
  </Q>
</Quiz>
