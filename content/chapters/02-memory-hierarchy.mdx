You meet the memory hierarchy whenever code gets slower as its data grows,
faster than the algorithm says it should. A hash table that was quick in tests
crawls in production. An O(n²) routine beats an O(n log n) one on real data. Two
threads updating two different counters slow each other down.

All three come from the same place. A load's cost depends on where its data
lives, and nothing in the source code tells you where that is. On the M4 in this
chapter one load instruction costs anywhere from 1.5 ns to 83 ns.

This chapter builds up caches from the problem they solve, shows how to measure
latency without fooling yourself, measures the whole curve from L1 to DRAM, and
puts a number on what sharing a cache line between cores costs.

<SectionHeading n="01" id="why-caches">Why a core needs caches</SectionHeading>

Chapter 01 ended with a core that can start several instructions every cycle.
Now give it some data to work on. Where does the data come from?

From DRAM, in the simplest design, and DRAM is slow next to the core. On the M4
a load that goes all the way out to main memory takes about **83 nanoseconds**,
long enough for the core to have run hundreds of instructions.

<Why>Why not just make memory faster?</Why>

Processors got faster much more quickly than memory did over the last forty
years. That gap is usually called the **memory wall**. If every load paid the
full trip to DRAM, a fast core would spend almost all its time waiting.

<Sub n="1.1" title="Two habits every program has">

The fix is to keep a small, fast copy of recently used memory right next to the
core: a **cache**. It works because programs are predictable in two ways.

| Habit | What it means | Example |
|---|---|---|
| **Temporal locality** | Something you touched a moment ago, you'll probably touch again soon | A loop counter, the top of a hash bucket |
| **Spatial locality** | Something *next to* what you touched, you'll probably touch soon too | The next element of an array |

The second habit shapes the whole design, as the next section shows.

</Sub>

<Sub n="1.2" title="Levels, and the working set">

<Why>Why not one big, fast cache?</Why>

Because a cache can't be both. Bigger arrays of memory take longer to search,
and they sit physically farther from the core.

So there are several, in levels: a tiny **L1**, a larger and slower **L2**,
then DRAM. A load checks each in turn:

What a load costs depends on which level holds its line. That depends on how
much memory your code keeps touching, its **working set**. The same instruction
can cost 1.5 ns or 83 ns, and section 3 shows one load doing exactly that.

</Sub>

<SectionHeading n="02" id="lines">Lines, not bytes</SectionHeading>

A cache doesn't fetch the byte you asked for. It fetches the block around it,
called a **cache line**.

<Sub n="2.1" title="The unit everything works in">

A line is 128 bytes on this machine and 64 on most x86 chips. Coherence is
tracked per line. Prefetching predicts in lines. Eviction happens per line.
There's no such thing as reading one byte.

That's what makes spatial locality pay. Walk an array of 4-byte `int`s and one
miss brings in 32 of them. A sequential scan misses once every 32 elements and
runs from cache the rest of the time.

</Sub>

<Sub n="2.2" title="Paying for bytes you don't read">

The flip side is that you pay for the whole line whether you use it or not.

<Predict
  q="Each element of your array is a 128-byte struct, and the loop reads one 4-byte field from each. How much of every line you pay for is useful?"
  options={[
    "All of it: the rest of the struct is nearby",
    "About half",
    "About 3%",
    "It depends on the compiler",
  ]}
  answer={2}
>
Four bytes of 128, about **3%**. The other 97% was moved and never read, and it
pushed something useful out of the cache on the way in.
</Predict>

<Callout label="Design implication">
A scan should read only the bytes it uses. That's why columnar databases like
DuckDB and ClickHouse store each column contiguously, and why game engines built
on entity-component systems lay out each component as its own array.
</Callout>

Mike Acton's 2014 CppCon talk, "Data-Oriented Design and C++", made the same
argument: the object-oriented layout most C++ teaching promotes is a cache
disaster, and transforming data in contiguous arrays is the actual job. The
games industry largely came round.

</Sub>

<Sub n="2.3" title="Sets, and power-of-two strides">

Caches are **set-associative**. The set a line goes into comes from middle
bits of its address, and each set holds only a few lines.

<Why>Why is matrix code fast at 1023×1023 and slow at 1024×1024?</Why>

With a power-of-two row stride, the same column across many rows maps to one
set. You exhaust that set's slots and evict lines you're about to reuse, even
though the data would fit in the cache as a whole.

The fix is to pad the row length so the stride isn't a power of two. One extra
element per row looks like waste, and it's the optimisation.

</Sub>

<SectionHeading n="03" id="pointer-chase">One load, sixty-eight times the cost</SectionHeading>

Here's a loop that does nothing but follow pointers:

```cpp
void** p = (void**)a[0];
for (long i = 0; i < REPS; i++) p = (void**)*p;   // one load, repeated
```

One instruction in the body. Run it over an 8 KB array of pointers and each
iteration costs **1.48 ns**. Run the identical loop over a 128 MB array and it
costs **82.92 ns**.

Sixty-eight times, from the same instruction. The code didn't change and the
work didn't change: it's still one dependent load. Only the size of the array
moved.

<Callout label="Design implication">
A cache-friendly O(n²) routinely beats a cache-hostile O(n log n) at real sizes,
because asymptotic analysis assumes every memory access costs the same. That
assumption has been wrong since roughly 1990 and gets wronger every generation.
Sixty-eight times is a lot of constant factor to hide inside a big-O.
</Callout>

<Sub n="3.1" title="Why the benchmark chases pointers">

Measuring this honestly is harder than it looks, and a naive attempt measures
something else entirely.

<Why>Why not just time a loop of loads over a big array?</Why>

Because a loop of *independent* loads measures **bandwidth**. The core issues
many at once (chapter 01's out-of-order execution), and the prefetcher runs
ahead guessing the next line. You can get twenty times the apparent speed, and
it's a different property.

For latency, each load must depend on the last. Step through what the chase
does to the memory system:

    { from: 1, to: 2, label: "miss", note: "The permutation is random, so the prefetcher has **no pattern to predict**. Another full trip." },
    { from: 2, to: 0, label: "next address", note: "Each iteration costs one full latency. Divide total time by iterations and you've measured it." },

/>

A random permutation linked into one cycle does both jobs. The dependency
defeats out-of-order overlap; the randomness defeats the prefetcher.

<Callout label="Common mistake" kind="warn">
Benchmarking memory latency with independent loads, or a sequential walk. You
measure bandwidth and the prefetcher instead, potentially twenty times better
than the latency you wanted.
</Callout>

</Sub>

<SectionHeading n="04" id="coherence">Coherence: what happens when cores share a line</SectionHeading>

Multiple cores add one more problem. If two cores each hold a copy of the same
line and one writes to it, the other copy is now wrong.

<Sub n="4.1" title="MESI, and why writes are different">

The hardware keeps copies in agreement with a **coherence protocol**. MESI and
its descendants give each cached line a state, and a core wanting to **write
must first invalidate every other copy**.

| State | Meaning | Cost to write |
|---|---|---|
| **Modified** | This core owns it, dirty | Free: already exclusive |
| **Exclusive** | Only copy, clean | Free |
| **Shared** | Several cores hold read copies | Invalidate all of them first |
| **Invalid** | Not here | Fetch, possibly from another core's cache |

Reads share freely. Writes serialise, because ownership can only be in one
place.

</Sub>

<Sub n="4.2" title="False sharing">

Two threads writing two *different* variables that happen to sit in the same
line still fight over it. Coherence works per line, not per variable. That's
**false sharing**:

<StepSequence
  title="Two counters, one cache line"
  actors={["Core A", "Shared line", "Core B"]}

    { from: 2, to: 1, label: "write b", note: "Core B increments counter `b`, a different variable in the **same 128-byte line**. It needs ownership too." },
    { from: 1, to: 0, label: "invalidate", note: "A's copy is **invalidated**. The line moves to B, which now holds it Modified." },
    { from: 0, to: 1, label: "write a", note: "A increments `a` again. Its copy is Invalid, so it has to **fetch the line back** from B's cache." },
    { from: 1, to: 2, label: "invalidate", note: "B's copy is invalidated. The line ping-pongs on every write, and neither thread shares any data." },
  ]}
/>

<Why>How much does it cost?</Why>

Chapter 13 measured it directly. Eight threads incrementing separate counters
that shared one cache line ran at **14.6 ns per operation**, against **0.27 ns**
when padded apart. That's 55×, with no lock and no shared data. It's purely the
invalidation traffic.

This is why Java has a `@Contended` annotation, and why the LMAX Disruptor pads
its sequence counters.

<Callout label="Common mistake" kind="warn">
Padding to 64 bytes on Apple Silicon. Lines are 128 bytes there, so two
64-byte-padded fields still share one and the padding fixes nothing. Query the
line size instead of assuming it.
</Callout>

C++17's answer to "how much should I pad" is
`std::hardware_destructive_interference_size`. It was immediately complicated by
ABI concerns: GCC warns when you use it, and Apple's libc++ doesn't ship it.
Hardcoding 64 is a portability bug that only shows up as slowness.

</Sub>

<SectionHeading n="05" id="curve">The curve, and where it cliffs</SectionHeading>

<Callout label="The machine" kind="note">
Apple M4, macOS 26.5.1, clang 21 `-O2`. Dependent pointer chase through a random
permutation, working set swept from 8 KB to 128 MB. The permutation defeats the
prefetcher; the dependency defeats out-of-order overlap.
</Callout>

| Working set | ns/access | Where it lives |
|---|---|---|
| 8–64 KB | 1.2 – 1.5 | L1 data cache |
| 128 KB | 2.7 | Falling out of L1 |
| 192 KB – 8 MB | 5.7 – 7.9 | L2, flat and fast |

| 32 MB | 42.0 | The cliff |
| 64–128 MB | 69 – 83 | DRAM |

<Why>Why are the plateaus so flat?</Why>

Within a level, every access costs about the same, so size barely matters.
Across a boundary, it's everything. That shape is why "make the working set fit"
is the highest-leverage change available, and why halving a struct can double
your throughput with no algorithmic change at all.

</Sub>

<SectionHeading n="06" id="controls">What you can control</SectionHeading>

<Sub n="6.1" title="Three variables you own">

| Variable | Effect | Can you reach it? |
|---|---|---|
| Working set size | Decides which plateau you sit on. Dominates everything. | Yes: shrink the struct, narrow the types |
| Access pattern | Sequential gets the prefetcher; random does not | Yes: contiguous layout, indices not pointers |
| Sharing between threads | A written line serialises the cores that hold it | Yes: pad with `alignas` |
| Cache line size | The granularity of everything above | No. Query it, never assume 64. |
| Associativity | Power-of-two strides can alias into one set | Indirectly: pad the row length |

Three of those five are yours, and the first is worth more than the other four
combined. **Moving left on the curve beats every micro-optimisation available.**

</Sub>

<Sub n="6.2" title="Smaller, contiguous, unshared">

Three interventions, in descending order of what they typically pay:

1. **Make it smaller.** Shrink structs, use narrower types, drop padding,
   replace 8-byte pointers with 4-byte indices. This moves you left on the
   curve, and the curve is steep.
2. **Make it contiguous.** Go from array-of-structs to struct-of-arrays when you
   only touch some fields. Sequential access recruits the prefetcher, which is
   the difference between the curve above and a much flatter one.
3. **Make it unshared.** Pad anything two threads write with `alignas`, using
   your platform's real line size. 55× is waiting otherwise.

<Sub n="6.3" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| Gets much slower past a certain data size | Working set fell off a plateau | Shrink records, narrower types, indices not pointers |
| A linked structure is slow; an array of the same data is fast | Dependent loads to scattered nodes | Contiguous layout |
| Threads writing separate variables scale badly | False sharing | Pad to the real line size with `alignas` |
| Padding to 64 bytes didn't help on an M-series Mac | Lines are 128 bytes there | Query the line size |
| Fast at 1023×1023, slow at 1024×1024 | Power-of-two stride aliasing into one set | Pad the row length |
| Latency benchmark looks twenty times too good | Measuring bandwidth, not latency | Chase a random permutation |

```shell
# Line size — query it, never assume
getconf LEVEL1_DCACHE_LINESIZE      # Linux
sysctl -n hw.cachelinesize          # macOS

# Is it memory, and which level?
perf stat -e cache-references,cache-misses,LLC-load-misses ./app
perf record -e cache-misses -g ./app && perf report

# Where is the padding in your struct?
pahole -C YourStruct ./app
```

</Sub>

<SectionHeading n="07" id="summary">Summary</SectionHeading>

1. **DRAM is far slower than the core.** About 83 ns on the M4, long enough to
   run hundreds of instructions.
2. **Caches work because programs repeat themselves.** They reuse what they just
   touched and touch what's next to it.
3. **Caches move lines, not bytes.** 128 bytes on Apple Silicon, 64 on most x86.
4. **You pay for the whole line.** Reading one 4-byte field from each 128-byte
   struct uses about 3% of what you fetched.
5. **The working set decides the cost of a load.** The same instruction cost
   1.48 ns at 8 KB and 82.92 ns at 128 MB.
6. **Latency needs a dependent, random chase.** Independent or sequential loads
   measure bandwidth and the prefetcher instead.
7. **Writes need exclusive ownership.** Coherence invalidates every other copy
   before a core can write.
8. **False sharing is real contention over no shared data.** 14.6 ns against
   0.27 ns padded, 55× across eight threads.
9. **Query the line size.** Padding to 64 on a 128-byte-line machine fixes
   nothing.
10. **Shrinking the working set beats every micro-optimisation.** Halving the
    record size in the worked example is roughly 2× from the curve alone.

<SectionHeading n="08" id="build">Build this</SectionHeading>

**Measure your own curve.** Forty lines, and you'll use the result for years.

- Build a random permutation of pointers linked into one cycle, for working sets
  from 4 KB to 256 MB.
- Chase it. Plot ns per access against size, log x-axis.
- Read your cache sizes off the cliffs, then check them against `sysctl -a | grep
  cachesize` or `lscpu`.

Then run it again with a **sequential** permutation instead of a random one and
watch the whole curve flatten. That second run is the prefetcher, and seeing its
effect as a before-and-after teaches more than any description.

<SectionHeading n="09" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why is iterating an array faster than a linked list with the same elements?">
Two reasons, the second mattering more. An array is contiguous, so each line
fetch brings several elements you're about to use. And the addresses are
predictable, so the prefetcher loads them before you ask.

A linked list gives a dependent load per node — you can't compute the next
address until the current one arrives — and nodes may be scattered. Past cache
size that's the difference between roughly 1 ns and 80 ns per step.
</QA>

<QA level="intermediate" q="How would you measure memory latency, and what's the trap?">
Chase pointers through a random permutation sized to the level you're probing.
Each load's address comes from the previous load's value, so one miss is
outstanding and the prefetcher has nothing to predict.

The trap is measuring independent loads. The core issues many concurrently and
you measure bandwidth — a different property, and potentially twenty times
better.
</QA>

<QA level="intermediate" q="What is false sharing and how do you fix it?">
Two threads writing different variables in one cache line. Coherence works per
line, so each write invalidates the other core's copy and they serialise despite
sharing no data.

Pad each onto its own line with `alignas`, using the real line size. It's 128
bytes on Apple Silicon and 64 on x86-64, so padding to 64 on an M-series chip
fixes nothing. Chapter 13 measured the penalty at 55× across eight threads.
</QA>

<QA level="deep" q="An O(n log n) algorithm is losing to an O(n²) one on real data. How?">
Constant factors, specifically cache behaviour. If the n² version walks
contiguous memory and the n log n version chases pointers, each step of the
better algorithm can cost seventy times more. I measured 1.22 ns for an
L1-resident dependent access against 82.92 ns at a 128 MB working set.

Asymptotic analysis assumes uniform access cost. That stopped being true around
1990 and the gap widens with every generation.
</QA>

<QA level="deep" q="Your matrix code is fast at 1023×1023 and slow at 1024×1024. Explain.">
Cache set aliasing. Caches are set-associative and the set index comes from
middle address bits. With a power-of-two row stride, the same column across many
rows maps to one set, so you exhaust associativity and evict lines you're about
to reuse — even though the data would fit.

Pad the row length so the stride isn't a power of two. One extra element per
row, which looks like waste and is the optimisation.
</QA>
