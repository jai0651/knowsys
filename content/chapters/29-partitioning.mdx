Sooner or later one table gets too big for one machine. Maybe it's the disk,
maybe the write rate, maybe the working set no longer fits in memory. Buying a
bigger box works a few times, and then there isn't a bigger box.

So you split the data into **partitions** (also called shards,
ranges, tablets, regions or vnodes, depending on who built it) and put
different partitions on different machines. That's easy to say. Hard parts
come after: deciding which partition owns each key, keeping the load even when
some keys are far more popular than others, and moving partitions between
machines without stopping writes.

This chapter works through those in order. It starts with the two basic
schemes, range and hash, measures exactly how many keys each hashing method
moves when a node joins, looks at hot keys, and ends with the resharding
procedures real systems use, step by step.

<SectionHeading n="01" id="why-partition">What partitioning is for</SectionHeading>

Replication, from the [previous chapter](/topics/28-replication-consistency),
puts the *same* data on several machines. Partitioning puts *different* data on
different machines. Real systems do both: each partition is replicated, so a
node holds replicas of many partitions, and each partition lives on several
nodes.

<Sub n="1.1" title="Two questions every scheme answers">

Every partitioning scheme is an answer to two questions:

1. **Which partition owns this key?** A function from key to partition.
2. **Which node holds that partition, and who knows?** A map from partition to
   node, and some way for clients to find it.

Keeping those separate is the most useful idea in this chapter. The first
function should almost never change, because changing it moves data. The second
map changes every time you add a node or one fails, and it's cheap to change as
long as it's small.

<Why>Why not just map each key straight to a node?</Why>

Because then any change to the set of nodes changes the mapping of keys, and
changing the mapping of a key means moving its data. With a layer of partitions
in between, adding a node means reassigning a few whole partitions: a small edit
to a small map, followed by a bulk copy of exactly those partitions.

</Sub>

<Sub n="1.2" title="The goals, and how they conflict">

| Goal | Why it matters | What works against it |
|---|---|---|
| **Even data** | No node runs out of disk first | Uneven key distribution, partitions of different sizes |
| **Even load** | No node saturates while others idle | Popular keys, time-ordered writes |
| **Cheap scans** | Range queries touch few partitions | Hashing, which scatters neighbouring keys |
| **Cheap rebalancing** | Adding a node moves little data | Schemes that tie key placement to node count |
| **Local operations** | Multi-key reads and transactions stay on one node | Any split of related keys |

No scheme wins every row. Range partitioning keeps scans cheap and is prone to
hot spots. Hash partitioning spreads load and makes range scans touch every
partition. Sections 2 and 3 take each in turn.

</Sub>

<SectionHeading n="02" id="range">Range partitioning</SectionHeading>

Sort the keys, cut the sorted order into contiguous ranges, and give each range
to a node. Google's [Bigtable](https://research.google/pubs/bigtable-a-distributed-storage-system-for-structured-data/)
called them tablets; HBase calls them regions; CockroachDB and TiKV call them
ranges.

<Sub n="2.1" title="Splitting and finding ranges">

Ranges aren't chosen up front. A table starts as one range, and a range splits
when it grows too big. In CockroachDB the default is to split at
[512 MiB](https://docs.cockroachlabs.com/docs/stable/configure-replication-zones)
(`range_max_bytes`) and merge adjacent ranges that fall below 128 MiB.

Finding a key's range is a lookup in a sorted index of range boundaries.
CockroachDB stores that index in the key space itself, as two levels of
[meta ranges](https://docs.cockroachlabs.com/docs/stable/architecture/distribution-layer),
and every node caches it.

<Why>Why split by load as well as size?</Why>

Because a small range can still be the busiest one in the cluster. CockroachDB's
[load-based splitting](https://docs.cockroachlabs.com/docs/stable/load-based-splitting)
splits a range whose request rate crosses a threshold, choosing the split key
from sampled requests so the two halves get similar load. Then the halves can
live on different nodes.

</Sub>

<Sub n="2.2" title="The hot-spot problem">

Range partitioning's weakness is keys that arrive in order. If the key is a
timestamp, an auto-increment ID or anything that starts with one, every new write
goes to the **last** range. Your cluster has fifty nodes and one of them takes
all the inserts.

<Why>Why doesn't splitting fix a time-ordered hot spot?</Why>

Because the new half gets all the new writes too. Split `[t0, now)` into two and
every insert still lands in the upper half. All that moves is the hot spot, to whichever
node owns the newest range.

Every fix breaks the ordering on purpose:

| Fix | How | What you lose |
|---|---|---|
| **Prefix with a hash** | Key = `hash(user) % 16` + timestamp | Time-range scans become 16 scans |
| **Lead with a high-cardinality column** | Key = (user_id, timestamp) instead of (timestamp) | Global "latest events" queries |
| **Random or hashed IDs** | UUIDv4 instead of a sequence | Insert locality in B-trees; see the storage chapter |
| **Hash-sharded index** | CockroachDB's `USING HASH` does the prefixing for you | Ordered scans on that index |

</Sub>

<Callout label="Design implication">
Choose a range-partitioned primary key by asking what the *write* order looks
like, not only what queries you'll run. A key that leads with a timestamp is a
single-node write bottleneck in every range-partitioned database, however many
nodes you add.
</Callout>

<SectionHeading n="03" id="hash">Hash partitioning, and how much a new node moves</SectionHeading>

Hash the key and use the hash to pick a partition. A good hash spreads even
sequential keys uniformly, which fixes the hot-spot problem for writes and gives
up range scans in exchange.

<Sub n="3.1" title="Why hash mod N fails">

An obvious version is `partition = hash(key) % N`, with one partition per node.
It spreads keys perfectly. Then you add an eleventh node.

<Predict
  q="1 million keys are spread across 10 nodes with hash(key) % 10. You add one node and switch to hash(key) % 11. Roughly what fraction of keys now belong to a different node?"
  options={["About 9% (one-eleventh)", "About 50%", "About 91%", "100%"]}
  answer={2}
>
About 91%. A key stays put only if `h % 10 == h % 11`, which holds for roughly
one key in eleven. A simulation below measured **90.9%** on 200,000 keys. The
ideal is the reverse: only the one-eleventh of keys that the new node should own
move, and everything else stays.
</Predict>

Moving 91% of your data to add 10% capacity is a full reshuffle of the cluster.
Every scheme in the rest of this section exists to get that number down to the
ideal, `1/(N+1)`.

</Sub>

<Sub n="3.2" title="Fix one: many fixed partitions">

Simplest of all is to separate the two questions from section 1.1. Pick a large,
**fixed** number of partitions when you create the system, hash keys into them,
and never change that number. Nodes own whole partitions. Adding a node means
handing it a fair share of partitions from the others.

This is what Redis Cluster does with its 16,384 hash slots:

<SourceRead
  file="src/cluster.c"
  repo="redis/redis"
  tag="7.0.15"
  href="https://github.com/redis/redis/blob/7.0.15/src/cluster.c#L939"
>
```c
unsigned int keyHashSlot(char *key, int keylen) {
    int s, e; /* start-end indexes of { and } */

    for (s = 0; s < keylen; s++)
        if (key[s] == '{') break;

    /* No '{' ? Hash the whole key. This is the base case. */
    if (s == keylen) return crc16(key,keylen) & 0x3FFF;

    /* '{' found? Check if we have the corresponding '}'. */
    for (e = s+1; e < keylen; e++)
        if (key[e] == '}') break;

    /* No '}' or nothing between {} ? Hash the whole key. */
    if (e == keylen || e == s+1) return crc16(key,keylen) & 0x3FFF;

    /* If we are here there is both a { and a } on its right. Hash
     * what is in the middle between { and }. */
    return crc16(key+s+1,e-s-1) & 0x3FFF;
}
```
</SourceRead>

`& 0x3FFF` is `% 16384`. The slot count never changes, so a key's slot never
changes; only the slot-to-node map does. The `{…}` **hash tag** lets you force
related keys into one slot: `{user:1000}:cart` and `{user:1000}:profile` both
hash only `user:1000`, so multi-key commands on them work.

Instagram did the same thing in Postgres. Their
[sharding post](https://instagram-engineering.com/sharding-ids-at-instagram-1cf5a71e5a5c)
describes several thousand **logical shards**, each a Postgres schema, mapped to
far fewer physical servers. Moving a logical shard moves a schema, and no key's
shard ever changes.

<Why>Why doesn't Kafka work this way?</Why>

Because in Kafka the partition count *is* the fixed number, and it's usually
small. Its default partitioner is a plain modulo over it:

<SourceRead
  file="clients/src/main/java/org/apache/kafka/clients/producer/internals/BuiltInPartitioner.java"
  repo="apache/kafka"
  tag="3.7.0"
  href="https://github.com/apache/kafka/blob/3.7.0/clients/src/main/java/org/apache/kafka/clients/producer/internals/BuiltInPartitioner.java#L327"
>
```java
    public static int partitionForKey(final byte[] serializedKey, final int numPartitions) {
        return Utils.toPositive(Utils.murmur2(serializedKey)) % numPartitions;
    }
```
</SourceRead>

So adding partitions to a keyed topic is the `% N` problem from 3.1. The
[docs](https://kafka.apache.org/37/documentation.html#basic_ops_modify_topic)
warn that "this partitioning will potentially be shuffled by adding partitions
but Kafka will not attempt to automatically redistribute data in any way", and
Kafka can't reduce the partition count at all. Existing messages stay where
they are, new ones for the same key go elsewhere, and per-key ordering breaks
across the change.

<Callout label="Common mistake" kind="warn">
Starting a keyed Kafka topic, or an Elasticsearch index, with the partition
count you need today. Both fix the key-to-partition function at creation.
Elasticsearch's [`_split`](https://www.elastic.co/guide/en/elasticsearch/reference/current/indices-split-index.html)
API can only multiply the shard count into a new index. Pick a count that
covers years of growth, since unused partitions are cheap and changing the count
later is not.
</Callout>

</Sub>

<Sub n="3.3" title="Fix two: the consistent-hash ring">

Karger et al.'s [consistent hashing](https://www.cs.princeton.edu/courses/archive/fall09/cos518/papers/chash.pdf)
(1997) avoids a fixed partition count entirely. Hash both keys and nodes onto
the same circle of 64-bit values. Each key belongs to the first node clockwise
from it.

<Steps
  title="Adding a node to a consistent-hash ring"
  lanes={[
    { t: "Hash the key", s: "h(user:42) on the circle", icon: "#" },
    { t: "Walk clockwise", s: "binary search of tokens", icon: "↻" },
    { t: "Owner", s: "first token found", icon: "●" },
    { t: "New node", s: "adds its tokens", icon: "+" },
    { t: "Moved keys", s: "only its arcs", icon: "⇢" },
  ]}
  steps={[
    [0, "Nodes are placed on the circle by hashing their names, and each placement is a **token**. A key is hashed onto the same circle."],
    [1, "To find the owner, walk clockwise from the key to the next token. With the tokens in a sorted array, that's a binary search: `O(log T)` for T tokens."],
    [2, "The key belongs to that token's node. Every key between the previous token and this one belongs to the same node: that stretch of circle is an **arc**."],
    [3, "A new node hashes its own tokens onto the circle. Each token cuts an existing arc in two."],
    [4, "Only keys in the cut-off pieces change owner, and they all move **to the new node**. No key moves between two old nodes, which is the property `% N` lacks."],
  ]}
/>

<Why>Why do rings use virtual nodes?</Why>

Because with one token per node, the arcs are wildly uneven. Random points on a
circle leave some gaps several times longer than others, and a node's share of
keys is the length of its arc. So give each node many tokens,
**virtual nodes**, so each node's share is the sum of many small arcs and
averages out.

Here's both effects, measured. 200,000 keys, 10 nodes growing to 11:

With one token per node, the busiest node in the median run held **2.8×** its
fair share. That's the node that fills its disk first, and it's roughly three
times too early. At 256 tokens the worst of nine layouts was 16% over.

Cassandra lowered its default `num_tokens` from 256 to
[16 in 4.0](https://github.com/apache/cassandra/blob/cassandra-4.1.0/conf/cassandra.yaml),
and paired it with a token *allocation* algorithm
(`allocate_tokens_for_local_replication_factor`) that places new tokens to even
out ownership instead of at random. Fewer tokens make repair and streaming
cheaper, and the allocator buys back the balance that 16 random tokens would
lose.

</Sub>

<Sub n="3.4" title="Fix three: jump hash and rendezvous hashing">

Two newer schemes reach the ideal without a ring.

**Jump consistent hash** ([Lamping and Veach, 2014](https://arxiv.org/abs/1406.2294))
is a few lines of arithmetic that maps a 64-bit key to a bucket in `[0, N)`. It
needs no memory at all, moves exactly `1/(N+1)` of keys when N grows by one,
and balances almost perfectly (1.01 above). Its limit: buckets are numbered, and
you can only add or remove at the *end*. That's a good fit for a storage system
whose shards are replicated and never disappear from the middle, and a poor
fit for a cache fleet where any node can die.

**Rendezvous hashing**, or highest-random-weight
([Thaler and Ravishankar, 1998](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/02/HRW98.pdf)),
scores every node for each key with `hash(key, node)` and picks the highest.
Removing any node moves only the keys it owned; the next-highest score takes
each one. It costs `O(N)` hashes per lookup, which is fine for tens of nodes
and not for thousands.

| Scheme | Lookup cost | Memory | Remove any node? | Weights? | Used by |
|---|---|---|---|---|---|
| Fixed slots | `O(1)` table lookup | Slot table | Yes, reassign its slots | By slot count | Redis Cluster, Instagram, Couchbase vBuckets |
| Ring + vnodes | `O(log T)` | T tokens | Yes | By token count | Cassandra, Riak, Dynamo |
| Jump hash | `O(log N)` arithmetic | None | Only the last | No | Storage shard selection |
| Rendezvous | `O(N)` hashes | Node list | Yes | Yes, with weighted scores | GitHub's [GLB director](https://github.com/github/glb-director/blob/master/docs/development/glb-hashing.md) (a variant) |
| Maglev | `O(1)` table lookup | Lookup table | Yes, with small disruption | Yes | Google's L4 load balancers |

[Maglev hashing](https://research.google/pubs/maglev-a-fast-and-reliable-software-network-load-balancer/)
belongs to load balancing more than storage: it trades a little extra
disruption on changes for a fast table lookup and near-perfect balance.

<Callout label="Design implication">
For a database, prefer many fixed partitions over clever hashing. A slot table
is small, explicit and easy to inspect: you can print exactly which node owns
which slot and move one slot at a time. Rings and jump hash shine where there's
no central map at all, such as clients picking a cache server.
</Callout>

</Sub>

<SectionHeading n="04" id="hot">Hot keys and hot shards</SectionHeading>

Hashing spreads *keys* evenly. It does nothing about *requests*, because a
single popular key always hashes to one place. When one user, product or
hashtag gets a large share of traffic, the partition holding it is hot no matter
how the keys were spread.

<Sub n="4.1" title="How skewed real traffic is">

A common model for popularity is a Zipf distribution, where the k-th most
popular key gets traffic proportional to `1/k`. Simulating that over one million
keys, hash-partitioned onto 10 nodes:

<Compare
  cols={["", "Share of all traffic"]}
  rows={[
    ["Most popular single key", "6.9%"],
    ["Fair share per node", "10.0%"],
    ["Hottest node", "16.8%"],
    ["Coolest node", "7.4%"],
    ["Hottest node, top 100 keys each split 8 ways", "12.4%"],

/>

One key alone takes 6.9% of all traffic, most of a node's fair share. The
hottest node ran at 1.68× the average, and adding nodes can't dilute a single
key: at 100 nodes, that one key would still be 6.9% of traffic on one node,
about seven times its share.

<Why>Why doesn't adaptive capacity make this go away?</Why>

Because one partition has a ceiling. DynamoDB's docs state that every partition
can serve at most
[3,000 read units and 1,000 write units per second](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html).
Its [adaptive capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/burst-adaptive-capacity.html)
can isolate a hot item into a partition of its own, but then that item gets at
most those 3,000 and 1,000. Past that, only a change to the key design helps.

</Sub>

<Sub n="4.2" title="What to do about a hot key">

| Technique | How it works | Cost |
|---|---|---|
| **Cache the reads** | Put a cache, or an in-process cache, in front of the hot key | Staleness; the cache is now the hot spot |
| **Read from replicas** | Spread reads over the partition's replicas | Replica lag; only helps reads |
| **Split the key (salting)** | Write to `key#0` … `key#7` at random; read all eight and combine | Every read fans out 8 ways |
| **Write sharding with aggregation** | Counters: increment a random sub-counter, sum on read or periodically | Reads are approximate or slower |
| **Give it a dedicated partition** | Detect hot keys and move them to their own node | Operational machinery to detect and move |
| **Bounded-load hashing** | Cap any server at c × average; overflow goes to the next server | Some requests land on a server without their cached data |

DynamoDB's own guide recommends
[write sharding](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-sharding.html)
with a random or calculated suffix, which is salting by another name.

**Consistent hashing with bounded loads** comes from Mirrokni, Thorup and
Zadimoghaddam ([2016](https://arxiv.org/abs/1608.01350)), and HAProxy ships it
as `hash-balance-factor`. From the
[HAProxy docs](https://docs.haproxy.org/2.8/configuration.html#4.2-hash-balance-factor):
"if `<factor>` is 150, then no server will be allowed to have a load more than
1.5 times the average", with 125 to 200 recommended.

<Callout label="Common mistake" kind="warn">
Salting every key "just in case". It multiplies the cost of every read by the
salt factor, for keys that were never hot. Salt only the keys that measurement
shows are hot, and keep the list of salted keys somewhere readers can find it.
</Callout>

</Sub>

<SectionHeading n="05" id="secondary">Secondary indexes and cross-partition queries</SectionHeading>

Partitioning by primary key makes lookups by primary key cheap. Every other
query has to decide where its index lives.

<Sub n="5.1" title="Local indexes versus global indexes">

| | Local (per-partition) index | Global index |
|---|---|---|
| **Where it lives** | Each partition indexes its own rows | The index is partitioned by the *indexed* value |
| **Write cost** | One partition, same transaction | A second partition, usually asynchronous |
| **Read by indexed value** | Ask **every** partition (scatter-gather) | Ask one index partition, then fetch rows |
| **Consistency** | Same as the base table | Often eventually consistent |
| **Examples** | Elasticsearch, Cassandra secondary indexes, DynamoDB LSIs | DynamoDB GSIs, CockroachDB and Spanner indexes |

<Why>Why is scatter-gather worse than it sounds?</Why>

Because a query that asks every partition is as slow as the *slowest*
partition. With 100 partitions, a 1-in-100 slow reply is in almost every query.
The [contention and tail latency chapter](/topics/16-contention-tail-latency)
shows how fan-out amplifies p99, and it applies to every scatter-gather read.

DynamoDB shows the trade-off in its API: global secondary indexes
[can only be read](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html)
with eventual consistency, because they're updated asynchronously from the base
table.

</Sub>

<Sub n="5.2" title="Keep things that change together together">

Operations that touch several partitions need coordination: a distributed
transaction, or a saga, or an application that tolerates partial results. The
[distributed transactions chapter](/topics/31-distributed-transactions) covers
those. A cheaper fix is to avoid them by choosing a partition key that keeps
related data together.

| Workload | Good partition key | Why |
|---|---|---|
| Multi-tenant SaaS | `tenant_id` | Almost every query is inside one tenant |
| Chat | `conversation_id` | Messages are read and written per conversation |
| Orders and their line items | `customer_id`, with items stored under it | An order and its items commit together |
| Time-series metrics | `(series_id, time bucket)` | Spreads writes across series, keeps one series' range scan local |

Redis hash tags, Vitess's vindexes and Spanner's interleaved tables are all ways
of saying "put these rows on the same shard".

</Sub>

<SectionHeading n="06" id="routing">Routing: who holds the map</SectionHeading>

Once partitions can move, a client needs a current map from key to node. There
are four places to keep it.

<Sub n="6.1" title="Four places to keep the map">

| Where the map lives | How a request finds its node | Examples |
|---|---|---|
| **Smart client** | Client caches the map, and servers redirect when it's stale | Redis Cluster (`MOVED`, `ASK`), Kafka clients, token-aware Cassandra drivers |
| **Proxy tier** | Clients talk to a proxy that routes | Vitess `vtgate`, MongoDB `mongos`, twemproxy, Envoy's Redis proxy |
| **Any node forwards** | Client talks to any node, which forwards or coordinates | Cassandra coordinators, CockroachDB gateways |
| **Metadata service** | An authoritative store holds the map; everyone watches it | ZooKeeper or etcd, Kafka's KRaft controller, CockroachDB meta ranges |

<Why>Why does the map need consensus?</Why>

Because two nodes that both believe they own a partition will both accept
writes for it. The map is the one piece of state that must be linearizable, even
when the data isn't. That's why it lives in etcd, ZooKeeper, a Raft group or
(for Redis Cluster) behind an epoch number that only increases. The
[consensus chapter](/topics/27-consensus) explains why those are safe, and the
[failure detection chapter](/topics/30-failure-detection) covers what happens
when a node wrongly believes it still owns something.

</Sub>

<SectionHeading n="07" id="resharding">Moving data without downtime</SectionHeading>

Adding capacity means moving some partitions to new nodes while clients keep
reading and writing them. Every system that does this online follows the same
shape, with different names for the steps.

<Sub n="7.1" title="The general recipe">

<Steps
  title="Online resharding, in six phases"
  lanes={[
    { t: "Copy", s: "snapshot to target", icon: "⧉" },
    { t: "Catch up", s: "stream changes", icon: "⇉" },
    { t: "Verify", s: "diff source and target", icon: "✓" },
    { t: "Switch reads", s: "replicas first", icon: "↪" },
    { t: "Switch writes", s: "brief pause", icon: "⏸" },
    { t: "Clean up", s: "drop old copies", icon: "🗑" },
  ]}
  steps={[
    [0, "Take a consistent snapshot of the rows that will move and copy them to the target shards. The source keeps serving all traffic."],
    [1, "Record where in the change log the snapshot was taken, and stream every change after it (MySQL binlog, Postgres logical replication, Kafka) to the targets until they're only seconds behind."],
    [2, "**Verify** that source and target hold the same data. Vitess does this with `VDiff`. Skipping it is how resharding silently loses rows."],
    [3, "Point **reads** at the targets, starting with replica reads. It's reversible: if something's wrong, point them back."],
    [4, "For **writes**: stop writes to the source briefly, wait for the stream to drain, flip the routing map, and resume against the targets. This pause is the only visible downtime, typically seconds."],
    [5, "Keep the reverse stream running for a while, so you can fail back, then drop the source copies and the old routing."],
  ]}
/>

Vitess's [resharding guide](https://vitess.io/docs/user-guides/configuration-advanced/resharding/)
maps onto those phases one-to-one: `Reshard create` copies and streams,
`VDiff` verifies, `SwitchTraffic --tablet-types=rdonly,replica` moves reads,
`SwitchTraffic` moves writes, `ReverseTraffic` exists for the way back, and
`complete` cleans up.

<Why>Why switch reads before writes?</Why>

Because a read switch is harmless to undo and a write switch isn't. Once
writes land on the targets, the source is stale, and failing back needs the
reverse stream. Moving reads first lets you find a bad routing rule, a missing
index or a cold cache while going back is still free.

</Sub>

<Sub n="7.2" title="Redis Cluster: moving one slot live">

Redis Cluster moves data a slot at a time, and it does it without a pause at
all, by letting clients be redirected mid-migration. The source is `MIGRATING`
the slot and the target is `IMPORTING` it:

<StepSequence
  title="Migrating slot 1649 from node A to node B"
  actors={["Client", "Node A (source)", "Node B (target)"]}
  messages={[
    { from: 1, to: 2, label: "SETSLOT IMPORTING / MIGRATING", note: "An operator (or `redis-cli --cluster reshard`) marks slot 1649 as `IMPORTING` on B and `MIGRATING` on A. A still owns the slot." },

    { from: 1, to: 0, label: "-ASK 1649 B", note: "A replies **ASK**: try B, **for this one request only**. The client must not update its slot map, since most of the slot is still on A." },
    { from: 0, to: 2, label: "ASKING + GET k", note: "The client sends `ASKING` then the command. Without `ASKING`, B would refuse with `MOVED` back to A, because B doesn't own the slot yet." },
    { from: 1, to: 2, label: "SETSLOT NODE B", note: "When the slot is empty on A, `CLUSTER SETSLOT 1649 NODE B` on both nodes transfers ownership. From now on A answers **MOVED**, and clients update their maps." },

It's decided in a dozen lines of `getNodeByQuery()`:

```c

     * an ASK redirection or TRYAGAIN. */
    if (migrating_slot && missing_keys) {
        /* If we have keys but we don't have all keys, we return TRYAGAIN */
```

Note the middle case: a multi-key command whose keys are split between the two
nodes gets `TRYAGAIN`, an error, for as long as the migration is in progress.
Here's the whole thing on a two-node cluster:

<TryIt what="Migrate half of one slot, then see ASK, MOVED and TRYAGAIN territory" lang="shell" toolchain="Redis 7.0.15, linuxkit 6.10.14 aarch64">
```shell
redis-cli -p 7291 cluster keyslot '{user:1000}:cart'        # 200 keys live in this slot
redis-cli -p 7292 cluster setslot 1649 importing $A
redis-cli -p 7291 cluster setslot 1649 migrating $B
redis-cli -p 7291 migrate 127.0.0.1 7292 "" 0 5000 keys $(redis-cli -p 7291 cluster getkeysinslot 1649 100)

M=<one of the migrated keys>
redis-cli -p 7291 get "$M"                   # a moved key, asked at the source
redis-cli -p 7292 get "$M"                   # same key at the target, no ASKING
redis-cli -p 7291 get '{user:1000}:k1'       # a key that hasn't moved yet
redis-cli -p 7291 -c get "$M"                # -c follows redirects
# ... migrate the rest, then SETSLOT 1649 NODE $B on both nodes
redis-cli -p 7291 get '{user:1000}:k1'
```

<Output>
```text
1649
ASK 1649 127.0.0.1:7292
MOVED 1649 127.0.0.1:7291
v
v
MOVED 1649 127.0.0.1:7292
```

During the migration, A answers the keys it still has and sends `ASK` for the
ones it doesn't; B refuses without `ASKING` and points back at A, the slot's
official owner. After `SETSLOT NODE`, A answers `MOVED` for everything.
</Output>
</TryIt>

<Callout label="Common mistake" kind="warn">
A client library that treats `ASK` like `MOVED` and rewrites its slot map. It
starts sending every request for that slot to B, which answers `MOVED` back to A,
and the client bounces between them until the migration ends. Test resharding
against your actual client library before you need it.
</Callout>

</Sub>

<Sub n="7.3" title="How fast to move">

Moving data competes with serving traffic for disk, network and CPU on both
sides. Every mature system throttles it: Cassandra's `stream_throughput_outbound`,
CockroachDB's rebalance snapshot rate settings, Kafka's replication quotas for
partition reassignment.

<Why>Why not rebalance automatically the moment a node looks dead?</Why>

Because "looks dead" is a guess, and moving its data is expensive. If a node is
merely slow and the cluster starts copying its partitions elsewhere, the copying
loads the other nodes, which can make them look slow too. That's why Kubernetes
waits five minutes before evicting pods from an unreachable node, and why
Cassandra never moves data on failure: it marks the node down and lets hints and
repair catch it up when it returns. That guess is the subject of the next chapter.

</Sub>

<SectionHeading n="08" id="operating">Running a partitioned system</SectionHeading>

<Sub n="8.1" title="What to watch">

- **Per-partition size and request rate, not just per node.** A node average hides
  one hot partition. Plot the busiest partition against the median.
- **The skew ratio:** busiest node ÷ mean, for disk and for requests. Above about
  1.5, find out why before you add hardware.
- **Top keys.** `redis-cli --hotkeys` (with an LFU eviction policy), DynamoDB's
  CloudWatch Contributor Insights, or sampled request logs.
- **Redirects and retries.** A steady rate of `MOVED`, stale-routing errors or
  `NotLeaderOrFollower` means clients hold a stale map.
- **Movement in progress.** Bytes remaining in rebalancing and its throttle, so a
  slow migration is visible before it's a surprise.

</Sub>

<Sub n="8.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| One node's disk fills first | Too few tokens per node, or uneven partition sizes | More vnodes or a token allocator; split big partitions |
| One node hot on writes; others idle | Time-ordered keys in a range-partitioned store | Hash-prefix the key, or lead with a high-cardinality column |
| One partition throttled; table far under capacity | A hot key | Cache, salt that key, or give it a dedicated partition |
| Adding a node triggers a huge data transfer | `hash % N` placement | Fixed partitions or consistent hashing |
| Per-key ordering broke after scaling a Kafka topic | Added partitions to a keyed topic | Create a new topic with more partitions and migrate consumers |
| Index queries slow, p99 worst | Scatter-gather over every partition | Global index, or a partition key that matches the query |
| `CROSSSLOT` or `TRYAGAIN` errors in Redis | Multi-key command over keys in different slots, or mid-migration | Hash tags; retry `TRYAGAIN` with backoff |

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **Separate key → partition from partition → node.** The first should never
   change; the second is a small map that changes all the time.
2. **Range partitioning keeps scans cheap and invites hot spots.** Time-ordered
   keys send every write to one node, and splitting doesn't help.
3. **`hash % N` moves almost everything.** Going from 10 to 11 nodes moved 90.9%
   of keys in the simulation; the ideal is 9.1%.
4. **Many fixed partitions are the simplest fix.** Redis's 16,384 slots and
   Instagram's logical shards never change a key's partition.
5. **Rings need virtual nodes.** With one token per node the busiest node held
   2.8× its share; with 256 tokens, about 1.1×.
6. **Kafka and Elasticsearch fix the partition count at creation.** Size them
   for years of growth.
7. **Hashing spreads keys, not requests.** One Zipf-popular key took 6.9% of all
   traffic, and no number of nodes dilutes it.
8. **Partitions have a ceiling.** In DynamoDB it's 3,000 reads and 1,000 writes
   a second, even for a partition holding one isolated hot item.
9. **Online resharding is copy, stream, verify, switch reads, switch writes,
   clean up.** Only the write switch pauses, and verifying is the step people skip.
10. **Redis Cluster redirects mid-migration with ASK, and afterwards with
    MOVED.** A client that confuses them ping-pongs.

<SectionHeading n="11" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What's the difference between partitioning and replication?">
Replication keeps copies of the same data on several nodes, for durability,
availability and read capacity. Partitioning splits the data so different nodes
hold different subsets, for capacity and write throughput. Real systems combine
them: each partition is replicated, so every node holds replicas of several
partitions.
</QA>

<QA level="beginner" q="Why is hash(key) % N a bad way to assign keys to nodes?">
Because changing N remaps almost every key. Going from 10 to 11 nodes changes
the owner of about 10/11 of the keys, so adding 10% capacity moves roughly 91%
of the data. Consistent hashing or a fixed number of partitions moves only the
share the new node should own.
</QA>

<QA level="intermediate" q="Range or hash partitioning for a table of events keyed by timestamp?">
Hash, or a range scheme with a hashed or high-cardinality prefix. Plain range
partitioning on a timestamp sends every new write to the last range, so one node
takes all inserts however many you add. If you need time-range scans, lead with
something like `(device_id, timestamp)` or a hash bucket, and accept that a
global time scan fans out.
</QA>

<QA level="intermediate" q="What are virtual nodes and why do consistent-hash rings need them?">
Each physical node owns many positions (tokens) on the ring instead of one. With
one token per node, arc lengths vary a lot: in the simulation the busiest of 10
nodes held about 2.8× its share. Many tokens average out the arcs (about 1.1× at
256), and when a node leaves, its load spreads across many nodes instead of
landing on one neighbour.
</QA>

<QA level="intermediate" q="One celebrity's account overloads a shard. What are your options?">
Cache reads for that key; spread reads across replicas; split the key into N
sub-keys (salting) and fan reads out; for counters, increment random
sub-counters and sum them; or detect hot keys and give them a dedicated
partition. Adding shards doesn't help, since one key always hashes to one place.
Salt only the keys that are measurably hot.
</QA>

<QA level="deep" q="In Redis Cluster, what's the difference between MOVED and ASK?">
`MOVED` means the slot now belongs to another node permanently: update your
slot map and send future requests there. `ASK` means the slot is mid-migration
and this particular key has already moved: send this one request to the target,
preceded by `ASKING`, and don't update the map. The target refuses requests for
an `IMPORTING` slot without `ASKING`, answering `MOVED` back to the source.
</QA>

<QA level="deep" q="Walk through resharding a live MySQL-backed service from 4 shards to 8.">
Create the 8 target shards. Copy a consistent snapshot of each source shard's
rows into the targets by the new key ranges, recording the binlog position.
Stream binlog changes from that position into the targets until lag is seconds.
Verify with a row-level diff. Switch replica reads, then primary reads. Stop
writes on the sources briefly, let the stream drain, flip the routing map to the
targets and resume. Keep a reverse stream so you can fail back, then drop the
old shards. Vitess automates exactly this as `Reshard`, `VDiff`, `SwitchTraffic`
and `complete`.
</QA>

<QA level="deep" q="Why must the partition map be strongly consistent when the data isn't?">
Because two nodes that each think they own a partition will each accept writes,
and nothing afterwards can merge them safely. The data may tolerate staleness;
ownership can't. So the map lives in a consensus system (etcd, ZooKeeper, a Raft
group, KRaft) or behind a monotonic epoch, and data nodes check the epoch on
every request so an old owner's writes are rejected.
</QA>

<Quiz>
  <Q q="What does & 0x3FFF do in Redis's keyHashSlot?">
    It's modulo 16384, the fixed number of hash slots. It works as a bit mask
    because 16384 is a power of two.
  </Q>
  <Q q="Which keys move when a node joins a consistent-hash ring?">
    Only keys on the arcs the new node's tokens cut off, and they all move to
    the new node. No key moves between two existing nodes.
  </Q>
  <Q q="Why can't jump consistent hash remove node 3 of 10 directly?">
    Its buckets are the numbers 0 to N−1, and it can only grow or shrink N at
    the end. Removing a middle bucket needs an extra mapping layer on top.
  </Q>
  <Q q="A Redis MULTI touching two keys in a slot that's half migrated. What happens?">
    TRYAGAIN, if the source holds some of the keys and not others. Retry after
    the migration step completes.
  </Q>
</Quiz>
