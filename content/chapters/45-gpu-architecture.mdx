If you run inference or training, you already operate GPUs, whether or not you
write kernels. You've seen `nvidia-smi` report 100% while throughput stays low,
a serving stack run out of memory long before it runs out of compute, or a
16,000-GPU job hang with no error at all.

Each of those makes sense once you know what the chip is built to do. A GPU is
a throughput machine, and nearly every surprise comes from memory, not math: an
H100 decoding one token of a 70B model at batch 1 uses about a third of one
percent of its tensor cores.

This chapter builds the GPU up from one job, then walks through SMs, warps and
registers, how a warp behaves at branches and loads, one kernel launch end to
end, the roofline arithmetic behind LLM serving, and how GPUs fail and get
measured in production.

<SectionHeading n="01" id="throughput-bet">The throughput bet</SectionHeading>

<Sub n="1.1" title="A chip for eight million pixels">

Start with a job that's easy to describe: brighten every pixel of a 4K image.
That's 3840 × 2160, about 8.3 million pixels. Each one needs the same few
arithmetic operations, independently of every other pixel.

<Why>Why not just use a CPU core?</Why>

Chapter 01 showed how much of a CPU core exists to make *one* stream of
instructions fast: branch prediction, out-of-order execution, deep caches.
Roughly, every transistor that isn't an ALU is there to hide **latency** from
one thread of control.

None of that helps here. There are no hard dependencies to untangle, just the
same small operation eight million times. So spend the silicon differently:
build thousands of simple arithmetic units and give up on making any single
thread quick.

<Why>Then what hides the memory latency?</Why>

Chapter 02 put a trip to DRAM at hundreds of cycles, and a simple unit can't
predict or reorder its way around that. The GPU's answer is to have something
else to do.

It keeps far more threads resident than there are units. When one group is
waiting on memory, the hardware switches to another group that isn't. For that
switch to be free, every thread's registers stay on the chip, which is why GPUs
carry enormous register files.

One more saving: control logic is expensive, so threads don't each get their
own. They run in groups of 32, called **warps**, that share one instruction
stream. The chip is divided into **streaming multiprocessors (SMs)**, and each
SM holds many warps at once and picks a ready one every cycle.

The program you launch onto all those threads is a **kernel**, and the CPU
that launches it is the **host**. The data sits in memory next to the GPU:
**HBM** on NVIDIA's data-centre parts.

</Sub>

<Sub n="1.2" title="What a GPU promises, and what it doesn't">

If you give it enough independent work, here's the contract:

| It promises | It doesn't promise |
|---|---|
| **Enormous aggregate arithmetic.** An H100 SXM does 989 dense BF16 teraFLOPS on its tensor cores (NVIDIA's [H100 page](https://www.nvidia.com/en-us/data-center/h100/) lists 1,979 with 2:4 sparsity; dense is half). | Any order between thread blocks, or that two blocks run at the same time |
| **Enormous memory bandwidth.** 3.35 TB/s from 80 GB of HBM3, on the same datasheet. | Anything about how fast a single thread goes. A lone GPU thread is slow. |
| **Free switches between thread groups**, since their state stays on-chip. | That the host keeps up. It runs whatever is in its queue and idles otherwise, and the queue is your problem. |

<Callout label="Design implication">
A CPU core assumes you have one hard thing to do and tries to finish it soon.
A GPU assumes you have a hundred thousand easy things to do and tries to finish
all of them soon. Nearly every performance bug in this chapter comes from
handing a GPU the first kind of problem and expecting the second kind of speed.
</Callout>

</Sub>

<SectionHeading n="02" id="sms-warps-registers">SMs, warps and registers</SectionHeading>

<Sub n="2.1" title="From GPU down to a thread">

An H100 SXM5 has **132 streaming multiprocessors**, according to NVIDIA's
[Hopper architecture post](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/).
A full GH100 die has 144; the PCIe card has 114.

Each SM is split into four partitions, and each partition has its own warp
scheduler.

The programmer's unit is the **thread block** (a CTA in NVIDIA's hardware
docs): up to 1,024 threads that share an SM's fast memory and can synchronise.

What the hardware schedules is the <em className="term">warp</em>, 32
consecutive threads of a block. NVIDIA's programming guide is blunt about it:
"A warp executes one common instruction at a time, so full efficiency is
realized when all 32 threads of a warp agree on their execution path."

That model is called **SIMT**, single instruction, multiple threads. Each
thread has its own registers and (since Volta) its own program counter, so you
write scalar code. Underneath, 32 of them march in lockstep.

</Sub>

<Sub n="2.2" title="How a scheduler hides a memory stall">

Inside the SM, the [CC 9.0 architecture notes](https://docs.nvidia.com/cuda/archive/12.4.0/cuda-c-programming-guide/index.html#compute-capability-9-0)
say an SM "statically distributes its warps among its schedulers. Then, at every
instruction issue time, each scheduler issues one instruction for one of its
assigned warps that is ready to execute, if any."

Step through one scheduler with two warps and a load that goes to HBM:

    { from: 0, to: 2, label: "issue: FMA", note: "And again. As long as some assigned warp is ready, the arithmetic units stay busy while A waits." },

/>

Four schedulers per SM, each picking one ready warp per issue slot. That's the
whole latency-hiding mechanism, and there's no public detail below it worth
trusting.

</Sub>

<Sub n="2.3" title="The register file sets your occupancy">

An SM's **register file is 256 KB**: 65,536 32-bit registers, as big as its L1
and shared memory put together.

<Why>Why is the register file so big?</Why>

Because every resident warp's registers live there for the warp's whole life.
NVIDIA's [programming guide](https://docs.nvidia.com/cuda/archive/12.4.0/cuda-c-programming-guide/index.html#hardware-multithreading)
says the execution context "is maintained on-chip during the entire lifetime of
the warp. Therefore, switching from one execution context to another has no
cost."

An SM can hold at most 64 warps (2,048 threads) on compute capability 9.0. The
fraction of those slots actually filled is **occupancy**, and registers are
usually what caps it:

<Why>Is 25% occupancy bad?</Why>

Not necessarily. Occupancy only matters as a way to hide latency: you need
enough ready warps that, each cycle, a scheduler finds one whose operands have
arrived.

A kernel with lots of independent loads per thread can hide latency with few
warps, and many of the fastest matmul kernels run at low occupancy on purpose,
trading warps for registers. A kernel that does one load and then waits on it
needs every warp it can get.

</Sub>

**Shared memory** is the one with no CPU equivalent: a scratchpad a thread
block reads and writes explicitly, at on-chip speed.

It's how serious GPU kernels avoid going to HBM twice for the same bytes.
"IO-aware" usually means an algorithm rearranged so its working tile fits
there.

</Sub>

<SectionHeading n="03" id="warp-behaviour">Branches and loads at warp granularity</SectionHeading>

Two things happen at warp granularity that decide whether the machine is busy
or just looks it: what a warp does at a branch, and what it does at a load.

<Sub n="3.1" title="Divergence: both sides of the if">

If threads of one warp take different sides of a branch, the warp runs both
sides, one after the other, with the threads not on each path masked off.

<Predict
  q="A million threads each run 2,048 dependent FMAs on one of two paths, and half take each side. In run A the split falls between 32-wide groups; in run B it falls inside every group. How much longer is run B?"
  options={[
    "About the same: the total work is identical",
    "About 2× as long",
    "About 32× as long",
    "Faster: the hardware overlaps the two paths",
  ]}
  answer={1}
>
Inside every group, each group has to execute both loops, with half its threads
idle each time. On the M4's GPU that measured 2.05× (below). The total work is
the same in both runs; only where the split falls changes.
</Predict>

Here's the measurement. The M4's GPU also uses 32-wide SIMD groups (Metal
reports `threadExecutionWidth` = 32).

<TryIt what="Same work, branch split by SIMD-group vs inside every SIMD-group" lang="cpp" toolchain="Metal, Swift 6.3.3 host, Apple M4 10-core GPU, macOS 26.5.1">
```cpp
kernel void diverge(device float* out    [[buffer(0)]],
                    constant uint& mode  [[buffer(1)]],
                    uint gid [[thread_position_in_grid]]) {
    // mode 0: all 32 threads of a SIMD-group take the same side
    // mode 1: odd and even threads split inside every SIMD-group
    bool odd = mode == 0 ? ((gid >> 5) & 1) : (gid & 1);
    float x = float(gid) * 1e-7f;
    if (odd) { for (int i = 0; i < 2048; i++) x = fma(x, 0.999f, 0.001f); }
    else     { for (int i = 0; i < 2048; i++) x = fma(x, 1.001f, -0.001f); }
    out[gid] = x;
}
// 1,048,576 threads, 256 per threadgroup, GPU timestamps, best of 7
```

<Output>
```text
branch uniform per SIMD-group:   6.10 ms
branch splits every SIMD-group:  12.50 ms  (2.05x)
```

Half the threads take each side in both runs. All that changes is whether the
split falls between SIMD-groups or inside them. Inside, each group executes
both loops, and the kernel takes almost exactly twice as long. Reproduced on a
second run: 6.09 and 12.51 ms.
</Output>
</TryIt>

</Sub>

<Sub n="3.2" title="Coalescing: 32 addresses, how many transactions">

When the 32 threads of a warp issue a load, the hardware merges their
addresses into as few memory transactions as it can.

NVIDIA's [Best Practices Guide](https://docs.nvidia.com/cuda/archive/12.4.0/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory)
states the rule for CC 6.0 and later: accesses "coalesce into a number of
transactions equal to the number of 32-byte transactions necessary to service
all of the threads of the warp."

| Warp access pattern | 32-byte sectors fetched | Useful bytes per sector |
|---|---|---|
| 32 threads read 32 adjacent floats | 4 | All 32 |
| 32 threads read floats 128 bytes apart | 32 | 4 of 32; the other 28 are thrown away |

Section 5.4 measures what that does on the M4: the same number of loads, and a
factor of eighteen in useful bandwidth.

<Callout label="Common mistake" kind="warn">
Counting loads instead of transactions. Two kernels that each read every float
exactly once can differ by more than an order of magnitude, because what the
memory system pays for is sectors, and a strided warp drags in a whole sector
for every 4 useful bytes.
</Callout>

</Sub>

<Sub n="4.1" title="No syscall on the launch path">

<Why>Isn't a kernel launch an ioctl?</Why>

It's natural to expect one. Chapter 07 spent a whole section on what a syscall
costs, and a GPU driver paying one per launch would seem obvious.

It doesn't. Work reaches the GPU through memory the process has already mapped,
and NVIDIA's own reference manual lists the steps:

<SourceRead
  file="manuals/turing/tu104/dev_usermode.ref.txt"
  repo="NVIDIA/open-gpu-doc"
  tag="9fdf5c4"
  href="https://github.com/NVIDIA/open-gpu-doc/blob/9fdf5c4062007929d9f4e6cbad9c9771fe61b880/manuals/turing/tu104/dev_usermode.ref.txt"
>
```text
NOTIFY_CHANNEL_PENDING - Notify Host that a channel has new work available

     NOTIFY_CHANNEL_PENDING is known as the channel doorbell register.  Writing
a channel's opaque handle to the NOTIFY_CHANNEL_PENDING register (sometimes
referred to as "ringing the doorbell") tells Host that new work is available to
run on that channel.
...
     Submitting new work to a channel involves the following steps:

     1. Write methods to a pushbuffer segment
     2. Construct a new GP entry pointing to that pushbuffer segment
     3. Update GP_PUT in USERD to indicate the new GP entry is ready
     4. Request the doorbell handle from RM, given the channel ID
     5. Write the channel's handle to the NOTIFY_CHANNEL_PENDING register
```
</SourceRead>

Step 4 happens once, at channel setup (RM is the kernel-side resource
manager). Steps 1, 2, 3 and 5 are ordinary stores from your process.

| Piece | What it is |
|---|---|
| **Pushbuffer** | A ring of commands ("methods") in memory |
| **GPFIFO** | A ring of 8-byte entries pointing into the pushbuffer |
| **`GP_PUT`** | The producer index into the GPFIFO |
| **Doorbell** | The `NOTIFY_CHANNEL_PENDING` register that tells Host to look |

If that sounds like io_uring's submission queue from chapter 07, it's the same
idea, older.

This doc is for Turing (TU104), and it warns that the handle format "is subject
to change in future chips". This chapter assumes Hopper keeps the same shape;
no Hopper manual found so far confirms it.

</Sub>

class, so it can't be far off.

</Sub>

<Sub n="4.4" title="From the queue to an SM">

After the doorbell, the public detail thins out quickly. The PBDMA (part of
what NVIDIA calls Host) reads `GP_PUT`, fetches the pushbuffer segment, and
forwards compute methods to the compute front end, which reads the QMD.

NVIDIA's whitepapers have described the next piece since Fermi: "The
GigaThread global scheduler distributes thread blocks to SM thread schedulers"
([Fermi whitepaper](https://www.nvidia.com/content/PDF/fermi_white_papers/NVIDIA_Fermi_Compute_Architecture_Whitepaper.pdf)).

<Why>Why does a big grid run in waves?</Why>

A block goes onto an SM only if that SM has room for all of it at once: free
registers, shared memory, and warp slots. Blocks that don't fit wait for
earlier ones to retire, so a grid of a million blocks runs as waves across the
132 SMs.

</Sub>

<SectionHeading n="05" id="roofline">Bytes per FLOP: the roofline</SectionHeading>

<Sub n="5.1" title="Two ceilings and a ridge point">

A kernel does some number of FLOPs and moves some number of bytes to and from
HBM. That ratio is its <em className="term">arithmetic intensity</em>, in FLOPs
per byte.

A **roofline model** (Williams, Waterman and Patterson,
[CACM 2009](https://doi.org/10.1145/1498765.1498785)) says attainable
throughput is the lower of two ceilings: peak compute, or bandwidth ×
intensity.

<Estimate
  rows={[
    { label: "Peak dense BF16 tensor compute", math: "H100 SXM, datasheet 1,979 sparse ÷ 2", value: "989 TFLOP/s" },
    { label: "Peak HBM3 bandwidth", math: "H100 SXM datasheet", value: "3.35 TB/s" },
    { label: "Ridge point", math: "989 × 10¹² / 3.35 × 10¹²", value: "≈ 295 FLOP/byte" },
  ]}
  result={{ label: "a kernel below ~295 FLOP/byte is waiting on memory, not math", value: "295" }}
/>

Below the ridge you're memory-bound, and more tensor cores wouldn't help at
all. Above it you're compute-bound.

An H100's ridge is very high, and it's been climbing for generations because
FLOPs have grown faster than bandwidth. A matmul of two big square matrices
clears it easily. An elementwise add (one FLOP per 6 bytes in BF16) is about
1,800 times below it.

**Tensor cores** are why the ceiling is so high. Plain FP32 on the CUDA cores
is 67 TFLOPS on the same datasheet, roughly a fifteenth of the dense BF16
tensor rate.

Tensor cores only do matrix multiply-accumulate. Anything in your model that
isn't a matmul (softmax, layernorm, activation functions, the attention mask)
runs on the slower pipe, and usually at low intensity too.

</Sub>

<Sub n="5.2" title="Decoding one token of a 70B model">

Llama 3 70B has 80 layers, model dimension 8,192, 64 attention heads and 8
key/value heads (Table 3 of the [Llama 3 paper](https://arxiv.org/abs/2407.21783)).
Call it 70 billion parameters.

In BF16 that's 140 GB, which doesn't fit on one 80 GB H100, so the usual
deployment splits it over two with tensor parallelism.

    [0, "To produce one token, every one of the **70 billion weights** has to come out of HBM once: 140 GB, split across two GPUs."],
    [1, "SMs stream the weights in, layer by layer. At 2 × 3.35 TB/s that takes **20.9 ms**, and nothing about the software can make it shorter."],
    [2, "Each weight feeds **one multiply and one add**. The tensor cores finish their 140 GFLOP in about **0.07 ms**, then wait for the next bytes."],
    [3, "One token comes out per 20.9 ms: a ceiling of **about 48 tokens a second**, with the tensor cores busy about 0.34% of the time."],

Here's the arithmetic in full:

<Estimate
  rows={[
    { label: "Weight bytes read per token", math: "70 × 10⁹ params × 2 B", value: "140 GB" },
    { label: "FLOPs per token", math: "2 × 70 × 10⁹", value: "140 GFLOP" },
    { label: "Arithmetic intensity", math: "140 GFLOP / 140 GB", value: "1 FLOP/byte" },
    { label: "Time to read the weights", math: "140 GB / (2 × 3.35 TB/s)", value: "20.9 ms" },
    { label: "Time to do the math", math: "140 GFLOP / (2 × 989 TFLOP/s)", value: "0.07 ms" },

  ]}
  result={{ label: "fraction of tensor-core peak used at batch 1", value: "≈ 0.34%" }}

One FLOP per byte, against a ridge of 295. That's what people mean by **decode
is memory-bandwidth-bound**, and it's a property of the arithmetic, not of any
framework.

These are ceilings. Real servers reach some fraction of peak bandwidth and pay
NVLink all-reduce time on top.

<Why>Why does FP8 let one GPU do the job of two?</Why>

Quantise to FP8 and the 70 GB of weights fit on one GPU. One H100 reading 70 GB
takes the same 20.9 ms as two reading 140 GB.

Half the hardware, the same per-token latency ceiling, because the only thing
that mattered was bytes per unit of bandwidth.

<Callout label="Design implication">
For decode, the levers are bytes, not FLOPs: batch requests so each weight read
feeds more tokens, quantise so there are fewer weight bytes, and keep the KV
cache compact. Buying more compute for a batch-1 decode workload buys nothing.
</Callout>

</Sub>

<Sub n="5.3" title="Batching fixes the weights, not the KV cache">

Run 32 sequences together and the weights are read once for all of them, so
intensity on the weight matmuls rises to about 32 FLOP/byte. That's why
continuous batching is the first thing every inference server does.

But each sequence also has its own **KV cache**, and attention has to read all
of it on every step:

<Estimate
  rows={[
    { label: "KV bytes per token", math: "2 (K,V) × 80 layers × 8 heads × 128 dim × 2 B", value: "320 KiB" },
    { label: "32 sequences × 2,000 tokens of context", math: "64,000 × 327,680 B", value: "21 GB" },
    { label: "Attention intensity per cached token", math: "64 q-heads × 512 FLOP / 4,096 B per layer", value: "8 FLOP/byte" },
    { label: "Bytes per step", math: "140 GB weights + 21 GB KV", value: "161 GB" },
    { label: "Step time, 2 × H100", math: "161 GB / 6.7 TB/s", value: "24 ms" },
  ]}
  result={{ label: "aggregate ceiling at batch 32 vs 48 tok/s at batch 1", value: "≈ 1,330 tok/s" }}
/>

Twenty-eight times the throughput for 15% more time per step.

<Why>Why doesn't batching fix attention too?</Why>

Look at the attention row: 8 FLOP/byte however big the batch gets, because no
two sequences share a cache. (Grouped-query attention makes it 8; with full
multi-head attention it would be 1.)

Then there's capacity. Two H100s have 160 GB, the weights take 140, and what's
left is about 20 GB before activations and the CUDA context take their share.

At 320 KiB per token that's **at most ~61,000 tokens of KV in flight** across
all requests. If 60–80% of that is wasted to fragmentation, you're down to
12,000 to 24,000, and the batch size you can run (the throughput you're paying
for) drops with it.

</Sub>

<Sub n="5.4" title="Coalesced against strided, measured on the M4">

<Callout label="The machine" kind="note">
Apple M4, 10-core GPU, 16 GB unified memory, macOS 26.5.1. Metal compute
kernels compiled at runtime from a Swift 6.3.3 host (`swiftc -O`), timed with
command-buffer GPU timestamps, best of 7. Apple quotes 120 GB/s for M4
([Apple newsroom](https://www.apple.com/newsroom/2024/10/apples-new-mac-mini-is-more-mighty-more-mini-and-built-for-apple-intelligence/)).
No NVIDIA hardware involved: same principle, different GPU.
</Callout>

Every thread reads exactly one float from a 256 MiB buffer. The only thing
that changes between runs is which float.

<TryIt what="Every thread reads one float; the stride decides which one" lang="cpp" toolchain="Metal, Swift 6.3.3 host, Apple M4 10-core GPU, macOS 26.5.1">
```cpp
kernel void gather(device const float* a [[buffer(0)]],
                   device float* out     [[buffer(1)]],
                   constant uint& n      [[buffer(2)]],
                   constant uint& stride [[buffer(3)]],
                   uint gid [[thread_position_in_grid]]) {
    uint rows = n / stride;
    uint idx = (gid % rows) * stride + gid / rows;   // a permutation of 0..n-1
    float v = a[idx];
    if (v == 12345.0f) out[0] = v;                   // never true; keeps the load
}
// n = 64M floats (256 MiB), 64M threads, 256 per threadgroup
```

Stride 1 hits 112 GB/s, 93% of Apple's quoted figure. Each doubling after that
halves useful bandwidth, as you'd expect if each thread drags in a whole
transaction for 4 useful bytes.

<Why>Why does it flatten at 64 bytes?</Why>

That part is still open. If the hardware fetched in 32-byte units, as NVIDIA's
do, the curve would go flat at 32 bytes. If it fetched whole 128-byte cache
lines (the M4's CPU line size, from chapter 02), it would keep falling until
128. It stops at 64.

My guess is that the M4 GPU's memory path moves 64 bytes at a time, but Apple
doesn't document it, and I haven't proven it. Xcode's GPU counters for bytes
read from DRAM would settle it in one run, and I haven't done that run.

There's a second surprise on this machine, and it's the reason the Mac can't
show you what an H100 is for. A plain C++ sum over the same 256 MiB on the CPU
(`clang++ -O2`, eight accumulators per thread) reached **55 GB/s** on one
thread and **106–108 GB/s** on ten.

The GPU's 112 is barely ahead. They share one pool of DRAM, so neither has more
bandwidth to offer. An H100's advantage lives in the HBM stacks next to the
die, and a laptop doesn't have any.

</Sub>

<Sub n="5.5" title="The host side: launches, PCIe and NVLink">

**Launch overhead.** Each launch costs microseconds of CPU and queue time. In
NVIDIA's [CUDA Graphs post](https://developer.nvidia.com/blog/cuda-graphs/), a
V100 kernel that executed in 2.9 µs cost 9.6 µs per kernel with a sync after
each, 3.8 µs launched back to back on a stream, and 3.4 µs captured into a
graph.

On the M4, an empty 32-thread kernel timed 2,000 times:

<Cost items={[
  { what: "Commit and wait for each kernel separately", value: "99.6 µs", source: "Metal, M4, one command buffer per kernel, wall clock" },
  { what: "All 2,000 encoded into one command buffer", value: "0.83 µs", source: "same kernel, one commit, one wait" },
  { what: "V100, sync after every kernel", value: "9.6 µs", source: "NVIDIA CUDA Graphs blog, 2.9 µs kernel" },
  { what: "V100, captured as a CUDA graph", value: "3.4 µs", source: "same post" },
]} />

Metal's round trip is much slower than CUDA's, and most of those 100 µs are
probably the CPU thread waking up on completion, not the GPU. The shape is the
same on both vendors, though: **submission is cheap only when it's batched.**

<Why>Why do launches matter for decode?</Why>

Eighty layers at several kernels each is hundreds of launches per token in
eager mode. At a few microseconds each, that's milliseconds against the
20.9 ms memory floor.

So vLLM captures decode steps as [CUDA graphs](https://docs.vllm.ai/en/stable/design/cuda_graphs/)
unless you pass `enforce_eager`.

**Interconnect.** NVIDIA's datasheet gives each link as a total of both
directions:

<Compare
  cols={["Link", "Datasheet figure", "One direction", "Relative to HBM"]}
  rows={[
    ["HBM3, on package", "3.35 TB/s", "n/a", "1×"],
    ["NVLink 4, GPU to GPU", "900 GB/s total", "450 GB/s", "≈ 1/7"],
    ["PCIe Gen5 x16, to host", "128 GB/s total", "64 GB/s", "≈ 1/52"],
  ]}
/>

Loading one GPU's 70 GB half of the model from host memory takes about 1.1 s
at PCIe line rate, and in practice longer. Moving one 2,000-token request's KV
cache (655 MB) over NVLink takes roughly 1.5 ms. Anything crossing PCIe inside
the per-token loop is a mistake.

**Pinned memory.** Copying from pageable memory, the driver first copies into
a temporary page-locked buffer and DMAs from there, per NVIDIA's
[data transfer post](https://developer.nvidia.com/blog/how-optimize-data-transfers-cuda-cc/).

Allocating pinned (`cudaMallocHost`, or `pin_memory=True` in a PyTorch
DataLoader) skips that copy and lets `cudaMemcpyAsync` overlap with compute on
a **stream**, an independent in-order queue.

**Unified memory** (`cudaMallocManaged`) gives CPU and GPU one pointer and
migrates pages on fault. `cudaMemPrefetchAsync` moves pages ahead of time.

<Callout label="Common mistake" kind="warn">
Leaving unified memory on a hot path. It's convenient, but each first GPU touch
is chapter 04's first-touch fault with a PCIe bus in the middle. Prefetch with
`cudaMemPrefetchAsync`, or allocate on the device.
</Callout>

</Sub>

<SectionHeading n="06" id="failure">How GPUs fail</SectionHeading>

<Sub n="6.1" title="Four hundred and nineteen interruptions in 54 days">

Probably the best public data on GPU failure at scale is in Meta's
[Llama 3 paper](https://arxiv.org/abs/2407.21783), section 3.3.4.

Training the 405B model on up to 16K H100s, they logged 466 job interruptions
in a 54-day window: 47 planned, 419 unexpected. "Approximately 78% of the
unexpected interruptions are attributed to confirmed hardware issues ... or
suspected hardware-related issues like silent data corruption."

<Compare
  cols={["Root cause (Table 5)", "Count", "Share of unexpected"]}
  rows={[
    ["Faulty GPU", "148", "30.1%"],
    ["GPU HBM3 memory", "72", "17.2%"],
    ["Software bug", "54", "12.9%"],
    ["Network switch / cable", "35", "8.4%"],
    ["Host maintenance, unplanned", "32", "7.6%"],
    ["GPU SRAM memory", "19", "4.5%"],
    ["GPU system processor", "17", "4.1%"],
    ["Silent data corruption", "6", "1.4%"],
  ]}
/>

Add the rows up and **GPU issues are 58.7%** of all unexpected interruptions,
the paper's own figure. HBM alone caused more interruptions than every network
problem combined.

<Why>Why does one bad GPU matter so much?</Why>

A training job that's synchronous across every GPU stops when one chip does,
so one bad chip stops all 16,000. That's why the paper's headline reliability
number is effective training time (above 90%) and not uptime.

Two more details from that section. Failures over NVLink "often manifest as
stalled load/store operations within CUDA kernels without returning a clear
error code", so a dead link looks like a hang, not an error. And they saw a
1–2% diurnal throughput swing from mid-day temperatures pushing GPUs to lower
clocks.

</Sub>

<Sub n="6.2" title="Xid: the error the driver writes to your kernel log">

When the NVIDIA driver sees a GPU error it prints an **Xid** to the kernel log.
Grep for `NVRM: Xid`.

From NVIDIA's [Xid documentation](https://docs.nvidia.com/deploy/xid-errors/index.html)
(release 615): Xids indicate "the driver programming the GPU incorrectly or ...
corruption of the commands sent to the GPU". They can mean a hardware problem,
a driver bug, or your application. These are the ones a fleet should expect
to see most:

| Xid | Meaning | Catalog action |
|---|---|---|
| **13**, **31** | Graphics engine exception; GPU memory page fault. Usually your code: an out-of-bounds access in a kernel. | Restart the application |
| **48** | Double-bit ECC error: HBM returned data ECC couldn't correct | Reset the GPU, or drain and reset if 63 or 64 comes with it |
| **63** | Memory row remapping event: the GPU retiring a bad HBM row | Listed as ignorable |
| **64** | Row remapping failure: it couldn't retire the row | Reset the GPU and contact support |
| **79** | "GPU has fallen off the bus": the host can't reach it over PCIe | Restart the machine |
| **94** | Contained memory error | Contained to the application that consumed the bad memory |
| **95** | Uncontained memory error | Not contained; the GPU needs a reset |

Your fleet's real policy is a mapping from each Xid to keep serving, restart
the job, or drain and repair. The catalog is a starting point for it.

</Sub>

<Sub n="6.3" title="Failures that don't log anything">

Plenty of GPU failures are the software kind, and they never produce an Xid:

- **KV cache OOM and fragmentation.** An inference server that reserves a
  max-length KV buffer per request runs out of HBM long before it runs out of
  compute. vLLM's authors measured existing systems wasting 60–80% of KV
  memory to fragmentation and over-reservation
  ([vLLM blog](https://vllm.ai/blog/2023-06-20-vllm)).
- **Dataloader starvation.** The GPU waits for the CPU to decode the next
  batch, and no GPU metric tells you why.
- **Stragglers.** A GPU that works but runs slow holds every rank back. From
  the Llama 3 paper: "Even a single straggler can slow down thousands of other
  GPUs."
- **Silent data corruption.** Six of Meta's 419 interruptions. Scarier is the
  kind that doesn't interrupt anything and just produces a wrong gradient.

</Sub>

<SectionHeading n="07" id="operating">Measuring a GPU in production</SectionHeading>

<Sub n="7.1" title="What 100% in nvidia-smi measures">

This is probably the most misread number in GPU operations. NVIDIA's
[nvidia-smi manual](https://docs.nvidia.com/deploy/nvidia-smi/index.html)
defines GPU utilization as "Percent of time over the past sample period during
which one or more kernels was executing on the GPU. The sample period may be
between 1 second and 1/6 second depending on the product."

One or more kernels. Not how many SMs, not how many warps, not whether the
tensor cores did anything. Work it through for a kernel that launches a single
block of 32 threads and spins:

| Metric | Reading |
|---|---|
| nvidia-smi utilization | **100%**, because a kernel is always running |
| SMs with any work | 1 of 132, about 0.8% |
| Warp slots filled on that one SM | 1 of 64 |

Batch-1 decode from 5.2 would honestly show close to 100% too, with tensor
cores at a third of a percent.

<Callout label="Common mistake" kind="warn">
Reading nvidia-smi's utilization as "how busy the chip is" and scaling a fleet
on it. It says a kernel was running, nothing more. Capacity decisions need the
DCGM fields below.
</Callout>

<Why>So what should you look at?</Why>

DCGM's [profiling metrics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/feature-overview.html)
are the ones that mean something:

<Compare
  cols={["DCGM field", "Definition (NVIDIA's words)", "Tells you"]}
  rows={[
    ["PROF_SM_ACTIVE (1002)", "fraction of time at least one warp was active on a multiprocessor, averaged over all multiprocessors", "Whether the SMs have work at all"],
    ["PROF_SM_OCCUPANCY (1003)", "fraction of resident warps on a multiprocessor, relative to the maximum", "Whether latency can be hidden"],
    ["PROF_PIPE_TENSOR_ACTIVE (1004)", "fraction of cycles the tensor (HMMA / IMMA) pipe was active", "Whether you're using what you paid for"],
    ["PROF_DRAM_ACTIVE (1005)", "fraction of cycles where data was sent to or received from device memory", "Whether you're memory-bound"],
  ]}
/>

For LLM decode, DRAM active high and tensor active low is the expected,
healthy shape. For training, tensor active low usually means something
upstream is starving you.

</Sub>

<Sub n="7.2" title="The commands">

```shell
# What's running, and the (misleading) utilization
nvidia-smi
nvidia-smi --query-gpu=utilization.gpu,memory.used,temperature.gpu,clocks.sm --format=csv -l 1

# The metrics that mean something: SM active, occupancy, tensor, DRAM
dcgmi dmon -e 1002,1003,1004,1005

# Hardware errors: Xids, ECC, row remapping
dmesg -T | grep 'NVRM: Xid'
nvidia-smi -q -d ECC,ROW_REMAPPER

# Links: are they all up, and at what width?
nvidia-smi nvlink --status
nvidia-smi topo -m
lspci -vv -s <bus-id> | grep -E 'LnkSta|LnkCap'

# Where did the time go? Timeline, then one kernel in depth
nsys profile --trace=cuda,nvtx,osrt ./app
ncu --section SpeedOfLight --section Occupancy -k <kernel> ./app
```

A PCIe link that trained at x8 instead of x16, or at Gen4 instead of Gen5, is a
classic silent halving; `lspci`'s `LnkSta` shows it.

</Sub>

<Sub n="7.3" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| nvidia-smi at 100%, throughput low | Kernels running, but few SMs or tensor cores busy | Check DCGM 1002–1005 before anything else |
| Gaps between kernels in an `nsys` timeline | Dataloader, Python overhead, or synchronous copies | Raise `num_workers`, set `pin_memory=True` |
| Hundreds of tiny kernels per step | Launch overhead | CUDA graphs, fused kernels, `torch.compile` |
| DRAM active high, tensor active low | Memory-bound kernel (expected for decode) | Fewer bytes: quantisation, fusion, a KV cache that isn't wasted |
| Batch size capped by OOM, compute idle | KV cache fragmentation or over-reservation | Paged KV allocation, as in vLLM |
| Training job hangs, no error | NVLink failure or a straggler | Xids across the fleet, the NCCL flight recorder, per-rank timing |
| Bandwidth to host about half what's expected | PCIe link trained at x8 or Gen4 | Check `LnkSta` in `lspci` |

Fix them in that order, top down. Coalescing, divergence and occupancy come
last: they matter a lot to people writing kernels and very little to people
running someone else's.

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **A GPU is a throughput machine.** It spends silicon on arithmetic and
   registers, and hides memory latency by switching warps, never by making one
   thread fast.
2. **The warp is the unit of execution.** 32 threads share one instruction
   stream, so a branch that splits a warp runs both sides: 2.05× on the M4.
3. **Registers cap occupancy.** A 128-register kernel fits 16 of 64 warps, and
   low occupancy is fine if each thread has independent work.
4. **Coalescing decides bandwidth.** The same loads, strided, took useful
   bandwidth from 112 GB/s to 6.1 GB/s on the M4.
5. **A kernel launch has no syscall.** The driver writes a QMD and methods into
   mapped memory and rings a doorbell with one store.
6. **The H100's ridge is about 295 FLOP/byte.** Anything below it waits on HBM,
   and more tensor cores wouldn't help.
7. **Decode is memory-bound.** A 70B model at batch 1 does 1 FLOP per byte and
   uses about 0.34% of tensor-core peak.
8. **Batching fixes the weights, not the KV cache.** Attention stays near
   8 FLOP/byte, and KV capacity caps the batch.
9. **GPUs and HBM dominate hardware failures.** 58.7% of Llama 3's unexpected
   interruptions, and an NVLink failure often looks like a hang.
10. **nvidia-smi's 100% means a kernel was running.** Use DCGM's SM, tensor and
    DRAM activity to see what the chip is doing.

<SectionHeading n="10" id="build">Build this</SectionHeading>

**Draw your own GPU's roofline, and find where decode sits on it.**

- Write the gather kernel from 5.4 in CUDA. Sweep the stride from 4 to 256
  bytes. On an NVIDIA part it should flatten at 32 bytes, the sector size from
  the Best Practices Guide. Does it?
- Write a matrix-vector multiply, then a matrix-matrix multiply with a batch
  dimension B. Sweep B from 1 to 512 and plot achieved TFLOPS.
- The curve should rise linearly and then flatten. Where it bends is your
  ridge point, measured, and it should land near peak FLOPs ÷ peak bandwidth
  (about 295 on an H100 in BF16).
- Run the whole thing under `dcgmi dmon -e 1002,1004,1005` and watch
  nvidia-smi's utilization sit at 100% throughout while tensor active climbs
  from nearly nothing.

<SectionHeading n="11" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="nvidia-smi says 100% GPU utilization. Is the GPU fully used?">
Not necessarily. That field is the fraction of time at least one kernel was
running. A single 32-thread kernel spinning forever reads 100% while using one
SM of 132. Use DCGM's SM active, SM occupancy, tensor pipe active and DRAM
active fields to see what's happening inside.
</QA>

<QA level="intermediate" q="Why is LLM decode memory-bound on an H100?">
Each token reads every weight once and does two FLOPs per parameter, one per
byte in BF16. An H100's ridge point is about 989 TFLOPS ÷ 3.35 TB/s ≈ 295
FLOP/byte. At 1 FLOP/byte a 70B model on two H100s needs 20.9 ms to read the
weights and 0.07 ms to do the math. Batching raises the weight intensity, but
attention over each sequence's own KV cache stays around 8 FLOP/byte with
grouped-query attention, however big the batch.
</QA>

<QA level="intermediate" q="What is occupancy, and is higher always better?">
Resident warps as a fraction of the SM's maximum (64 on Hopper). It's capped
by registers, shared memory and block size: a kernel using 128 registers per
thread fits 512 threads in 65,536 registers, so 25%. Higher isn't always
better. Occupancy only exists to hide latency, and a kernel with lots of
independent work per thread can hide it with fewer warps. Many fast GEMM
kernels deliberately trade occupancy for registers.
</QA>

<QA level="deep" q="Walk through what happens when you launch a CUDA kernel.">
Runtime into driver, which builds a launch descriptor (a QMD:
grid and block dimensions, register count, shared memory size, program and
constant buffer addresses), writes methods into a pushbuffer, adds a GPFIFO
entry and advances `GP_PUT`, then rings a doorbell with one MMIO store. No
syscall. Host fetches the methods; the compute front end
reads the QMD; a block scheduler places blocks on SMs that have room for their
registers and shared memory; each SM's four warp schedulers issue one
instruction per slot from a ready warp.
</QA>

<QA level="deep" q="A 16K-GPU training job hangs with no error. Where do you look?">
NVLink failures often show up as stalled loads and stores inside a kernel with
no error code, per the Llama 3 paper, so a hang is the expected symptom. Look
for Xids in `dmesg` across the fleet (74 for NVLink, 79 for a GPU off the bus,
48/94/95 for memory), dump the NCCL flight recorder to see which collective
and which rank is stuck, and check for a straggler: one slow GPU holds every
rank at the next collective.
</QA>

<Quiz>
  <Q q="What is the H100 SXM's approximate ridge point in dense BF16?">
    About 295 FLOP/byte: 989 TFLOPS over 3.35 TB/s. Anything below it is
    waiting on HBM.
  </Q>
  <Q q="Why does FP8 let one H100 match two BF16 H100s on decode latency?">
    Decode time is weight bytes over bandwidth. 70 GB over 3.35 TB/s equals
    140 GB over 6.7 TB/s: both 20.9 ms.
  </Q>
  <Q q="Half of a warp takes each side of an if. What happens?">
    The warp executes both sides with the inactive half masked. The M4
    measured 2.05× when the split fell inside SIMD-groups.
  </Q>
  <Q q="Which Xid means the host can no longer reach the GPU over PCIe?">
    79, "GPU has fallen off the bus".
  </Q>
