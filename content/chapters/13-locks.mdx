Every service with more than one thread shares something: a connection pool, a
cache, a counter. The moment two threads write the same data, you need a rule
about who goes first, and a mutex is the usual rule. It sits under `std::mutex`,
Go's `sync.Mutex`, Java's locks, Postgres's internal `LWLock`s and CPython's
global interpreter lock.

Most of us picked up "locks are slow, avoid them" somewhere. It's mostly wrong.
An uncontended lock costs a few nanoseconds and never enters the kernel. What's
slow is **contention**, many threads wanting the same lock at once, and the
failures that come with it.

This chapter starts from the bug a lock exists to prevent, builds a lock from
one atomic instruction, and then follows `lock()` and `unlock()` down to the
kernel. It ends with how locks fail, what they cost at one thread and at eight,
and how to find the lock that's hurting you.

<Sub n="1.1" title="Why count++ loses increments">

`count++` isn't one step. It's a load, an add and a store. The add happens in a
register, where the other thread can't see it.

What you need is a rule that only one thread at a time may run that
load-add-store. That stretch of code is the **critical section**, and a
**mutex** (short for mutual exclusion) is how you enforce the rule.

<Sub n="1.2" title="Why a flag isn't a lock">

How would you build one? The first idea is a flag: wait while it's set, then set
it and go in.

```cpp
while (locked) {}   // wait
locked = true;      // take it
```

<Why>Why does that fail?</Why>

It's the same race again. Both threads can see `locked == false`, both fall out
of the loop, and both set it. Checking and setting are two steps, just like the
load and the store in `count++`.

Checking and setting have to happen as one indivisible step. Chapter 03 showed
that processors provide exactly that: an atomic compare-and-swap that changes a
value only if it still holds what you expected, and tells you whether it
worked. Loop on that until you flip the flag from 0 to 1, and you have a working
lock, a **spinlock**.

</Sub>

<Sub n="1.3" title="Spin, sleep, or both">

A spinlock has a cost, and it's mostly in the waiting. A thread that can't get
the lock burns a whole core going round the loop. If the thread holding the lock
has been descheduled (chapter 06), everyone waiting may spin for a whole time
slice while nothing useful happens.

It would be better for a waiter to sleep and be woken when the lock is free.

<Why>Why not always sleep, then?</Why>

Sleeping needs the kernel, and a syscall costs hundreds of nanoseconds (chapter
07). You don't want to pay that on every lock, when most locks are probably free
when you ask for them.

| Strategy | Free lock costs | Held lock costs | Problem |
|---|---|---|---|
| **Spin** | One atomic | A burning core while you wait | Terrible if the holder is descheduled |
| **Always sleep** | A syscall, every time | A syscall and a context switch | Pays the kernel even when nobody's waiting |
| **Futex** | One atomic | A syscall, only now | A subtle unlock (section 4) |

Linux's answer is the last row, the **futex**, the "fast userspace mutex". The
lock stays an ordinary integer in your memory. If it's free, one atomic
instruction takes it and the kernel never hears about it. Only if another thread
holds it does the waiter make a syscall that says "sleep until this address
changes".

</Sub>

<SectionHeading n="02" id="contract">What a mutex promises, and what it doesn't</SectionHeading>

A mutex promises one thing: at most one thread holds it at a time. Everything
else you might assume, it doesn't promise.

<Sub n="2.1" title="Exclusion, ordering, and some progress">

You do get two things beyond exclusion.

| You get | What it means |
|---|---|
| **Mutual exclusion** | At most one holder at a time |
| **Release/acquire ordering** | Everything a thread wrote before unlocking is visible to whichever thread locks next, so you can skip extra fences inside a critical section |
| **Conditional progress** | If holders keep releasing, some waiter proceeds. Which one is unspecified. |

| You don't get | What that means for you |
|---|---|
| **Fairness** | No FIFO, no bound on how long you wait |
| **Reentrancy** | Locking a `PTHREAD_MUTEX_NORMAL` twice from one thread deadlocks instantly |
| **Priority awareness** | Not unless you ask for `PTHREAD_PRIO_INHERIT` |
| **A link to the data** | Nothing ties a mutex to what it guards; that lives only in your head and your reviewers' |

</Sub>

<Sub n="2.2" title="No fairness, on purpose">

A mutex says nothing about who gets it next, or how long you'll wait. A thread
that just released a lock and immediately asks for it again will often win it
back, while a thread that's been queued for a millisecond waits longer.

<Why>Why would anyone design it that way?</Why>

Because barging like that is what keeps the uncontended path at four
nanoseconds, and the uncontended path is the one that runs a billion times a
day. The relocking thread probably already has the lock's cache line, too. Handing the
lock to a sleeping waiter instead would mean a wake-up and a context switch on
every release.

<Callout label="Common mistake" kind="warn">
Assuming FIFO. `pthread_mutex_lock` with default attributes gives you no FIFO
guarantee, and neither does `std::mutex`. If your design needs fairness you have
to build it. Assuming fairness you were never given is how a background thread
ends up starved for seconds under load.
</Callout>

`std::recursive_mutex` exists for the reentrancy case, but reaching for it is
usually a sign the ownership model needs rethinking.

</Sub>

<SectionHeading n="03" id="futex-word">One integer, three states</SectionHeading>

Underneath `std::mutex` on Linux is `pthread_mutex_t`, and underneath that is
one 32-bit integer.

<Sub n="3.1" title="The futex word">

The integer has three meaningful values: 0 free, 1 held with no waiters, 2 held
with waiters queued.

<Figure caption="The futex word. Three states, and a syscall that only happens when the value is 2.">
<MemoryLayout
  unit="bits"
  fields={[
    { name: "futex word", bits: 32, accent: true, note: "0 = free · 1 = held, no waiters · 2 = held, waiters queued" },
  ]}
/>
</Figure>

A full `pthread_mutex_t` carries more: an owner TID, a recursion count, a kind
field, a waiter list pointer. But the hot path touches only that first word.
Everything else is for error checking, recursion and robustness, and none of it
is read when the lock is uncontended.

That's the layout under `std::mutex`, Go's `sync.Mutex` and Java's locks on
Linux.

</Sub>

<Sub n="3.2" title="Why two states aren't enough">

Two states would be enough for correctness: free and held.

<Why>So why a third?</Why>

So unlock can tell whether anyone needs waking. With two states, unlock would
have to call into the kernel every single time, just in case.

At roughly a microsecond per syscall against four nanoseconds for the fast
path, that's a couple of hundred times the cost. It would be paid on every
release, to handle a case that almost never happens. The third state turns it
into a branch on a value you already have in a register.

<Callout label="Design implication">
Uncontended locking is cheap enough that "avoid locks for speed" is usually
optimising a path you don't hit. Design to keep locks *uncontended*: short
critical sections, no I/O while holding one, and state split so threads rarely
want the same lock.
</Callout>

</Sub>

<SectionHeading n="04" id="lock-path">lock() and unlock(), step by step</SectionHeading>

Here's the canonical algorithm, from Drepper's paper. It's about twenty lines
and worth reading twice.

<SourceRead
  file="Futexes Are Tricky — Ulrich Drepper, 2011"
  repo="mutex3"
  tag="the canonical algorithm"
  href="https://www.akkadia.org/drepper/futex.pdf"
>
```c
void lock(int *futex) {
    int c;
    /* Fast path: 0 -> 1. If it works, we are done. No syscall. */
    if ((c = cmpxchg(futex, 0, 1)) != 0) {
        do {
            /* Someone holds it. Announce that a waiter exists (state 2)
               and sleep until the value stops being 2.                   */
            if (c == 2 || cmpxchg(futex, 1, 2) != 0)
                futex_wait(futex, 2);
        } while ((c = cmpxchg(futex, 0, 2)) != 0);
    }
}

void unlock(int *futex) {
    /* If the value was 2, someone is asleep and has to be woken.
       If it was 1, nobody is waiting and we skip the kernel entirely. */
    if (atomic_fetch_sub(futex, 1) != 1) {
        *futex = 0;
        futex_wake(futex, 1);
    }
}
```
</SourceRead>

<Sub n="4.1" title="The fast path: no kernel at all">

When nobody else wants the lock, the whole pair is two atomic instructions.

  title="An uncontended lock() and unlock()"

    { t: "futex word", s: "in your memory", icon: "▦" },
    { t: "Critical section", s: "your code", icon: "◉" },
    { t: "unlock()", s: "fetch_sub 1", icon: "⇤" },

  ]}
  steps={[
    [0, "`lock()` does one `cmpxchg(futex, 0, 1)`: if the word is 0, make it 1."],
    [1, "The word was 0, so it's now **1: held, no waiters**. The lock is taken. **No syscall.**"],
    [2, "The critical section runs. Acquire ordering means it sees everything the previous holder wrote."],
    [3, "`unlock()` does `atomic_fetch_sub(futex, 1)`, which returns the **previous** value: 1."],
    [3, "Previous value 1 means nobody was waiting. The word is back to 0 and `unlock()` returns. The kernel lane never lit up."],
  ]}
/>

That second function is the clever half. `atomic_fetch_sub` returns the
*previous* value, so comparing it against 1 is asking "was I the only one
interested?" When the answer is yes, and it overwhelmingly is, the function
returns without ever entering the kernel. That's where the four nanoseconds
comes from.

</Sub>

<Sub n="4.2" title="The slow path: parking in the kernel">

When a thread does have to wait, `futex_wait` hashes the *physical* address of
the futex word into a global table of wait queues and sleeps the caller on that
bucket.

<StepSequence
  title="Thread B waits for a lock that Thread A holds"
  actors={["Thread A", "futex word", "Kernel queue", "Thread B"]}
  messages={[
    { from: 0, to: 1, label: "cmpxchg 0 → 1", note: "A finds the word at 0 and takes the lock. **No syscall.**" },
    { from: 3, to: 1, label: "cmpxchg 0 → 1 fails", note: "B tries the fast path and reads 1: someone holds it." },
    { from: 3, to: 1, label: "cmpxchg 1 → 2", note: "B sets the word to **2** to announce that a waiter exists." },
    { from: 3, to: 2, label: "futex_wait(addr, 2)", note: "B makes the syscall. The kernel checks the word still reads 2, then parks B on the bucket for that address. **B is off-CPU entirely.**", dashed: true },
    { from: 0, to: 1, label: "fetch_sub → was 2", note: "A unlocks. The previous value was 2, not 1, so a waiter exists. A sets the word to 0." },
    { from: 0, to: 2, label: "futex_wake(addr, 1)", note: "A makes a syscall to wake one waiter." },
    { from: 2, to: 3, label: "wake", note: "B is scheduled again and returns from `futex_wait`." },
    { from: 3, to: 1, label: "cmpxchg 0 → 2", note: "B takes the lock, as **2**, because it can't know whether others are still waiting. So the next unlock will call `futex_wake`, even if nobody is left waiting." },
  ]}
/>

B never spins. It parks in a kernel queue and is woken by A's unlock, which is
the whole reason the contended path costs microseconds instead of nanoseconds.

<Why>Why hash the physical address, not the virtual one?</Why>

Hashing on the physical address is what lets two processes share a futex in
shared memory without agreeing on a virtual address. No kernel state about the
lock survives between calls. The word in userspace *is* the lock, and all the
kernel manages is the queue of disappointed threads.

</Sub>

<Sub n="4.3" title="The race that futex_wait's argument closes">

There's a race hiding in the slow path. B sets the word to 2 and then calls
`futex_wait`. Those are two separate steps, and A can unlock between them.

<StepSequence
  title="Unlock lands between B's cmpxchg and B's syscall"
  actors={["Thread A", "futex word", "Kernel queue", "Thread B"]}
  messages={[
    { from: 3, to: 1, label: "cmpxchg 1 → 2", note: "B finds the lock held and sets the word to 2. It's about to call `futex_wait`." },
    { from: 0, to: 1, label: "fetch_sub → was 2", note: "Before B's syscall, A unlocks. It sees the 2 and sets the word to 0." },
    { from: 0, to: 2, label: "futex_wake(addr, 1)", note: "A wakes one waiter, but **B isn't in the queue yet**. The wake hits nothing." },
    { from: 3, to: 2, label: "futex_wait(addr, 2)", note: "Now B calls. If the kernel just slept it, B would sleep forever on a free lock, with nobody left to wake it." },
    { from: 2, to: 3, label: "returns at once", note: "But the kernel compares `*addr` against the expected **2** under the bucket lock. It reads 0, so it returns immediately instead of parking." },
    { from: 3, to: 1, label: "cmpxchg 0 → 2", note: "B goes round Drepper's loop and takes the free lock." },
  ]}
/>

`futex_wait(addr, expected)` passes the value the caller expects, and that value
check is what closes the window.

macOS has no futex. `os_unfair_lock` uses `__ulock_wait`/`__ulock_wake`, and
Windows uses `WaitOnAddress`. Different syscalls, same shape: an atomic in
userspace, a kernel queue keyed by address, and a value check to close that
race.

</Sub>

<SectionHeading n="05" id="failure">How locks fail: deadlock, inversion, convoys</SectionHeading>

Locks fail in three classic ways. None of them crash; they hang, or stall, or
quietly slow down.

| Failure | What happens | Fix |
|---|---|---|
| **Deadlock** | Two threads each hold a lock the other wants | A global lock order |
| **Priority inversion** | A high-priority thread waits on a low-priority holder that isn't running | Priority inheritance (`PTHREAD_PRIO_INHERIT`, PI futexes) |
| **Convoy** | A descheduled holder makes every waiter queue, then they move in lockstep | Shorter critical sections, less sharing |

<Sub n="5.1" title="Deadlock and the one strategy that scales">

Deadlock everyone can picture: two threads, two locks, opposite order. There's
exactly one prevention strategy that scales, a global lock order. Number your
locks, document the order, never acquire downward.

`lockdep` in the kernel and ThreadSanitizer in userspace both enforce it by
watching the acquisition graph at runtime.

<Callout label="Common mistake" kind="warn">
Treating timeouts as a cure. A `try_lock` with backoff turns a deadlock into a
livelock and a latency spike, and the bug survives to production.
</Callout>

</Sub>

<Sub n="5.2" title="Priority inversion and Mars Pathfinder">

Priority inversion is the one that grounded a Mars lander. A low-priority thread
holds a lock, and a high-priority thread wants it. Then a medium-priority thread
that wants nothing preempts the holder. The high-priority thread is now waiting
on a thread that isn't running.

On Pathfinder in 1997, a high-priority bus management task blocked on a mutex
held by a low-priority meteorological task, which a medium-priority comms task
kept preempting. A watchdog rebooted the lander repeatedly. A fix uploaded from
Earth enabled priority inheritance on that one mutex.

That fix is still the fix, and the reason `PTHREAD_PRIO_INHERIT` exists in the
standard: the holder is temporarily boosted to the priority of its highest
waiter. Linux implements this with PI futexes, a separate kernel path with
ownership recorded in the futex word itself.

</Sub>

<Sub n="5.3" title="Convoys">

Convoys are probably the hardest to spot. A holder gets descheduled mid-critical-section,
and every other thread piles into the wait queue. When the holder is
rescheduled and releases, one waiter wakes, runs, and the pattern repeats. The
whole group now moves in lockstep, one context switch per handoff.

<Why>Why don't the dashboards show it?</Why>

Throughput can look fine while latency falls apart, because the system is still
doing work. It's just doing it in a queue whose service order nobody chose.
Section 6.2 shows one turning up as a number.

</Sub>

<Sub n="6.2" title="Adding threads">

The first version of this contention benchmark said this:

```
2 threads    67.1 ns per critical section
4 threads    24.6 ns
8 threads    18.9 ns
```

Contention getting *cheaper* as threads were added. The benchmark was wrong: it
fixed the *total* work at 2,000,000 operations and split it across threads, so
eight threads each did 250,000 while one thread did two million. Thread startup
was in the timer too. It measured less work per thread, not contention.

<Callout label="Common mistake" kind="warn">
Splitting a fixed total across threads in a scaling benchmark. Fix the work
*per thread*, so adding threads adds work, and keep thread startup out of the
timer.
</Callout>

With fixed work per thread, before you look: going from four threads to eight,
what happens to the cost per critical section?

<Why>Why is eight threads faster than four?</Why>

Once enough threads are waiting they stop spinning and park, and a parked thread
doesn't fight for the cache line. One thread then runs a long batch of critical
sections unopposed. Throughput improves and fairness is destroyed. That's the
convoy from section 5.3, showing up as a number instead of as a description.

The four-thread row is still open. It swings between 31 and 63 nanoseconds
across runs while every other row is stable to two decimal places. My best guess
is core placement: the M4 has performance and efficiency cores, and four threads
sits right at the boundary where the scheduler's choice changes the answer. It
isn't proven. Pinning threads to core types would settle it, and macOS makes
that awkward. An unexplained 2× is exactly the kind of thing benchmarks quietly
average away.

</Sub>

as completely as if they shared a lock, with none of the protection.

<TryIt what="Two counters, one cache line, then padded apart" lang="cpp" toolchain="clang++ 21 -O2 -pthread, Apple M4">
```cpp
constexpr int LINE = 128;                  // M-series. On x86-64 it's 64.

std::atomic<long> packed[8] = {};          // 64 bytes, all inside one line

struct alignas(LINE) Padded { std::atomic<long> v{0}; };
std::vector<Padded> padded(8);             // one counter per line

// Each thread hammers its OWN counter 5,000,000 times.
// No thread ever touches another thread's data.
for (int t = 0; t < T; t++)
    threads.emplace_back([&, t] {
        for (long i = 0; i < 5'000'000; i++)
            packed[t].fetch_add(1, std::memory_order_relaxed);
    });
```

<Output>
| threads | shared line | padded | penalty |
| --- | --- | --- | --- |
| 2 | 3.0 ns | 0.82 ns | 3.7× |
| 4 | 5.1 ns | 0.45 ns | 11× |
| 8 | 14.6 ns | 0.27 ns | **55×** |

Stable within 5% over six runs. Look at the padded column: it gets *faster*

At eight threads one `alignas(128)` is worth fifty-five times. No algorithm
changed, no lock was involved, and the only difference is which cache line the
bytes landed in.

<Callout label="Common mistake" kind="warn">
Padding to 64 bytes out of habit. It's the x86-64 value and it's what most
padding code hardcodes, but on an M4 the line is 128 bytes, so two
64-byte-padded counters still share one line and nothing improves. `sysctl -n
hw.cachelinesize` takes two seconds; run it first.
</Callout>

C++17 added `std::hardware_destructive_interference_size` for exactly this
padding problem. Then libstdc++ and libc++ disagreed about whether it's
ABI-stable, so GCC warns when you use it and Apple's libc++ doesn't ship it at
all. Check your platform's real line size before you pad.

</Sub>

<SectionHeading n="07" id="operating">Finding the lock that's hurting you</SectionHeading>

<Sub n="7.1" title="Off-CPU time, not a CPU profile">

When a lock is hurting you, reach first for `perf lock contention --threads`.
It ranks contended locks by total wait time.

<Why>Why not just look at a flame graph?</Why>

A blocked thread burns no cycles, so it never shows up in a flame graph at all.
Wait time answers "where is the time going" far more directly than a CPU
profile does. Off-CPU analysis, via `perf record -e sched:sched_switch -g`, is
the other half.

```shell
perf lock record ./yourapp && perf lock contention --threads
perf record -e sched:sched_switch -g ./yourapp
perf stat -e cache-misses,cache-references ./yourapp     # lock, or line?
xcrun xctrace record --template 'System Trace' --launch ./yourapp   # macOS
```

</Sub>

<Sub n="7.2" title="Symptom, cause, fix">

The symptoms are distinctive enough to shortcut most of this.

| Symptom | Likely cause | Fix |
|---|---|---|
| High p99, flat p50, flat CPU | A convoy | Find the lock by wait time; shorten or split the critical section |
| Throughput falls as you add cores | False sharing, or a global lock | Check cache misses per operation, then your struct layout and line size |
| One thread starves for seconds | You assumed FIFO somewhere | Build fairness explicitly, such as a ticket lock |
| Latency spike under a priority mix | Priority inversion | Check `PTHREAD_PRIO_INHERIT` is set |
| A hang with every thread idle | Deadlock | `gdb thread apply all bt` shows the cycle; impose a lock order |

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **`count++` is three instructions.** Two threads interleaving the load and
   the store lose increments silently.
2. **A lock needs an atomic check-and-set.** A plain flag has the same race as
   the counter it's meant to protect.
3. **A futex is an integer with three states.** 0 free, 1 held, 2 held with
   waiters, so unlock can skip the kernel when nobody's waiting.
4. **An uncontended lock costs about 4 ns.** 4.25 ns on the M4, two and a half
   times a bare atomic, with no syscall.
5. **Contention is the slow part.** A waiter parks in a kernel queue, and each
   handoff costs about a microsecond and two context switches.
6. **`futex_wait` takes the expected value** so a wake that lands before the
   waiter sleeps isn't lost.
7. **A mutex isn't fair.** Barging is what keeps it fast; assume FIFO and a
   thread starves.
8. **Deadlock has one scalable fix, a global lock order.** Timeouts turn it into
   livelock.
9. **False sharing can cost more than any lock.** 55× at eight threads, and the
   line is 128 bytes on the M4, not 64.
10. **Find lock pain in off-CPU time.** A blocked thread never appears in a
    flame graph; `perf lock contention` ranks by wait.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Write a mutex.** Drepper's three-state algorithm is about twenty lines, and
implementing it against `futex(2)` or `__ulock_wait` directly teaches more than
any amount of reading it.

- Then do the part people skip: make it fair and measure what fairness costs.
  Add a ticket: each waiter takes a number, and unlock wakes the holder of the
  next one.
- Benchmark both against `std::mutex` at 2, 4 and 8 threads, and plot
  throughput *and* the spread of per-thread completion times.

You should find the fair lock is slower on throughput and dramatically tighter
on spread. That trade is the entire reason the default is unfair, and your own
numbers for it are worth more than being told.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Roughly what does an uncontended mutex cost?">
A handful of nanoseconds, and no syscall. On an M4 I measured 4.25 ns for lock
plus unlock against 1.60 ns for a bare atomic increment. More important is the *no syscall* half: the fast path is a compare-exchange in
userspace, so the kernel is never involved unless another thread already holds
the lock.
</QA>

<QA level="intermediate" q="Why does a futex-based mutex need three states and not two?">
So that unlock can tell whether anybody needs waking. With free and held only,
every unlock would have to make a `futex_wake` syscall just in case a waiter
existed. A third state, held-with-waiters, turns that into a check of a value the
unlocking thread already has in a register, so the common case costs a
branch instead of about a microsecond.
</QA>

<QA level="intermediate" q="Your service has a flat p50 and a p99 forty times higher. CPU is unremarkable. Where do you look?">
Off-CPU time, not a CPU profile. A thread blocked on a lock burns no cycles, so
it's invisible in a flame graph. `perf lock contention` ranks locks by total
wait time; `perf sched` shows where threads went to sleep. Flat median, terrible
tail, unremarkable utilisation is what a convoy looks like from outside.
</QA>

<QA level="deep" q="Two threads increment two different counters and never touch each other's data. Adding the second thread makes it slower. Why?">
False sharing. Both counters sit in the same cache line, and coherence works at
line granularity, so each write invalidates the other core's copy of the whole
line. Logically independent, physically serialised.

Padding each counter onto its own line with `alignas` fixes it. On an M4 at
eight threads I measured 14.6 ns per operation shared against 0.27 ns padded,
about 55×. Note the line is 128 bytes there, not 64, so padding to 64 fixes
nothing on that hardware.
</QA>

<QA level="deep" q="Explain the race that futex_wait's value argument prevents.">
Thread B finds the lock held, sets the word to 2, and is about to call
`futex_wait`. Between those two steps thread A unlocks: it sees the 2, sets the
word to 0 and calls `futex_wake`. But B isn't in the queue yet, so the wake
hits nothing. B then calls `futex_wait` and sleeps on a lock that's free, with
nobody remaining to wake it.

`futex_wait(addr, expected)` closes this. Under the bucket lock, the kernel
compares `*addr` against `expected` and only sleeps if they still match. B
passes 2, the word now reads 0, the comparison fails, and the syscall returns
immediately instead of parking.
</QA>

<SectionHeading n="11" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="A thread unlocks and immediately relocks. Another thread has been queued for 1 ms. Who probably wins?">
    The one that just released. Barging is permitted and common (there's no
    FIFO guarantee), and the relocking thread already has the line in its cache.
  </Q>
  <Q q="You pad a struct to 64 bytes to stop false sharing. On an Apple M4, what happens?">
    Nothing improves. The line is 128 bytes, so two 64-byte-padded counters
    still land in one line.
  </Q>
  <Q q="Why is an uncontended unlock allowed to skip the kernel entirely?">
    Because `fetch_sub` returns the previous value. If it was 1, the thread was
    the only party interested and there is no queue to wake.
  </Q>
  <Q q="Does a mutex give you any memory-ordering guarantee?">
    Yes: release on unlock, acquire on lock. Everything written before an
    unlock is visible to the next thread that locks.
  </Q>
</Quiz>
