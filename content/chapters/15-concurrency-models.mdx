Every server has to answer the same question: while one request waits on a
database, what runs? A web backend in Java, a Node.js API, a Go microservice
and an Erlang chat server all answer it differently, and the answer shapes how
you write every handler.

The choice is usually made by accident, inherited from the framework or from
whatever the team used last. It decides how much memory each connection costs,
what a single blocking call can break, and how hard the code is to debug.

This chapter works out how many requests a core has to keep in flight, then
goes through the five designs that do it: OS threads, the event loop,
async/await, goroutines and actors. For each it shows how a switch happens,
what it costs, and where it breaks. It ends with four questions that decide
most real cases.

<SectionHeading n="01" id="in-flight">Keeping a core busy while requests wait</SectionHeading>

Picture a server with ten thousand open connections. Each request needs about
1 ms of CPU, then spends 50 ms waiting on a database.

<Sub n="1.1" title="How many requests one core needs in flight">

If a request computes for 1 ms and waits for 50, one core needs about **51
requests in progress** to stay busy. While one is computing, fifty are waiting.

<Why>Why not just serve them one at a time?</Why>

Because the core would sit idle for 50 ms of every 51. Serving requests in
sequence uses about 2% of the CPU you paid for.

So what you're really choosing is how you keep dozens of requests per core in
progress at once, and what each one in progress costs you.

</Sub>

<Sub n="1.2" title="Who decides when to switch">

Underneath every model sits one question: who decides when to stop running one
piece of work and start another?

The kernel can take a thread away at any instruction. That's **preemption**.
An async task gives up the CPU only where you wrote `await`. Most of the
practical differences between the models follow from that answer, and from the
cost of creating and switching the unit.

<Callout label="Design implication">
Don't ask which model is fastest. Ask how many concurrent units you need, and
whether they block. Ten thousand mostly-idle sockets and ten CPU-bound
computations are completely different problems, and the model that wins one
loses the other badly.
</Callout>

</Sub>

<SectionHeading n="02" id="threads">OS threads: one per connection</SectionHeading>

The most natural answer is a thread per connection. You write plain blocking
code: read the request, query the database, write the response.

<Sub n="2.1" title="Blocking code, and the kernel switches">

When a thread blocks, the kernel runs another one. Here's what happens when
thread A waits on the database:

/>

That's easy to read and debug. Each request is a straight line of code, and a
stack trace shows exactly where it is.

<Why>Why is preemption a feature, not just overhead?</Why>

Because nothing one thread does can hang the others. A runaway loop in one
thread doesn't stop the rest; the kernel takes the CPU away anyway. None of the
other models here can say that.

</Sub>

<Sub n="2.2" title="What each thread costs">

The costs are memory and scheduling. Every thread has its own stack, and the
kernel's scheduler ([chapter 06](/topics/06-processes-scheduling)) has to
juggle all of them.

A few thousand threads is fine. A hundred thousand gets painful.

<Why>Why can't you just create a hundred thousand OS threads?</Why>

Two limits. Each thread reserves a stack, 8 MB of virtual address space by
default on Linux, so a hundred thousand reserve 800 GB. That memory is
committed lazily, so 8 MB per thread isn't 8 MB of RAM. But address space and
kernel bookkeeping run out long before.

And scheduler cost grows with runnable threads, so switching starts eating the
CPU you wanted.

| | OS threads |
|---|---|
| **Best for** | CPU-bound work, and any concurrency count under about a thousand. Easiest to debug by a wide margin. |
| **Breaks** | Above a few thousand units. Each reserves an 8 MB virtual stack on Linux, and scheduler cost grows with runnable threads. |

</Sub>

<SectionHeading n="03" id="event-loop">The event loop: one thread that never blocks</SectionHeading>

The opposite answer is a single thread that never blocks. It's how nginx and
Node.js handle huge numbers of connections with almost no memory per
connection.

<Sub n="3.1" title="Asking the kernel what's ready">

The loop asks the kernel which connections are ready right now, using `epoll`
from [chapter 07](/topics/07-syscalls-kernel-boundary). It does a little work on
each, then goes back to ask again.

  ]}
/>

</Sub>

<Sub n="3.2" title="Where the cost moves">

The cost moves into your code. Nothing may ever block, so every "wait for the
database" has to become a callback that runs later.

The logic of one request ends up scattered across several functions.
Local variables have to be saved somewhere between callbacks, and a stack trace
no longer shows how you got here.

</Sub>

<SectionHeading n="04" id="async">async/await: stackless tasks</SectionHeading>

Two designs try to get the cheapness of the event loop with the readability of
threads, from opposite ends. **async/await** keeps the event loop and fixes the
code. Rust's Tokio, JavaScript and Python work this way.

<Sub n="4.1" title="A function compiled into a state machine">

The compiler turns an `async` function into a small object that can pause at
each `await` and be resumed later. You write something that reads like blocking
code, but it runs on the loop.

That object is a struct sized to the variables live across `await` points.
There's no stack at all. A task might be 96 bytes, and that's why a million
concurrent tasks is reasonable.

  title="An async handler waits on the database"

    { from: 3, to: 2, label: "reply", dashed: true, note: "The database reply arrives, and the socket becomes readable." },
    { from: 2, to: 1, label: "ready", note: "epoll reports the socket, and the executor marks the task runnable again." },
    { from: 1, to: 0, label: "resume", note: "The executor calls the task again. The state machine jumps to just after the `await`, and the handler carries on." },
  ]}
/>

A task can only suspend at points the compiler knew about in advance. Marking
those is the entire job of `await`.

</Sub>

<Sub n="4.2" title="Function colouring">

An `async` function can only be awaited from another `async` function. Once a
function is `async`, its callers must be `async` too, or block to call it.

<Why>Why does async spread through a codebase?</Why>

Because that property propagates up the entire call graph. Adding one async
function to a library can force every user to restructure. Bob Nystrom's 2015
essay *What Color Is Your Function?* named it, and it's still the clearest
statement of the problem.

</Sub>

<Sub n="4.3" title="One blocking call stops the executor">

This is the defining failure of async. An executor runs a small number of
worker threads, often one per core. A task that blocks *the thread*, instead of
yielding at an `await`, removes that worker from service entirely.

```rust
// Tokio, 8 workers on an 8-core box
async fn handler() -> Response {
    let data = std::fs::read("/big/file")?;   // BLOCKS the worker thread
    process(data)
}
```

<Predict
  q="Eight requests hit this handler at the same moment, on a Tokio runtime with eight workers. What does the rest of the service do while the reads run?"
  options={[
    "Runs a little slower, since the other tasks share what's left",
    "Stops completely: no task makes progress, and the CPU looks idle",
    "Carries on normally, because Tokio moves blocked tasks to spare threads",
    "Crashes with a runtime error about blocking",
  ]}
  answer={1}
>
Each read blocks one worker thread, and there are only eight. With all eight
blocked, nothing else is ever polled. It isn't slow, it's dead, with zero tasks
progressing. And because a blocked thread burns no CPU, the machine looks idle.
</Predict>

The same shape catches `std::sync::Mutex` in async code, synchronous database
drivers, and any CPU loop longer than a few milliseconds. The fix is
`spawn_blocking`, an async-aware library, or an explicit yield inside long
loops.

<Callout label="Common mistake" kind="warn">
Calling one synchronous library from async code "just this once". One blocking
dependency poisons an async design. If that dependency is synchronous and you
can't replace it, that probably decides the model for you.
</Callout>

| | async / await |
|---|---|
| **Best for** | Hundreds of thousands of mostly-idle I/O-bound connections, where per-unit memory is the binding constraint. |
| **Breaks** | One blocking call poisons the executor. And function colouring propagates through your entire call graph. |

</Sub>

<SectionHeading n="05" id="green-threads">Goroutines and virtual threads: stackful and cheap</SectionHeading>

The other fix keeps blocking code and makes threads cheap. A **goroutine**, or a
Java 21 virtual thread, is a thread the language runtime manages itself.

<Sub n="5.1" title="A thread the runtime manages">

A runtime multiplexes many goroutines onto a few OS threads, switching at safe
points it inserts. Each goroutine starts with an 8 KB stack, which is copied and
grown as needed. A switch costs around 100 ns, all in user space.

<Why>Why don't goroutines need an async keyword?</Why>

Because they're **stackful**. Each one has a real stack, so an ordinary
function can block and the runtime switches underneath it. There's no `async`
keyword and no colouring. Go answered Nystrom's problem this way; Rust accepted
the colouring and got tasks with no stack at all.

</Sub>

<Sub n="5.3" title="Work stealing, and what it costs">

Go's scheduler and Tokio's multi-threaded runtime both use **work stealing**:
an idle worker takes queued tasks from a busy one. That improves utilisation.

<Why>What does stealing cost?</Why>

Locality. Your task can resume on a different core than it suspended on, so
anything warm in that core's cache is gone, and thread-local assumptions break.
For short tasks, the steal can cost more than the work it enabled.

Runtimes soften this by stealing from the opposite end of the victim's queue,
so the victim keeps popping locally without synchronisation, and by preferring
older work. Where you can't tolerate migration at all, there's
`runtime.LockOSThread` in Go and `spawn_local` in Tokio.

| | Goroutines (stackful green threads) |
|---|---|
| **Best for** | High concurrency where you still want to write ordinary blocking code. The best ergonomics of the four. |
| **Breaks** | Memory at very high counts, since every unit carries a growable stack. And you inherit a garbage collector. |

</Sub>

<SectionHeading n="06" id="actors">Actors: nothing shared</SectionHeading>

A fifth model leaves switching alone and changes what's shared.

<Sub n="6.1" title="State you reach only by message">

An **actor** keeps its state private and can only be reached by sending it
messages, so there's nothing to lock. Erlang is built entirely on this idea,
and WhatsApp's servers ran on Erlang.

<Why>Why accept a message send on every interaction?</Why>

For the isolation boundary nothing else here offers. One actor can crash and be
restarted by its supervisor without corrupting anyone else's state. That's
worth real overhead in systems where partial failure is routine and expected,
and dead weight in most others.

| | Actors |
|---|---|
| **Best for** | Systems needing a per-unit failure boundary and supervision. Telecoms, and stateful distributed services. |
| **Breaks** | Message-passing overhead on every interaction, and mailboxes that grow without bound under sustained overload. |

</Sub>

<SectionHeading n="08" id="choosing">Choosing a model</SectionHeading>

<Sub n="8.1" title="Four questions, in order">

Most decisions are settled by the first two.

1. **How many concurrent units?** Under a few thousand, use threads. They're
   dramatically easier to debug, and preemption means one bad unit can't hang
   the rest. Above ten thousand you need something stackless or growable.
2. **Do they mostly wait?** I/O-bound work wants async or goroutines. CPU-bound
   work wants exactly as many OS threads as you have cores, and nothing else
   helps.
3. **Do you control the whole dependency tree?** One blocking library call
   poisons an async design (section 4.3).
4. **Do you need per-unit isolation?** Actors give a failure boundary nothing
   else does. That's worth real overhead in some systems and dead weight in
   most.

</Sub>

<Sub n="8.2" title="The five side by side">

| Model | Best for | Breaks when | Debugging |
|---|---|---|---|
| **OS threads** | CPU-bound work; under ~1,000 units | A few thousand units: stacks and scheduler cost | Easiest: real stacks, preemption |
| **Event loop** | Huge numbers of idle connections (nginx, Node.js) | Anything blocks the one thread | Hard: logic split across callbacks |
| **async / await** | Hundreds of thousands of I/O-bound connections | One blocking call; colouring spreads | Medium: reads like blocking code |
| **Goroutines** | High concurrency with ordinary blocking code | Memory at very high counts; you inherit a GC | Easy: real stacks, no colouring |
| **Actors** | Per-unit failure boundaries and supervision | Mailboxes grow without bound under overload | Medium: follow the messages |

</Sub>

<Sub n="8.3" title="Mistakes that look like choices">

<Callout label="Common mistake" kind="warn">
Choosing async when you have 200 connections. Async buys you per-unit memory,
and at two hundred units per-unit memory isn't your problem. You've paid function
colouring through your whole API for nothing, when threads would have been
simpler, easier to debug, and about as fast. It comes from picking the model
that sounds most modern instead of counting the units.
</Callout>

Cheap concurrency also invites too much of it. `go handle(conn)` in an accept
loop with no limit is the canonical bug. The units are individually cheap, so
nothing pushes back, and collectively they aren't.

<Callout label="Design implication">
Every model needs a bound: a semaphore, a bounded channel, a fixed pool. The
mechanism matters less than that one exists. Backpressure isn't a feature you
add later; it's what stops load becoming an outage.
</Callout>

| Symptom | Likely cause | Fix |
|---|---|---|
| Async service stops serving; CPU looks idle | Tasks blocking the worker threads (sync I/O, `std::sync::Mutex`, long CPU loops) | `spawn_blocking`, an async-aware library, or explicit yields |
| Memory climbs with load until the process dies | Unbounded spawning, such as `go handle(conn)` with no limit | A semaphore, bounded channel or fixed pool |
| Thread-per-connection falls over around 10,000 connections | Stack address space and scheduler cost | A pool, or a stackless or growable model |
| Short work items are slow on fresh threads | Thread creation (~14 µs) dwarfs the work | A thread pool |
| An actor's latency keeps growing under load | Its mailbox is growing without bound | Bound the mailbox and shed or push back |

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **Waiting sets the concurrency you need.** At 1 ms of CPU and 50 ms of
   waiting, one core needs about 51 requests in flight.
2. **The core question is who switches.** The kernel preempts threads anywhere;
   async tasks yield only at `await`.
3. **Threads are the easiest to debug**, and preemption means one bad unit can't
   hang the rest. They get painful above a few thousand.
4. **An event loop never blocks**, so every wait becomes a callback and a
   request's logic is scattered.
5. **async/await compiles a function into a state machine** with no stack, which
   makes a million tasks reasonable.
6. **One blocking call can stop an async executor dead**, with the CPU looking
   idle.
7. **Goroutines are stackful**, so ordinary code can block, and there's no
   function colouring.
8. **Actors trade a message send per interaction** for a failure boundary with
   supervision.
9. **Creating a thread costs 127 round trips through one.** Thread pools exist
   for that reason.
10. **Count the units before choosing**, and bound every model, whichever you
    pick.

<SectionHeading n="10" id="build">Build this</SectionHeading>

**Write the echo server three times** and find where your curves cross. This
takes an evening and settles the argument with data instead of taste.

- Thread per connection, `std::thread`.
- A fixed pool of eight with a work queue.
- One thread with `epoll` or `kqueue` and a hand-rolled state machine.

Drive all three at 100, 1,000 and 10,000 concurrent connections. Record
throughput, p99 and **resident memory**. That third column is the one that
decides it, and the one people forget to measure.

Thread-per-connection will win at 100 and will probably fail outright at 10,000.
Watching your own machine run out of something is worth more than any table
here.

<SectionHeading n="11" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why can't you just create a hundred thousand OS threads?">
Two limits. Each reserves a stack, 8 MB of virtual address space by default on
Linux, so a hundred thousand reserve 800 GB. That memory is committed lazily,
but address space and kernel bookkeeping run out long before. And scheduler cost
grows with runnable threads, so switching starts eating the CPU you wanted.
</QA>

<QA level="intermediate" q="What is function colouring and which languages avoid it?">
Once a function is `async`, its callers must be `async` or block to call it. The
property propagates up the entire call graph, so adding one async function to a
library can force every user to restructure.

Go avoids it with stackful goroutines: any function can block and the runtime
switches underneath, so there's no distinction to propagate. It pays a growable
stack per goroutine. Rust accepted the colouring and got tasks with no stack at
all, sized to their state machine.
</QA>

<QA level="intermediate" q="Your async service stops serving entirely and CPU looks idle. What happened?">
Something blocked the worker threads. An executor runs roughly one worker per
core, so a handful of tasks doing synchronous file I/O, holding a
`std::sync::Mutex`, or running a long CPU loop can take every worker out of
service. No task progresses and nothing burns CPU, so it looks like an idle
machine that has stopped responding.

Fix with `spawn_blocking`, an async-aware library, or an explicit yield inside
long loops.
</QA>

<QA level="deep" q="Why is a thread pool faster than a thread per work item?">
Creation dominates when items are short. I measured 13.8 µs to create and join a
thread against 109 ns for a round trip between two existing ones, about 127×.
For a 200 ns work item, creation is 69 times the useful work; handing it to a
pooled worker costs roughly one handoff instead.

Pools also bound concurrency, which often matters more than the speed. A pool of
N workers is backpressure you get for free.
</QA>

<QA level="deep" q="Work stealing improves utilisation. What does it cost?">
Locality. Your task can resume on a different core than it suspended on, so
anything warm in that core's cache is gone and thread-local assumptions break.
For short tasks the steal can cost more than the work it enabled.

Runtimes mitigate by stealing from the opposite end of the victim's queue, so
the victim keeps popping locally without synchronisation, and by preferring
older work. Where you genuinely can't tolerate migration there's
`runtime.LockOSThread` in Go and `spawn_local` in Tokio.
</QA>
