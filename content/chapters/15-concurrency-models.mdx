<SectionHeading n="01" cmd="cat DECISION.md" id="choice">The choice you're making</SectionHeading>

You have work that can proceed independently and you need to pick a unit to run
it on. Four options are genuinely viable, and the decision is usually made by
accident — inherited from the framework, or from whatever the team used last.

Underneath the four sits one question: **who decides when to switch?** Either
something can take the CPU away at any instruction, or it cannot and your code
has to yield voluntarily. Nearly every practical difference follows.

<Compare
  cols={["Model", "Who switches", "Switch cost", "Unit footprint"]}
  rows={[

    ["Goroutines", "Runtime, at safe points", "~100 ns", "8 KB, growable"],
    ["async / await", "Compiler, at await points", "~10 ns", "Its state machine — often under 100 B"],
    ["Actors", "Runtime, per message", "A message send", "Mailbox plus state"],
  ]}
/>

<Callout label="The question that actually decides it">
Not "which is fastest". Ask **how many concurrent units do I need, and do they
block?** Ten thousand mostly-idle sockets and ten CPU-bound computations are
completely different problems, and the model that wins one loses the other
badly.
</Callout>

<SectionHeading n="02" cmd="ls ./options/" id="options">The options</SectionHeading>

<Approach
  n="1"
  name="OS threads"
  breaks="Above a few thousand units. Each reserves an 8 MB virtual stack on Linux, and scheduler cost grows with runnable threads."
  bestFor="CPU-bound work, and any concurrency count under about a thousand. Easiest to debug by a wide margin."
>
The kernel schedules them preemptively, so nothing a thread does can hang the
others. That preemption is the feature: a runaway loop in one thread doesn't stop the
rest. No other option here can say that.

Stacks are reserved virtual address space committed lazily, so 8 MB per thread
isn't 8 MB of RAM — but it is 8 MB of address space and a kernel object.
</Approach>

<Approach
  n="2"
  name="Goroutines (stackful green threads)"
  breaks="Memory at very high counts, since every unit carries a growable stack. And you inherit a garbage collector."
  bestFor="High concurrency where you still want to write ordinary blocking code. The best ergonomics of the four."
>
A runtime multiplexes many goroutines onto few OS threads, switching at safe
points it inserts. Each starts at 8 KB and the stack is copied and grown as
needed.

Because they're **stackful**, an ordinary function can block and the runtime
switches underneath it. No `async` keyword, no colouring, and blocking C calls
survive — the runtime spins up another OS thread to cover.
</Approach>

<Approach
  n="3"
  name="async / await (stackless tasks)"
  breaks="One blocking call poisons the executor. And function colouring propagates through your entire call graph."
  bestFor="Hundreds of thousands of mostly-idle I/O-bound connections, where per-unit memory is the binding constraint."
>
The compiler rewrites your function into a state machine struct sized to the
variables live across await points. **No stack at all** — a task might be 96 bytes, and that's why a million
concurrent tasks is reasonable.

A task can only suspend at points the compiler knew about in advance. Marking
those is the entire job of `await`.
</Approach>

<Approach
  n="4"
  name="Actors"
  breaks="Message-passing overhead on every interaction, and mailboxes that grow without bound under sustained overload."
  bestFor="Systems needing a per-unit failure boundary and supervision. Telecoms, and stateful distributed services."
>
State is private to an actor and reachable only by message. That gives you an
isolation boundary nothing else here offers: one actor can crash and be
restarted by its supervisor without corrupting anyone.

Worth real overhead in systems where partial failure is routine and expected.
</Approach>

<SectionHeading n="04" cmd="./choose --explain" id="choosing">How to choose</SectionHeading>

Four questions, in order. Most decisions are settled by the first two.

1. **How many concurrent units?** Under a few thousand, use threads — they're
   dramatically easier to debug and preemption means one bad unit can't hang the
   rest. Above ten thousand you need something stackless or growable.
2. **Do they mostly wait?** I/O-bound wants async or goroutines. CPU-bound wants
   exactly as many OS threads as you have cores, and nothing else helps.
3. **Do you control the whole dependency tree?** One blocking library call
   poisons an async design. If a dependency is synchronous and unreplaceable,
   that probably decides it for you.
4. **Do you need per-unit isolation?** Actors give a failure boundary nothing
   else here does. That's worth real overhead in some systems and dead weight in
   most.

<SectionHeading n="05" cmd="git log --grep=revert" id="mistakes">What people get wrong</SectionHeading>

<Sub n="5.1" title="Blocking inside a non-preemptive runtime">

The defining failure of async, and it deserves a precise statement. An executor
runs a small number of workers — often one per core. A task that blocks *the
thread* instead of yielding removes that worker from service entirely.

```rust
// Tokio, 8 workers on an 8-core box
async fn handler() -> Response {
    let data = std::fs::read("/big/file")?;   // BLOCKS the worker thread
    process(data)
}
```

Eight concurrent requests doing that and the runtime is dead. Not slow — dead,
with zero tasks progressing and a CPU that looks idle. The same shape catches
`std::sync::Mutex` in async code, synchronous database drivers, and any CPU loop
longer than a few milliseconds.

</Sub>

<Sub n="5.2" title="Choosing async when you have 200 connections">

Async buys you per-unit memory. At two hundred concurrent units, per-unit memory
is not your problem, and you've paid function colouring through your whole API
for nothing. Threads would have been simpler, more debuggable, and about as
fast.

This is the most common wrong answer in the chapter, and it comes from picking
the model that sounds most modern instead of counting the units.

</Sub>

<Sub n="5.3" title="Unbounded spawning">

Cheap concurrency invites too much of it. `go handle(conn)` in an accept loop
with no limit is the canonical bug: the units are individually cheap, so nothing
pushes back, and collectively they aren't.

Every model needs a bound — a semaphore, a bounded channel, a fixed pool. The
mechanism matters less than one existing. Backpressure isn't a feature you add
later; it's what stops load becoming an outage.

</Sub>

<SectionHeading n="06" cmd="./worksheet" id="worksheet">Decide it for your case</SectionHeading>

**Write the echo server three times** and find where your curves cross. This
takes an evening and settles the argument with data instead of taste.

- Thread per connection, `std::thread`.
- A fixed pool of eight with a work queue.
- One thread with `epoll` or `kqueue` and a hand-rolled state machine.

Drive all three at 100, 1,000 and 10,000 concurrent connections. Record
throughput, p99 and **resident memory** — that third column is the one that
decides it, and the one people forget to measure.

Thread-per-connection will win at 100 and will probably fail outright at 10,000.
Watching your own machine run out of something is worth more than any table
here.

<SectionHeading n="08" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why can't you just create a hundred thousand OS threads?">
Two limits. Each reserves a stack — 8 MB of virtual address space by default on
Linux — so a hundred thousand reserve 800 GB. That memory is committed lazily,
but address space and kernel bookkeeping run out long before. And scheduler cost
grows with runnable threads, so switching starts eating the CPU you wanted.
</QA>

<QA level="intermediate" q="What is function colouring and which languages avoid it?">
Once a function is `async`, its callers must be `async` or block to call it. The
property propagates up the entire call graph, so adding one async function to a
library can force every user to restructure.

Go avoids it with stackful goroutines: any function can block and the runtime
switches underneath, so there's no distinction to propagate. It pays a growable
stack per goroutine. Rust accepted the colouring and got tasks with no stack at
all, sized to their state machine.
</QA>

<QA level="intermediate" q="Your async service stops serving entirely and CPU looks idle. What happened?">
Something blocked the worker threads. An executor runs roughly one worker per
core, so a handful of tasks doing synchronous file I/O, holding a
`std::sync::Mutex`, or running a long CPU loop can take every worker out of
service. No task progresses and nothing burns CPU, so it looks like an idle
machine that has stopped responding.

Fix with `spawn_blocking`, an async-aware library, or an explicit yield inside
long loops.
</QA>

<QA level="deep" q="Why is a thread pool faster than a thread per work item?">
Creation dominates when items are short. I measured 13.8 µs to create and join a
thread against 109 ns for a round trip between two existing ones — about 127×.
For a 200 ns work item, creation is 69 times the useful work; handing it to a
pooled worker costs roughly one handoff instead.

Pools also bound concurrency, which often matters more than the speed. A pool of
N workers is backpressure you get for free.
</QA>

<QA level="deep" q="Work stealing improves utilisation. What does it cost?">
Locality. Your task can resume on a different core than it suspended on, so
anything warm in that core's cache is gone and thread-local assumptions break.
For short tasks the steal can cost more than the work it enabled.

Runtimes mitigate by stealing from the opposite end of the victim's queue — so
the victim keeps popping locally without synchronisation — and by preferring
older work. Where you genuinely can't tolerate migration there's
`runtime.LockOSThread` in Go and `spawn_local` in Tokio.
</QA>

<Quiz>
  <Q q="Which of the four has no stack at all?">
    An async task. The compiler turns the function into a state machine struct
    sized to the variables live across await points — often under 100 bytes.
  </Q>
  <Q q="You call a blocking C library from a goroutine. What happens?">
    Go's runtime notices the blocked OS thread and spins up another to keep
    other goroutines running. It survives, unlike a stackless executor, and
    that's why Go tolerates cgo where Tokio would stall.
  </Q>
  <Q q="Your work items take 500 ns. Spawn a thread each?">
    No. Creation is about 14 µs here — roughly 28× the work. Use a pool.
  </Q>
  <Q q="You have 200 concurrent connections. Is async the right call?">
    Probably not. Async buys per-unit memory, and at 200 units that isn't your
    problem. You'd pay function colouring across your API for nothing.
  </Q>
</Quiz>
