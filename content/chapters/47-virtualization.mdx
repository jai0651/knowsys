You're inside a virtual machine more often than you might think. Every EC2
instance is a guest on AWS's KVM-based Nitro hypervisor. Lambda runs each
function in a Firecracker microVM. Docker Desktop runs your containers inside a
Linux VM, because macOS has no Linux kernel to share.

When a workload is slower there than on bare metal, or `top` shows a `%st`
column you've never seen move, the cause is almost always the same event: the
guest stopped and the hypervisor ran. Knowing when that happens tells you where
the speed went.

This chapter builds the idea from the ground up: how one machine runs many
kernels, how x86 and ARM were made to trap, the two page tables under every
guest address, one packet's trip through virtio and KVM, the ways it fails, and
what each exit costs.

<SectionHeading n="01" id="trap-and-emulate">How one machine runs many kernels</SectionHeading>

Say you want to run ten operating systems on one physical machine: ten
customers' Linux kernels on one cloud server, or Linux next to macOS on your
laptop.

Each of those kernels was written believing it owns the hardware. It sets up
page tables, switches interrupts on and off, and talks to the disk controller
directly. Two kernels doing that to the same machine would wreck each other
within a second.

<Sub n="1.1" title="Simulate, or deprivilege">

<Why>Why not just simulate the CPU?</Why>

You can. Simulate the whole CPU in software, instruction by instruction, and
the guest kernel never touches real hardware. That's correct, and it's many
times slower than running natively.

The better idea is from 1974, when Gerald Popek and Robert Goldberg wrote down
the conditions for doing it properly. Most of what a kernel does is ordinary:
additions, loads, stores, branches. Let all of that run directly on the real
CPU at full speed.

Only a few instructions touch machine state that has to stay under control,
like the page-table base register or the interrupt flag. Run the guest kernel
with less privilege than it thinks it has, so every one of those instructions
**traps**.

The trap hands control to a small program in charge of the real machine, the
**hypervisor**. It emulates that one instruction and resumes the guest.

| Term | Meaning |
|---|---|
| **Guest** | The operating system being run inside the VM |
| **Host** | The real machine, and the software in charge of it |
| **Hypervisor** | The program that owns the hardware and handles the guest's traps |
| **VM exit** | The trap out of the guest into the hypervisor |

<Sub n="1.2" title="Popek and Goldberg's three properties">

Popek and Goldberg's
[CACM paper](https://dl.acm.org/doi/10.1145/361011.361073) still reads well,
and it names three properties a virtual machine monitor has to provide:

| Property | What it means |
|---|---|
| **Equivalence** | A program in the VM behaves as it would on the real machine, apart from timing and resource availability |
| **Resource control** | The monitor stays in charge of all the hardware, and a guest can't grab memory or devices it wasn't given |
| **Efficiency** | Most instructions run directly on the CPU, with no monitor involvement |

Their theorem is the part people cite. A machine can be virtualized by plain
<em className="term">trap-and-emulate</em> if every *sensitive* instruction
(one that reads or changes machine state the monitor owns) is also
*privileged*, meaning it traps when run outside the most privileged mode.

Run the guest kernel deprivileged, let every sensitive instruction trap,
emulate it, resume. The 246 ms against 245 ms loop is the efficiency property
in action: nothing in that loop is sensitive.

What a VM doesn't promise is timing. Popek and Goldberg exempted it
explicitly, and it's probably the part tenants notice first: stolen CPU,
jittery I/O.

</Sub>

happened (section 6.1).
</Callout>

</Sub>

<SectionHeading n="02" id="hardware">Getting x86 and ARM to trap</SectionHeading>

The theory needs hardware where every sensitive instruction traps. It took a
long time to get that. The original x86 didn't have it, so the early
hypervisors had to cheat. Intel and AMD added hardware support in the
mid-2000s, and ARM builds it into the architecture as a separate privilege
level.

<Sub n="2.1" title="Seventeen instructions that did not trap">

x86 failed the Popek and Goldberg test. In 2000, John Robin and Cynthia Irvine
went through the Pentium instruction set and
[found seventeen](https://www.usenix.org/legacy/events/sec00/full_papers/robin/robin_html/)
sensitive instructions that run in user mode without trapping.

<Why>Why was popf the famous one?</Why>

In kernel mode `popf` can change the interrupt flag. Run the same guest kernel
at ring 3 and `popf` silently ignores the IF bit, so the monitor never learns
the guest tried to disable interrupts.

In the words of VMware's Keith Adams and Ole Agesen
([ASPLOS 2006](https://pdos.csail.mit.edu/6.828/2018/readings/adams06vmware.pdf)):
"a deprivileged popf, like any user-mode popf, simply suppresses attempts to
modify IF; no trap happens."

Three workarounds followed, roughly in order:

| Approach | How it works | Cost |
|---|---|---|
| **Binary translation** (VMware, 1999) | Rewrite guest kernel code just before it runs, swapping the problem instructions for calls into the monitor, and cache the result. User code runs unmodified. | A translator inside the monitor |
| **Paravirtualization** (Xen, [SOSP 2003](https://dl.acm.org/doi/10.1145/945445.945462)) | Modify the guest kernel so it calls the hypervisor directly (a *hypercall*) instead of executing sensitive instructions | You need the guest source, so no unmodified Windows |
| **Hardware assist** (Intel VT-x 2005, AMD-V 2006) | A new mode lets the guest kernel run at ring 0, and the CPU itself decides what exits | Early on, expensive exits |

<Why>Why did first-generation VT-x lose to binary translation?</Why>

That's the surprise in the Adams and Agesen paper: on real workloads, it did.
Their table has a VM entry at 2,409 cycles on a 3.8 GHz Pentium 4.

Worse, VT-x did nothing for the MMU, so every guest page table write still had
to be tracked in software, now with an expensive exit attached. Hardware only
won once the MMU got help too (section 3).

</Sub>

<Sub n="2.2" title="VMX root, non-root, and the VMCS">

VT-x doesn't add a ring. It adds a second copy of all of them. A hypervisor
runs in **VMX root mode**, a guest in **VMX non-root mode**, and each has its
own rings 0 to 3. So a guest kernel sits in non-root ring 0 and believes it
owns the machine.

Switching between them is governed by an in-memory structure per vCPU, the
<em className="term">VMCS</em> (virtual machine control structure). You don't
read it with loads; you use `VMREAD` and `VMWRITE`. It has four parts:

| Part | What it holds |
|---|---|
| **Guest state** | Registers saved on exit, loaded on entry: RIP, CR3, segments |
| **Host state** | Where the CPU lands in root mode on an exit |
| **Execution controls** | What exits: `HLT`? `CPUID` (always)? Which ports, which MSRs? |
| **Exit information** | Why the last exit happened, and a qualification (which port, which address) |

`VMLAUNCH` and `VMRESUME` enter the guest. An exit is the CPU saving guest
state into the VMCS and jumping to the host RIP. Step through one:

<Sub n="2.3" title="ARM: a separate exception level, and VHE">

ARMv8 was designed with this in mind. There's a dedicated exception level for
the hypervisor, **EL2**, below the kernel's EL1 and user EL0.

A trap from the guest lands at EL2 with a syndrome register (`ESR_EL2`) saying
what happened. The Mac test in section 5.2 reads exactly that field: exception
class `0x16` for `hvc`, `0x24` for a data abort from a lower level.

KVM itself was the awkward part. Linux is a normal kernel that runs at EL1, so
original KVM/arm64 had to bounce between a small EL2 stub and the kernel for
every exit.

ARMv8.1 added the **Virtualization Host Extensions (VHE)**: set
`HCR_EL2.E2H` and the host kernel runs directly at EL2, with EL1 register
accesses redirected to their EL2 twins. Linux gained
[VHE support](https://lwn.net/Articles/650524/) in 2016, and KVM on ARM
became what it is on x86: pretty much a kernel module.

</Sub>

<SectionHeading n="03" id="nested-paging">Memory: two page tables at once</SectionHeading>

Trapping instructions solves the CPU. Memory is the first of two problems that
remain. The guest thinks it's managing physical memory, but the hypervisor has
to put its own translation underneath, so every address goes through two sets
of page tables.

<Sub n="3.1" title="Guest-physical isn't physical">

[Chapter 04](/topics/04-virtual-memory) walked one 4-level page table. A guest
has its own page tables, mapping guest-virtual to *guest-physical* addresses.

Guest-physical isn't real either. A second table owned by the hypervisor maps
it to host-physical: **EPT** on Intel, **NPT** on AMD, **stage-2** on ARM.

| Approach | How it works | Cost |
|---|---|---|
| **Shadow page tables** (before 2008) | The hypervisor keeps a merged guest-virtual → host-physical table, rebuilt by trapping every guest page table write | An exit per guest page table write: the software MMU tracking that made early VT-x slow |
| **Nested paging** (Intel EPT with Nehalem, 2008) | The hardware walks both tables itself | Longer page walks on a TLB miss |

</Sub>

<Sub n="3.2" title="The two-dimensional walk">

With nested paging the hardware walks both. Here's the catch: every pointer in
the guest's table is a guest-physical address, so each one needs its own trip
through the host's table before it can be dereferenced.

(5 + 1)(5 + 1) − 1 = 35. Each of the five guest entries needs a five-read host

<Sub n="3.3" title="Cutting the walk down">

<Why>Why doesn't every TLB miss cost 24 references?</Why>

Because hardware caches the pieces. Page-walk caches and TLB tags (VPID on
Intel, VMID on ARM) exist so the full worst-case walk is rare.

Huge pages cut it from both ends:

| Guest pages | Host pages | Worst-case references |
|---|---|---|
| 4 KB, 4-level | 4 KB, 4-level | (4 + 1)(4 + 1) − 1 = 24 |
| 2 MB (one guest level fewer) | 4 KB, 4-level | (3 + 1)(4 + 1) − 1 = 19 |
| 2 MB | 1 GB (two host levels fewer) | (3 + 1)(2 + 1) − 1 = 11 |
| 5-level | 5-level | 35 |

</Sub>

<SectionHeading n="04" id="virtio">Devices: virtio, and one packet's exit</SectionHeading>

Devices are the second problem. If the guest drives an emulated network card by
poking its registers one at a time, every poke is an exit, and a real NIC driver
touches a lot of registers.

So modern guests use paravirtual devices like **virtio**, which pass whole
batches of requests through a shared queue and exit only to say "there's more".

<Sub n="4.1" title="A virtqueue, as bytes">

**virtio** (Rusty Russell,
[2008](https://dl.acm.org/doi/10.1145/1400097.1400108), now an
[OASIS standard](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html))
replaces register-by-register emulation with shared memory the guest and host
both read. Its unit is the <em className="term">virtqueue</em>, and in the
split layout that's three arrays in guest memory.

<Figure caption="One descriptor from include/uapi/linux/virtio_ring.h, widths to scale. The guest writes these; the device reads them. `next` chains descriptors so one packet can span several buffers.">

| Array | What's in it | Who writes it |
|---|---|---|
| **Descriptor table** | 16 bytes per entry, above | The guest |
| **Available ring** | `flags`, `idx`, then chain heads the guest has offered | Only the guest |
| **Used ring** | `(id, len)` pairs the device has finished | Only the device |

Each side owns exactly one ring's write side, so there's no lock. What's left
is telling the other side something changed, and that's where the exits come
back.

</Sub>

<Why>Why doesn't the guest kick the device for every packet?</Why>

Because a kick is an exit, and the device may not need one. This is the most
important optimisation in virtio, and it's a few lines long.

If the device is already busy draining the ring, it says so (`NO_NOTIFY`, or an
*event index* further ahead), and the guest skips the kick. Under load a
thousand packets can go out on one exit.

Without vhost, the middle two lanes collapse into one: KVM returns from
`KVM_RUN`, and the eventfd wakes a thread in the VMM process instead, which
does the device work itself.

Firecracker works this way. It registers an ioeventfd and an irqfd per queue
([device_manager/mmio.rs](https://github.com/firecracker-microvm/firecracker/blob/v1.10.0/src/vmm/src/device_manager/mmio.rs#L198))
and does the device work in its own process.

`KVM_RUN` with `exit_reason = KVM_EXIT_MMIO` and lands here, the userspace
mirror of KVM's table:

```rust
        Ok(run) => match run {
            VcpuExit::MmioRead(addr, data) => {
                if let Some(mmio_bus) = &peripherals.mmio_bus {
                    let _metric = METRICS.vcpu.exit_mmio_read_agg.record_latency_metrics();
                    mmio_bus.read(addr, data);
                    METRICS.vcpu.exit_mmio_read.inc();
                }
                Ok(VcpuEmulation::Handled)
            }
            VcpuExit::MmioWrite(addr, data) => {
                if let Some(mmio_bus) = &peripherals.mmio_bus {
                    let _metric = METRICS.vcpu.exit_mmio_write_agg.record_latency_metrics();
                    mmio_bus.write(addr, data);
                    METRICS.vcpu.exit_mmio_write.inc();
                }
                Ok(VcpuEmulation::Handled)
            }
            VcpuExit::Hlt => {
                info!("Received KVM_EXIT_HLT signal");
                Ok(VcpuEmulation::Stopped)
            }
            ...
```
</SourceRead>

Notice the latency metric wrapped around every MMIO exit. Firecracker records
exit timing for every microVM, which is probably the cheapest observability
anyone ever got.

</Sub>

<SectionHeading n="05" id="kvm-api">The KVM API, and an exit you can time</SectionHeading>

<Sub n="5.1" title="Six ioctls">

Under that Rust sit about six ioctls. Josh Triplett's
[Using the KVM API](https://lwn.net/Articles/658511/) (LWN, 2015) builds a
complete VM in one short C file; its guest adds two numbers and writes the
result to a serial port.

Condensed, and quoted from the article (it wasn't run here, since there's no
`/dev/kvm` on the test machine):

```c
kvm    = open("/dev/kvm", O_RDWR | O_CLOEXEC);
ioctl(kvm, KVM_GET_API_VERSION, NULL);             /* must return 12 */
vmfd   = ioctl(kvm, KVM_CREATE_VM, 0);             /* new EPT, no vCPUs yet */

struct kvm_userspace_memory_region region = {
    .slot = 0, .guest_phys_addr = 0x1000,
    .memory_size = 0x1000, .userspace_addr = (uint64_t)mem,
};
ioctl(vmfd, KVM_SET_USER_MEMORY_REGION, &region); /* guest RAM = our mmap */

vcpufd = ioctl(vmfd, KVM_CREATE_VCPU, 0);
run    = mmap(NULL, ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, NULL),
              PROT_READ | PROT_WRITE, MAP_SHARED, vcpufd, 0);
/* ...KVM_SET_SREGS / KVM_SET_REGS: rip = 0x1000, rax = rbx = 2 ... */

while (1) {
    ioctl(vcpufd, KVM_RUN, NULL);                  /* returns on an exit */
    switch (run->exit_reason) {
    case KVM_EXIT_HLT: return 0;
    case KVM_EXIT_IO:                              /* the guest's out to 0x3f8 */
        putchar(*(((char *)run) + run->io.data_offset));
        break;
    }
}
```

| Object | What it really is |
|---|---|
| Guest RAM | Memory the VMM `mmap`ed |
| A vCPU | A file descriptor |
| `KVM_RUN` | A syscall that returns when the guest does something the kernel won't handle alone |

QEMU, Firecracker and crosvm are, at the bottom, this loop.

</Sub>

<Sub n="5.2" title="The same loop on a Mac, and what one exit costs">

Hypervisor.framework has the same shape: `hv_vm_create`, `hv_vm_map`,
`hv_vcpu_create`, then `hv_vcpu_run` in a loop. So it's easy to time.

The guest here is two instructions, an `hvc` or a store to an unmapped
guest-physical address, followed by a branch back. It's a bit of a toy, and
that's the point.

<TryIt what="Time a guest exit round trip with Hypervisor.framework" lang="cpp" toolchain="Apple clang 21 -O2, Apple M4, macOS 26.5.1">

<Why>Why does one exit cost about two syscalls?</Why>

About 670 ns is roughly 2,700 cycles, if the billion-iteration loop from
section 1 really ran one iteration per clock (245 ms implies about 4.1 GHz).
It's almost exactly twice a `write()` syscall on the same Mac
([chapter 07](/topics/07-syscalls-kernel-boundary) measured 348 ns).

That seems about right if you count crossings. As far as I understand it, XNU
on Apple silicon runs at EL2 itself, so an exit is guest to kernel, kernel up
to the VMM process, then both of those again in reverse: two kernel crossings
where a syscall has one.

</Sub>

<SectionHeading n="06" id="failure">Escapes, stolen time, and memory nobody owns</SectionHeading>

<Sub n="6.1" title="VENOM: the floppy drive nobody had">

On 13 May 2015 Jason Geffner at CrowdStrike disclosed
[VENOM, CVE-2015-3456](https://venom.crowdstrike.com/), a buffer overflow in
QEMU's emulated floppy disk controller.

A guest with enough privilege to talk to the FDC's I/O ports could overflow a
buffer in the host's QEMU process and, per
[Red Hat's advisory](https://access.redhat.com/articles/1444903), potentially
run code there. That code had been in QEMU since 2004, and it was reachable on
KVM and Xen setups using QEMU's device model.

<Why>Why was a floppy controller reachable at all?</Why>

Nobody uses a floppy drive. That's the point. It was reachable because it was
*emulated*, and emulation is code that parses attacker-controlled input on
every exit.

Firecracker's paper names the result:

| VMM | Size | Devices |
|---|---|---|
| **QEMU** | Over 1.4 million lines; "can require up to 270 unique syscalls" | A large emulated machine |
| **Firecracker** | About 50,000 lines of Rust; its whole virtio block implementation is "around 1400 lines" | virtio-net, virtio-block, a serial port and a partial i8042 |

Fewer devices is fewer exits is fewer places for the next VENOM.

</Sub>

<Sub n="6.2" title="Steal time, and when %st lies">

When the host runs something else on the physical CPU your vCPU was using,
your guest's clock keeps advancing and its work doesn't.

KVM tells a cooperating guest how long it was descheduled through a shared page
([`MSR_KVM_STEAL_TIME`](https://docs.kernel.org/virt/kvm/x86/msr.html) on
x86, the SMCCC PV-time interface on arm64), and Linux reports it as **steal**:
the `st` column in `top`, the eighth number on the `cpu` line of `/proc/stat`.

A rising `%st` is the one signal inside a guest that says "your neighbour is
busy". Firecracker's rate limiters exist partly for "preventing a small number
of busy MicroVMs on a server from affecting the performance of other
MicroVMs", in the paper's words.

Here's the catch. In Docker Desktop's guest, two days up, steal was zero:

```shell
$ grep '^cpu ' /proc/stat        # 8th number is steal
cpu  36035 0 20977 27010020 998 0 13880 0 0 0
$ dmesg | grep -c arm-pv
0
```

Linux prints `arm-pv: using stolen time PV` at boot
([arch/arm64/kernel/paravirt.c](https://github.com/torvalds/linux/blob/v6.10/arch/arm64/kernel/paravirt.c#L173))
when the hypervisor offers stolen-time accounting. This guest never did.

<Callout label="Common mistake" kind="warn">
Reading `%st = 0` as "no noisy neighbour". Zero can mean nobody's counting.
Before you trust it on a cloud VM, check the interface exists: look for the
`arm-pv` or `kvm-clock` lines in `dmesg`.
</Callout>

</Sub>

<Sub n="6.3" title="Two kernels managing the same memory">

A guest kernel thinks its free memory is free. Meanwhile the host sees a
process with gigabytes of anonymous memory it can reclaim, compress or swap.
Neither can see the other's decisions, and that's where the strangest numbers
in this chapter came from.

In a test timing first-touch faults over 512 MB inside Docker's VM (source in
section 7.2), the results depended on the VM's history:

| VM state | First pass, per 4 KB | Second pass, per 4 KB |
|---|---|---|
| Up two days, Mac tight on memory (`vm_stat`: about 4,000 free 16 KB pages, over a million in the compressor) | **600 to 1,150 ns** | **45 to 100 ns**, over memory the guest had just freed and re-used |
| Freshly restarted Docker Desktop | 44 to 48 ns | 44 to 48 ns |

Ten to twenty times apart on the old VM, and no gap at all on the fresh one.

My guess is host-side reclaim. Maybe the macOS compressor had squeezed pages
the guest considered free, so each "fresh" guest frame cost a host fault and a
decompression.

It isn't proven. Host faults on the VM process moved by roughly the right
amount on some runs and not on others, and a dozen other people's containers
were sharing that VM. Settling it needs one VM with nothing else in it, and
the host's fault count on the VM process sampled before and after each pass.

Free-page reporting in the balloon driver exists to close this gap. This
guest's balloon doesn't negotiate it (bit 5 is clear in
`/sys/bus/virtio/devices/virtio11/features`).

</Sub>

<Sub n="6.4" title="Nested virtualization">

Running a hypervisor inside a VM (CI runners, Kata on a cloud VM) multiplies
every exit. A guest hypervisor's `VMRESUME` is itself a sensitive instruction
that the real hypervisor must emulate, so one nested exit is really several.

| Source | Nested overhead |
|---|---|
| IBM's [Turtles project](https://www.usenix.org/conference/osdi10/turtles-project-design-and-implementation-nested-virtualization) (OSDI 2010) | Nested KVM within 6 to 8% of single-level virtualization for common workloads |
| [Google Cloud's documentation](https://docs.cloud.google.com/compute/docs/instances/nested-virtualization/overview) | Expect "a 10% or greater decrease" for CPU-bound workloads, and possibly more for I/O-bound ones |

</Sub>

<Callout label="The machines" kind="note">

**Guest:** Docker Desktop 28.4's Linux VM on the same Mac, kernel

</Callout>

<Sub n="7.1" title="Things that exit, and things that don't">

<Cost items={[

Look at the register read. It's a plain 16-bit load of `num_queues` from the
virtio RNG's config space (harmless to read), through an `mmap` of
`/sys/bus/pci/devices/0000:00:0e.0/resource0`.

A RAM load in the same loop took 0.3 ns. This one took a microsecond, **about
three thousand times slower**, because each load is a stage-2 fault handled by
Apple's device model in a host process. It's slower than the bare `hvc` too,
which is roughly what you'd expect from a real VMM doing real decoding.

`clock_gettime` is the counterexample. On arm64 the guest reads the virtual
counter `CNTVCT_EL0` directly, with no exit, so it costs the same in a VM as
out of one.

</Sub>

<Sub n="7.2" title="A syscall inside the guest is not a VM exit">

<TryIt what="The same benchmark, native macOS and inside the Linux guest" lang="cpp" toolchain="clang 21 / g++ 13.3, -O2, M4 host and linuxkit 6.10 guest">
```cpp

for (long i = 0; i < 1'000'000; i++) write(fd_devnull, &c, 1);

                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);

for (size_t off = 0; off < len; off += pagesize) p[off] += 1;   // no faults
```

<Output>
| | macOS native | Linux guest (fresh VM) |
| --- | --- | --- |
| `clock_gettime` | 16.7 ns | 14.1 ns |
| `write(/dev/null)` | 351 ns | 108 ns |
| First touch, per 4 KB of memory | ~195 ns (16 KB pages, ~780 ns each) | 45 ns with THP, 375 ns without |

Medians of three runs each. THP-off used `prctl(PR_SET_THP_DISABLE)`.
</Output>

<Why>Is the guest's write() really three times faster than the host's?</Why>

It is, and virtualization has nothing to do with it. A syscall inside a guest
goes from guest EL0 to guest EL1 without the hypervisor knowing, so you're
comparing Linux 6.10's syscall path against XNU's.

Adams and Agesen saw it in 2006: under VT-x, "system calls execute without VMM
intervention".

Fault numbers hide the same trap. With THP on, the guest takes one fault per
2 MB (about 23 µs, spread over 512 small pages), so it looks eight times
cheaper per byte. None of that is about stage-2; the fresh VM's memory was
presumably already backed by the host. Only the old VM's runs in section 6.3
look like stage-2 costs.

<Callout label="Common mistake" kind="warn">
Benchmarking syscalls or page faults in a VM and reading the result as
virtualization overhead. Neither exits. You're measuring the guest kernel
against the host kernel. To measure the hypervisor, time something that
actually exits: a device register, a hypercall, an I/O round trip.
</Callout>

</Sub>

<SectionHeading n="08" id="operating">Counting exits on a real host</SectionHeading>

<Sub n="8.1" title="Where am I, and what can I see">

Inside a guest, find out what you're running on before you trust any number:

```shell
systemd-detect-virt                 # kvm, amazon, microsoft, none...
lscpu | grep -i hypervisor          # x86: "Hypervisor vendor: KVM"
ls -l /dev/kvm                      # can *this* machine run VMs?
grep -E '^cpu ' /proc/stat          # 8th field is steal, in USER_HZ ticks
dmesg | grep -i -E 'arm-pv|kvm-clock|steal'   # is steal even reported?
grep virtio /proc/interrupts        # which CPU takes the device interrupts
```

That last one was a surprise in Docker's VM: all twelve virtio devices use
level-triggered INTx, and every interrupt landed on CPU 0. On a busy network
guest that's a hot CPU you'd want to find early.

On a KVM host, the exit counters are the tool. These weren't run here, since
there's no KVM to point them at:

```shell
perf kvm stat live                  # exits by reason, with time spent in each
perf kvm stat record -p $QEMU_PID   # then: perf kvm stat report
bpftrace -e 'tracepoint:kvm:kvm_exit { @[args->exit_reason] = count(); }'
cat /sys/kernel/debug/kvm/*/exits   # per-VM exit counters (debugfs)
```

</Sub>

<Sub n="8.2" title="Symptom, cause, fix">

When a workload is slower in a VM than on metal, look at exits before you look
at anything else. Count them by reason first.

| Symptom | Likely cause | Fix |
|---|---|---|
| `EPT_MISCONFIG` or `IO_INSTRUCTION` dominates the exit counts | An emulated device is on the hot path; an emulated e1000 or IDE disk exits per register | Move I/O to virtio, which exits per batch, then to vhost, which keeps the exit in the kernel |
| High `PAUSE_INSTRUCTION` counts | A guest spinning on a lock whose holder's vCPU was descheduled, burning its slice; usually overcommitted CPUs | Reduce CPU overcommit |
| Slow random access over large memory | Nested page walks: up to 24 references per TLB miss with 4 KB pages | Huge pages on both sides: 2 MB guest and 1 GB host pages bring it to 11 (section 3.3) |
| I/O still too slow after virtio and vhost | The exit budget is gone | Pass the device through with SR-IOV: the NIC exposes *virtual functions*, the IOMMU maps one into the guest, and the guest driver talks to hardware with no hypervisor on the data path. You lose easy live migration. |
| Latency suggests a noisy neighbour, but `%st` is 0 | The hypervisor doesn't publish steal time | Check `dmesg` for `arm-pv` or `kvm-clock` before trusting `%st` |
| Every virtio interrupt on CPU 0 | Level-triggered INTx, not spread across CPUs | Check `/proc/interrupts` early on busy network guests |

</Sub>

<SectionHeading n="09" id="in-the-wild">Where you meet this in production</SectionHeading>

<Sub n="9.1" title="AWS Lambda and Fargate on Firecracker">

Lambda used to run each customer's functions in containers inside that
customer's own VM. Firecracker replaced that, and per the
[NSDI paper](https://www.usenix.org/conference/nsdi20/presentation/agache) it
"powers millions of workloads and trillions of requests per month".

Its jailer allows the VMM 24 syscalls and 30 ioctls. It's VM isolation at
container density, paid for in I/O throughput.

</Sub>

<Sub n="9.2" title="AWS Nitro">

Starting with C5 in 2017, AWS
[removed Xen's dom0](https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/the-nitro-system-journey.html)
and moved network, EBS and instance storage onto dedicated Nitro cards,
leaving a minimal KVM-based hypervisor.

Brendan Gregg
[measured its overhead](https://www.brendangregg.com/blog/2017-11-29/aws-ec2-virtualization-2017.html)
as "miniscule, often less than 1% (it's hard to measure)".

<Callout label="Design implication">
If exits are the cost, take the I/O off the host CPU entirely. Nitro's answer
to "how do we make device emulation cheap?" was to stop emulating devices in
host software at all.
</Callout>

</Sub>

<Sub n="9.3" title="gVisor and Kata Containers">

Both give a container a boundary that isn't the host kernel, in different ways.

| Project | How it isolates |
|---|---|
| **gVisor** | Its Sentry reimplements Linux syscalls in Go, catching them with seccomp on its default [systrap platform](https://gvisor.dev/docs/architecture_guide/platforms/) |
| **Kata Containers** | Runs each pod in a lightweight VM on one of [five VMMs](https://github.com/kata-containers/kata-containers/blob/main/docs/hypervisors.md) |

</Sub>

<SectionHeading n="10" id="summary">Summary</SectionHeading>

1. **A VM only loses speed when it exits.** A billion-iteration loop took
   246 ms in a guest and 245 ms on the host; one exit round trip took about
   670 ns.
2. **Trap-and-emulate needs every sensitive instruction to be privileged.**
   x86 had seventeen that weren't, which is why VMware translated binaries and
   Xen modified guests.
3. **VT-x adds a second copy of the rings, not a new ring.** The VMCS decides
   what exits, and KVM dispatches each exit through a table indexed by reason.
4. **A VM's attack surface is its list of exits.** VENOM was an emulated
   floppy controller nobody used, reachable because it was emulated.
5. **Nested paging costs up to 24 references per TLB miss.** It's
   (n + 1)(m + 1) − 1; huge pages on both sides bring it to 11.
6. **virtio batches, and suppresses kicks when the device is busy.** Under load
   a thousand packets can go out on one exit.
7. **vhost keeps the exit in the kernel.** An ioeventfd and an irqfd let KVM
   hand the packet to a kernel thread without returning to the VMM.
8. **Syscalls and page faults inside a guest don't exit.** A faster guest
   `write()` is one kernel beating another.
9. **`%st = 0` can mean nobody's counting.** Check that the hypervisor offers
   stolen-time accounting before you trust it.
10. **microVMs trade I/O throughput for density.** Firecracker boots in under
    125 ms with about 3 MB of overhead, and is slower than PCI pass-through.

<SectionHeading n="11" id="build">Build this</SectionHeading>

**Write a VM monitor with one device, and time its exits.**

- On a Linux box with `/dev/kvm` (a bare-metal cloud instance, or a VM with
  nested virtualization enabled), type in the program from LWN's
  [Using the KVM API](https://lwn.net/Articles/658511/). Get it printing `4`.
- Wrap `KVM_RUN` in `clock_gettime` and make the guest loop on `out` to port
  `0x3f8`. That's your exit round-trip cost. Compare it with the ~670 ns on
  Apple silicon from section 5.2.
- Add a fake MMIO device: pick an unmapped guest-physical address, handle
  `KVM_EXIT_MMIO`, return a counter on reads. Now you've written the
  `handle_kvm_exit` from section 4.3.
- Then register that address with `KVM_IOEVENTFD` and see how much faster a
  write gets when it never leaves the kernel.

On a Mac, Hypervisor.framework works too, and the code in section 5.2 is most
of it. Sign it with the entitlement. Without it `hv_vm_create` returns
`0xfae94007` (`HV_DENIED`), and since the code above doesn't check, the
unsigned binary just segfaults.

<SectionHeading n="12" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why does a guest run CPU-bound code at native speed?">
Because nothing in it exits. Arithmetic, branches and loads from mapped memory
run directly on the CPU; the hypervisor only runs when the guest does
something the VMCS or `HCR_EL2` says to trap. A billion-iteration loop took
246 ms in a guest, 245 ms on the host.
</QA>

<QA level="beginner" q="What's the isolation difference between a container and a VM?">
A container shares the host kernel, so its boundary is the whole syscall
interface. A VM has its own kernel, and its boundary is the set of exits plus
the device emulation behind them: much smaller, though VENOM shows it isn't
zero.
</QA>

<QA level="intermediate" q="Why was x86 not virtualizable before VT-x, in Popek and Goldberg's sense?">
Every sensitive instruction must be privileged, so it traps when run
deprivileged. x86 had seventeen that didn't (Robin and Irvine, 2000). In ring 3
`popf` silently ignores changes to the interrupt flag, so a deprivileged guest
kernel's attempt to disable interrupts was invisible. VMware answered with
binary translation, Xen by modifying the guest.
</QA>

<QA level="intermediate" q="Derive the worst-case memory references for a TLB miss with 4-level guest and 4-level EPT tables.">
Each of the four guest entries sits at a guest-physical address needing a
4-reference host walk, plus the entry read: 4 × 5 = 20. The data's final
guest-physical address needs one more host walk: 24. In general
(n+1)(m+1) − 1.
</QA>

<QA level="intermediate" q="Your syscall benchmark is faster inside a VM than on the host. Did virtualization speed it up?">
No. A syscall in a guest goes from guest user mode to guest kernel mode
without any exit, so you're comparing the guest kernel's syscall path with the
host's. On an M4, Linux 6.10 in Docker's VM did `write()` in 108 ns and macOS
did it in 351 ns. That's Linux against XNU, and the VM isn't in the picture.
</QA>

<QA level="deep" q="Walk through what happens when a virtio-net guest transmits a packet on KVM with vhost-net.">
Descriptor into the available ring; check whether the device wants a kick; if
so, a 16-bit MMIO store to the notify register. That exits (`EPT_MISCONFIG`),
KVM matches an ioeventfd and resumes the guest without visiting userspace. A
vhost thread reads the ring, sends to a tap, writes the used ring and raises an
irqfd, which KVM injects as an interrupt.
</QA>

<QA level="deep" q="%st is 0 on your VM but latency suggests a noisy neighbour. How can both be true?">
Steal only exists if the hypervisor publishes it (`MSR_KVM_STEAL_TIME` on x86
KVM, SMCCC PV time on arm64). Without that, the guest reports zero whatever
happens. Docker Desktop's arm64 guest is like this: no `arm-pv` line in dmesg,
steal zero after two days up.
</QA>

<QA level="deep" q="Why did AWS move I/O onto Nitro cards?">
Under Xen, device models ran in dom0 on the same CPUs customers paid for, and
every I/O went through that software. Nitro put network and storage
virtualization on dedicated cards and left a minimal KVM-based hypervisor with
little to do: host CPU freed, dom0's attack surface gone, and overhead Brendan
Gregg measured as often under 1%.
</QA>

<Quiz>
  <Q q="Which of these exit on arm64: clock_gettime, write(), a load from a virtio register?">
    Only the register load, about 1 µs in Docker's VM. The other two never
    leave the guest.
  </Q>
  <Q q="Guest uses 2 MB pages, host uses 4 KB pages, both otherwise 4-level. Worst-case references per TLB miss?">
    (3 + 1)(4 + 1) − 1 = 19.
  </Q>
  <Q q="What stops a virtio guest from exiting once per packet?">
    Notification suppression: a device that's already draining says so, and
    `virtqueue_kick_prepare` returns false.
  </Q>
  <Q q="Why was first-generation VT-x often slower than VMware's binary translation?">
    No hardware MMU help. Shadow paging still trapped guest page table
    writes, now with a costly exit each time.
  </Q>
</Quiz>
