<SectionHeading n="01" cmd="cat CONTRACT.md" id="contract">The contract</SectionHeading>

A syscall is a controlled transfer of execution into code you can't see, running
at a privilege level you don't have. What the kernel promises is that it will
validate every argument, do the thing, and hand control back — or fail with an
error instead of a corrupted system.

Everything expensive about it follows from "controlled". Each crossing must
switch privilege level, swap stacks, validate pointers that user code could have
changed, and eventually undo all of it.

<Callout label="The measurement that reframes this chapter">
On this machine `write()` to `/dev/null` costs **348 ns**. `getpid()` costs
**1.9 ns**. Both look identical in C. The second one isn't a syscall at all —
the value is cached in userspace — and that 180× gap is the difference between
crossing the boundary and only appearing to.
</Callout>

That middle row is the clever one. The kernel maps a small page of code and data
into every process; calling `clock_gettime` jumps into that page, reads a
timestamp the kernel keeps current, and returns without ever trapping. You get
kernel-maintained data at userspace speed.

</Sub>

Argument validation deserves attention. User code may pass any pointer, and may
change it concurrently from another thread, so the kernel copies data across the
boundary instead of trusting addresses. That copy is a real cost and it's why
large transfers behave differently from small ones.

</Sub>

<SectionHeading n="03" cmd="perf record ./hot-path" id="hot-path">The hot path</SectionHeading>

<Sub n="3.1" title="Interrupts, and why your syscall is not the only thing happening">

Devices interrupt asynchronously. A network packet arrives, the NIC raises an
interrupt, the CPU stops what it's doing and runs a handler.

Handlers must be short, because interrupts are disabled or restricted while one
runs. Linux splits the work: the **top half** acknowledges the device and
queues, while the **bottom half** — softirqs, tasklets, threaded handlers —
does real processing later with interrupts enabled.

Under heavy load this can starve userspace entirely. NAPI exists for exactly
that: past a packet rate threshold the driver stops taking interrupts and
switches to polling, trading latency for the ability to make progress at all.

</Sub>

<Sub n="3.2" title="Batching, and why io_uring exists">

If each crossing costs ~350 ns, a million small operations spend 350 ms just
crossing. Every serious optimisation here is some form of doing more per
crossing:

- **Buffered I/O.** stdio accumulates writes and flushes in blocks. That's why
  `printf` in a loop isn't a syscall per call.
- **Vectored I/O.** `writev` and `readv` take an array of buffers, one crossing.
- **`sendfile` and `splice`.** Move bytes between descriptors without copying
  through userspace at all.
- **io_uring.** Two shared ring buffers, submission and completion, mapped into
  the process. You write entries and the kernel consumes them — potentially with
  **zero** syscalls per operation in polled mode.

io_uring is the endpoint of that progression: the boundary stops being crossed
per operation and becomes a queue both sides can see.

</Sub>

<SectionHeading n="04" cmd="dmesg | grep -i fail" id="failure">When it fails</SectionHeading>

<Sub n="4.1" title="A syscall in the inner loop">

The classic: logging with an unbuffered `write` per line, reading a file a byte
at a time, calling `gettimeofday` on every iteration to measure something.

At 350 ns each, a syscall per item caps you around three million operations per
second (and that's before any of your own work). Buffering to 4 KB blocks turns
roughly forty log lines into one crossing.

</Sub>

<Sub n="4.2" title="Spectre mitigations, and benchmarks that no longer reproduce">

Speculative execution vulnerabilities forced the kernel to stop sharing
prediction state and, with page table isolation, most of its address space
across the boundary. Every crossing got more expensive from 2018 onward.

If you find a syscall benchmark from before then and can't reproduce its
numbers, that's usually the reason and not anything you did wrong.

</Sub>

<Sub n="4.3" title="Signals, and what you may do inside one">

A signal handler runs on a borrowed stack, at an arbitrary instruction, possibly
while the interrupted code holds a lock. So the handler may only call
**async-signal-safe** functions — a short POSIX list that excludes `malloc`,
`printf` and almost everything else.

Take a mutex in a handler that interrupted the same thread already holding it
and you deadlock immediately. Standard safe pattern: set a
`volatile sig_atomic_t` flag, or write one byte to a self-pipe, then do the real
work back in the main loop.

</Sub>

**Only one row in that table crosses the boundary.** `getpid` is 183× cheaper
than `write` because libc remembers the answer from process start. `sbrk(0)`
just reads a variable. `clock_gettime` reads a shared page.

Which means a microbenchmark "measuring syscall overhead" with `getpid` — a
common choice, because it's the simplest syscall — measures nothing at all on
these platforms.

</Sub>

<SectionHeading n="06" cmd="watch -n1 ./status" id="operating">Operating it</SectionHeading>

<Sub n="6.1" title="Finding the crossings">

```shell
# Count syscalls by type. Start here — it is usually immediately obvious.
strace -c -f ./app              # Linux
dtruss -c ./app                 # macOS (needs SIP considerations)

# Which call site?
perf trace ./app
perf record -e raw_syscalls:sys_enter -g ./app

# Time in kernel versus user
/usr/bin/time -v ./app | grep -E 'System time|User time'

# Is the interrupt load the problem?
cat /proc/interrupts
mpstat -P ALL 1                 # %irq and %soft columns
```

`strace -c` is the first command to run and it answers the question most of the
time. A count of 4 million `write` calls where you expected a few thousand is
the entire diagnosis.

</Sub>

<Sub n="6.2" title="Reducing crossings, in order">

1. **Buffer.** Biggest win, least effort, no new API.
2. **Batch.** `writev`, `readv`, `sendmmsg`, `recvmmsg` — one crossing, many
   items.
3. **Avoid the copy.** `sendfile`, `splice`, or `mmap` for large file reads.
4. **io_uring**, on Linux 5.10 or newer, when you genuinely need hundreds of
   thousands of operations per second. It's a real API-shape change, so it
   belongs last.

</Sub>

<SectionHeading n="07" cmd="git init ./weekend-project" id="build">Build this</SectionHeading>

**Measure your own boundary, and find a call that isn't crossing it.**

- Time `getpid`, `clock_gettime`, `write` to `/dev/null`, and an empty loop.
- Confirm with `strace -c` which ones actually produce a syscall. At least one
  will surprise you.
- Then write one megabyte to a file, one byte at a time, and again in 4 KB
  blocks. Compare wall time and `strace -c` counts.

Your 4 KB version should be roughly a thousand times fewer crossings and dramatically
faster. Having produced that ratio yourself makes buffering an instinct instead
of advice.

<SectionHeading n="10" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Roughly what does a syscall cost, and why isn't it free?">
A few hundred nanoseconds — I measured 348 ns for `write` to `/dev/null` on an
M4. Cost comes from the controlled crossing: switch privilege level, swap stacks,
dispatch through a table, validate every pointer the caller passed, do the work,
then restore everything. Validation matters because user code could change a
pointer concurrently, so the kernel copies instead of trusting addresses.
</QA>

<QA level="intermediate" q="Why is calling clock_gettime so much cheaper than calling write?">
It usually isn't a syscall. Linux and macOS both map a small read-only page — the vDSO on
Linux, the commpage on macOS — containing code and a timestamp it keeps current.
Calling `clock_gettime` jumps into that page and reads the value without ever
trapping.

I measured 13.4 ns for it against 348 ns for `write`. Same-looking C, one
crossing the boundary and one not.
</QA>

<QA level="intermediate" q="Your service spends 20% of CPU in the kernel and you expected almost none. First step?">
`strace -c -f`. It gives you syscall counts and time by type in one command, and
the answer is usually obvious — a few million `write` calls from unbuffered
logging, or a `gettimeofday` per loop iteration.

At roughly 350 ns each, half a million log lines a second is about 17% of a core
spent purely crossing. Buffering to 4 KB blocks cuts that by a factor of forty.
</QA>

<QA level="deep" q="What may you safely call inside a signal handler, and why is the list so short?">
Only async-signal-safe functions — a short POSIX list. A handler runs at an
arbitrary instruction on a borrowed stack, possibly while the interrupted code
holds a lock or is midway through updating allocator state.

Call `malloc` from a handler that interrupted `malloc` and you corrupt the heap
or deadlock. Safe pattern: set a `volatile sig_atomic_t` flag or write
one byte to a self-pipe, then do real work from the main loop.
</QA>

<QA level="deep" q="How does io_uring reduce syscall cost to nearly zero?">
By replacing per-operation crossings with shared memory. Two ring buffers —
submission and completion — are mapped into both the process and the kernel. The
application writes submission entries directly into memory the kernel can
already see and advances a tail pointer.

With `IORING_SETUP_SQPOLL` a kernel thread polls that ring, so the data path can
run with no syscalls at all. You trade a much harder API and a dedicated polling
thread for removing the boundary from the hot path entirely.
</QA>

<Quiz>
  <Q q="You benchmark syscall overhead with getpid and measure 2 ns. What went wrong?">
    getpid isn't a syscall on most libcs — the value is cached at process start.
    Use something that must reach the kernel, like write to /dev/null.
  </Q>
  <Q q="Why can't you call printf in a signal handler?">
    It isn't async-signal-safe. The handler may have interrupted stdio or the
    allocator mid-update, so calling back in can deadlock or corrupt state.
  </Q>
  <Q q="Unbuffered logging at 500k lines/sec. Roughly what does it cost?">
    About 17% of a core in crossings alone, at ~350 ns each. Buffering to 4 KB
    cuts it to under half a percent.
  </Q>
  <Q q="Why did syscalls get slower in 2018?">
    Spectre and Meltdown mitigations — page table isolation and predictor
    flushing across the boundary. Old benchmarks stopped reproducing.
  </Q>
</Quiz>
