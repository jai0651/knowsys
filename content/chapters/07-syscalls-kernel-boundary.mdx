Every read, every write, every new connection and every sleep your program does
goes through the kernel. Your code can't touch the disk or the network card
itself. It has to ask, and asking has a price.

That price is small enough to ignore once and large enough to matter a million
times a second. It's the reason stdio buffers `printf`, the reason `epoll`
exists, and the reason io_uring was built.

This chapter starts with why the boundary exists, walks through one syscall
step by step, then covers the calls that skip it, interrupts coming the other
way, batching, where the boundary hurts, and how to count crossings on a live
system.

<SectionHeading n="01" id="boundary">Why there's a boundary at all</SectionHeading>

<Sub n="1.1" title="Two privilege modes">

<Why>Why can't your program just talk to the disk itself?</Why>

Because then every program could. A bug in your text editor could overwrite the
filesystem, and any process could read another's memory or reprogram the
network card.

So processors have (at least) two modes. In **user mode**, where your code runs,
the instructions that touch hardware or change the memory mapping simply fault.
In **kernel mode** they work, and only the kernel ever runs there.

</Sub>

<Sub n="1.2" title="The one door in">

That raises the obvious problem. If your program can't touch the disk, how does
it ever read a file?

<Why>Why not call the kernel like a library function?</Why>

Because if your program could jump anywhere in the kernel, it could jump past
the line that checks permissions.

So there's exactly one way in: a special instruction (`syscall` on x86-64, `svc`
on ARM) that switches to kernel mode and jumps to a single entry point the
kernel chose at boot. Your program puts a number in a register to say which
service it wants, `read` or `write` or `openat`, and the kernel takes it from
there. That door is a **syscall**.

A syscall is a controlled transfer of execution into code you can't see,
running at a privilege level you don't have. The kernel promises to validate
every argument, do the thing, and hand control back, or fail with an error
instead of a corrupted system.

</Sub>

<Sub n="1.3" title="Why the kernel copies your arguments">

The kernel can't trust anything you pass through the door.

<Why>Why not just use the pointer you gave it?</Why>

A pointer you hand over might point into kernel memory. And another of your
threads might change the buffer while the kernel is reading it.

So the kernel validates every argument and copies data across instead of using
yours in place. That copy is a real cost, and it's why large transfers behave
differently from small ones.

<Callout label="Design implication">
Everything expensive about a syscall follows from "controlled". Each crossing
must switch privilege level, swap stacks, validate pointers that user code could
have changed, and eventually undo all of it. You can't make one crossing much
cheaper, so fast code makes fewer of them.
</Callout>

</Sub>

    [3, "The kernel's single entry point looks the number up in its **syscall table** and jumps to the handler for `write`."],
    [4, "The handler **validates every pointer and length**, then copies your bytes across rather than trusting the address. Only now does the part you wanted happen."],

  ]}
/>

Four of those six steps are overhead. Only the handler's work is the part you
asked for, and on `/dev/null` there's almost none of it.

</Sub>

<Sub n="2.2" title="What 348 nanoseconds adds up to">

On this M4, `write()` to `/dev/null`, which does no real work at all, takes
**348 ns**.

<Why>Is that a lot?</Why>

Try it on a real case. A service that writes each log line with its own
`write()` and logs four million lines a minute spends about 1.4 seconds of every
minute just crossing, before any bytes go anywhere.

Buffer a hundred lines per call and that falls to 14 ms. Every logging library
and stdio's `printf` buffer for this reason, and `epoll` exists so that nginx
and Redis can ask about thousands of connections in one crossing, not one each.

</Sub>

<SectionHeading n="03" id="not-crossing">Calls that don't cross</SectionHeading>

Some things don't need the kernel's authority at all, only its data. And some
calls that look like syscalls aren't.

<Sub n="3.2" title="The vDSO and the commpage">

<Why>Why is clock_gettime so cheap?</Why>

The current time is the best example of data without authority. So the kernel
maps a small page of its own code and data into every process, called the
**vDSO** on Linux. macOS's commpage plays the same role.

Calling `clock_gettime` jumps into that page, reads a timestamp the kernel keeps
current, and returns without ever switching modes. You get kernel-maintained
data at userspace speed: about 13 ns.

    [2, "That code reads the timestamp the kernel keeps current in a **read-only shared page**, and returns it. About 13 ns."],
    [3, "The kernel was never entered: **no trap, no dispatch, no validation**. It only did the work of keeping the page up to date."],

</Sub>

<Callout label="Common mistake" kind="warn">
Benchmarking "syscall overhead" with `getpid`. It's a common choice, because it's
the simplest syscall, and on these platforms it measures nothing at all. Use a
call that must reach the kernel, like `write` to `/dev/null`, and confirm with
`strace -c` that it did.
</Callout>

</Sub>

<SectionHeading n="04" id="interrupts">Interrupts: the door from the other side</SectionHeading>

The same door is used from the other side. When a network card has a packet or
a timer fires, the hardware forces the core into the kernel exactly as a syscall
would, without your code asking. That's an **interrupt**.

<Sub n="4.1" title="Top halves and bottom halves">

Devices interrupt asynchronously. A packet arrives, the NIC raises an interrupt,
and the CPU stops what it's doing and runs a handler.

<Why>Why split an interrupt handler in two?</Why>

Because interrupts are disabled or restricted while a handler runs, so it has to
be short. Linux splits the work: the **top half** acknowledges the device and
queues, while the **bottom half** (softirqs, tasklets, threaded handlers) does
the real processing later with interrupts enabled.

    { from: 1, to: 2, label: "enter kernel", note: "The core switches to kernel mode exactly as a syscall would, and runs the **top half** with interrupts restricted." },
    { from: 2, to: 0, label: "ack", note: "The top half acknowledges the device so it can interrupt again. It does as little as possible." },
    { from: 2, to: 3, label: "queue work", note: "It queues the real processing for the **bottom half**: a softirq, tasklet or threaded handler." },
    { from: 3, to: 3, label: "process", note: "The bottom half runs **with interrupts enabled** and does the expensive part, like pushing the packet up the network stack." },
    { from: 3, to: 1, label: "resume", note: "Your thread resumes where it stopped. It never saw the interrupt, only lost the time." },
  ]}
/>

</Sub>

<Sub n="4.2" title="NAPI: when interrupts are the problem">

Under heavy load, interrupt work can starve userspace entirely.

NAPI exists for exactly that. Past a packet-rate threshold the driver stops
taking interrupts and switches to polling, trading latency for the ability to
make progress at all. [Chapter 10](/topics/10-linux-networking) follows that
poll loop through the network stack.

</Sub>

<SectionHeading n="05" id="batching">Doing more per crossing</SectionHeading>

If each crossing costs ~350 ns, a million small operations spend 350 ms just
crossing. Every serious optimisation here is some form of doing more per
crossing.

<Sub n="5.1" title="From buffering to io_uring">

| Technique | What it does | Crossings |
|---|---|---|
| **Buffered I/O** | stdio accumulates writes and flushes in blocks, so `printf` in a loop isn't a syscall per call | One per block |
| **Vectored I/O** | `writev` and `readv` take an array of buffers | One per array |
| **`sendfile` and `splice`** | Move bytes between descriptors without copying through userspace | One per transfer, no user copy |
| **io_uring** | Two shared ring buffers, submission and completion, mapped into the process | Potentially **zero** per operation in polled mode |

io_uring is the endpoint of that progression: the boundary stops being crossed
per operation and becomes a queue both sides can see.

</Sub>

<Sub n="5.2" title="io_uring's two rings">

Jens Axboe's design replaces per-operation crossings with shared memory. Both
the process and the kernel can see the two rings.

<StepSequence
  title="An operation through io_uring with SQPOLL"
  actors={["Your app", "Submission ring", "Kernel poll thread", "Completion ring"]}
  messages={[
    { from: 0, to: 1, label: "write SQE", note: "The app writes a submission entry **directly into memory the kernel can already see**. No syscall." },
    { from: 0, to: 1, label: "advance tail", note: "It advances the ring's tail pointer to publish the entry. Still no syscall." },
    { from: 2, to: 1, label: "poll", note: "With `IORING_SETUP_SQPOLL`, a **kernel thread polls the ring** and picks the entry up on its own." },
    { from: 2, to: 3, label: "post CQE", note: "When the I/O finishes, the kernel writes a completion entry into the completion ring." },
    { from: 0, to: 3, label: "read CQE", note: "The app reads the result from shared memory. **The data path crossed the boundary zero times.**" },
  ]}
/>

<Why>So why isn't everything built on io_uring?</Why>

Because you pay for it elsewhere: a much harder API, a newer kernel, and a
dedicated polling thread burning a core. It's a real change to the shape of
your code, so it belongs last in the list of fixes (section 7.2).

</Sub>

<Sub n="5.3" title="What batching is worth">

<Estimate

/>

<Callout label="Design implication">
Seventeen percent of a core, for a change that's one line of configuration in
most logging libraries. Buffering is the single highest-leverage fix in this
chapter and it needs no new API. The cost is that buffered data sits in
userspace until it's flushed, so a crash loses the last few lines.
</Callout>

</Sub>

<SectionHeading n="06" id="failure">Where the boundary hurts</SectionHeading>

<Sub n="6.1" title="A syscall in the inner loop">

The classic cases: logging with an unbuffered `write` per line, reading a file a
byte at a time, calling `gettimeofday` on every iteration to measure something.

At 350 ns each, a syscall per item caps you around three million operations per
second, before any of your own work. Buffering to 4 KB blocks turns roughly
forty log lines into one crossing.

</Sub>

<Sub n="6.2" title="Spectre, KPTI and benchmarks that don't reproduce">

Speculative execution vulnerabilities forced the kernel to stop sharing
prediction state across the boundary, and with page table isolation, most of
its address space too. Every crossing got more expensive from 2018 onward.

<Why>Why can't you reproduce a pre-2018 syscall benchmark?</Why>

Kernel page table isolation (KPTI) unmapped most kernel memory from the user
page table to block Meltdown. Every syscall now changes page tables, and syscall
cost roughly doubled on some workloads overnight.

If an old benchmark's numbers look impossibly good, that's usually the reason,
not anything you did wrong. [Chapter 44](/topics/44-speculative-execution)
covers the mitigations themselves.

</Sub>

<Sub n="6.3" title="Signals, and what you may do inside one">

A signal handler runs on a borrowed stack, at an arbitrary instruction, possibly
while the interrupted code holds a lock. So it may only call
**async-signal-safe** functions: a short POSIX list that excludes `malloc`,
`printf` and almost everything else.

<Why>Why is the safe list so short?</Why>

Because the handler may have interrupted the very function it wants to call,
midway through updating its state. Step through the deadlock:

  title="A signal handler that calls malloc"
  actors={["Main code", "Allocator lock", "Kernel", "Signal handler"]}
  messages={[
    { from: 0, to: 1, label: "lock", note: "Your main code calls `malloc`, which takes the allocator's lock and starts updating its free lists." },
    { from: 2, to: 0, label: "signal", note: "A signal arrives. The kernel interrupts the thread **at whatever instruction it was on**, lock still held." },
    { from: 2, to: 3, label: "run handler", note: "The thread now runs your handler, on a borrowed stack. The interrupted `malloc` is frozen halfway through." },
    { from: 3, to: 1, label: "lock?", note: "The handler calls `malloc` (or `printf`, which may allocate). It tries to take the **same lock**." },
    { from: 1, to: 3, label: "wait forever", note: "The lock's owner is this same thread, which can't continue until the handler returns. **Deadlock**, or a corrupted heap if there's no lock." },
  ]}
/>

<Callout label="Common mistake" kind="warn">
Logging from a signal handler. The safe pattern is to set a
`volatile sig_atomic_t` flag, or write one byte to a self-pipe, then do the real
work back in the main loop.
</Callout>

</Sub>

<SectionHeading n="07" id="operating">Counting your crossings</SectionHeading>

<Sub n="7.1" title="Finding the crossings">

```shell
# Count syscalls by type. Start here: it is usually immediately obvious.
strace -c -f ./app              # Linux
dtruss -c ./app                 # macOS (needs SIP considerations)

# Which call site?
perf trace ./app
perf record -e raw_syscalls:sys_enter -g ./app

# Time in kernel versus user
/usr/bin/time -v ./app | grep -E 'System time|User time'

# Is the interrupt load the problem?
cat /proc/interrupts
mpstat -P ALL 1                 # %irq and %soft columns
```

`strace -c` is the first command to run and it answers the question most of the
time. A count of 4 million `write` calls where you expected a few thousand is
the entire diagnosis.

</Sub>

<Sub n="7.2" title="Reducing crossings, in order">

1. **Buffer.** Biggest win, least effort, no new API.
2. **Batch.** `writev`, `readv`, `sendmmsg`, `recvmmsg`: one crossing, many
   items.
3. **Avoid the copy.** `sendfile`, `splice`, or `mmap` for large file reads.
4. **io_uring**, on Linux 5.10 or newer, when you really need hundreds of
   thousands of operations per second. It's a real API-shape change, so it
   belongs last.

</Sub>

<Sub n="7.3" title="What each choice costs">

| You get | You pay | When the bill arrives |
|---|---|---|
| A protected kernel that validates everything | ~350 ns per crossing | In any loop that calls per item |
| vDSO and cached values for cheap calls | You can't tell which is which by reading C | When you benchmark `getpid` and measure nothing |
| Buffered I/O, far fewer crossings | Data sits in userspace until flushed | On crash, as lost log lines |
| io_uring, potentially zero syscalls | A harder API and a newer kernel | As complexity, up front |
| Spectre mitigations keeping you safe | Every crossing got more expensive in 2018 | As old benchmarks that won't reproduce |

</Sub>

<Sub n="7.4" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| High system time you didn't expect | A syscall per item: unbuffered logging, byte-at-a-time reads | `strace -c -f` to find it, then buffer |
| A syscall benchmark reads ~2 ns | The call is cached in libc and never crosses | Benchmark `write` to `/dev/null` instead |
| An old benchmark won't reproduce | KPTI and Spectre mitigations since 2018 | Compare against a post-2018 baseline |
| High `%irq` or `%soft` in `mpstat` | Interrupt load starving user threads | Check `/proc/interrupts`; see NAPI and chapter 10 |
| Process hangs inside a signal handler | A non-async-signal-safe call, like `malloc` or `printf` | Set a flag or write to a self-pipe |

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **User code can't touch hardware.** Those instructions fault in user mode, so
   every I/O goes through the kernel.
2. **There's one door in.** A trap instruction jumps to a single entry point,
   and a number in a register picks the service.
3. **The kernel trusts nothing you pass.** It validates every pointer and copies
   data across, which is where much of the cost comes from.
4. **A real crossing costs about 350 ns.** `write` to `/dev/null` took 348 ns on
   an M4.
5. **Some calls don't cross.** `clock_gettime` reads the vDSO or commpage in
   13 ns, and `getpid` returns a cached value in 1.9 ns.
6. **You can't tell which is which from the C.** Check with `strace -c`.
7. **Interrupts use the same door from the other side.** A short top half acks
   the device; the bottom half does the work with interrupts enabled.
8. **Fast code crosses less.** Buffer, then batch, then avoid the copy, then
   io_uring, in that order.
9. **Mitigations made every crossing dearer in 2018.** KPTI roughly doubled
   syscall cost on some workloads.
10. **Signal handlers may call almost nothing.** Set a flag and do the work in
    the main loop.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Measure your own boundary, and find a call that isn't crossing it.**

- Time `getpid`, `clock_gettime`, `write` to `/dev/null`, and an empty loop.
- Confirm with `strace -c` which ones actually produce a syscall. At least one
  will surprise you.
- Then write one megabyte to a file, one byte at a time, and again in 4 KB
  blocks. Compare wall time and `strace -c` counts.

Your 4 KB version should make roughly a thousand times fewer crossings and run
much faster. Having produced that ratio yourself makes buffering an instinct
instead of advice.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Roughly what does a syscall cost, and why isn't it free?">
A few hundred nanoseconds: I measured 348 ns for `write` to `/dev/null` on an
M4. Cost comes from the controlled crossing: switch privilege level, swap stacks,
dispatch through a table, validate every pointer the caller passed, do the work,
then restore everything. Validation matters because user code could change a
pointer concurrently, so the kernel copies instead of trusting addresses.
</QA>

<QA level="intermediate" q="Why is calling clock_gettime so much cheaper than calling write?">
It usually isn't a syscall. Linux and macOS both map a small read-only page (the
vDSO on Linux, the commpage on macOS) containing code and a timestamp the kernel
keeps current. Calling `clock_gettime` jumps into that page and reads the value
without ever trapping.

I measured 13.4 ns for it against 348 ns for `write`. Same-looking C, one
crossing the boundary and one not.
</QA>

<QA level="intermediate" q="Your service spends 20% of CPU in the kernel and you expected almost none. First step?">
`strace -c -f`. It gives you syscall counts and time by type in one command, and
the answer is usually obvious: a few million `write` calls from unbuffered
logging, or a `gettimeofday` per loop iteration.

At roughly 350 ns each, half a million log lines a second is about 17% of a core
spent purely crossing. Buffering to 4 KB blocks cuts that by a factor of forty.
</QA>

<QA level="deep" q="What may you safely call inside a signal handler, and why is the list so short?">
Only async-signal-safe functions, a short POSIX list. A handler runs at an
arbitrary instruction on a borrowed stack, possibly while the interrupted code
holds a lock or is midway through updating allocator state.

Call `malloc` from a handler that interrupted `malloc` and you corrupt the heap
or deadlock. Safe pattern: set a `volatile sig_atomic_t` flag or write
one byte to a self-pipe, then do real work from the main loop.
</QA>

<QA level="deep" q="How does io_uring reduce syscall cost to nearly zero?">
By replacing per-operation crossings with shared memory. Two ring buffers,
submission and completion, are mapped into both the process and the kernel. The
application writes submission entries directly into memory the kernel can
already see and advances a tail pointer.

With `IORING_SETUP_SQPOLL` a kernel thread polls that ring, so the data path can
run with no syscalls at all. You trade a much harder API and a dedicated polling
thread for removing the boundary from the hot path entirely.
</QA>
