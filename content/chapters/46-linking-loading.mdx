My first timing said the statically linked hello world was *slower* than the
dynamic one. 320 µs against 186 µs at the minimum, over 2,000 runs. A static
binary skips the dynamic loader entirely, so that's backwards, and I spent a
while convinced I'd mislabelled the files.

I hadn't. Both binaries sat on a bind mount from the Mac host, so every page the
kernel faulted in for the 640 KB static file came over the VM's file-sharing
layer. My dynamic one is 70 KB, and the libc it pulls in lives on the
container's own disk, already in page cache. Copy both into `/tmp` and the
order flips: **103 µs static, 132 µs dynamic** at p10.

So the loader's cost is real, roughly 30 µs for hello, and it's also easy to
mismeasure by a factor of three. This chapter follows `./hello` from `execve` to
`main` and shows where the time goes. One question about lazy binding, in section
5, I still can't fully close.

<SectionHeading n="01" cmd="man 8 ld.so" id="contract">What you're promised at main</SectionHeading>

When control reaches `main`, the kernel and `ld.so` between them have promised
you a few things:

- **Every undefined symbol will resolve.** Either it's already bound, or it'll be
  bound on first call. If some symbol can't be found at all, the process dies
  before `main`, not halfway through a request.
- **Constructors have run**, libraries' before yours, dependencies before
  their dependents.
- **The stack holds `argc`, `argv`, `envp` and the auxiliary vector**, the
  kernel's note to userspace about what it just did.
- **With full RELRO, the tables of resolved addresses are read-only.**

What it won't promise is a longer list, and probably more interesting. It won't
promise *which* definition of `malloc` you get: the first object in search
order that exports the name wins, and `LD_PRELOAD` puts itself first. It won't
promise that the glibc on the machine is the one you built against. And it
promises nothing about how long any of this takes.

<Callout label="The name you call isn't bound to the code you wrote">
In a normal ELF shared library, a call from `f1` to `f2` inside the *same*
library still goes through a table lookup, because some other object might
define `f2` first and the rules say it wins. That's **symbol interposition**. It
costs a relocation per call target at startup, and it's why `-fvisibility=hidden`
cut startup by 700 µs in section 5.
</Callout>

<Sub n="2.1" title="The header, and the 64 bytes the kernel reads first">

Every ELF file opens with a fixed 64-byte header (on 64-bit targets). Linux
checks the magic, the type and the machine, then uses two offsets to find
everything else.

Those numbers are from my `hello`, built with plain `gcc -O2` on Ubuntu 24.04.
Its `Type` is `DYN`, not `EXEC`. A default Ubuntu build is a position-independent
executable. Linux treats that almost exactly like a shared library.

</Sub>

<Sub n="2.2" title="Program headers are for loading, section headers are for tools">

An ELF file describes itself twice. **Program headers** (segments) say what
to map and with which permissions. **Section headers** say what the bytes mean:
`.text`, `.dynsym`, `.rela.plt`. Kernel and `ld.so` only need segments. The
linker, `objdump` and `gdb` use sections.

```text
$ readelf -lW hello          # trimmed
  Type           Offset   VirtAddr           FileSiz  MemSiz   Flg Align
  PHDR           0x000040 0x0000000000000040 0x0001f8 0x0001f8 R   0x8
  INTERP         0x000238 0x0000000000000238 0x00001b 0x00001b R   0x1
      [Requesting program interpreter: /lib/ld-linux-aarch64.so.1]
  LOAD           0x000000 0x0000000000000000 0x0008b4 0x0008b4 R E 0x10000
  LOAD           0x00fd90 0x000000000001fd90 0x000280 0x000288 RW  0x10000
  DYNAMIC        0x00fda0 0x000000000001fda0 0x0001f0 0x0001f0 RW  0x8
  GNU_STACK      0x000000 0x0000000000000000 0x000000 0x000000 RW  0x10
  GNU_RELRO      0x00fd90 0x000000000001fd90 0x000270 0x000270 R   0x1
```

Two `LOAD` segments, one executable, one writable, and never a segment
that's both. `INTERP` names the program that'll actually run first.
`GNU_RELRO` marks the part of the writable segment that goes read-only once
relocation is done.

That `0x10000` alignment is why this file is 70 KB for 2 KB of code. The
aarch64 toolchain aligns segments to 64 KB so the same binary works on kernels
with 4 KB, 16 KB or 64 KB pages, and the file is padded to match.

</Sub>

<Sub n="2.3" title=".dynamic, relocations, and the GOT">

`PT_DYNAMIC` points at `.dynamic`, an array of tag/value pairs that is the
loader's table of contents. My hello has 27 entries. Those that matter:

- `NEEDED libc.so.6`: the dependency list, by soname.
- `SYMTAB`, `STRTAB`, `GNU_HASH`: the dynamic symbol table, its strings, and
  the hash table for looking names up.
- `RELA` and `JMPREL`: two relocation tables, `.rela.dyn` for data and
  `.rela.plt` for function calls.
- `PLTGOT`: the address of the **GOT**, the Global Offset Table.
- `FLAGS BIND_NOW` and `FLAGS_1 NOW PIE`. Hold that thought.

A relocation is an instruction to the loader: *at this offset, write the
address of that symbol, plus this addend.* `readelf -r` on a lazily linked
build of the same hello:

```text
Relocation section '.rela.dyn' at offset 0x480 contains 8 entries:
    Offset             Type               Symbol's Name + Addend
000000000001fdc8  R_AARCH64_RELATIVE                        790
000000000001ffc8  R_AARCH64_GLOB_DAT     __cxa_finalize@GLIBC_2.17 + 0
...
Relocation section '.rela.plt' at offset 0x540 contains 5 entries:
0000000000020000  R_AARCH64_JUMP_SLOT    __libc_start_main@GLIBC_2.34 + 0
0000000000020020  R_AARCH64_JUMP_SLOT    puts@GLIBC_2.17 + 0
```

Three kinds, three costs. `RELATIVE` needs no lookup at all: add the load base
and store. `GLOB_DAT` and `JUMP_SLOT` need a symbol lookup: a hash, a
walk over every loaded object, and a string compare. The `JUMP_SLOT`s are the
ones that can be deferred.

</Sub>

<Sub n="2.4" title="GNU hash: a Bloom filter in front of every lookup">

A symbol lookup asks each loaded object in turn, "do you define `puts`?" Most
say no. `DT_GNU_HASH` makes "no" cheap with a Bloom filter checked before any
bucket is touched. Here's the lookup in glibc 2.39:

<SourceRead
  file="elf/dl-lookup.c"
  repo="bminor/glibc"
  tag="glibc-2.39"
  href="https://github.com/bminor/glibc/blob/glibc-2.39/elf/dl-lookup.c#L408-L440"
>
```c
const ElfW(Addr) *bitmask = map->l_gnu_bitmask;
if (__glibc_likely (bitmask != NULL))
  {
    ElfW(Addr) bitmask_word
      = bitmask[(new_hash / __ELF_NATIVE_CLASS)
                & map->l_gnu_bitmask_idxbits];

    unsigned int hashbit1 = new_hash & (__ELF_NATIVE_CLASS - 1);
    unsigned int hashbit2 = ((new_hash >> map->l_gnu_shift)
                             & (__ELF_NATIVE_CLASS - 1));
    /* Two bits must both be set, or this object can't define the name. */
    if (__glibc_unlikely ((bitmask_word >> hashbit1)
                          & (bitmask_word >> hashbit2) & 1))
      {
        Elf32_Word bucket = map->l_gnu_buckets[new_hash % map->l_nbuckets];
        if (bucket != 0)
          {
            const Elf32_Word *hasharr = &map->l_gnu_chain_zero[bucket];
            do
              /* Compare 31 bits of hash before any strcmp. */
              if (((*hasharr ^ new_hash) >> 1) == 0)
                { /* ... check_match(): the actual string compare ... */ }
            while ((*hasharr++ & 1u) == 0);   /* low bit ends the chain */
          }
      }
```
</SourceRead>

Note the `__glibc_unlikely` on the Bloom test. glibc's authors expect most
objects to answer "no", and they're right: a lookup for `puts` from hello
checks the executable first, then libc. In a C++ program with a dozen
libraries, I'd guess most of those probes end at one 64-bit load and two shifts. Why
bother with a filter for hello's two objects? You wouldn't; it pays off at forty.

</Sub>

So there are two entry points. The CPU starts in `ld.so`, and your program's own
entry goes on the stack as `AT_ENTRY` for `ld.so` to jump to later.
`create_elf_tables` writes that auxiliary vector, and glibc will print it for you:

```text
$ LD_SHOW_AUXV=1 ./hello        # trimmed

AT_HWCAP:             efb3ffff            # CPU features, for IFUNC resolvers
```

`ld.so` doesn't have to parse your ELF file again. Linux already did, and
this is it handing over its notes.

</Sub>

A few things surprised me a bit. Nobody opens `hello` or `ld.so`, because the kernel
mapped both already. Next, the loader checks `/etc/ld.so.preload` before anything
else, a system-wide `LD_PRELOAD` that persists across reboots (it's also a

`PROT_NONE` first, then maps the segments into it with `MAP_FIXED`, so nothing
else can land in the gap between them.

32 syscalls in total. A static build makes 15.

Between the last `close(3)` and the first `mprotect` is where relocations get
applied, with no syscalls to see. `LD_DEBUG=statistics` counts them:

```text
$ LD_DEBUG=statistics ./hello
      3992:	                 number of relocations: 98
      3992:	      number of relocations from cache: 7
      3992:	        number of relative relocations: 1116
```

Almost all of the 1,116 relative ones are probably libc fixing up its own pointers. The 98
symbol relocations are what cost lookups. glibc can print a cycle count here
too, but not on this aarch64 build; the line simply isn't there.

</Sub>

<Sub n="3.3" title="Lazy binding, and why I couldn't see it at first">

The textbook version: calls to `puts` go through a PLT stub. It jumps
through a GOT slot that initially points back into the loader. That first
call resolves `puts` and patches the slot; every call after that goes straight
to libc.

I went to watch it in `gdb`, and the slot was already filled before `main`. Had I
broken something? The
`FLAGS BIND_NOW` in section 2.3 is why: **Ubuntu 24.04's gcc links with
`-z now` by default**, so every `JUMP_SLOT` is resolved at startup and the GOT
becomes read-only. To see lazy binding at all, I had to ask for it with
`-Wl,-z,lazy`. Here's the PLT from that build, `objdump -d` on aarch64:

```text
00000000000005d0 <.plt>:                    # PLT0: the path into the loader
 5d0:	stp	x16, x30, [sp, #-16]!
 5d4:	adrp	x16, 1f000
 5d8:	ldr	x17, [x16, #4088]            # GOT[2]: _dl_runtime_resolve
 5dc:	add	x16, x16, #0xff8
 5e0:	br	x17

0000000000000630 <puts@plt>:
 630:	adrp	x16, 20000                   # page of .got.plt
 634:	ldr	x17, [x16, #32]              # load the puts slot
 638:	add	x16, x16, #0x20              # x16 = &slot, for the resolver
 63c:	br	x17                          # jump wherever it points

0000000000000640 <main>:
 ...
 650:	bl	630 <puts@plt>
```

Four instructions per stub. On the first call the slot holds `0x5d0`, the
address of PLT0, so the `br x17` lands in PLT0. PLT0 pushes `x16` (the slot
address) and jumps into the loader. I stopped on the `bl` and stepped over it:

```text
puts slot before the call:
0xaaaaaaac0020 <puts@got.plt>:	0x0000aaaaaaaa05d0      # PLT0, rebased
puts slot after the call:
0xaaaaaaac0020 <puts@got.plt>:	0x0000fffff7e619d0      # __GI__IO_puts in libc
```

q7, 208 bytes of stack), turned the slot address back into a relocation index,
and called this:

`LD_DEBUG=bindings` shows the order in which the bindings happen. On the lazy
build, `__libc_start_main` binds after libc's constructors run, and `puts`
binds after the loader prints `transferring control`, i.e. inside `main`:

```text
calling init: /lib/aarch64-linux-gnu/libc.so.6
binding file ./hello-lazy [0] to libc.so.6 [0]: normal symbol `__libc_start_main' [GLIBC_2.34]
initialize program: ./hello-lazy
transferring control: ./hello-lazy
binding file ./hello-lazy [0] to libc.so.6 [0]: normal symbol `puts' [GLIBC_2.17]
```

There's also an odd pair in that output: `hello-lazy` appears to bind `malloc`,
`calloc`, `realloc` and `free`, even though it never calls them. That's `ld.so`
itself. It runs on a tiny internal allocator until libc is relocated, then looks
up the real `malloc` through the main program's scope. That's also how
`LD_PRELOAD` gets to replace the loader's allocator.

</Sub>

<Sub n="3.4" title="IFUNC: code that runs during relocation">

`memcpy` in glibc isn't one function. `readelf --dyn-syms` on this libc marks it
`IFUNC`, along with `memmove`, `memset`, `memchr`, `strlen` and
`gettimeofday`. An IFUNC symbol points at a **resolver**, and the loader
*calls* it and uses the return value as the symbol's address. A resolver typically
checks CPU features and picks the SVE, SIMD or generic version.

That means arbitrary code, from any library, runs inside the loader while it's
still patching tables. I wrote one to check exactly when:

```c
static int resolver_ran_before_main = 0;
static unsigned long hwcap_seen;

// Runs inside ld.so, while it processes this executable's relocations.
// On aarch64 the loader hands the resolver AT_HWCAP as its first argument.
static int (*resolve_sum(unsigned long hwcap))(const int *, int) {
    resolver_ran_before_main = 1;
    hwcap_seen = hwcap;
    return (hwcap & HWCAP_ASIMD) ? sum_simd : sum_generic;
}
int sum(const int *a, int n) __attribute__((ifunc("resolve_sum")));

__attribute__((constructor)) static void ctor(void) {
    printf("constructor: resolver already ran? %d\n", resolver_ran_before_main);
}
```

```text
$ ./ifunc
constructor: resolver already ran? 1
main: sum=10, hwcap=0x40000000efb3ffff, ASIMD=yes
```

My resolver ran before any constructor, as an `R_AARCH64_IRELATIVE` relocation.
Bit 62 in that hwcap is glibc's flag saying a second argument with more feature
words follows. Resolvers run this early by design, before RELRO makes the
GOT read-only. Section 4.4 is about what happened when someone noticed.

</Sub>

<Sub n="3.5" title="Constructors, __libc_start_main, and finally main">

After relocation `ld.so` runs each library's `DT_INIT_ARRAY` (libc's first,
because the executable depends on it), then jumps to `AT_ENTRY`. That's your
`_start`: a few instructions from `crt1.o` that call
`__libc_start_main`. Those strings from the `LD_DEBUG` output above are right
there in the source:

`__libc_start_call_main` calls `main` and passes its return value to `exit`.
That `init != NULL` branch is also where the most common deployment error on
Linux comes from.

</Sub>

<Sub n="4.1" title="'No such file or directory', for a file that's right there">

I patched the `.interp` string in a copy of hello to point at musl's loader, the
path an Alpine binary would ask for, and ran it on Ubuntu:

```text
$ ls -l hello-badinterp
-rwxr-xr-x 1 root root 70312 Sep 25 13:26 hello-badinterp
$ ./hello-badinterp
bash: line 2: ./hello-badinterp: cannot execute: required file not found
$ strace ./hello-badinterp
execve("./hello-badinterp", ...) = -1 ENOENT (No such file or directory)
```

That file exists. `ENOENT` is about the interpreter, straight out of the
`open_exec` failure in 3.1. Bash 5.2 at least says "required file", and older
shells just print "No such file or directory". That's how Julia Evans
[ran into it](https://jvns.ca/blog/2021/11/17/debugging-a-weird--file-not-found--error/)
with a glibc binary in an Alpine container. Fix: check `readelf -l | grep
interpreter` before believing the error message.

</Sub>

<Sub n="4.2" title="version `GLIBC_2.34' not found">

Look at what my hello world requires:

```text
$ objdump -T hello | grep GLIBC
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.34) __libc_start_main
0000000000000000  w   DF *UND*	0000000000000000 (GLIBC_2.17) __cxa_finalize
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.17) abort
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.17) puts
```

A program that calls one function needs glibc 2.34 or later, because of
`_start`, code you didn't write. In 2.34, `__libc_start_main` stopped using
the `init` argument, and the glibc source says so:

> Starting with glibc 2.34, the init parameter is always NULL. Older libcs are
> not prepared to handle that. The macro DEFINE_LIBC_START_MAIN_VERSION creates
> GLIBC_2.34 alias, so that newly linked binaries reflect that dependency.
> ([csu/libc-start.c](https://github.com/bminor/glibc/blob/glibc-2.39/csu/libc-start.c#L363-L368))

So anything built on Ubuntu 22.04 or newer won't start on a glibc 2.31 or 2.28
system, and the error lands at exec time. Two working rules:

- **Build on the oldest system you ship to.** glibc versioning is
  backward-compatible only, old binaries run on new glibc, never the reverse.
  Python's manylinux wheels are this rule turned into a standard
  ([PEP 600](https://peps.python.org/pep-0600/)).
- **Or don't depend on the host's libc at all**: static linking, or a
  container that brings its own.

</Sub>

<Sub n="4.3" title="Interposition working exactly as designed">

`LD_PRELOAD` puts an object at the front of the search order, so its `malloc`
beats libc's for every lookup in the process, libc's own included. A
working malloc counter is 30 lines of C++:

```cpp
// mallocount.cpp: count every malloc the program makes, print the total at exit.
#include <dlfcn.h>
#include <atomic>
#include <cstddef>
#include <cstdio>
#include <unistd.h>

using malloc_fn = void *(*)(size_t);
static malloc_fn real_malloc = nullptr;
static std::atomic<unsigned long> calls{0};

// dlsym can itself allocate. Serve those early requests from a static arena.
alignas(16) static char arena[4096];
static size_t arena_used = 0;

extern "C" void *malloc(size_t n) {
    if (!real_malloc) {
        static bool resolving = false;
        if (resolving) {                       // re-entered from inside dlsym
            void *p = arena + arena_used;
            arena_used += (n + 15) & ~size_t(15);
            return p;
        }
        resolving = true;
        real_malloc = reinterpret_cast<malloc_fn>(dlsym(RTLD_NEXT, "malloc"));
        resolving = false;
    }
    calls.fetch_add(1, std::memory_order_relaxed);
    return real_malloc(n);
}

__attribute__((destructor)) static void report() {
    char buf[64];
    int len = std::snprintf(buf, sizeof buf, "[mallocount] %lu calls\n",
                            calls.load(std::memory_order_relaxed));
    if (write(2, buf, len) < 0) {}              // not stdio: it may already be torn down
}
```

```text
$ g++ -std=c++20 -O2 -shared -fPIC -o mallocount.so mallocount.cpp
$ LD_PRELOAD=$PWD/mallocount.so ./allocs          # pushes 1,000 std::strings
[mallocount] 1013 calls
$ LD_PRELOAD=$PWD/mallocount.so python3 -c 'print(1)'
[mallocount] 3167 calls
$ LD_PRELOAD=$PWD/mallocount.so ./hello-static
hello
$ LD_PRELOAD=$PWD/mallocount.so ls /
$
```

Those last two are the interesting ones. A static binary ignores `LD_PRELOAD`
completely, since there's no loader to read it. And `ls` printed nothing.
`strace` explains it: coreutils closes fd 2 in its exit handler, and my
destructor runs after that.

```text
close(2)                                = 0
write(2, "[mallocount] 35 calls\n", 22) = -1 EBADF (Bad file descriptor)
```

On macOS the same shim counted **zero** calls, with or without
`DYLD_FORCE_FLAT_NAMESPACE`. macOS binds each import to a named library (the
two-level namespace), so defining `malloc` somewhere else doesn't change
anything. You have to say what you're replacing in a `__DATA,__interpose`
section. With that version, the same C++ program on an M4 counted 1,038 calls.

</Sub>

<Sub n="4.4" title="The xz backdoor, an IFUNC resolver doing too much">

On 29 March 2024 Andres Freund
[posted to oss-security](https://www.openwall.com/lists/oss-security/2024/03/29/4)
that xz-utils 5.6.0 and 5.6.1 contained a backdoor, now CVE-2024-3094. He'd
noticed ssh logins on Debian sid taking a lot of CPU plus valgrind errors, and
measured a login going from 0.299 s to 0.807 s. Everything after that is loader
mechanics:

1. **OpenSSH doesn't use liblzma.** But Debian and several other distributions
   patch `sshd` to call libsystemd for service notification, and **libsystemd
   depends on liblzma**. So liblzma gets loaded into `sshd`.
2. A malicious build step, present in release tarballs and absent from git,
   **replaced liblzma's IFUNC resolvers** `crc32_resolve()` and `crc64_resolve()`.
   Those run during relocation, before `main`, before RELRO.
3. From inside the resolver, the payload parsed the loader's data structures and
   **installed an audit hook in the dynamic linker**. When the loader resolved
   `RSA_public_decrypt@....plt`, the hook swapped in its own code.
4. It only activated under narrow conditions, per Freund: x86-64 Linux, built
   by gcc and the GNU linker as a Debian or RPM package, `argv[0]` equal to
   `/usr/sbin/sshd`, `TERM` unset, `LANG` set, and `LD_DEBUG` and `LD_PROFILE`
   unset.

<Callout label="Why full RELRO didn't stop it">
RELRO makes the GOT read-only *after* relocation. IFUNC resolvers run *during*
relocation. So full RELRO couldn't have helped here: the attacker's code ran at a
point when the tables it went after were still writable by design. That the detection trigger was slower logins, measured in hundreds
of milliseconds, is the other lesson of this chapter.
</Callout>

</Sub>

<Sub n="5.2" title="Lazy versus now: a crossover, measured">

To make relocation cost visible I generated a shared library with 20,000
functions, `f0` calling `f1` calling `f2` all the way to `f20000`. With default
visibility every one of those internal calls goes through the PLT, since any of
them could be interposed. `readelf -r` counts **20,002 `JUMP_SLOT`s**.
With `-fvisibility=hidden` and only `f0` exported: **2**.

So which wins? Lazy binding wins by 3.5× when you call a handful of what you link, and loses
by 24% when you call everything. Most real programs call a small fraction of
libc and a large fraction of their own code, so that argues for lazy. Full
RELRO needs eager binding, though, and that's why distributions pay anyway.

<Callout label="The number that makes visibility matter">
`-fvisibility=hidden` beat *both* binding modes by a wide margin: 488 µs against
1,184 for the same 20,000 calls. Nothing is deferred and nothing is looked up,
because the calls were resolved by the static linker into plain `bl`
instructions. And the library shrank from 3.7 MB to 2.0 MB, since 20,000
dynamic symbols, their strings and their hash entries all disappear.
</Callout>

What I can't fully explain is the 14 ns. `_dl_runtime_resolve` stores and
reloads 208 bytes of registers on every first call. That should cost maybe a few
nanoseconds, and the lookup is the same one eager binding does. I'd guess it's
the page faults: eager binding writes the GOT in one sequential pass, and lazy
binding writes one slot at a time scattered through execution. I didn't
separate the two. `perf stat -e page-faults,dTLB-load-misses` on both variants
would settle it, and this container doesn't expose those counters.

</Sub>

<Sub n="5.3" title="The history of trying to make this cheaper">

Big C++ programs are where this used to hurt, and you're probably running the result of
the fixes:

- **prelink** (Jakub Jelinek, Red Hat, [paper](https://people.redhat.com/jakub/prelink.pdf))
  computed relocations ahead of time for a fixed library layout. Fedora and RHEL
  ran it by default, and Jelinek reported "an order of magnitude difference" in
  relocation time for OpenOffice.org Writer
  ([LWN, 2009](https://lwn.net/Articles/341244/)). It's fundamentally at odds
  with ASLR, since the whole point is that addresses stay put.
- **Firefox's elfhack** (Mike Hommey, 2010) rewrote libxul's relative relocations
  into a compact form to cut startup I/O
  ([glandium.org](https://glandium.org/blog/?p=1177)).
- **RELR** (`DT_RELR`) standardised the idea. Chrome OS carried patches from
  2018, Android and Fuchsia adopted it, and it landed in glibc 2.36
  ([MaskRay](https://maskray.me/blog/2021-10-31-relative-relocations-and-relr)).
  Linkers emit it with `-z pack-relative-relocs`, and Hommey retired elfhack for
  it in 2023 ([glandium.org](https://glandium.org/blog/?p=4297)).

</Sub>

**Don't run `ldd` on a binary you don't trust.** The `ldd(1)` man page warns
that some versions may execute the program to get the answer. `readelf -d` and
`LD_DEBUG=libs` on a trusted loader give you the same information.

</Sub>

<Sub n="6.2" title="What to change, roughly in order">

1. **Build shared libraries with `-fvisibility=hidden`** and export an explicit
   API. Smaller file, fewer lookups, faster calls. It was the biggest single win
   measured here.
2. **Keep full RELRO** (`-z relro -z now`). Ubuntu's default already does. It
   costs eager binding, and in exchange an attacker can't overwrite GOT entries
   after startup.
3. **Link RELR** with `-z pack-relative-relocs` if your toolchain and target
   glibc (2.36 or newer) support it.
4. **Count your libraries.** Each `NEEDED` is an `openat`, several `mmap`s,
   relocations and its constructors. `ldd` on a large C++ service can easily list
   dozens.
5. **Go static for tools you exec a lot**, if you can live with the
   consequences in section 8.

</Sub>

<SectionHeading n="07" cmd="git init ./weekend-project" id="build">Build this</SectionHeading>

**Write an `LD_AUDIT` library that times every binding in a real program.**

glibc's [rtld-audit(7)](https://man7.org/linux/man-pages/man7/rtld-audit.7.html)
interface calls your `la_objopen` for every library loaded and `la_symbind64`
for every symbol bound. That's more or less the same machinery the xz payload hooked.

- Implement `la_version`, `la_objopen` and `la_symbind64`, and log object name,
  symbol name and a `clock_gettime` timestamp for each.
- Run it on `python3 -c pass` and on a C++ service you own. Count bindings per
  library.
- Then rebuild one of your own libraries with `-fvisibility=hidden` and watch its
  bindings disappear from the log.

Your first run will probably show you a library you didn't know was loaded. On
Debian and Ubuntu, liblzma in `sshd` was exactly that.

<SectionHeading n="10" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What's the difference between program headers and section headers?">
Program headers describe segments: what to map, where, with which permissions.
That's all the kernel and the dynamic loader read. Section headers describe
the file for tools like the linker, `objdump` and `gdb`: `.text`, `.dynsym`,
`.rela.plt`. Linux never looks at them, so a binary can run with its
section header table stripped.
</QA>

<QA level="beginner" q="A binary exists and is executable, and running it says 'No such file or directory'. Why?">
Almost always the interpreter named in `PT_INTERP` doesn't exist, typically a
glibc binary in an Alpine container asking for `/lib/ld-linux-*.so`. Linux
opens that path inside `load_elf_binary` and returns its `ENOENT` from
`execve`. `readelf -l ./bin | grep interpreter` shows what it wants.
</QA>

<QA level="intermediate" q="Walk through the first call to puts in a lazily bound program.">
`main` calls `puts@plt`. That stub loads the `puts` slot from `.got.plt`. It
still points at PLT0, and jumps there. PLT0 pushes the slot address and jumps to
`_dl_runtime_resolve`. That saves the argument registers and calls `_dl_fixup`.
That finds the `.rela.plt` entry, looks `puts` up through the GNU hash tables of
each loaded object, writes the address into the slot, and returns it. The
trampoline restores registers and jumps to `puts`. Later calls skip all of it.
</QA>

<QA level="intermediate" q="Why does a program built on Ubuntu 24.04 fail with GLIBC_2.34 not found on an older box?">
glibc versions its symbols, and a program records the version it linked
against. Even a hello world references `__libc_start_main@GLIBC_2.34`, from
`crt1.o`, because 2.34 changed how that function handles constructors. Older
glibc doesn't have that version node, so the loader refuses before `main`.
Build on the oldest target, use a manylinux-style build image, or link
statically.
</QA>

<QA level="intermediate" q="What does full RELRO protect, and what does it cost?">
It makes the GOT and other relocated data read-only once the loader finishes, so
a memory-corruption bug can't redirect a function pointer in the GOT. It
requires binding every symbol at startup (`-z now`). In my 20,000-symbol
test cost 547 µs against lazy binding when only two functions were called.
</QA>

<QA level="deep" q="How did the xz backdoor get code running inside sshd, and why didn't RELRO help?">
Distro-patched `sshd` links libsystemd, which links liblzma. That malicious
liblzma replaced its IFUNC resolvers. The loader calls those during relocation,
before `main` and before RELRO is applied. From there it installed a
dynamic-linker audit hook and redirected `RSA_public_decrypt` when that symbol
was bound. RELRO locks tables after relocation, and the attack happened during it.
</QA>

<QA level="deep" q="Why does -fvisibility=hidden make a shared library start faster?">
Default visibility means every exported function can be interposed by an
earlier object, so even internal calls go through the PLT and need a
`JUMP_SLOT` relocation. Hidden symbols can't be interposed, so the static
linker emits direct branches and drops them from `.dynsym`. In my test that took
a library from 20,002 jump slots to 2, from 3.7 MB to 2.0 MB, and cut startup
from 1,184 µs to 488.
</QA>

<QA level="deep" q="Your LD_PRELOAD malloc shim deadlocks or crashes at startup. What's the likely cause?">
Probably recursion during bootstrap. Your shim's `malloc` calls `dlsym(RTLD_NEXT, "malloc")`
to find the real one, and `dlsym` itself can allocate, and that re-enters the shim
before the pointer is set. Usual fix: is a static arena for re-entrant calls
during resolution, or a glibc-specific entry point. Printing from a destructor
has its own trap: some programs close stderr before destructors run.
</QA>
