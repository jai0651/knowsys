When you run a program on Linux, the kernel usually doesn't jump to your code.
It starts a second program first, the dynamic loader, which finds your
libraries, maps them, patches their addresses into your program and runs their
constructors. Only then does `main` run.

You meet this step mostly when it fails. `error while loading shared libraries:
libfoo.so.1: cannot open shared object file`, ``version `GLIBC_2.34' not found``,
and a binary that plainly exists but says "No such file or directory" all come
from it. So does `LD_PRELOAD`, which is how jemalloc and many profilers get into
a program without a rebuild. So did the 2024 xz backdoor, which reached sshd
through code the loader runs while it relocates.

This chapter follows `./hello` from `execve` to `main`: the ELF file the kernel
reads (ELF is Linux's executable format), the loader's relocations, lazy
binding, constructors, and the ways it refuses to start. Then it measures what
all of that costs on every process start.

<SectionHeading n="01" id="why-a-loader">Why programs need a loader</SectionHeading>

You write `printf("hi\n")` and compile it. The compiler turns the call into a
branch instruction, `bl printf` on ARM, which means "jump to the address of
`printf`".

What address? `printf` lives in the C library, and the compiler never saw the C
library's code. Somebody has to supply that number. The two answers are static
and dynamic linking.

<Sub n="1.1" title="Static linking: copy the code in">

The simplest answer is to do it at build time. The linker copies the machine
code for `printf`, and everything `printf` calls, into your executable, and
patches the branch to point at it. That's **static linking**, and it works.

<Why>Why not just do that for every program?</Why>

Think about what it means across a whole system. Every program on the disk
carries its own copy of the C library. Every running process holds its own copy
in RAM. And when a security fix lands in the library, every program has to be
relinked to pick it up.

</Sub>

<Sub n="1.2" title="Dynamic linking: one copy, many processes">

So most systems share instead. One copy of `libc.so.6` sits on disk, and every
process that needs it maps the same file into its address space.

Chapter 04 showed that pages mapped from the same file can share physical
memory, so a thousand processes cost roughly one copy. That's **dynamic
linking**, and it creates a new problem.

<Why>Why can't the program just contain the address of printf?</Why>

Because the library lands somewhere different in each process. That's partly on
purpose: randomising library addresses makes exploits harder. So the address
isn't known until the process starts.

The fix is a level of indirection. The program's call goes through a table
entry, and the table starts out empty. Before `main` runs, someone has to find
each library by name, map it, work out where each function landed, and write
those addresses into the table.

That someone is the **dynamic loader**, `ld.so`, which the kernel starts before
your program gets control. Each filled entry is a **relocation**. A hello world
needs 1,214 of them, by the loader's own statistics, and almost all are fix-ups
for where things landed.

| | Static linking | Dynamic linking |
|---|---|---|
| **When addresses are filled in** | At build time, by the linker | At process start (or first call), by `ld.so` |
| **Copies of libc** | One per program, on disk and in RAM | One file, shared pages |
| **A libc security fix** | Relink every program | Replace one file |
| **Who runs first** | Your `_start` | `ld.so` |

</Sub>

<Sub n="1.3" title="What you're promised at main">

When control reaches `main`, the kernel and `ld.so` between them have promised
you a few things:

- **Every undefined symbol will resolve.** Either it's already bound, or it'll be
  bound on first call. If some symbol can't be found at all, the process dies
  before `main`, not halfway through a request.
- **Constructors have run**, libraries' before yours, dependencies before
  their dependents.
- **The stack holds `argc`, `argv`, `envp` and the auxiliary vector**, the
  kernel's note to userspace about what it just did.
- **With full RELRO, the tables of resolved addresses are read-only.**

What it won't promise is a longer list, and more interesting. It won't promise
*which* definition of `malloc` you get: the first object in search order that
exports the name wins, and `LD_PRELOAD` puts itself first. It won't promise that
the glibc on the machine is the one you built against. And it promises nothing
about how long any of this takes.

<Why>Why does a call inside a library go through the table too?</Why>

In a normal ELF shared library, a call from `f1` to `f2` inside the *same*
library still goes through a table lookup. Some other object might define `f2`
first, and the rules say it wins. That's **symbol interposition**.

<Callout label="Design implication">
Interposition costs a relocation per call target at startup, even for calls
that never leave the library. Marking internal functions hidden with
`-fvisibility=hidden` removes them from the table; in section 6 it cut startup
by 700 µs.
</Callout>

</Sub>

<SectionHeading n="02" id="elf">Inside an ELF file</SectionHeading>

The loader's instructions all come from the executable itself. An ELF file is a
header, two tables that describe the rest of the file, and the data those tables
point at.

<Sub n="2.1" title="The header, and the 64 bytes the kernel reads first">

Every ELF file opens with a fixed 64-byte header (on 64-bit targets). Linux
checks the magic, the type and the machine, then uses two offsets to find
everything else.

Those numbers are from a `hello` built with plain `gcc -O2` on Ubuntu 24.04.
Its `Type` is `DYN`, not `EXEC`. A default Ubuntu build is a
position-independent executable (PIE), and Linux treats that almost exactly like
a shared library.

</Sub>

<Sub n="2.2" title="Program headers are for loading, section headers are for tools">

An ELF file describes itself twice:

| Table | Describes | Read by |
|---|---|---|
| **Program headers** (segments) | What to map, where, and with which permissions | The kernel and `ld.so` |
| **Section headers** | What the bytes mean: `.text`, `.dynsym`, `.rela.plt` | The linker, `objdump`, `gdb` |

Here are hello's segments:

```text
$ readelf -lW hello          # trimmed
  Type           Offset   VirtAddr           FileSiz  MemSiz   Flg Align
  PHDR           0x000040 0x0000000000000040 0x0001f8 0x0001f8 R   0x8
  INTERP         0x000238 0x0000000000000238 0x00001b 0x00001b R   0x1
      [Requesting program interpreter: /lib/ld-linux-aarch64.so.1]
  LOAD           0x000000 0x0000000000000000 0x0008b4 0x0008b4 R E 0x10000
  LOAD           0x00fd90 0x000000000001fd90 0x000280 0x000288 RW  0x10000
  DYNAMIC        0x00fda0 0x000000000001fda0 0x0001f0 0x0001f0 RW  0x8
  GNU_STACK      0x000000 0x0000000000000000 0x000000 0x000000 RW  0x10
  GNU_RELRO      0x00fd90 0x000000000001fd90 0x000270 0x000270 R   0x1
```

There are two `LOAD` segments, one executable and one writable, and never a
segment that's both. `INTERP` names the program that'll actually run first.
`GNU_RELRO` marks the part of the writable segment that goes read-only once
relocation is done.

<Why>Why is this file 70 KB for 2 KB of code?</Why>

Because of that `0x10000` alignment. The aarch64 toolchain aligns segments to
64 KB so the same binary works on kernels with 4 KB, 16 KB or 64 KB pages, and
the file is padded to match.

</Sub>

<Sub n="2.3" title=".dynamic, relocations, and the GOT">

`PT_DYNAMIC` points at `.dynamic`, an array of tag/value pairs that is the
loader's table of contents. Hello has 27 entries. These are the ones that
matter:

| Tag | What it tells the loader |
|---|---|
| `NEEDED libc.so.6` | The dependency list, by soname |
| `SYMTAB`, `STRTAB`, `GNU_HASH` | The dynamic symbol table, its strings, and the hash table for looking names up |
| `RELA`, `JMPREL` | Two relocation tables: `.rela.dyn` for data, `.rela.plt` for function calls |
| `PLTGOT` | The address of the **GOT**, the Global Offset Table |
| `FLAGS BIND_NOW`, `FLAGS_1 NOW PIE` | Bind everything at startup. Section 4 comes back to this. |

A relocation is an instruction to the loader: *at this offset, write the
address of that symbol, plus this addend.* Here's `readelf -r` on a lazily
linked build of the same hello:

```text
Relocation section '.rela.dyn' at offset 0x480 contains 8 entries:
    Offset             Type               Symbol's Name + Addend
000000000001fdc8  R_AARCH64_RELATIVE                        790
000000000001ffc8  R_AARCH64_GLOB_DAT     __cxa_finalize@GLIBC_2.17 + 0
...
Relocation section '.rela.plt' at offset 0x540 contains 5 entries:
0000000000020000  R_AARCH64_JUMP_SLOT    __libc_start_main@GLIBC_2.34 + 0
0000000000020020  R_AARCH64_JUMP_SLOT    puts@GLIBC_2.17 + 0
```

That's three kinds, with three costs:

| Type | What the loader does | Cost |
|---|---|---|
| `RELATIVE` | Adds the load base and stores | No lookup at all |
| `GLOB_DAT` | Looks up a data or function symbol | A hash, a walk over every loaded object, a string compare |
| `JUMP_SLOT` | Looks up a function called through the PLT | Same lookup, but it can be deferred to the first call |

</Sub>

<Sub n="2.4" title="GNU hash: a Bloom filter in front of every lookup">

A symbol lookup asks each loaded object in turn, "do you define `puts`?" Most
say no. `DT_GNU_HASH` makes "no" cheap with a Bloom filter checked before any
bucket is touched.

<Steps

    [1, "It picks one 64-bit word of the object's Bloom filter, indexed by `(hash / 64) & idxbits`."],
    [2, "It tests two bits of that word, one from the low bits of the hash and one from a shifted copy. **If either is clear, this object can't define the name**, and the lookup moves on."],
    [3, "Only if both are set does it touch the hash table: `bucket = hash % nbuckets`. A zero bucket also means no."],
    [4, "It walks the chain, comparing 31 bits of stored hash against the name's hash before any string compare. The low bit of an entry marks the end of the chain."],

Here's the same lookup in glibc 2.39:

<SourceRead
  file="elf/dl-lookup.c"
  repo="bminor/glibc"
  tag="glibc-2.39"
  href="https://github.com/bminor/glibc/blob/glibc-2.39/elf/dl-lookup.c#L408-L440"

```c
const ElfW(Addr) *bitmask = map->l_gnu_bitmask;
if (__glibc_likely (bitmask != NULL))
  {
    ElfW(Addr) bitmask_word
      = bitmask[(new_hash / __ELF_NATIVE_CLASS)
                & map->l_gnu_bitmask_idxbits];

    unsigned int hashbit1 = new_hash & (__ELF_NATIVE_CLASS - 1);
    unsigned int hashbit2 = ((new_hash >> map->l_gnu_shift)
                             & (__ELF_NATIVE_CLASS - 1));
    /* Two bits must both be set, or this object can't define the name. */
    if (__glibc_unlikely ((bitmask_word >> hashbit1)
                          & (bitmask_word >> hashbit2) & 1))
      {
        Elf32_Word bucket = map->l_gnu_buckets[new_hash % map->l_nbuckets];
        if (bucket != 0)
          {
            const Elf32_Word *hasharr = &map->l_gnu_chain_zero[bucket];
            do
              /* Compare 31 bits of hash before any strcmp. */
              if (((*hasharr ^ new_hash) >> 1) == 0)
                { /* ... check_match(): the actual string compare ... */ }
            while ((*hasharr++ & 1u) == 0);   /* low bit ends the chain */
          }
      }
```
</SourceRead>

Note the `__glibc_unlikely` on the Bloom test. glibc's authors expect most
objects to answer "no". In a C++ program with a dozen libraries, most probes
probably end at one 64-bit load and two shifts. For hello's two objects the
filter barely matters; it pays off at forty.

</Sub>

`execve` walks a list of binary formats until one claims the file. For ELF that's

first thing it hunts for is `PT_INTERP`:

</Sub>

<Sub n="3.2" title="The auxiliary vector: the kernel's notes">

`create_elf_tables` writes the auxiliary vector onto the stack, next to `argv`
and `envp`. glibc will print it for you:

```text
$ LD_SHOW_AUXV=1 ./hello        # trimmed
AT_SYSINFO_EHDR:      0xffffbc9dc000      # the vDSO from chapter 07
AT_HWCAP:             efb3ffff            # CPU features, for IFUNC resolvers
AT_PAGESZ:            4096
AT_PHDR:              0xaaaac8e80040      # where your program headers ended up
AT_BASE:              0xffffbc99f000      # where ld.so was mapped
AT_ENTRY:             0xaaaac8e80680      # 0x680 from the header, plus the bias

```

`ld.so` doesn't have to parse your ELF file again. Linux already did, and

</Sub>

That's 32 syscalls in total. A static build makes 15.

<Why>Why does nobody open hello or ld.so?</Why>

Because the kernel mapped both already, in `load_elf_binary`. The loader only
opens what the kernel didn't: the cache and the libraries.

Two more things stand out:

- **The loader checks `/etc/ld.so.preload` before anything else.** It's a
  system-wide `LD_PRELOAD` that persists across reboots, and a favourite of
  rootkits.
- **It reserves libc's whole address range as `PROT_NONE` first**, then maps the
  segments into it with `MAP_FIXED`, so nothing else can land in the gap between
  them.

Between the last `close(3)` and the first `mprotect` is where relocations get
applied, with no syscalls to see. `LD_DEBUG=statistics` counts them:

```text
$ LD_DEBUG=statistics ./hello
      3992:	                 number of relocations: 98
      3992:	      number of relocations from cache: 7
      3992:	        number of relative relocations: 1116
```

Almost all of the 1,116 relative ones are probably libc fixing up its own
pointers. The 98 symbol relocations are the ones that cost lookups. glibc can
print a cycle count here too, but not on this aarch64 build; the line simply
isn't there.

</Sub>

because the executable depends on it), then jumps to `AT_ENTRY`. That's your
`_start`: a few instructions from `crt1.o` that call `__libc_start_main`. The
strings `LD_DEBUG` prints in section 4.2 are right here in the source:

<SectionHeading n="04" id="binding">Lazy binding and IFUNC</SectionHeading>

The relocations for function calls don't have to be done up front. With lazy
binding, each one waits until the function is first called. And some symbols
aren't looked up at all: the loader runs a function to decide what they are.

<Sub n="4.1" title="The PLT stub and its GOT slot">

Calls to `puts` go through a small stub in the PLT (procedure linkage table).
The stub jumps through a GOT slot that initially points back into the loader.
The first call resolves `puts` and patches the slot; every call after that goes
straight to libc.

<Why>Why was the slot already filled before main?</Why>

Because of the `FLAGS BIND_NOW` in section 2.3. **Ubuntu 24.04's gcc links with
`-z now` by default**, so every `JUMP_SLOT` is resolved at startup and the GOT
becomes read-only. Watching a slot in `gdb` on a default build shows it filled
before `main`. To see lazy binding at all, you have to ask for it with
`-Wl,-z,lazy`.

Here's the PLT from that build, `objdump -d` on aarch64:

```c
_dl_fixup (struct link_map *l, ElfW(Word) reloc_arg)
{
  const ElfW(Sym) *const symtab = (const void *) D_PTR (l, l_info[DT_SYMTAB]);
  const char *strtab = (const void *) D_PTR (l, l_info[DT_STRTAB]);
  const uintptr_t pltgot = (uintptr_t) D_PTR (l, l_info[DT_PLTGOT]);

  const PLTREL *const reloc                 /* which .rela.plt entry? */
    = (const void *) (D_PTR (l, l_info[DT_JMPREL])
                      + reloc_offset (pltgot, reloc_arg));
  const ElfW(Sym) *sym = &symtab[ELFW(R_SYM) (reloc->r_info)];
  void *const rel_addr = (void *)(l->l_addr + reloc->r_offset);  /* the slot */
  ...
      result = _dl_lookup_symbol_x (strtab + sym->st_name, l, &sym, l->l_scope,
                                    version, ELF_RTYPE_CLASS_PLT, flags, NULL);
  ...
  if (sym != NULL
      && __builtin_expect (ELFW(ST_TYPE) (sym->st_info) == STT_GNU_IFUNC, 0))
    value = elf_ifunc_invoke (DL_FIXUP_VALUE_ADDR (value));   /* see 4.3 */
  ...
  /* Finally, fix up the plt itself.  */

}
```

`LD_DEBUG=bindings` shows the order in which the bindings happen. On the lazy
build, `__libc_start_main` binds after libc's constructors run, and `puts`
binds after the loader prints `transferring control`, which means inside `main`:

```text
calling init: /lib/aarch64-linux-gnu/libc.so.6
binding file ./hello-lazy [0] to libc.so.6 [0]: normal symbol `__libc_start_main' [GLIBC_2.34]
```

The same output has an odd pair: `hello-lazy` appears to bind `malloc`,
`calloc`, `realloc` and `free`, though it never calls them. That's `ld.so`
itself. It runs on a tiny internal allocator until libc is relocated, then looks
up the real `malloc` through the main program's scope. That's also how
`LD_PRELOAD` gets to replace the loader's allocator.

</Sub>

<Sub n="4.3" title="IFUNC: code that runs during relocation">

`memcpy` in glibc isn't one function. `readelf --dyn-syms` on this libc marks it
`IFUNC`, along with `memmove`, `memset`, `memchr`, `strlen` and `gettimeofday`.

An IFUNC symbol points at a **resolver**. The loader *calls* it and uses the
return value as the symbol's address. A resolver typically checks CPU features
and picks the SVE, SIMD or generic version.

<Why>When exactly does a resolver run?</Why>

During relocation, inside the loader, while it's still patching tables. That
means arbitrary code, from any library, runs at that point. A test program makes
it visible:

```c
static int resolver_ran_before_main = 0;
static unsigned long hwcap_seen;

// Runs inside ld.so, while it processes this executable's relocations.
// On aarch64 the loader hands the resolver AT_HWCAP as its first argument.
static int (*resolve_sum(unsigned long hwcap))(const int *, int) {
    resolver_ran_before_main = 1;
    hwcap_seen = hwcap;
    return (hwcap & HWCAP_ASIMD) ? sum_simd : sum_generic;
}
int sum(const int *a, int n) __attribute__((ifunc("resolve_sum")));

__attribute__((constructor)) static void ctor(void) {
    printf("constructor: resolver already ran? %d\n", resolver_ran_before_main);
}
```

```text
$ ./ifunc
constructor: resolver already ran? 1
main: sum=10, hwcap=0x40000000efb3ffff, ASIMD=yes
```

The resolver ran before any constructor, as an `R_AARCH64_IRELATIVE`
relocation. Bit 62 in that hwcap is glibc's flag saying a second argument with
more feature words follows.

Resolvers run this early by design, before RELRO makes the GOT read-only.
Section 5.4 is about what happened when someone noticed.

</Sub>

<SectionHeading n="05" id="failures">When the loader says no</SectionHeading>

to log anything. Each one has a specific cause you can read off the binary.

</Sub>

<Sub n="5.2" title="version `GLIBC_2.34' not found">

Look at what hello requires:

```text
$ objdump -T hello | grep GLIBC
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.34) __libc_start_main
0000000000000000  w   DF *UND*	0000000000000000 (GLIBC_2.17) __cxa_finalize
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.17) abort
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.17) puts
```

A program that calls one function needs glibc 2.34 or later, because of
`_start`, code you didn't write. In 2.34, `__libc_start_main` stopped using
the `init` argument, and the glibc source says so:

> Starting with glibc 2.34, the init parameter is always NULL. Older libcs are
> not prepared to handle that. The macro DEFINE_LIBC_START_MAIN_VERSION creates
> GLIBC_2.34 alias, so that newly linked binaries reflect that dependency.
> ([csu/libc-start.c](https://github.com/bminor/glibc/blob/glibc-2.39/csu/libc-start.c#L363-L368))

So anything built on Ubuntu 22.04 or newer won't start on a glibc 2.31 or 2.28
system, and the error lands at exec time. Two working rules:

- **Build on the oldest system you ship to.** glibc versioning is
  backward-compatible only: old binaries run on new glibc, never the reverse.
  Python's manylinux wheels are this rule turned into a standard
  ([PEP 600](https://peps.python.org/pep-0600/)).
- **Or don't depend on the host's libc at all**: static linking, or a
  container that brings its own.

</Sub>

<Sub n="5.3" title="LD_PRELOAD: interposition working as designed">

`LD_PRELOAD` puts an object at the front of the search order, so its `malloc`
beats libc's for every lookup in the process, libc's own included. A working
malloc counter is 30 lines of C++:

```cpp
// mallocount.cpp: count every malloc the program makes, print the total at exit.
#include <dlfcn.h>
#include <atomic>
#include <cstddef>
#include <cstdio>
#include <unistd.h>

using malloc_fn = void *(*)(size_t);
static malloc_fn real_malloc = nullptr;
static std::atomic<unsigned long> calls{0};

// dlsym can itself allocate. Serve those early requests from a static arena.
alignas(16) static char arena[4096];
static size_t arena_used = 0;

extern "C" void *malloc(size_t n) {
    if (!real_malloc) {
        static bool resolving = false;
        if (resolving) {                       // re-entered from inside dlsym
            void *p = arena + arena_used;
            arena_used += (n + 15) & ~size_t(15);
            return p;
        }
        resolving = true;
        real_malloc = reinterpret_cast<malloc_fn>(dlsym(RTLD_NEXT, "malloc"));
        resolving = false;
    }
    calls.fetch_add(1, std::memory_order_relaxed);
    return real_malloc(n);
}

__attribute__((destructor)) static void report() {
    char buf[64];
    int len = std::snprintf(buf, sizeof buf, "[mallocount] %lu calls\n",
                            calls.load(std::memory_order_relaxed));
    if (write(2, buf, len) < 0) {}              // not stdio: it may already be torn down
}
```

```text
$ g++ -std=c++20 -O2 -shared -fPIC -o mallocount.so mallocount.cpp
$ LD_PRELOAD=$PWD/mallocount.so ./allocs          # pushes 1,000 std::strings
[mallocount] 1013 calls
$ LD_PRELOAD=$PWD/mallocount.so python3 -c 'print(1)'
[mallocount] 3167 calls
$ LD_PRELOAD=$PWD/mallocount.so ./hello-static
hello
$ LD_PRELOAD=$PWD/mallocount.so ls /
$
```

Those last two are the interesting ones:

- **A static binary ignores `LD_PRELOAD` completely**, since there's no loader
  to read it.
- **`ls` printed nothing.** `strace` explains it: coreutils closes fd 2 in its
  exit handler, and the destructor runs after that.

```text
close(2)                                = 0
write(2, "[mallocount] 35 calls\n", 22) = -1 EBADF (Bad file descriptor)
```

<Why>Why did the same shim count nothing on macOS?</Why>

On macOS it counted **zero** calls, with or without `DYLD_FORCE_FLAT_NAMESPACE`.
macOS binds each import to a named library (the two-level namespace), so
defining `malloc` somewhere else doesn't change anything. You have to say what
you're replacing in a `__DATA,__interpose` section. With that version, the same
C++ program on an M4 counted 1,038 calls.

</Sub>

<Sub n="5.4" title="The xz backdoor: an IFUNC resolver doing too much">

On 29 March 2024 Andres Freund
[posted to oss-security](https://www.openwall.com/lists/oss-security/2024/03/29/4)
that xz-utils 5.6.0 and 5.6.1 contained a backdoor, now CVE-2024-3094. He'd
noticed ssh logins on Debian sid taking a lot of CPU, plus valgrind errors, and
measured a login going from 0.299 s to 0.807 s. Everything after that is loader
mechanics:

It only activated under narrow conditions, per Freund: x86-64 Linux, built by
gcc and the GNU linker as a Debian or RPM package, `argv[0]` equal to
`/usr/sbin/sshd`, `TERM` unset, `LANG` set, and `LD_DEBUG` and `LD_PROFILE`
unset.

<Why>Why didn't full RELRO stop it?</Why>

RELRO makes the GOT read-only *after* relocation. IFUNC resolvers run *during*
relocation. So the attacker's code ran at a point when the tables it went after
were still writable, by design.

<Callout label="Design implication">
The loader runs third-party code before `main`, with the tables writable. Every
library in your process, including the ones pulled in by a dependency's
dependency, is part of your attack surface. And the detection trigger here was
slower logins, measured in hundreds of milliseconds. Watch your startup
times.
</Callout>

</Sub>

<SectionHeading n="06" id="cost">What startup costs</SectionHeading>

All of this happens before `main`, so it's a cost every process start pays.

<Callout label="The machine" kind="note">
Ubuntu 24.04, glibc 2.39, gcc 13.3, kernel 6.10.14-linuxkit on aarch64,
in a shared 4-CPU container on an Apple M4. Binaries in the container's own
`/tmp`, not on the bind mount. Each row is `posix_spawn` + `waitpid` timed
with `steady_clock`, 5,000 runs interleaved across all rows, three repeats; the
table shows the median of the three medians. Absolute numbers are noisy on a
shared box. But the deltas held across every repeat.
</Callout>

<Sub n="6.1" title="Static, dynamic, C++, Python">

Dynamic linking costs hello about 30 µs, maybe a little less. Swapping `puts`
for `std::cout` costs another 240, most of it likely loading and relocating
libstdc++. Python's 3–4 ms is mostly Python itself, the interpreter's own init
and imports, and `-S` (skip `site`) takes a millisecond off.

Where the file lives matters too. In a first measurement, with both files on a
bind mount from the Mac, a static hello looked *slower* than the dynamic one:
320 µs against 186 µs. The bigger static file paid more to be paged in. Copied
to local disk, the p10s were **103 µs** static and **132 µs** dynamic.

<Why>Does 30 µs matter?</Why>

For a long-lived server, probably not. But a build that runs the compiler 20,000
times pays it several times per file, since `gcc` execs `cc1`, `as` and `ld`. A
shell script calling `grep` in a loop pays it every iteration.

</Sub>

<Sub n="6.2" title="Lazy versus now: a crossover, measured">

To make relocation cost visible, a generated shared library has 20,000
functions, `f0` calling `f1` calling `f2` all the way to `f20000`. With default
visibility every one of those internal calls goes through the PLT, since any of
them could be interposed. `readelf -r` counts **20,002 `JUMP_SLOT`s**. With
`-fvisibility=hidden` and only `f0` exported: **2**.

<Predict

Hidden visibility, by a wide margin: 488 µs, against 1,184 µs for eager binding
and 1,469 µs for lazy. With every function called, lazy binding does the same

So which wins? Lazy binding wins by 3.5× when you call a handful of what you
link, and loses by 24% when you call everything. Most real programs call a small
fraction of libc and a large fraction of their own code, which argues for lazy.
Full RELRO needs eager binding, though, and that's why distributions pay anyway.

<Callout label="Design implication">
`-fvisibility=hidden` beat *both* binding modes: 488 µs against 1,184 for the
same 20,000 calls. Nothing is deferred and nothing is looked up, because the
static linker resolved the calls into plain `bl` instructions. The library also
shrank from 3.7 MB to 2.0 MB, since 20,000 dynamic symbols, their strings and
their hash entries all disappear.
</Callout>

<Why>Why does a lazy first call cost 14 ns more than eager binding?</Why>

That one is still open. `_dl_runtime_resolve` stores and reloads 208 bytes of
registers on every first call, which should cost a few nanoseconds, and the
lookup is the same one eager binding does. A likely candidate is page faults:
eager binding writes the GOT in one sequential pass, and lazy binding writes one
slot at a time, scattered through execution. The two weren't separated here.
`perf stat -e page-faults,dTLB-load-misses` on both variants would settle it,
and this container doesn't expose those counters.

</Sub>

<Sub n="6.3" title="The history of trying to make this cheaper">

Big C++ programs are where this used to hurt, and you're probably running the
result of the fixes:

| Fix | What it did | Where it went |
|---|---|---|
| **prelink** (Jakub Jelinek, Red Hat, [paper](https://people.redhat.com/jakub/prelink.pdf)) | Computed relocations ahead of time for a fixed library layout | Fedora and RHEL ran it by default. Jelinek reported "an order of magnitude difference" in relocation time for OpenOffice.org Writer ([LWN, 2009](https://lwn.net/Articles/341244/)). It's at odds with ASLR, since the whole point is that addresses stay put. |
| **Firefox's elfhack** (Mike Hommey, 2010) | Rewrote libxul's relative relocations into a compact form to cut startup I/O ([glandium.org](https://glandium.org/blog/?p=1177)) | Retired in 2023 in favour of RELR ([glandium.org](https://glandium.org/blog/?p=4297)) |
| **RELR** (`DT_RELR`) | Standardised the compact relative-relocation format | Chrome OS carried patches from 2018, Android and Fuchsia adopted it, and it landed in glibc 2.36 ([MaskRay](https://maskray.me/blog/2021-10-31-relative-relocations-and-relr)). Linkers emit it with `-z pack-relative-relocs`. |

MaskRay measured relative relocations at 7.9% of total file size across Arch's
`/usr/bin`, which is why three browser and OS teams each rebuilt the format.

</Sub>

<SectionHeading n="07" id="choosing">Choosing how to link</SectionHeading>

<Sub n="7.1" title="What each choice costs">

| Choice | You get | You pay |
|---|---|---|
| **Dynamic linking** | Shared pages, security fixes without rebuilds, `LD_PRELOAD` | ~30 µs per exec for hello, far more for C++; `GLIBC_x.y` errors |
| **Static linking** | One file, no loader, no version skew | No `LD_PRELOAD`, rebuild for every libc CVE, and glibc's NSS/`dlopen` features break |
| **Lazy binding** | 3.5× faster startup when few symbols are called | Writable GOT for the process lifetime; a missing symbol is a crash mid-run |
| **Full RELRO** (`-z now`) | Read-only GOT after startup | Every symbol bound up front, used or not |
| **`-fvisibility=hidden`** | Fewer relocations, direct calls, smaller file | You must mark the API explicitly; nobody can interpose internals |
| **musl (Alpine)** | Small, simple, static-friendly | No lazy binding, `dlclose` is a no-op, DNS over TCP only since 1.2.4 |

</Sub>

<Sub n="7.2" title="Go: static by default">

Go sidesteps `GLIBC_x.y` errors and missing libraries by linking statically.
With cgo off, a Go binary has no `PT_INTERP`, so it runs even in a `scratch`
container with no libc at all.

The catch is that it can't use glibc's resolver. The
[net package](https://pkg.go.dev/net) prefers its pure-Go resolver on Unix and
falls back to cgo for nsswitch or resolv.conf features it doesn't implement.
`GODEBUG=netdns=go` or `=cgo` forces one; `netdns=1` logs the choice. If a Go
service resolves names differently from curl on the same box, check which
resolver it's using.

</Sub>

<Sub n="7.3" title="Alpine and musl">

A glibc binary on Alpine fails with the `ENOENT` from section 5.1, because
Alpine's loader is musl's. And a musl binary behaves differently from glibc in
ways musl [documents](https://wiki.musl-libc.org/functional-differences-from-glibc.html):
no lazy binding at all, `dlclose` as a no-op, and a resolver that didn't support
DNS over TCP until [1.2.4 in May 2023](https://www.openwall.com/lists/musl/2023/05/02/1).
Before that, a truncated UDP answer just failed, so a name that resolved fine on
your laptop could fail under a big DNS answer.

</Sub>

<SectionHeading n="08" id="tools">Seeing inside the loader</SectionHeading>

<Sub n="8.1" title="The commands">

```shell
# What will run first, and what does this need?
readelf -lW ./app | grep -A1 INTERP
readelf -dW ./app | grep -E 'NEEDED|RUNPATH|RPATH|FLAGS'
objdump -T ./app | grep -o 'GLIBC_[0-9.]*' | sort -V | tail -1   # minimum glibc

# RELRO status: GNU_RELRO present + BIND_NOW = full RELRO
readelf -lW ./app | grep GNU_RELRO
readelf -dW ./app | grep -E 'BIND_NOW|FLAGS_1'

# The loader's own diagnostics
LD_DEBUG=libs ./app          # search paths, which file each soname became
LD_DEBUG=bindings ./app      # every symbol, who asked, who answered
LD_DEBUG=statistics ./app    # relocation counts
LD_DEBUG=help ./app          # the list
LD_SHOW_AUXV=1 ./app         # what the kernel handed over

# Startup syscalls
strace -f -e trace=openat,mmap,mprotect ./app
```

<Callout label="Common mistake" kind="warn">
Running `ldd` on a binary you don't trust. The `ldd(1)` man page warns that some
versions may execute the program to get the answer. `readelf -d` and
`LD_DEBUG=libs` on a trusted loader give you the same information.
</Callout>

</Sub>

<Sub n="8.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| "No such file or directory" (or "required file not found") for a file that exists | `PT_INTERP` names a loader that isn't installed, often a glibc binary on Alpine | `readelf -l ./bin \| grep interpreter`; build for the target's libc |
| ``version `GLIBC_2.34' not found`` | Built against a newer glibc than the target has | Build on the oldest target, use a manylinux-style image, or link statically |
| `cannot open shared object file` | The loader can't find a `NEEDED` soname | `readelf -d` for `NEEDED` and `RUNPATH`; `LD_DEBUG=libs` for the search |
| `LD_PRELOAD` has no effect | The binary is static, or it's macOS's two-level namespace | Check for `PT_INTERP`; on macOS use `__DATA,__interpose` |
| A preload shim crashes or hangs at startup | `dlsym` allocating and re-entering your `malloc` | Serve re-entrant calls from a static arena |
| Slow start for a big C++ service | Tens of thousands of symbol relocations | `-fvisibility=hidden`, fewer libraries, RELR |
| A Go service resolves names differently from curl | The pure-Go resolver | `GODEBUG=netdns=1` to see which, `=go` or `=cgo` to force one |

</Sub>

<Sub n="8.3" title="What to change, roughly in order">

1. **Build shared libraries with `-fvisibility=hidden`** and export an explicit
   API. Smaller file, fewer lookups, faster calls. It was the biggest single win
   measured here.
2. **Keep full RELRO** (`-z relro -z now`). Ubuntu's default already does. It
   costs eager binding, and in exchange an attacker can't overwrite GOT entries
   after startup.
3. **Link RELR** with `-z pack-relative-relocs` if your toolchain and target
   glibc (2.36 or newer) support it.
4. **Count your libraries.** Each `NEEDED` is an `openat`, several `mmap`s,
   relocations and its constructors. `ldd` on a large C++ service can easily list
   dozens.
5. **Go static for tools you exec a lot**, if you can live with the trade-offs
   in section 7.

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **The CPU starts in ld.so, not your program.** The kernel maps both, reads
   `PT_INTERP`, and hands your entry point over as `AT_ENTRY`.
2. **An ELF file describes itself twice.** Program headers are for loading;
   section headers are for tools, and the kernel never reads them.
3. **A relocation is "write this address here".** Relative ones are cheap;
   symbol ones need a lookup through every loaded object.
4. **GNU hash makes "not here" cheap.** A Bloom filter rejects most objects with
   one load and two shifts.
5. **Ubuntu binds everything at startup by default.** `-z now` gives full RELRO
   and a read-only GOT; lazy binding needs `-z lazy`.
6. **IFUNC resolvers run inside the loader, before RELRO.** That's the door the
   xz backdoor used to reach `sshd`.
7. **"No such file or directory" usually means the interpreter.** The kernel
   returns `ENOENT` for the loader that isn't there.
8. **Even hello needs GLIBC_2.34** if you build it on a recent distribution, so
   build on the oldest system you ship to.
9. **`LD_PRELOAD` wins every lookup, and static binaries ignore it.**
10. **Hidden visibility beats both binding modes.** 488 µs against 1,184 for the
    same 20,000 calls, and a library half the size.

<SectionHeading n="10" id="build">Build this</SectionHeading>

**Write an `LD_AUDIT` library that times every binding in a real program.**

glibc's [rtld-audit(7)](https://man7.org/linux/man-pages/man7/rtld-audit.7.html)
interface calls your `la_objopen` for every library loaded and `la_symbind64`
for every symbol bound. That's more or less the same machinery the xz payload hooked.

- Implement `la_version`, `la_objopen` and `la_symbind64`, and log object name,
  symbol name and a `clock_gettime` timestamp for each.
- Run it on `python3 -c pass` and on a C++ service you own. Count bindings per
  library.
- Then rebuild one of your own libraries with `-fvisibility=hidden` and watch its
  bindings disappear from the log.

Your first run will probably show you a library you didn't know was loaded. On
Debian and Ubuntu, liblzma in `sshd` was exactly that.

<SectionHeading n="11" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What's the difference between program headers and section headers?">
Program headers describe segments: what to map, where, with which permissions.
That's all the kernel and the dynamic loader read. Section headers describe
the file for tools like the linker, `objdump` and `gdb`: `.text`, `.dynsym`,
`.rela.plt`. Linux never looks at them, so a binary can run with its
section header table stripped.
</QA>

<QA level="beginner" q="A binary exists and is executable, and running it says 'No such file or directory'. Why?">
Almost always the interpreter named in `PT_INTERP` doesn't exist, typically a
glibc binary in an Alpine container asking for `/lib/ld-linux-*.so`. Linux
opens that path inside `load_elf_binary` and returns its `ENOENT` from
`execve`. `readelf -l ./bin | grep interpreter` shows what it wants.
</QA>

<QA level="intermediate" q="Walk through the first call to puts in a lazily bound program.">
`main` calls `puts@plt`. That stub loads the `puts` slot from `.got.plt`. It
still points at PLT0, and jumps there. PLT0 pushes the slot address and jumps to
`_dl_runtime_resolve`. That saves the argument registers and calls `_dl_fixup`.
That finds the `.rela.plt` entry, looks `puts` up through the GNU hash tables of
each loaded object, writes the address into the slot, and returns it. The
trampoline restores registers and jumps to `puts`. Later calls skip all of it.
</QA>

<QA level="intermediate" q="Why does a program built on Ubuntu 24.04 fail with GLIBC_2.34 not found on an older box?">
glibc versions its symbols, and a program records the version it linked
against. Even a hello world references `__libc_start_main@GLIBC_2.34`, from
`crt1.o`, because 2.34 changed how that function handles constructors. Older
glibc doesn't have that version node, so the loader refuses before `main`.
Build on the oldest target, use a manylinux-style build image, or link
statically.
</QA>

<QA level="intermediate" q="What does full RELRO protect, and what does it cost?">
It makes the GOT and other relocated data read-only once the loader finishes, so
a memory-corruption bug can't redirect a function pointer in the GOT. It
requires binding every symbol at startup (`-z now`). In the 20,000-symbol
test that cost 547 µs against lazy binding when only two functions were called.
</QA>

<QA level="deep" q="How did the xz backdoor get code running inside sshd, and why didn't RELRO help?">
Distro-patched `sshd` links libsystemd, which links liblzma. That malicious
liblzma replaced its IFUNC resolvers. The loader calls those during relocation,
before `main` and before RELRO is applied. From there it installed a
dynamic-linker audit hook and redirected `RSA_public_decrypt` when that symbol
was bound. RELRO locks tables after relocation, and the attack happened during it.
</QA>

<QA level="deep" q="Why does -fvisibility=hidden make a shared library start faster?">
Default visibility means every exported function can be interposed by an
earlier object, so even internal calls go through the PLT and need a
`JUMP_SLOT` relocation. Hidden symbols can't be interposed, so the static
linker emits direct branches and drops them from `.dynsym`. In the test that took
a library from 20,002 jump slots to 2, from 3.7 MB to 2.0 MB, and cut startup
from 1,184 µs to 488.
</QA>

<QA level="deep" q="Your LD_PRELOAD malloc shim deadlocks or crashes at startup. What's the likely cause?">
Probably recursion during bootstrap. Your shim's `malloc` calls `dlsym(RTLD_NEXT, "malloc")`
to find the real one, and `dlsym` itself can allocate, and that re-enters the shim
before the pointer is set. The usual fix is a static arena for re-entrant calls
during resolution, or a glibc-specific entry point. Printing from a destructor
has its own trap: some programs close stderr before destructors run.
</QA>

<SectionHeading n="12" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="Where does the CPU start executing after execve of a dynamic PIE?">
    In ld.so, at the interpreter's entry point. The program's own entry goes on
    the stack as AT_ENTRY and ld.so jumps there after relocation.
  </Q>
  <Q q="Why did LD_PRELOAD do nothing to the static binary?">
    There's no dynamic loader to read the variable. Static binaries have no
    PT_INTERP and resolve everything at link time.
  </Q>
  <Q q="Lazy binding or BIND_NOW: which starts faster?">
    It depends on how much you call. Lazy was 3.5× faster when two of 20,000
    functions ran, and 24% slower when all of them did.
  </Q>
  <Q q="Your hello world was built on Ubuntu 24.04 with gcc -O2. Is it lazily bound?">
    No. Ubuntu's toolchain links with -z now by default, so FLAGS shows BIND_NOW
    and the GOT is read-only before main.
  </Q>
</Quiz>
