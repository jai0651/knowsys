You meet virtual memory long before you learn its name. A process shows 40 GB
of virtual memory on a 16 GB machine. A container gets killed while its heap
looks half empty. Redis snapshots a 50 GB dataset by calling `fork()`, and the
machine doesn't run out of RAM.

None of those is a bug. Each one follows from a single idea: the addresses your
program uses aren't the addresses the RAM sees, and the kernel decides, page by
page, what's behind each one.

This chapter builds that idea from a machine without it, then follows one
memory access through the translation hardware, one page fault through the
kernel, and one `fork()` through copy-on-write. It ends with what a fault
costs, where translation stops being free, and how to watch it in production.

<SectionHeading n="01" id="why-virtual-memory">Why addresses need translating</SectionHeading>

Start with a computer that has no virtual memory. For a long time that's how
computers were built, and its problems are the reason everything in this
chapter exists.

<Sub n="1.1" title="A machine without translation">

On that machine an address is just a position in the RAM chips. Address
`0x1000` is byte 4,096 of physical memory, whoever asks for it.

With one program running, that's fine. Try to run two and three problems show
up almost at once:

- **They collide.** Both programs were compiled to expect their code and data
  at particular addresses, and two programs can't both own `0x1000`.
- **Nothing protects them from each other.** A stray pointer in your editor can
  overwrite your compiler's data, or the operating system's.
- **Memory has to be contiguous and real.** A program needs one unbroken block
  of free RAM as big as it might ever use, even if most of it sits idle.

</Sub>

<Sub n="1.2" title="One idea: translate in pages">

Virtual memory fixes all three with one idea. Put a translation step between
the address a program uses and the address the RAM sees.

Your program says `0x1000`, and the hardware looks up where the kernel has put
*this process's* `0x1000`. Another process's `0x1000` goes somewhere else. The
addresses a program sees are **virtual**; the ones the RAM sees are
**physical**.

<Why>Why translate in pages, not bytes?</Why>

Translating every byte separately would need a table as big as memory. So the
hardware translates in fixed-size chunks called **pages**, 4 KB on most x86-64
Linux machines.

An address splits into two parts: which page, and where inside it. With 4 KB
pages the low 12 bits are the offset, so virtual address `0x3A7C` is page
`0x3`, offset `0xA7C`.

If this process's **page table** says page 3 lives in physical frame `0x51`,
the load goes to `0x51A7C`. The offset never changes; only the page number is
swapped.

| Problem | How per-process page tables fix it |
|---|---|
| Collisions | Each process has its own table, so two processes' `0x1000` map to different frames |
| No protection | A process can only reach the frames listed in its own table |
| Contiguous RAM | Consecutive virtual pages can sit in frames scattered all over RAM |

</Sub>

<Sub n="1.3" title="What the contract gives you">

So the contract comes down to three things, and most people only notice the
first.

| You get | What it means in practice |
|---|---|
| **A private address space** | Your pointers mean nothing in another process |
| **More address space than RAM** | Allocation reserves addresses; physical pages arrive later, or never |
| **Protection and sharing** | Per-page permissions, and one physical page mappable into many address spaces at different addresses |

What it doesn't sell you is free translation. Every load and store needs a
virtual-to-physical lookup, and section 6 measures what happens when those
lookups stop hitting their cache.

<Callout label="Common mistake" kind="warn">
Assuming the page size. It's 4 KB on x86-64 Linux and **16 KB on Apple
Silicon**. That changes the arithmetic for TLB reach, for internal
fragmentation, and for how many pages your allocation actually touches. Query
it with `getconf PAGE_SIZE`.
</Callout>

</Sub>

<SectionHeading n="02" id="page-tables">Page tables and the TLB</SectionHeading>

Translation needs a table per process, and the table has to live somewhere.
This section covers its shape, and the cache that keeps it off the critical
path.

<Sub n="2.1" title="A page table is a tree">

<Why>Why not one flat array per process?</Why>

Mapping every address individually would need a table bigger than memory, and
most of a 64-bit address space is never used. So the address is split into
fields that index successive levels of a radix tree, and only populated
branches exist.

Finding one translation means walking that tree from the top: four dependent
memory accesses, each of which can itself miss cache.

</Sub>

<Sub n="2.2" title="The TLB, and the word 'reach'">

The tree lives in memory. So every load would need several more loads first,
just to find out where to go.

Processors avoid that with a small cache of recent translations, the **TLB**.
The number that matters is **reach**: entries × page size. That's how much
memory you can touch before translations start missing.

<Compare
  cols={["Configuration", "Entries (typical)", "Reach"]}
  rows={[
    ["x86-64, 4 KB pages", "~1,500 L2 TLB", "~6 MB"],
    ["x86-64, 2 MB huge pages", "~1,500", "~3 GB"],
    ["Apple Silicon, 16 KB pages", "~3,000 (undocumented)", "~48 MB"],
  ]}
/>

Look at rows one and two. Same TLB, same silicon, 500× the reach, purely from
page size.

<Why>How many translations does 1 GB need?</Why>

If a process touches 1 GB of memory at random with 4 KB pages, it needs
262,144 different translations. No TLB holds anywhere near that many, so most
of those accesses will walk the tree. That arithmetic is behind most of the
performance story in sections 5 and 6.

<Callout label="Design implication">
Page size is the biggest lever on translation cost. That's the entire argument
for huge pages, and it's why databases and JVMs go out of their way to get
them for large, randomly accessed heaps.
</Callout>

</Sub>

<Sub n="2.3" title="Page-table isolation and every syscall">

The kernel lives in a process's page tables too. The 2018 Meltdown mitigation,
**KPTI**, unmapped most kernel pages from the user page table, so every syscall
now switches page tables and flushes translations.

That made virtual memory bookkeeping visible in ordinary application latency.
If a 2017 syscall benchmark won't reproduce on a current kernel, page-table
isolation is a likely reason.

</Sub>

the time it ends in the first step or two.

Two things in that walk matter for the rest of the chapter. A TLB hit makes
translation nearly free, and a miss costs a chain of dependent loads that no
cache-miss counter labels as translation.

</Sub>

<Sub n="3.2" title="Lazy allocation, and why malloc is a liar">

The last step is where allocation gets lazy. If a page has no entry, the kernel
gets control, so it doesn't have to find a frame until you touch the page.

<Predict
  q="On a machine with 8 GB of RAM, you call malloc(1_000_000_000) and never touch the memory. What happens?"
  options={[
    "malloc fails: not enough free RAM",

    "It succeeds after the kernel zeroes 1 GB",
    "It succeeds, and RSS grows by 1 GB straight away",
  ]}
  answer={1}
>
Nothing was allocated. The kernel recorded that a range of addresses is valid
and returned. Physical frames arrive on **first touch**, one page at a time,
so RSS only grows as your code writes to the pages.
</Predict>

Here's what happens when you do touch one of those pages:

  ]}
/>

<Why>Why zero the page first?</Why>

Because the frame last belonged to someone else. Handing it over with another
process's data in it would undo the protection from section 1.

Two consequences people meet in production:

- **Memory use appears at touch time, not allocation time.** RSS climbs while
  your code does nothing that looks like allocating.
- **Overcommit.** Linux by default hands out more address space than it can
  back. When touches eventually exceed physical memory, the OOM killer decides
  who dies, and it decides late.

<Callout label="Design implication">
A process with 40 GB of virtual memory on a 16 GB machine has *reserved*
addresses, not used RAM. A container's memory limit counts pages that really
have frames behind them, so it can be killed while the heap looks half empty.
Watch resident memory, not virtual size.
</Callout>

</Sub>

<Sub n="3.3" title="Minor and major faults">

Not every fault is the same size. The first distinction to make is whether the
kernel had to go to disk.

| Fault | What the kernel does | Cost |
|---|---|---|
| **Minor** | Finds a free frame, zeroes it and installs a mapping, or maps a page already in the page cache | About 570 ns on the M4 (section 6.1) |
| **Major** | Reads the page from disk | Tens of microseconds or more |

Minor faults are normal. A high major fault rate means you're swapping, and
nothing else you measure will make sense until it stops.

</Sub>

<SectionHeading n="04" id="fork-cow">Sharing pages: fork and copy-on-write</SectionHeading>

Per-page mappings let two address spaces point at the same physical frame.
`fork()` uses that to copy a process without copying its memory.

<Sub n="4.1" title="How Redis snapshots 50 GB">

Redis writes a snapshot by forking. The child writes the dataset to disk while
the parent keeps serving requests. Step through it:

<StepSequence
  title="fork() and copy-on-write during a Redis snapshot"
  actors={["Redis parent", "Kernel", "Child"]}
  messages={[
    { from: 0, to: 1, label: "fork()", note: "Redis forks to write a snapshot. The child gets **a copy of the page tables**, pointing at the same frames. No data is copied." },
    { from: 1, to: 2, label: "child runs", note: "The child sees the whole dataset at once, even at 50 GB, because nothing was duplicated." },
    { from: 2, to: 1, label: "reads", note: "The child reads every page to write the snapshot. Reading a shared frame costs nothing extra." },
    { from: 0, to: 1, label: "write → fault", note: "The parent keeps serving writes. Its first write to a shared page traps into the kernel." },
    { from: 1, to: 0, label: "private copy", note: "The kernel copies that one page for the parent, and the write goes ahead. **A page is only duplicated when one side writes to it.**" },
  ]}
/>

<Why>So what does a snapshot cost in memory?</Why>

One page per page the parent writes while the child is running. A mostly-read
workload barely grows. A write-heavy one can approach a second copy of the
dataset, and those copies show up as RSS climbing during code that's only
serving requests.

</Sub>

<Sub n="4.2" title="Copy-on-write with huge pages">

The copy is one page, so page size sets the bill. Before Linux 5.8, the first
write to a huge page shared after `fork()` copied all 2 MB: 512× the memory
traffic of a 4 KB page for the same logical write.

For Redis that turned a cheap snapshot into a memory spike and a latency cliff,
and "disable THP" went into every guide. Kirill Shutemov's
[commit 3917c80280c9](https://github.com/torvalds/linux/commit/3917c80280c93a7123f1a3a6dcdb10a3ea19737d)
changed that: the kernel now splits the mapping and copies 4 KB, and the commit
message names Redis as the workload it was for.

What's left is the split itself, and losing the huge page in that range until
khugepaged rebuilds it.

</Sub>

<SectionHeading n="05" id="failure">When translation gets expensive</SectionHeading>

Each piece so far has a failure mode. They share a trait: none of them shows up
where you'd first look.

<Sub n="5.1" title="TLB thrashing">

A working set that fits in cache but exceeds TLB reach performs terribly for a
reason no cache-miss counter explains.

Random access over a few hundred megabytes is the usual shape. The data may be
in L2, and every access still pays a page walk.

<Predict
  q="Your working set is 200 MB, fits in L3, and random access is still slow. With 4 KB pages, which counter do you expect to be high?"
  options={[
    "cache-misses",
    "dTLB-load-misses",
    "major page faults",
    "context-switches",
  ]}
  answer={1}
>
Two hundred megabytes is roughly 50,000 pages at 4 KB, far past any TLB's entry
count. A random pattern pays a page walk almost every time even though the data
itself is cached. Cache-miss counters look fine, and the code looks fine.
</Predict>

The symptom is `dTLB-load-misses` high while `cache-misses` looks reasonable.
Fix it with huge pages, or by making the access pattern sequential so one
translation serves many accesses.

</Sub>

<Sub n="5.2" title="Huge pages, and their cost">

Transparent huge pages (THP) promote 2 MB regions automatically. Reach improves
enormously. Two costs come with it:

| Cost | What happens | Still true? |
|---|---|---|
| **Compaction stalls** | Finding a contiguous 2 MB physical region can require compaction, which can stall the faulting thread for milliseconds | Yes |
| **COW after fork** | The first write to a shared huge page copied 2 MB | Fixed in Linux 5.8 (section 4.2) |
| **RSS bloat on sparse data** | A sparse heap touching one byte per huge page holds 2 MB for each | Yes |

<Callout label="Common mistake" kind="warn">
Following "disable THP" without checking why. Plenty of database guides still
say it, and some of their reasons outlived the kernel that justified them.
[The optimisation every database tells you to turn off](/blog/transparent-huge-pages)
goes through which ones still hold.
</Callout>

</Sub>

<Sub n="5.3" title="Fragmentation you cannot see">

A 16 KB page holding one live 32-byte object is 16 KB of resident memory.

A long-running process with a scattered live set can hold far more RSS than the
sum of its live allocations. No allocator statistic will show it, because the
allocator's own accounting is correct. Chapter 05 covers the allocator side of
this.

</Sub>

<Sub n="5.4" title="What you give up">

Every benefit in this chapter has a bill, and each arrives somewhere different.

| You get | You pay | When the bill arrives |
|---|---|---|
| A private, contiguous-looking address space | A translation on every access | As TLB misses nobody profiles for |
| Allocate now, commit later | RSS grows while your code appears idle | When the OOM killer arrives, late |
| Huge pages, 500× the reach | Compaction stalls, RSS bloat on sparse data | The first fault that has to compact memory |
| Per-page protection and sharing | Page-granular internal fragmentation | As RSS far above your live set |

</Sub>

<SectionHeading n="06" id="cost">What a page fault costs</SectionHeading>

<Callout label="The machine" kind="note">
Apple M4, macOS 26.5.1, clang 21 `-O2`, 16 KB pages. TLB numbers come from a
dependent pointer chase touching exactly one line per page, so translation is
on the critical path.
</Callout>

<Sub n="6.1" title="A minor page fault">

<Cost items={[

  { what: "Second touch, page resident", value: "116 ns", source: "same loop, same stride, immediately after" },
  { what: "Incremental cost of the fault itself", value: "≈ 570 ns", source: "difference of the two rows" },

<Why>Why is a resident write 116 ns?</Why>

Be careful reading the second row. It's high because the loop strides 16 KB,
so every access is a cache miss and probably a TLB miss too.

Subtracting it gives roughly 570 ns for the kernel's fault handling: trap, find
a frame, zero 16 KB, install a PTE, return. Zeroing alone is a meaningful share
of that.

</Sub>

<SectionHeading n="07" id="operating">Seeing translation pressure</SectionHeading>

<Sub n="7.1" title="What to look at">

```shell
# Is it translation or data?
perf stat -e dTLB-load-misses,dtlb_load_misses.walk_active,page-faults ./app

# Minor versus major faults. Major means disk
/usr/bin/time -v ./app | grep -i fault

# What's actually mapped, and how much is resident
cat /proc/$PID/smaps_rollup          # Linux
vmmap $PID | tail -30                # macOS

# Huge page status
cat /sys/kernel/mm/transparent_hugepage/enabled
grep -i huge /proc/meminfo
```

</Sub>

<Sub n="7.2" title="Reducing translation pressure">

1. **Shrink the working set.** Same advice as chapter 02, and it helps twice
   here: fewer pages means fewer translations.
2. **Make access sequential.** One translation then serves many accesses within
   the page.
3. **Consider huge pages** for large, long-lived, randomly accessed regions. A
   database buffer pool is the textbook case. Check whether you `fork()` first.
4. **Pre-fault if latency matters.** `MAP_POPULATE` or a warm-up pass moves the
   fault cost off the critical path.

</Sub>

<Sub n="7.3" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| `dTLB-load-misses` high, `cache-misses` fine | Working set past TLB reach | Huge pages, or sequential access |
| RSS climbs while the code does nothing that allocates | First touch of reserved pages, or copy-on-write after `fork()` | Expected; pre-fault with `MAP_POPULATE` if latency matters |
| Everything slow, measurements make no sense | High major fault rate: swapping | Stop the swapping first |
| Millisecond stalls on page faults | THP compaction | Check `transparent_hugepage/enabled`; use `madvise` for chosen regions |
| Memory spike during a fork-based snapshot | Huge-page COW on a kernel before 5.8 | Upgrade, or disable THP for that process |
| RSS far above the live set | Page-granular fragmentation | Chapter 05's mitigations |

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **Every address your program uses is virtual.** Hardware translates it, page
   by page, through a table the kernel keeps for each process.
2. **Translation fixes collisions, protection and contiguity** with one
   mechanism: each process can only reach the frames in its own table.
3. **Page tables are trees.** Absent branches cost nothing, so a process can
   reserve terabytes and consume kilobytes.
4. **The TLB makes translation nearly free, until it misses.** Reach is entries
   × page size; 2 MB pages give the same TLB 500× the reach of 4 KB ones.
5. **Allocation is lazy.** `malloc` reserves addresses; frames arrive on first
   touch, one minor fault at a time, about 570 ns each on the M4.
6. **Major faults mean disk.** A high major fault rate means swapping, and
   nothing else you measure will make sense.
7. **`fork()` copies page tables, not pages.** A page is duplicated only when
   one side writes to it.
8. **Huge-page COW copied 2 MB before Linux 5.8.** Since then it splits and
   copies 4 KB, so check which reasons for "disable THP" still apply.
9. **TLB thrashing hides from cache counters.** Look at `dTLB-load-misses`, not
   just `cache-misses`.
10. **Page size isn't always 4 KB.** Apple Silicon uses 16 KB; query it.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Find your machine's TLB reach.**

- `mmap` an anonymous region and touch one byte per page, chasing pointers in a
  random page order so each translation is on the critical path.
- Sweep from 4 pages to 16,384 and plot ns per access.
- On Linux, run it under `perf stat -e dTLB-load-misses` so you can prove the
  knee is translation and not cache, the thing I couldn't do cleanly on macOS.
- Then enable huge pages with `madvise(MADV_HUGEPAGE)` and rerun.

The huge-page run should push the knee out by roughly the page size ratio. Watch
the first-touch cost go up at the same time, and you'll have both halves of the
trade in your own numbers.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why does malloc of a gigabyte succeed on a machine with less free RAM?">
Because allocation reserves addresses, not physical memory. The kernel records
that a range is valid and returns immediately. Physical frames arrive on first
touch, one page at a time, via minor faults. That's also why resident memory
climbs later, during code that isn't obviously allocating.
</QA>

<QA level="intermediate" q="What is TLB reach and why do huge pages help?">
Reach is entries × page size: how much memory you can touch before
translations start missing. A TLB with 1,500 entries covers about 6 MB with
4 KB pages and about 3 GB with 2 MB pages. Same hardware, 500× the reach.

That's why databases and JVMs with large heaps chase huge pages: a random
access pattern over a multi-gigabyte buffer pool misses the TLB on nearly every
access otherwise.
</QA>

<QA level="intermediate" q="Minor fault versus major fault?">
A minor fault needs no I/O. The kernel finds a free frame, zeroes it and
installs a mapping, or maps a page already in the page cache. I measured about
570 ns of incremental cost for one on an M4.

A major fault reads from disk and costs tens of microseconds at best. A high
major fault rate means swapping, and no other measurement you take will be
meaningful until it stops.
</QA>

<QA level="deep" q="Why did Redis tell you to disable transparent huge pages, and is the reason still true?">
Redis forks for snapshots and relies on copy-on-write to keep that cheap. Before
Linux 5.8, a parent's write to a huge page copied the full 2 MB: 512× the memory
traffic of a 4 KB page for the same logical write, so a snapshot turned into a
memory spike and a latency cliff.

Since 5.8 the kernel splits the huge page and copies 4 KB, so that particular
reason is gone on a modern kernel. Two remain: compaction stalls when a
contiguous 2 MB region has to be assembled at fault time, and RSS bloat when a
sparse heap touches one byte per huge page. A good answer names the kernel
version.
</QA>

<QA level="deep" q="Your working set is 200 MB, fits in L3, and random access is still slow. What do you check?">
TLB misses. Two hundred megabytes is roughly 50,000 pages at 4 KB, far past any
TLB's entry count, so a random access pattern pays a page walk almost every
time even though the data itself is cached. Cache-miss counters look fine and
the code looks fine.

Check `dTLB-load-misses` against `dTLB-loads`. If that ratio is high, try huge
pages, or restructure so access is sequential within a page.
</QA>

<Quiz>
  <Q q="What is the base page size on Apple Silicon?">
    16 KB, not 4 KB. It changes TLB reach, fragmentation and fault counts, so
    query it instead of assuming the x86 value.
  </Q>
  <Q q="RSS is climbing but your code is only reading. How?">
    Copy-on-write, or first-touch of pages mapped earlier. Reserved address
    space becomes resident when touched, not when allocated.
  </Q>
  <Q q="Why can a page table for a 128 TB address space fit in a few kilobytes?">
    It's a radix tree and absent branches simply don't exist. Only populated
    regions cost anything.
  </Q>
  <Q q="Huge pages fixed your TLB misses and your fork-based snapshot got much worse. Why?">
    On a kernel older than 5.8, COW copies 2 MB per faulting write instead of
    4 KB. On 5.8 and later the huge page is split and only 4 KB is copied, so
    look at compaction stalls and khugepaged instead.
  </Q>
</Quiz>
