Start with a computer that has no virtual memory, because for a long time
that's how computers were built, and its problems are the reason everything in
this chapter exists.

On that machine an address is just a position in the RAM chips. Address
`0x1000` is byte 4,096 of physical memory, whoever asks for it. With one
program running, that's fine. Try to run two and three problems show up almost
at once:

- **They collide.** Both programs were compiled to expect their code and data
  at particular addresses, and two programs can't both own `0x1000`.
- **Nothing protects them from each other.** A stray pointer in your editor can
  overwrite your compiler's data, or the operating system's.
- **Memory has to be contiguous and real.** A program needs one unbroken block
  of free RAM as big as it might ever use, even if most of it sits idle.

Virtual memory fixes all three with one idea: put a translation step between
the address a program uses and the address the RAM sees. Your program says
`0x1000`, and the hardware looks up where the kernel has put *this process's*
`0x1000`. Another process's `0x1000` goes somewhere else. The addresses a
program sees are **virtual**; the ones the RAM sees are **physical**.

Translating every byte separately would need a table as big as memory, so the
hardware translates in fixed-size chunks called **pages**, 4 KB on most x86-64
Linux machines. An address splits into two parts: which page, and where inside
it. With 4 KB pages the low 12 bits are the offset, so virtual address
`0x3A7C` is page `0x3`, offset `0xA7C`. If this process's **page table** says
page 3 lives in physical frame `0x51`, the load goes to `0x51A7C`. The offset
never changes; only the page number is swapped.

Why does that fix collisions and protection? Because each process gets its own
table and can only reach the frames listed in it. It fixes the contiguity problem
too: consecutive virtual pages can sit in frames scattered all over RAM.

It creates a new problem, though. Where does the page table live? In memory,
so every load would need another load first to find out where to go. Processors avoid that
with a small cache of recent translations, the **TLB**. A quick question before
going on: if a process touches 1 GB of memory at random, how many different
translations does it need? With 4 KB pages it's 262,144, and no TLB holds
anywhere near that many. That arithmetic is behind most of the performance
story in section 5.

One more consequence falls out for free. If a page has no entry in the table,
the hardware can't translate the address, so it stops and hands control to the
kernel. That's a **page fault**, and it's how allocation can be lazy. The
kernel records that you reserved the memory and only finds a physical frame the
first time you touch each page. That's why `malloc` of a gigabyte can return
instantly on a machine with 8 GB free, and why the bill arrives later, one
fault at a time. On this machine each of those faults costs about **570
nanoseconds**, measured in section 5.1.

With that model, some behaviour that looks broken turns out to be normal. A
process with 40 GB of virtual memory on a 16 GB machine has *reserved*
addresses, not used RAM. A container's memory limit counts pages that really
have frames behind them, so it can be killed while the heap looks half
empty. And Redis can snapshot a 50 GB dataset by calling `fork()`, because
the child gets a copy of the page tables pointing at the same frames, and a
page is only duplicated when one side writes to it.

The rest of the chapter makes each of those pieces precise: what the contract
is, how the tables are laid out, what happens on every access, where it goes
wrong, what it costs and how to watch it in production.

<SectionHeading n="01" cmd="cat /proc/self/maps" id="contract">The three things you're buying</SectionHeading>

So the contract comes down to three things, and most people only notice the
first.

- **A private address space.** Your pointers mean nothing in another process.
- **More address space than RAM.** Allocation reserves addresses; physical
  pages arrive later, or never.
- **Protection and sharing.** Per-page permissions, and one physical page
  mappable into many address spaces at different addresses.

What it doesn't sell you is free translation. Every load and store needs a
virtual-to-physical lookup, and section 5 measures what happens when those
lookups stop hitting their cache.

<Callout label="The size that is probably not what you think">
Page size is 4 KB on x86-64 Linux and **16 KB on Apple Silicon**. That changes
the arithmetic for TLB reach, for internal fragmentation, and for how many
pages your allocation actually touches. Query it — `getconf PAGE_SIZE` — instead of
assuming.
</Callout>

<SectionHeading n="02" cmd="getconf PAGE_SIZE" id="layout">A tree, and the cache in front of it</SectionHeading>

<Sub n="2.1" title="A page table is a tree">

Mapping every address individually would need a table bigger than memory. So
the address is split into fields that index successive levels of a radix tree,
and only populated branches exist.

A miss in the translation cache means walking that tree: four dependent memory
accesses, each of which can itself miss cache. That's the cost section 5
isolates.

</Sub>

<Sub n="2.2" title="The TLB, and the word 'reach'">

Walking the tree on every access would be unusable, so translations are cached
in the **TLB**. The number that matters is **reach** — entries × page size —
because that's how much memory you can touch before translations start missing.

Look at rows one and two. Same TLB, same silicon, 500× the reach, purely
from page size. That's the entire argument for huge pages, and it's why
databases and JVMs go out of their way to get them.

</Sub>

<Sub n="3.2" title="Lazy allocation, and why malloc is a liar">

`malloc(1_000_000_000)` usually succeeds instantly on a machine with 8 GB of
RAM. Nothing was allocated. The kernel recorded that a range of addresses is
valid and returned.

Physical pages arrive on **first touch**. Your first write to each page traps
into the kernel, which finds a free frame, zeroes it, installs a page table
entry, and returns to re-execute your instruction. That's a **minor fault** —
no disk involved — and section 5 measures it.

Two consequences people meet in production:

- **Memory use appears at touch time, not allocation time.** RSS climbs while
  your code does nothing that looks like allocating.
- **Overcommit.** Linux by default hands out more address space than it can
  back. When touches eventually exceed physical memory, the OOM killer decides
  who dies, and it decides late.

</Sub>

<SectionHeading n="04" cmd="grep -i huge /proc/meminfo" id="failure">Running out of TLB reach</SectionHeading>

<Sub n="4.1" title="TLB thrashing">

A working set that fits in cache but exceeds TLB reach performs terribly for a
reason no cache-miss counter explains. Random access over a few hundred
megabytes is the usual shape: the data may be in L2, and every access still
pays a page walk.

Symptom: `dTLB-load-misses` high while `cache-misses` looks reasonable. Fix
with huge pages, or by making the access pattern sequential so one translation
serves many accesses.

</Sub>

<Sub n="4.2" title="Huge pages, and their cost">

Transparent huge pages promote 2 MB regions automatically. Reach improves
enormously. Two costs come with it:

- **Fragmentation and stalls.** Finding a contiguous 2 MB physical region can
  require compaction, and that can stall the faulting thread for milliseconds.
- **Copy-on-write used to get 512× more expensive.** Before Linux 5.8, the
  first write to a huge page shared after `fork()` copied all 2 MB. Kirill
  Shutemov's [commit 3917c80280c9](https://github.com/torvalds/linux/commit/3917c80280c93a7123f1a3a6dcdb10a3ea19737d)
  changed that: the kernel now splits the mapping and copies 4 KB, and the
  commit message names Redis as the workload it was for. What's left is the
  split itself, and losing the huge page in that range until khugepaged
  rebuilds it.

Plenty of database guides still say to disable THP, and some of their reasons
outlived the kernel that justified them. [The optimisation every database tells
you to turn off](/blog/transparent-huge-pages) goes through which ones still hold.

</Sub>

<Sub n="4.3" title="Fragmentation you cannot see">

A 16 KB page holding one live 32-byte object is 16 KB of resident memory. A
long-running process with a scattered live set can hold far more RSS than the
sum of its live allocations, and no allocator statistic will show it, because
the allocator's own accounting is correct.

</Sub>

<Callout label="The machine" kind="note">
Apple M4, macOS 26.5.1, clang 21 `-O2`, 16 KB pages. TLB numbers come from a

</Callout>

<SectionHeading n="06" cmd="cat /proc/$PID/smaps_rollup" id="operating">Seeing translation pressure</SectionHeading>

<Sub n="6.1" title="What to look at">

```shell
# Is it translation or data?
perf stat -e dTLB-load-misses,dtlb_load_misses.walk_active,page-faults ./app

# Minor versus major faults — major means disk
/usr/bin/time -v ./app | grep -i fault

# What's actually mapped, and how much is resident
cat /proc/$PID/smaps_rollup          # Linux
vmmap $PID | tail -30                # macOS

# Huge page status
cat /sys/kernel/mm/transparent_hugepage/enabled
grep -i huge /proc/meminfo
```

**Minor versus major faults is the first distinction to make.** Minor faults
are the ~570 ns above and are normal. Major faults touch disk and cost tens of
microseconds or more; a high major fault rate means you're swapping and nothing
else you measure will make sense.

</Sub>

<Sub n="6.2" title="Reducing translation pressure">

1. **Shrink the working set.** Same advice as chapter 02, and it helps twice
   here — fewer pages means fewer translations.
2. **Make access sequential.** One translation then serves many accesses within
   the page.
3. **Consider huge pages** for large, long-lived, randomly accessed regions —
   a database buffer pool is the textbook case. Check whether you `fork()`
   first.
4. **Pre-fault if latency matters.** `MAP_POPULATE` or a warm-up pass moves the
   fault cost off the critical path.

</Sub>

<SectionHeading n="07" cmd="git init ./weekend-project" id="build">Build this</SectionHeading>

**Find your machine's TLB reach.**

- `mmap` an anonymous region and touch one byte per page, chasing pointers in a
  random page order so each translation is on the critical path.
- Sweep from 4 pages to 16,384 and plot ns per access.
- On Linux, run it under `perf stat -e dTLB-load-misses` so you can prove the
  knee is translation and not cache — the thing I couldn't do cleanly on macOS.
- Then enable huge pages with `madvise(MADV_HUGEPAGE)` and rerun.

The huge-page run should push the knee out by roughly the page size ratio. Watch
the first-touch cost go up at the same time, and you'll have both halves of the
trade in your own numbers.

<SectionHeading n="10" cmd="./drill --level all" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Why does malloc of a gigabyte succeed on a machine with less free RAM?">
Because allocation reserves addresses, not physical memory. The kernel records
that a range is valid and returns immediately. Physical frames arrive on first
touch, one page at a time, via minor faults. That's also why resident memory
climbs later, during code that isn't obviously allocating.
</QA>

<QA level="intermediate" q="What is TLB reach and why do huge pages help?">
Reach is entries × page size — how much memory you can touch before
translations start missing. A TLB with 1,500 entries covers about 6 MB with
4 KB pages and about 3 GB with 2 MB pages. Same hardware, 500× the reach.

That's why databases and JVMs with large heaps chase huge pages: a random
access pattern over a multi-gigabyte buffer pool misses the TLB on nearly every
access otherwise.
</QA>

<QA level="intermediate" q="Minor fault versus major fault?">
A minor fault needs no I/O — the kernel finds a free frame, zeroes it and
installs a mapping, or maps a page already in the page cache. I measured about
570 ns of incremental cost for one on an M4.

A major fault reads from disk and costs tens of microseconds at best. A high
major fault rate means swapping, and no other measurement you take will be
meaningful until it stops.
</QA>

<QA level="deep" q="Why did Redis tell you to disable transparent huge pages, and is the reason still true?">
Redis forks for snapshots and relies on copy-on-write to keep that cheap. Before
Linux 5.8, a parent's write to a huge page copied the full 2 MB: 512× the memory
traffic of a 4 KB page for the same logical write, so a snapshot turned into a
memory spike and a latency cliff.

Since 5.8 the kernel splits the huge page and copies 4 KB, so that particular
reason is gone on a modern kernel. Two remain: compaction stalls when a
contiguous 2 MB region has to be assembled at fault time, and RSS bloat when a
sparse heap touches one byte per huge page. A good answer names the kernel
version.
</QA>

<QA level="deep" q="Your working set is 200 MB, fits in L3, and random access is still slow. What do you check?">
TLB misses. Two hundred megabytes is roughly 50,000 pages at 4 KB, far past any
TLB's entry count, so a random access pattern pays a page walk almost every
time even though the data itself is cached. Cache-miss counters look fine and
the code looks fine.

Check `dTLB-load-misses` against `dTLB-loads`. If that ratio is high, try huge
pages, or restructure so access is sequential within a page.
</QA>

<Quiz>
  <Q q="What is the base page size on Apple Silicon?">
    16 KB, not 4 KB. It changes TLB reach, fragmentation and fault counts, so
    query it instead of assuming the x86 value.
  </Q>
  <Q q="RSS is climbing but your code is only reading. How?">
    Copy-on-write, or first-touch of pages mapped earlier. Reserved address
    space becomes resident when touched, not when allocated.
  </Q>
  <Q q="Why can a page table for a 128 TB address space fit in a few kilobytes?">
    It's a radix tree and absent branches simply don't exist. Only populated
    regions cost anything.
  </Q>
  <Q q="Huge pages fixed your TLB misses and your fork-based snapshot got much worse. Why?">
    On a kernel older than 5.8, COW copies 2 MB per faulting write instead of
    4 KB. On 5.8 and later the huge page is split and only 4 KB is copied, so
    look at compaction stalls and khugepaged instead.
  </Q>
</Quiz>
