You rely on lock-free code more than you might think. Java's
`java.util.concurrent` is largely built on compare-and-swap, the LMAX Disruptor
passes messages between threads without a lock, audio software moves samples
through lock-free ring buffers, and Linux readers walk routing tables under RCU
without taking any lock.

"Lock-free" is also one of the most misunderstood terms in systems work. People
use it as a synonym for fast. It's a guarantee about *progress*, and under
contention a lock-free loop can be ten times slower than the mutex it replaced.

This chapter starts from the one weakness a mutex can't tune away, builds a
lock-free stack from compare-and-swap, and lays out the four ways to update
shared state. Then it measures where each one wins, and covers the bugs that
make this hard: ABA, reclamation and livelock.

<SectionHeading n="01" id="holder-problem">The problem with holding a lock</SectionHeading>

Chapter 13 built a mutex, and it works. It also has one weakness that no amount
of tuning removes: while a thread holds the lock, everyone else who wants it
waits for *that thread*.

<Sub n="1.1" title="A holder that stops">

If the holder gets descheduled, or takes a page fault, or is interrupted by a
signal handler that then tries to take the same lock, the waiters are stuck
until it comes back.

<Why>How bad is that, really?</Why>

Usually it's a few microseconds of latency: annoying, not fatal. But for an
audio callback that must produce samples every few milliseconds, it can be a
glitch. For a signal handler that wants the lock its own thread already holds,
it's a deadlock.

So here's a different question. Could threads update shared data without any of
them ever holding anything?

</Sub>

<Sub n="1.2" title="Compare-and-swap">

The tool is the same atomic instruction the lock was built from,
**compare-and-swap** (CAS): "if this word still holds the value I read, replace
it with my new one; otherwise tell me it changed".

Instead of locking, a thread reads the current value, computes the new one
privately, and tries to swap it in. If another thread got there first, the CAS
fails, and it reads again and retries. The work it did privately is simply
thrown away.

| | Mutex | CAS loop |
|---|---|---|
| **While updating** | Holds the lock; others wait | Holds nothing; others carry on |
| **If it's descheduled midway** | Everyone waiting is stuck | Nothing shared has changed yet |
| **When two collide** | One sleeps | One retries |

</Sub>

<SectionHeading n="02" id="cas-loop">A lock-free stack</SectionHeading>

A shared stack is the classic example, often called a **Treiber stack**. It's
short enough to follow completely.

<Sub n="2.1" title="Push, in three lines">

To push a node, a thread points the node's `next` at the current head, then
CASes the head from the old value to the new node. Almost every lock-free
structure is this pattern: read, compute, swap in if nothing changed, retry if
something did.

```cpp
void push(int v) {
    Node* n = new Node{v, head.load(std::memory_order_relaxed)};
    while (!head.compare_exchange_weak(n->next, n,
               std::memory_order_release, std::memory_order_relaxed)) {}
}
```

<Why>Why is the loop body empty?</Why>

On failure, `compare_exchange_weak` writes the current value back into
`n->next`. So the retry is already set up, and there's nothing left for the body
to do.

</Sub>

Step through two threads racing to push:

One CAS succeeds. The other sees that the head moved, fails, and retries with
the new head.

<Why>What if Thread 1 is descheduled halfway through?</Why>

Nothing happens to anyone else. Because nobody holds anything, a thread stopped
halfway through its update hasn't changed anything shared, so everyone else
carries on without it.

That property is what **lock-free** means: some thread always makes progress,
however the others are scheduled.

</Sub>

<SectionHeading n="03" id="progress">Progress, not speed</SectionHeading>

Notice what that definition doesn't say. It's a guarantee about *progress*, not
about speed, and it's easy to confuse the two.

<Sub n="3.1" title="Four progress guarantees">

<Compare
  cols={["Guarantee", "What it promises", "What it costs"]}
  rows={[
    ["Blocking", "Nothing. A suspended holder blocks everyone.", "Simplest, and often fastest under real contention."],
    ["Obstruction-free", "A thread running alone finishes.", "Livelock is permitted."],
    ["Lock-free", "At least one thread progresses, always.", "Individual threads may starve indefinitely."],
    ["Wait-free", "Every thread finishes in bounded steps.", "Usually far slower; needs helping schemes."],
  ]}
/>

Read the lock-free row twice. **The system progresses; your thread might not.**
A thread can lose a compare-exchange race forever and the algorithm is still
formally lock-free, because someone won each time.

</Sub>

<Sub n="3.2" title="What you're actually buying">

<Callout label="Design implication">
Rarely throughput. What lock-free buys is that **no thread can be descheduled
while holding anything**. That matters when a signal handler, an interrupt
context, or a real-time deadline can't tolerate an arbitrary wait. There it
isn't an optimisation; it's a correctness requirement.
</Callout>

What happens when eight threads hammer the same word? Most of them lose most of
their races and retry, and every retry is another trip for the cache line
between cores. Section 5 measures exactly that.

</Sub>

<SectionHeading n="04" id="options">Four ways to update shared state</SectionHeading>

Several threads need to update shared state. Here are the four options, from
the simplest to the strongest guarantee.

<Approach
  n="1"
  name="std::mutex"
  breaks="A holder descheduled mid-section blocks everyone. Unusable in a signal handler or interrupt context."
  bestFor="Almost everything. Notably flat under contention — see section 5 — and trivially debuggable."
>
Chapter 13 has the mechanism. For this decision what matters is that the
uncontended path is about 4 ns with no syscall, and the contended path degrades
gracefully instead of catastrophically.
</Approach>

<Approach
  n="2"
  name="A single hardware atomic"
  breaks="Only works for operations the ISA implements — add, or, exchange, compare-exchange. No good for anything compound."
  bestFor="Counters, flags, bitsets. Should be your first thought, and often isn't."
>
`fetch_add`, `fetch_or`, `exchange`. On ARMv8.1 and later these compile to one
LSE instruction that the interconnect resolves. No retry loop exists, and
section 5 shows them holding up where a CAS loop collapses.
</Approach>

<Approach
  n="3"
  name="A compare-exchange loop"
  breaks="Throughput collapses under contention — 162 ns at eight threads against a mutex's 16 ns — and reclamation becomes a research problem."
  bestFor="Low contention, or where blocking is a correctness problem. The Treiber stack and most lock-free structures are this shape."
>
The `push` from section 2: read the current value, compute the new one, swap it
in if nothing changed, retry if something did.
</Approach>

<Approach
  n="4"
  name="Wait-free"
  breaks="Usually needs helping schemes where threads complete each other's operations. Complexity goes up sharply and throughput usually goes down."
  bestFor="Hard real-time, where a bounded worst case is the actual deliverable."
>
Every thread finishes in a bounded number of steps regardless of what others do.
Genuinely rare in production code, and you'll probably know when you need it because
someone handed you a latency budget with no asterisk.
</Approach>

<SectionHeading n="05" id="crossover">Six times faster, then ten times slower</SectionHeading>

<Callout label="The machine" kind="note">
Apple M4, 10 cores, macOS 26.5.1, clang 21 `-O2 -pthread`, median of 3 runs,
200,000 increments **per thread** so adding threads adds work. ARMv8.6 means LSE
atomics are available.
</Callout>

<Sub n="5.1" title="The measurement that decides it">

Same operation, increment a shared counter, three ways. Before you look:

The CAS loop, by a long way: 162 ns per increment, against 16.3 ns for the mutex

</Predict>

At one thread the CAS loop is **six times faster** than the mutex. At eight it's
**ten times slower**. Crossover sits at four on this machine, and the mutex

stable strategy.

`fetch_add` stays fast throughout because it never retries.

</Sub>

<Sub n="5.2" title="Why, in eleven instructions">

<SourceRead
  file="clang++ -O2 -c, disassembled with objdump"
  repo="aarch64"
  tag="Apple M4, ARMv8.6-A"
  href="https://developer.arm.com/documentation/ddi0487/latest/"
>
```asm
;; a.fetch_add(1, relaxed)  —  ONE instruction, no branch
add:
    mov   w8, #0x1
    ldadd x8, x0, [x0]        ; LSE atomic: hardware resolves it
    ret

;; compare_exchange_weak loop  —  a SOFTWARE retry branch
cas:
    ldr   x8, [x0]
    add   x10, x8, #0x1
    mov   x9, x8
.Lretry:
    cas   x9, x10, [x0]
    cmp   x9, x8
    b.eq  .Ldone
    mov   x8, x9
    add   x10, x9, #0x1
    b     .Lretry             ;        GO ROUND AGAIN
```
</SourceRead>

A losing core in the `ldadd` case re-executes nothing; the interconnect sorts it
out. A losing thread in the CAS case reloads, recomputes and branches back.
Step through one losing attempt:

</Sub>

<Callout label="Common mistake" kind="warn">
Writing a CAS loop for something a single hardware atomic does. A counter, a
flag or a bitset wants `fetch_add` or `fetch_or`, which never retries. The CAS
loop version is the 162 ns row.
</Callout>

</Sub>

<SectionHeading n="06" id="hard-parts">ABA, reclamation, livelock and ordering</SectionHeading>

Writing a lock-free stack takes an afternoon. The bugs are in four places, and
the famous ones are in the first two.

<Sub n="6.1" title="ABA">

Compare-exchange compares a *value*, not a history. If a pointer goes from A to
B and back to A, the CAS succeeds and the algorithm is wrong.

<StepSequence
  title="ABA: the head is A again, but not the same A"
  actors={["Thread 1", "stack head", "Thread 2"]}
  messages={[
    { from: 1, to: 0, label: "read head → A", note: "Thread 1 starts a pop. It reads head **A** and A's `next`, and plans `CAS(A → A.next)`. Then it's descheduled." },
    { from: 2, to: 1, label: "pop A", note: "Thread 2 pops A. The head is now **B**." },
    { from: 2, to: 1, label: "pop B, free A", note: "Thread 2 pops B and frees A. The head is now **C**." },
    { from: 2, to: 1, label: "push A (reused address)", note: "A new node is allocated at A's old address and pushed. The head is **A again**." },
    { from: 0, to: 1, label: "CAS(A → A.next) ✓", note: "Thread 1 wakes. Its CAS sees A and **succeeds**, but the `next` it read is stale garbage. The stack now points at freed memory." },
  ]}
/>

Fixes, roughly: a **tagged pointer**, pairing the address with a counter in one
wide CAS so the value differs even when the address repeats. Or never reusing
memory until you can prove nobody holds a reference, which is the harder problem
below.

</Sub>

<Sub n="6.2" title="When can you free a node?">

A thread reads `head`, gets pointer `A`, and is descheduled before dereferencing
it. Another thread pops and deletes `A`. The first wakes and reads freed memory.

<Why>Why is this so much harder than with a lock?</Why>

There's no lock to hold, and no obvious moment when `A` becomes safe to free.
Freeing a lock-free stack's nodes safely is a research area. Schemes exist to
answer "when can I free this?":

<Compare
  cols={["Scheme", "Read cost", "Fails when"]}
  rows={[
    ["Hazard pointers", "A store plus a fence per read", "Reclaimer must scan every thread's slots"],
    ["Epoch-based", "Nearly free", "One stalled thread blocks reclamation for everyone"],
    ["RCU", "Literally zero on many builds", "Writers serialise; bad for write-heavy data"],
  ]}
/>

Linux's **RCU** (read-copy-update) is the most successful lock-free technique in
production anywhere. It protects the kernel's routing tables, dentry cache and
much else. Readers take no atomics at all on many configurations; writers wait
for a grace period before freeing. It works by making reads free and pushing all
the cost onto writers.

**crossbeam-epoch** is Rust's standard answer to reclamation, and why lock-free
structures are approachable in that ecosystem. The stalled-thread failure mode
in the table is documented directly in its guide, and the epoch bookkeeping is
clearer there than in most C++ implementations.

<Callout label="Common mistake" kind="warn">
Assuming you can just free popped nodes. The code works in light testing and
then crashes intermittently and unhelpfully under load, because the
use-after-free depends on one thread being descheduled at exactly the wrong
moment.
</Callout>

</Sub>

<Sub n="6.3" title="Livelock that looks like healthy CPU">

Under heavy contention, threads can spend most of their time losing
compare-exchanges. The algorithm keeps its lock-free guarantee while aggregate
throughput collapses.

<Why>Why doesn't profiling catch it?</Why>

Because **it looks like healthy CPU utilisation.** A blocked thread shows as
off-CPU time and turns up in `perf sched`. A thread spinning in a CAS retry loop
is 100% on-CPU, and appears in a flame graph as a hot function someone will
conclude is "just expensive".

Count instructions retired against operations completed. If you finished a
million pushes but retired six million loop bodies, that's your answer, and no
flame graph would have shown it.

</Sub>

<Sub n="6.4" title="Dropping release ordering because x86 didn't care">

The `memory_order_release` in the push above is load-bearing. Downgrade it to
`relaxed` and the code compiles, passes light testing, and fails on a weakly
ordered machine under load. Another core can observe the new head pointer while
the node's fields are still in the writing core's store buffer.

x86-64 hides that almost perfectly. Chapter 03 has the detail; the operational
advice is to run your tests on ARM.

</Sub>

<SectionHeading n="07" id="choosing">Choosing, in five questions</SectionHeading>

<Sub n="7.1" title="The five questions">

Most decisions are settled by the first two.

1. **Can you not share the thing at all?** Per-thread state with a periodic
   merge beats every algorithm here. Try this first, always.
2. **Is there a single hardware atomic for it?** Counters, flags and bitsets
   want `fetch_add` or `fetch_or`, never a CAS loop.
3. **Is contention low, or the critical section long?** Use a mutex.
4. **Is blocking a correctness problem?** Signal handler, interrupt, hard
   real-time: then lock-free, and use an existing implementation.
5. **Otherwise measure both.** The crossover is machine-specific and the table
   in section 5 is probably one data point on one unusual laptop.

</Sub>

<Sub n="7.2" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| CAS loop at 100% CPU, throughput falling as threads are added | Livelock: most attempts lose | `fetch_add` if one atomic will do; otherwise a mutex |
| Intermittent crashes after pops, under load only | A node freed while another thread still held a pointer | Hazard pointers, epochs or RCU |
| A pop returns a node that was already removed | ABA | Tagged pointer, or safe reclamation |
| Passes on x86, fails on ARM | A `relaxed` where `release` was needed | Restore release/acquire; test on ARM |
| One thread never finishes while others do | Lock-free isn't wait-free | Accept it, or pay for a wait-free design |

</Sub>

<SectionHeading n="08" id="summary">Summary</SectionHeading>

1. **A mutex's weakness is the holder.** If it stops, every waiter stops with
   it.
2. **CAS lets a thread update without holding anything.** Read, compute
   privately, swap in if unchanged, retry if not.
3. **Lock-free is a progress guarantee, not a speed claim.** Some thread always
   progresses; yours might not.
4. **Wait-free bounds every thread**, and usually costs throughput and a great
   deal of complexity.
5. **CAS loops collapse under contention.** 2.6 ns at one thread, 162 ns at
   eight, against a nearly flat mutex.
6. **84% of attempts were thrown away at eight threads**, and each still paid
   for a cache line transfer.
7. **A single hardware atomic never retries.** `fetch_add` compiles to one
   `ldadd` on ARMv8.1 and later.
8. **ABA happens because CAS compares values, not history.** A reused address
   passes the check.
9. **Reclamation is the hard half.** Hazard pointers, epochs and RCU each trade
   read cost against a failure mode.
10. **Try not sharing first.** Per-thread state with a periodic merge beats
    every algorithm in this chapter.

<SectionHeading n="09" id="build">Build this</SectionHeading>

**Write the Treiber stack, then break it on purpose.**

- Implement `push` and `pop` with `compare_exchange_weak`. Thirty lines.
- Free popped nodes immediately, run eight threads, and watch it crash
  intermittently and unhelpfully. That's section 6.2, experienced instead of
  read.
- Add a retry counter. Print attempts-per-success at 1, 2, 4 and 8 threads, and
  find **your** crossover against a `std::mutex` stack.
- Then implement epoch reclamation and measure what the read path now costs.

The number to hunt is where your two curves cross. Mine was four threads; yours
is probably somewhere else, and knowing which side of it you're on is the whole
decision.

<SectionHeading n="10" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="Does lock-free mean faster?">
No. It's a progress guarantee: at least one thread always progresses, so no
thread can be blocked by another being descheduled. Under real contention a
mutex is often faster.

On an M4 I measured a CAS retry loop at 2.6 ns with one thread against a mutex
at 15.6 ns, and at eight threads those became 162 ns and 16.3 ns. The lock-free
version was ten times slower.
</QA>

<QA level="intermediate" q="What is ABA and why doesn't compare-exchange catch it?">
Compare-exchange compares a value, not a history. A pointer goes from A to B and
back to A while your thread is descheduled; your CAS sees A, succeeds, and
installs a `next` pointer you read before any of that happened.

The classic fix is a tagged pointer (address plus a monotonically increasing
counter in a single wide compare-exchange) so the value differs even when the
address repeats.
</QA>

<QA level="intermediate" q="Why can a lock-free algorithm starve a thread?">
Because the guarantee is system-wide, not per-thread. Lock-freedom requires that
*someone* completes; nothing says it can't always be someone else. A thread that
keeps losing its compare-exchange makes no progress while the algorithm remains
formally lock-free.

Wait-freedom is the stronger property that bounds each thread's steps, and it
usually costs enough that people don't.
</QA>

<QA level="deep" q="Why is fetch_add so much faster than a compare_exchange loop under contention?">
They compile to different things. On ARMv8.1 and later `fetch_add` becomes a
single LSE instruction, `ldadd`, and the interconnect resolves contention
without the core re-executing anything. A `compare_exchange_weak` loop compiles
to a `cas`, a compare and a backward branch, so a losing thread re-reads,
recomputes and retries in software.

At eight threads I measured 6.36 attempts per successful increment: 84% of work
discarded, each discarded attempt still paying a cache line transfer. That's the
difference between 18 ns and 162 ns.
</QA>

<QA level="deep" q="You have a lock-free queue. Why can't you just delete popped nodes?">
Another thread may hold a pointer it read before you popped. There's no lock and
no obvious moment the node becomes unreachable, so freeing creates a
use-after-free that's timing-dependent and nearly impossible to reproduce.

You need a reclamation scheme. Hazard pointers publish in-use pointers per
thread and cost a store and a fence on every read. Epoch reclamation is cheaper
to read but a thread stalled inside an epoch blocks all reclamation and memory
grows until it leaves. RCU makes reads free and defers everything to writers,
which only works if you're overwhelmingly read-mostly.
</QA>

<SectionHeading n="11" id="resources">Go deeper</SectionHeading>

<Quiz>
  <Q q="Your CAS loop is at 100% CPU and throughput is falling. Deadlock or livelock?">
    Livelock. Deadlock consumes no CPU. Threads burning cycles losing races look
    identical to useful work in a flame graph, so check attempts per success.
  </Q>
  <Q q="Why does dropping release to relaxed pass on x86 and fail on ARM?">
    x86-64 is strongly ordered and won't reorder the stores publishing the node.
    ARM is weakly ordered, so another core can see the new head before the
    node's fields.
  </Q>
  <Q q="When is a tagged pointer not enough to fix ABA?">
    When the counter wraps. With a 16-bit tag on a hot structure, 65,536
    operations is maybe a millisecond.
  </Q>
  <Q q="What's the first thing to try before any of this?">
    Not sharing. Per-thread state with a periodic merge beats every algorithm in
    the chapter, and it's the option people skip past fastest.
  </Q>
</Quiz>
