Every backend engineer runs into the network stack eventually. A load balancer
reports timeouts your application never logged. A Kubernetes node stops
accepting new connections while old ones carry on. A UDP metrics collector
quietly loses a tenth of what it's sent.

In each case the packet reached the machine and the kernel threw it away,
before your code ran. Knowing the path a packet takes, and the queues along it,
turns those mysteries into a counter you can read.

This chapter follows one packet from the network card to your `read()` call,
then one back out. Along the way it shows where each queue sits, how it
overflows, where the drop is counted, and which setting fixes it.

<SectionHeading n="01" id="why-a-stack">Why the kernel needs a network stack</SectionHeading>

A network card delivers **frames**: a few hundred to a few thousand bytes each,
with headers for Ethernet, IP and TCP stacked in front of the payload. They
arrive out of order, some are duplicated, and some never arrive at all.

Your program wants something far simpler: a stream of bytes, in order, from one
other program. Everything in between is the kernel's network stack. It
reassembles, reorders, acknowledges and retransmits for every socket on the
machine, so that each application sees a clean stream.

<Sub n="1.1" title="What the stack promises you">

What you're promised depends on the protocol you ask for.

| Protocol | What you're promised | What you're not |
|---|---|---|
| **TCP** | An ordered, reliable byte stream per socket | How long it takes, or how much gets retransmitted |
| **UDP** | Each datagram arrives intact, or not at all | That it arrives, arrives once, or arrives in order |

<Why>Why doesn't TCP's reliability mean nothing gets dropped?</Why>

Because reliability is about the *stream*, not the *packets*. TCP hides loss by
retransmitting, so a dropped packet costs you time, not data. UDP doesn't hide
it at all.

Neither promise says anything about how many packets the kernel may throw away
along the way. And it throws away a lot, every time a queue fills up.

<Callout label="Design implication">
"The network dropped it" is rarely the right diagnosis. Most drops happen
inside the receiving machine, in a queue with a fixed size and a counter you can
read. Section 3 lists all of them.
</Callout>

</Sub>

<SectionHeading n="02" id="receive-path">The receive path, step by step</SectionHeading>

A network card receives frames off the wire and turns them into bytes. Your
program, somewhere above, calls `read()` and gets the payload. It's easiest to
understand the path between them by starting from the naive version and fixing
it.

<Sub n="2.1" title="From the wire to memory">

In the naive design, the card interrupts the CPU for every packet and let
the kernel copy it in. That works at dial-up speeds.

<Why>Why not one interrupt per packet?</Why>

Because of the numbers. A 10 Gbit/s link can carry close to **15 million
minimum-size frames a second** (section 7 works it out). A core taking an
interrupt for each one would do nothing else.

So modern drivers make two changes:

- **DMA into a ring.** It owns a ring of descriptors, each pointing at a
  buffer the driver allocated in advance. It writes each frame into the next free
  buffer by itself. No CPU touches the bytes.
- **Poll instead of interrupt.** The driver takes one interrupt, switches
  further interrupts off, and polls the ring in batches until it's empty. Linux
  calls this **NAPI** (the "new API"; LWN's [history](https://lwn.net/Articles/244640/)
  is still the best account).

touch the packet until step 3, and every hand-off between stages is a **queue
with a fixed size**.

</Sub>

<Sub n="2.2" title="The softirq budget: 300 packets at a time">

NAPI polling runs in a **softirq**: deferred interrupt work that runs on the CPU
that took the interrupt, ahead of any normal thread. Here's the loop:

<SourceRead
  file="net/core/dev.c"
  repo="torvalds/linux"
  tag="v6.10"
  href="https://github.com/torvalds/linux/blob/v6.10/net/core/dev.c#L6870"
>
```c
static __latent_entropy void net_rx_action(struct softirq_action *h)
{
	struct softnet_data *sd = this_cpu_ptr(&softnet_data);
	unsigned long time_limit = jiffies +
		usecs_to_jiffies(READ_ONCE(net_hotdata.netdev_budget_usecs));
	int budget = READ_ONCE(net_hotdata.netdev_budget);
	/* ... */
	for (;;) {
		struct napi_struct *n;
		/* ... empty-list handling ... */
		n = list_first_entry(&list, struct napi_struct, poll_list);
		budget -= napi_poll(n, &repoll);

		/* If softirq window is exhausted then punt.
		 * Allow this to run for 2 jiffies since which will allow
		 * an average latency of 1.5/HZ.
		 */
		if (unlikely(budget <= 0 ||
			     time_after_eq(jiffies, time_limit))) {
			sd->time_squeeze++;
			break;
		}
	}
	/* ... re-queue anything unfinished, re-raise the softirq ... */
```
</SourceRead>

It stops at whichever limit comes first:

| Setting | Default | Meaning |
|---|---|---|
| `netdev_budget` | 300 | Packets per softirq run, across all devices |
| `netdev_budget_usecs` | 2 jiffies (2,000 µs on the box measured) | Time per softirq run |
| `dev_weight` | 64 | Packets one device's `poll()` may take per turn |

<Why>Why have a budget at all?</Why>

Because softirqs run ahead of every thread. Without a limit, a flood of packets
could keep one CPU in softirq forever, and nothing else on that CPU would run.

When the loop runs out of budget with work still pending, it increments
`time_squeeze`. That's column three of `/proc/net/softnet_stat`, and it's the only
direct evidence that a CPU couldn't keep up with its queues.

</Sub>

<Sub n="2.3" title="sk_buff: a record about a packet">

Every packet in the kernel is a `struct sk_buff` ("socket buffer"). The key
idea is that it's *metadata about* a packet. It doesn't contain the bytes; it
points at them.

```c

	struct sock		*sk;

				data_len;
	__u16			transport_header;
	__u16			network_header;

	/* These elements must be at the end, see alloc_skb() for details.  */
	sk_buff_data_t		tail;

				*data;
	unsigned int		truesize;
	refcount_t		users;
	/* ... */
};
```
</SourceRead>

A handful of fields do most of the work:

| Field | What it's for |
|---|---|
| `next`, `prev` | Lets the skb sit on a queue with no extra allocation. Every queue in this chapter is a list of these. |
| `head`, `data`, `tail`, `end` | Bracket the real buffer. `data` moves forward as each layer strips its header, so IP never copies the Ethernet frame. |
| `mac_header`, `network_header`, `transport_header` | 16-bit offsets from `head` to each layer's header |
| `_nfct` | Conntrack's pointer to this packet's flow entry |
| `truesize` | What the socket is charged for. It isn't `len`. |

<Why>Why does truesize matter?</Why>

Because receive buffers are charged by `truesize`, not by the bytes you'll
`recv()`. In a test on Linux 6.10, a UDP socket with a 128 KB buffer held only
**158 datagrams of 100 bytes**. That's about **830 bytes of buffer per 100-byte
payload**: the skb struct and the whole slab allocation behind the data. Sizing a
UDP buffer as "buffer ÷ message size" is off by roughly 8× for small messages.

Past `end`, in the same allocation, sits `skb_shared_info` with an array of
`frags[]`, each a reference to a page. That array is how the stack avoids
copying: GRO glues packets together by appending frags, and `sendfile` hands
page-cache pages to TCP the same way.

</Sub>

<Sub n="2.4" title="Up the stack: GRO, netfilter and TCP">

Inside the driver's poll, each frame goes to `napi_gro_receive()`.

<Why>Why merge packets before processing them?</Why>

Processing costs roughly the same per packet whatever its size. **GRO**
(generic receive offload; LWN covered it in [2009](https://lwn.net/Articles/358910/))
holds packets from the same flow and merges consecutive ones into one large
skb. About forty-five 1,500-byte segments can travel up the stack as one 64 KB
skb and pay the per-packet cost once.

After that it's a chain of function calls, all still in softirq:

    { label: "tc ingress", sub: "cls_bpf, policing" },
    { label: "ip_rcv", sub: "netfilter PREROUTING: conntrack", accent: true },
    { label: "route + LOCAL_IN", sub: "iptables INPUT rules" },
    { label: "tcp_v4_rcv", sub: "socket lookup by 4-tuple" },
    { label: "sk_receive_queue", sub: "then sk_data_ready()", accent: true },
  ]}
/>

At `PREROUTING`, **conntrack** looks up the packet's flow in its hash table and
creates an entry for a new flow. On a Kubernetes node running kube-proxy in
iptables mode, that happens to every packet, because service NAT depends on
connection state.

`tcp_v4_rcv()` then finds the socket. If a user thread holds the socket lock at
that moment, the skb waits on the socket's *backlog* until the lock is released.
Otherwise the fast path appends the data to `sk_receive_queue` and calls
`sk_data_ready`.

</Sub>

<Sub n="2.5" title="Waking your thread: epoll">

`sk_data_ready` wakes whoever is waiting on the socket. If you're blocked in
`read()`, that's you. If the socket is in an epoll set, epoll's callback puts
the socket on the ready list and wakes the thread in `epoll_wait()`.

<Why>Why can one connection wake every worker?</Why>

Put one listening socket in many workers' epoll sets, and a single new
connection wakes all of them: the **thundering herd**. `EPOLLEXCLUSIVE` (Linux
4.5, [man page](https://man7.org/linux/man-pages/man2/epoll_ctl.2.html)) limits
it to one waiter.

But which one? Cloudflare found that
[wake-ups go LIFO](https://blog.cloudflare.com/the-sad-state-of-linux-socket-balancing/):
the most recently added waiter gets the connection, so one NGINX worker ended up
with most of the load.

</Sub>

<SectionHeading n="03" id="drops">Where packets get dropped</SectionHeading>

Each queue on the receive path drops when it's full, and each one counts its
drops somewhere different. This is the table to keep open during an incident.

| Queue | Fills when | Where it's counted | Usual fix |
|---|---|---|---|
| **RX ring** | The CPU can't drain it fast enough | `ethtool -S eth0` | Bigger ring, spread load with RSS |
| **Per-CPU backlog** | Softirq processing falls behind (default 1,000 packets) | `/proc/net/softnet_stat` | Raise `netdev_max_backlog`, use RPS |
| **Conntrack table** | Too many tracked flows | `dmesg`: "table full" | Raise `nf_conntrack_max` |
| **Socket receive buffer** | Your app reads too slowly | `nstat` RcvbufErrors | Read faster, raise `SO_RCVBUF` |
| **Accept queue** | The app doesn't `accept()` in time | `nstat` ListenOverflows | Faster accept loop, bigger backlog |

<Sub n="3.1" title="The accept queue">

A new TCP connection passes through two queues before your application sees it.
Step through the handshake:

When the accept queue is full, Linux doesn't refuse new connections. It
silently ignores their SYNs.

The kernel drops the SYNs that don't fit. Each client retransmits after about a
second, so those users see an extra second or more of latency. Your logs show
nothing, because the requests never reached your code. `nstat` counts every one
as a ListenOverflow.
</Predict>

<Why>Why doesn't the kernel just refuse the connection?</Why>

Because a refusal is final, and a full queue is probably temporary. Dropping the
SYN lets the client's normal retry logic try again a moment later, when there
may be room.

Here's a forty-line program that makes the counter move. It listens with a
backlog of 4, never calls `accept()`, and connects twenty clients.

<Callout label="Common mistake" kind="warn">
Drop reasons, dropwatch and `perf record -e skb:kfree_skb` all miss listen
overflows, the most common TCP overload signal. For the accept queue, trust
`nstat` and `ss -ltn`, not the tracer.
</Callout>

Raising the backlog helps you ride out bursts. `somaxconn` went from 128 to 4096
in Linux 5.4 ([19f92a030ca6](https://github.com/torvalds/linux/commit/19f92a030ca6d772ab44b22ee6a01378a8cb32d4)),
and Cloudflare runs 16k ([SYN packet handling in the wild](https://blog.cloudflare.com/syn-packet-handling-in-the-wild/)).
But a full accept queue usually means the application isn't calling `accept()`
fast enough: a blocked event loop, a GC pause, a thread pool at its cap. That's
the thing to fix.

</Sub>

<Sub n="3.2" title="nf_conntrack: table full, dropping packet">

This is the one that shows up in Kubernetes postmortems. Conntrack keeps a
fixed-size table of flows. When it's full, as Cloudflare's
[Conntrack tales](https://blog.cloudflare.com/conntrack-tales-one-thousand-and-one-flows/)
puts it, "packets creating new flows will be dropped. No questions asked."

<Why>Why do old connections keep working?</Why>

Because existing flows already have an entry. Only packets that would *create*
an entry are dropped. So the symptom is new connections timing out while
dashboards for established traffic look fine.

Its default size scales with RAM. On 64-bit hosts with more than 4 GB,
`nf_conntrack_max` is 262,144
([`nf_conntrack-sysctl.rst`](https://github.com/torvalds/linux/blob/v6.10/Documentation/networking/nf_conntrack-sysctl.rst)),
and the 8 GB VM used here read exactly that. Smaller nodes get smaller tables,
which is how [loveholidays](https://deploy.live/blog/kubernetes-networking-problems-due-to-the-conntrack/)
hit it: they halved node RAM while connection counts doubled.
Mark Betz's [GKE incident](https://www.markbetz.net/2023/12/12/exhausting-conntrack-table-space-crippled-our-k8s-cluster/)
was a misbehaving CDN flooding an RPC client through Linkerd.

<Callout label="Design implication">
Conntrack is node-wide. Writing `nf_conntrack_max` from inside a pod's network
namespace returns `Permission denied`, so the fix happens on the node
([kubernetes#71261](https://github.com/kubernetes/kubernetes/issues/71261)).
Alert on `nf_conntrack_count` against `nf_conntrack_max` well before 100%.
</Callout>

</Sub>

<Sub n="3.3" title="One core pinned in softirq">

Cloudflare's [How to receive a million packets per second](https://blog.cloudflare.com/how-to-receive-a-million-packets/)
is the classic example. A single-threaded UDP receiver got about 370k packets a
second. The limit probably wasn't where you'd guess: it wasn't the application. Every packet from one source hashed to
one RX queue, so one CPU was "totally busy just reading the 350kpps."

<Why>Why doesn't adding receiver threads help?</Why>

Because the bottleneck is the softirq on the CPU that owns the queue, not the
threads reading the socket. What helped was spreading flows across more RX
queues, using `SO_REUSEPORT` for several receiving sockets, and keeping the
receiver on the NIC's NUMA node (the wrong node cost up to 4×). That got them to
1.4 million packets a second on one NUMA node.

You'll probably recognise it: `mpstat -P ALL 1` shows one CPU at 100% `%soft` and the
rest idle. On a VM with a single virtio queue you'll hit it early.

</Sub>

<Sub n="3.4" title="ksoftirqd, and a fix reverted seven years later">

To keep softirqs from starving everything, `__do_softirq()` gives up after 2 ms
or 10 restarts ([`kernel/softirq.c`](https://github.com/torvalds/linux/blob/v6.10/kernel/softirq.c#L475))
and hands the rest to the per-CPU `ksoftirqd` thread, which is scheduled like
any other thread.

That handoff has been argued about for a decade:

- **2016, Linux 4.9.** Eric Dumazet's "softirq: Let ksoftirqd do its job"
  ([4cd13c21b207](https://github.com/torvalds/linux/commit/4cd13c21b207))
  stopped softirqs sneaking back in while `ksoftirqd` ran. Under a UDP flood, the
  receiving process went from "~2,000 packets per second" to "~900,000".
- **2023, Linux 6.5.** Paolo Abeni reverted it
  ([d15121be7485](https://github.com/torvalds/linux/commit/d15121be7485))
  because deferring to a normal-priority thread caused "high latencies". The
  revert points to **threaded NAPI** (5.12) instead, which gives each NAPI
  instance its own kernel thread you can pin and prioritise.

If `top` shows `ksoftirqd/N` near 100%, the softirq budget on CPU N is
permanently exhausted. It's section 3.3 wearing a different hat.

</Sub>

<Sub n="3.5" title="The UDP receive buffer">

UDP has no flow control, so a slow reader loses data, and the sender can't
tell. Here's a socket that asks for 64 KB and never reads:

<TryIt what="A UDP socket that asks for 64 KB and never reads" lang="cpp" toolchain="g++ 13.3 -O2, linuxkit 6.10.14 aarch64">
```cpp

int want = 65536, got = 0;
socklen_t l = sizeof got;
setsockopt(rx, SOL_SOCKET, SO_RCVBUF, &want, sizeof want);
getsockopt(rx, SOL_SOCKET, SO_RCVBUF, &got, &l);
bind(rx, (sockaddr*)&a, sizeof a);             // 127.0.0.1:9001

int tx = socket(AF_INET, SOCK_DGRAM, 0);
char payload[100] = {};
for (int i = 0; i < 10000; i++)
    if (sendto(tx, payload, sizeof payload, 0, (sockaddr*)&a, sizeof a) == sizeof payload) ok++;

while (recv(rx, buf, sizeof buf, MSG_DONTWAIT) > 0) queued++;
```

<Output>
```text

sendto() succeeded 10000 times out of 10000
datagrams actually waiting in the socket: 158

UdpInErrors                     9842

```

Linux **doubles** what you ask for (`__sock_set_rcvbuf()` stores
`val * 2` to leave room for skb overhead), then charges each datagram its

For DNS servers, statsd collectors and syslog receivers, `UdpRcvbufErrors` is
the first counter to check. Raising `SO_RCVBUF` also needs `net.core.rmem_max`
raised (212,992 on this box), or the request is silently capped.

<Why>So should TCP buffers just be huge?</Why>

No. TCP can't lose data this way, but it pays in time. Cloudflare's
[story of one latency spike](https://blog.cloudflare.com/the-story-of-one-latency-spike/)
traced multi-millisecond stalls to `tcp_collapse()`, which compacts a bloated
receive queue inside softirq. Cutting the `tcp_rmem` maximum from 32 MiB took
`net_rx_action` from 23 ms to 3 ms.

</Sub>

<SectionHeading n="04" id="send-path">The send path</SectionHeading>

Sending runs the same layers in reverse, with one important difference: data
waits in the socket until TCP decides it's allowed to send it.

<Steps
  title="One write(), from your buffer to the wire"
  lanes={[
    { t: "Your app", s: "write()", icon: "◉" },
    { t: "Socket", s: "write queue", icon: "≡" },
    { t: "TCP", s: "cwnd · pacing", icon: "⇆" },
    { t: "IP + netfilter", s: "OUTPUT", icon: "⇅" },
    { t: "qdisc", s: "fq_codel · fq", icon: "▤" },
    { t: "TX ring · NIC", s: "on the wire", icon: "⌁" },
  ]}
  steps={[
    [0, "`write()` enters the kernel through `tcp_sendmsg()`, which copies your bytes into skbs. This is the one copy a normal send makes."],
    [1, "The skbs sit on the socket's **write queue**. `write()` can return now, **before anything has been sent**."],
    [2, "`tcp_write_xmit()` decides how much may go: the congestion window, the receiver's window and pacing. With TSO it builds segments up to 64 KB for the NIC to cut up."],
    [3, "`ip_queue_xmit()` adds the IP header and passes netfilter's `OUTPUT` and `POSTROUTING` hooks."],
    [4, "`dev_queue_xmit()` hands the packet to the **qdisc**, the device's queueing discipline, usually `fq_codel` or `fq` on a real NIC."],
    [5, "The driver writes a descriptor into the **TX ring** and rings the NIC's doorbell. A completion interrupt later frees the skb."],
  ]}

<Why>Why doesn't write() returning mean the data was sent?</Why>

Because `write()` only copies into the socket's write queue. Whether and when
the bytes leave depends on TCP's windows, which depend on the network and the
receiver. A successful `write()` means "the kernel has your data", nothing more.

Loopback skips the qdisc entirely. `tc -s qdisc show dev lo` reported `noqueue`
with 0 packets sent, straight after three iperf3 runs had pushed about 250 GB
through `lo`.

<SectionHeading n="05" id="scaling">Scaling across cores: RSS, RPS, RFS and SO_REUSEPORT</SectionHeading>

Everything in section 2 ran on the CPU that took the interrupt. On a busy
server, one CPU isn't enough, so Linux has four ways to spread the work. All are
documented in [`scaling.rst`](https://github.com/torvalds/linux/blob/v6.10/Documentation/networking/scaling.rst).

| Mechanism | Where it runs | What it does | Cost |
|---|---|---|---|
| **RSS** | The NIC | Hashes each flow's 4-tuple into one of several RX queues, each with its own IRQ | Free, but limited by the number of hardware queues |
| **RPS** | Software, on the receiving CPU | Hashes the packet and hands it to another CPU's backlog | An inter-processor interrupt per batch |
| **RFS** | Software | Like RPS, but picks the CPU where the reading thread last ran | Same as RPS, plus a flow table |
| **`SO_REUSEPORT`** | The socket layer (Linux 3.9, [LWN](https://lwn.net/Articles/542629/)) | Several sockets bind one port; each new flow is hashed to one of them | Uneven load if flows are uneven |

<Why>Which one should you reach for first?</Why>

RSS, if the NIC has more queues than you're using (`ethtool -l eth0`). RPS when
it doesn't: the VM measured here reported `Combined: 1`, a single virtio queue,
so every packet from outside landed on one CPU. And `SO_REUSEPORT` when the
application itself is the bottleneck, with one accept loop.

Loopback is a special case. `lo` has no ring and no IRQ. Its transmit function
drops each skb onto the *current* CPU's backlog, so loopback traffic shows up
in `softnet_stat`. During one five-second iperf3 run, the processed
column rose by 2,397,701 while `IpInReceives` rose by 2,397,255.

<SectionHeading n="06" id="bypass">Skipping copies, and skipping the stack</SectionHeading>

A normal `write()` copies once, from your memory into skb memory. And every
packet pays the full cost of the stack. Four features cut one or both:

| Feature | What it skips | Best for | Watch out for |
|---|---|---|---|
| **`sendfile()`** | Copying file data through user space | Serving static files | Only file → socket |
| **`MSG_ZEROCOPY`** (4.14) | The copy on send, by pinning your pages | Sends over about 10 KB | Completion bookkeeping; no gain on loopback |
| **XDP** | The whole stack: runs in the driver before any skb exists | DDoS drops, L4 load balancing | No sockets, no TCP, BPF limits |
| **AF_XDP** (4.18) | The stack, delivering raw frames to a user-space ring | Custom packet processing | You rebuild what the stack did |

`sendfile` is how Netflix serves video: page-cache pages go straight to the
socket, plus kernel TLS. Drew Gallatin's
[400 Gb/s talk](https://papers.freebsd.org/2021/eurobsdcon/gallatin-netflix-freebsd-400gbps.files/gallatin-netflix-freebsd-400gbps-slides.pdf)
is the reference (on FreeBSD; Linux got kTLS transmit in 4.13).

<Why>Why didn't MSG_ZEROCOPY help on loopback?</Why>

In a test, every one of 64 one-megabyte sends came back flagged
`SO_EE_CODE_ZEROCOPY_COPIED`. The
[kernel doc](https://github.com/torvalds/linux/blob/v6.10/Documentation/networking/msg_zerocopy.rst)
explains it: anything "looped to a local socket will incur a deferred copy". You
pay for the pinning and the notification *and* still get the copy.

XDP's appeal is speed. The
[CoNEXT 2018 paper](https://dl.acm.org/doi/10.1145/3281411.3281443) reports
single-core processing "as high as 24 million packets per second". Cloudflare
runs its DDoS drops there ([L4Drop](https://blog.cloudflare.com/l4drop-xdp-ebpf-based-ddos-mitigations/)),
and Facebook's [Katran](https://engineering.fb.com/2018/05/22/open-source/open-sourcing-katran-a-scalable-network-load-balancer/)
load balancer does the same. How XDP programs are verified and run is covered in
[chapter 48, eBPF](/topics/48-ebpf).

Last, **busy polling**. `SO_BUSY_POLL` (3.11) lets a thread in `recv()` spin on
the NAPI queue itself instead of sleeping until the softirq wakes it. It trades
a burnt core for fewer wake-ups. The newer knobs are in
[`napi.rst`](https://github.com/torvalds/linux/blob/v6.10/Documentation/networking/napi.rst).

<Why>Why is the cost per write almost flat for small writes?</Why>

From 64 bytes to 1 KB, the time per call barely moves, so small writes pay a
fixed ~250 ns each on Linux: the syscall, the socket lock and skb allocation.
Past 16 KB the copy dominates and throughput flattens. Batch small writes and
most of that fixed cost disappears.

iperf3 on the same loopback reached a median of **142 Gbit/s**. Loopback isn't
really a network; it's closer to a memcpy with a TCP state machine attached.

</Sub>

<SectionHeading n="08" id="tools">Tools for a Monday morning</SectionHeading>

<Sub n="8.1" title="Where each drop is counted">

```shell
# Ring and driver: rx_drops, rx_missed, per-queue counters, xdp counters
ethtool -S eth0 | grep -iE 'drop|miss|err|xdp'
ethtool -l eth0            # how many RX/TX queues. "Combined: 1" means no RSS
ethtool -g eth0            # ring size; -G to grow it

# Per-CPU backlog and budget. One row per CPU, hex
cat /proc/net/softnet_stat   # col1 processed, col2 dropped, col3 time_squeeze

# Listener and socket counters, as deltas since the last call
nstat | grep -E 'ListenOverflows|ListenDrops|RcvbufErrors|TCPBacklogDrop|PruneCalled'

# One socket, in detail
ss -tin 'dport = :443'     # rtt, cwnd, retrans, rwnd_limited, dsack_dups
ss -ltn                    # on LISTEN rows: Recv-Q = queued, Send-Q = limit

# Conntrack headroom
cat /proc/sys/net/netfilter/nf_conntrack_{count,max}
dmesg | grep 'table full'

# Is one CPU drowning in softirq?
mpstat -P ALL 1            # %soft column
```

The 6.10 `softnet_stat` layout is in
[`net/core/net-procfs.c`](https://github.com/torvalds/linux/blob/v6.10/net/core/net-procfs.c).
Older guides, including packagecloud's excellent
[Monitoring and Tuning the Linux Networking Stack](https://blog.packagecloud.io/monitoring-tuning-linux-networking-stack-receiving-data/),
describe column 9 as `cpu_collision`; it's always 0 now.

</Sub>

<Sub n="8.2" title="Tracing drops">

For drops that go through `kfree_skb`, drop reasons turn a count into a
location:

```shell
# Counts drops by function and reason code
bpftrace -e 'tracepoint:skb:kfree_skb { @[ksym(args->location), args->reason] = count(); }'

# Or the older tool
dropwatch -l kas
```

Reason codes are listed in
[`include/net/dropreason-core.h`](https://github.com/torvalds/linux/blob/v6.10/include/net/dropreason-core.h);
`SOCKET_RCVBUFF`, `SOCKET_BACKLOG`, `CPU_BACKLOG` and `PROTO_MEM` are the ones
you'll see under load. Two cautions: the tracepoint is global, not
per-namespace, so filter on a port, and it never sees listen overflows
(section 3.1).

</Sub>

<Sub n="8.3" title="Symptom, cause, fix">

| Symptom | Likely cause | Fix |
|---|---|---|
| New connections time out; logs show nothing | Accept queue full | Speed up the accept loop, then raise the backlog and `somaxconn` |
| New connections fail on one node; old ones fine | Conntrack table full | Raise `nf_conntrack_max` on the node, shorten timeouts, `notrack` stateless traffic |
| One CPU at 100% `%soft`, others idle | All traffic on one RX queue | More queues (`ethtool -L`), RSS, then RPS, then `SO_REUSEPORT` |
| `time_squeeze` climbing | Softirq budget exhausted | Raise `netdev_budget`, or threaded NAPI on dedicated cores |
| UDP messages lost, sender sees no error | Receive buffer full | Read faster, raise `SO_RCVBUF` and `rmem_max` |
| Multi-millisecond latency spikes on TCP | Oversized receive buffers collapsing | Lower the `tcp_rmem` maximum |

<Callout label="Common mistake" kind="warn">
Tuning sysctls without a counter that's moving. Find the counter first; that's
how people end up with 32 MB `tcp_rmem` and the latency spike from section 3.5.
</Callout>

</Sub>

<SectionHeading n="09" id="summary">Summary</SectionHeading>

1. **The stack is a chain of queues.** Ring, backlog, conntrack, socket buffer,
   accept queue: each has a fixed size, and each drops when full.
2. **The CPU doesn't see a packet until the softirq.** The NIC writes it into RAM
   itself, and NAPI polls in batches instead of taking an interrupt per packet.
3. **Softirq work has a budget.** 300 packets or 2 jiffies per run; running out
   shows up as `time_squeeze`.
4. **An skb points at a packet; it doesn't hold it.** Sockets are charged
   `truesize`, about 830 bytes for a 100-byte UDP datagram.
5. **A full accept queue drops SYNs silently.** Clients retry after about a
   second, your logs show nothing, and drop tracers miss it; `nstat` doesn't.
6. **Conntrack exhaustion is node-wide.** New flows fail while existing ones
   work, and a pod can't fix it.
7. **UDP loses data the sender can't see.** Check `UdpRcvbufErrors` first.
8. **`write()` returning means the kernel has your data**, not that it was sent.
9. **Spread load in order:** RSS, then RPS, then `SO_REUSEPORT`.
10. **The full stack costs microseconds per packet.** Line rate with small
    packets needs XDP. That's why DDoS mitigation lives there.

<SectionHeading n="11" id="interview">Interview questions</SectionHeading>

<QA level="beginner" q="What's the difference between the SYN queue and the accept queue?">
The SYN queue holds half-open connections: SYN received, SYN-ACK sent, waiting
for the final ACK. The accept queue holds completed connections waiting for
`accept()`. Both are sized from the `listen()` backlog and capped by
`net.core.somaxconn`. When the accept queue is full, Linux drops incoming SYNs
and counts them in `ListenOverflows` and `ListenDrops`.
</QA>

<QA level="beginner" q="What does NAPI do, and why does it exist?">
It switches a busy NIC from interrupt-per-packet to polling. The first packet
raises an IRQ, the driver masks further interrupts and schedules a softirq that
polls the ring, up to a budget (300 packets or 2 jiffies per run by default).
Interrupts are re-enabled only when the ring is empty. Without it, a high packet
rate becomes an interrupt storm and nothing else runs.
</QA>

<QA level="intermediate" q="Your UDP service loses messages but the sender sees no errors. Where do you look?">
`nstat` for `UdpRcvbufErrors`. The receive buffer is full, and `sendto()`
succeeds regardless. The socket is charged `truesize`: in the test above, a
100-byte datagram cost about 830 bytes of buffer. Raise `SO_RCVBUF` (and
`rmem_max`, or the request is capped), read faster, or spread load with
`SO_REUSEPORT`.
</QA>

<QA level="intermediate" q="RSS, RPS and RFS: what does each do?">
RSS is the NIC hashing flows into multiple hardware queues with separate IRQs.
RPS is the same hash done in software by the receiving CPU, which hands the
packet to another CPU's backlog via IPI. RFS extends RPS to pick the CPU where
the consuming thread last ran, for cache locality. RSS is free but limited by
queue count; RPS and RFS cost an IPI and some CPU.
</QA>

<QA level="intermediate" q="A Kubernetes node starts timing out new connections; existing ones are fine. First guess?">
Conntrack. When the table's full, packets that would create a new entry are
dropped while established flows keep matching existing entries. Check `dmesg`
for "nf_conntrack: table full" and compare `nf_conntrack_count` to
`nf_conntrack_max`. It's node-wide, so the fix happens on the node.
</QA>

<QA level="deep" q="Why might dropwatch show nothing during a SYN flood that's overflowing your accept queue?">
In v6.10 (and through v6.17), `tcp_rcv_state_process()` hands the SYN to
`tcp_conn_request()`, which records the overflow and returns, and then frees
the SYN with `consume_skb()`, not `kfree_skb()`. Drop tracing hooks
`kfree_skb`. Reproduced: 105 listen overflows in `nstat`, zero matching
`kfree_skb` events, 110 matching `consume_skb` events.
</QA>

<QA level="deep" q="When does MSG_ZEROCOPY make things slower?">
Below roughly 10 KB per send, where pinning pages and processing completion
notifications cost more than the copy (the kernel doc's own guidance). And on
loopback or to any local socket, where the kernel does a deferred copy anyway:
64 of 64 one-megabyte sends came back flagged `SO_EE_CODE_ZEROCOPY_COPIED`.
</QA>

<QA level="deep" q="Where does XDP run relative to the rest of the stack, and what do you lose?">
In the driver's NAPI poll, on the raw DMA buffer, before an skb is allocated,
so before GRO, tc, netfilter and sockets. That's why it can drop or forward tens
of millions of packets per second per core. You lose everything above it: no
conntrack, no TCP, no socket lookup, and the BPF verifier's limits apply. AF_XDP
hands frames to user space when you need more logic.
</QA>

<Quiz>
  <Q q="listen(fd, 4) and no accept(). How many connections complete on Linux 6.10?">
    Five. The full check is `sk_ack_backlog > sk_max_ack_backlog`, so the queue
    holds backlog + 1. macOS admitted four in the same test.
  </Q>
  <Q q="softnet_stat column 3 is climbing. What does it mean?">
    time_squeeze: net_rx_action ran out of budget (packets or time) with work
    still queued. The CPU isn't keeping up with its RX queues.
  </Q>
  <Q q="You set SO_RCVBUF to 64 KB. What does getsockopt return?">
    128 KB. The kernel doubles the value to allow for skb overhead, subject to

  </Q>

    lo's transmit queues the skb on the per-CPU backlog, and process_backlog
    delivers it like any other NAPI instance.
  </Q>
</Quiz>
